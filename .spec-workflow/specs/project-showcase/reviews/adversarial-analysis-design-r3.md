## Attack 1 — The `translate-X(-50%)` media-escape trick (Component 10)

v3 abandoned per-tag prose modifiers and committed to a two-div pattern. Good move. The escape mechanism it picked is clever but undertested.

- **[Novel] Stress-test the `margin-left: 50%; transform: translateX(-50%)` claim against the actual parent geometry.** The CSS rule is scoped to `.projects-article .prose :is(img, picture, ...)`. The `.prose` div is itself wrapped in `<div className="mx-auto max-w-prose">`. So the wide-media child is **two levels deep** inside the narrow column, not one. `margin-left: 50%` is computed relative to the IMMEDIATE PARENT'S content-box width — that parent is `.prose`, which inherits the ~65ch width of `max-w-prose`. So `margin-left: 50%` is `~32.5ch ≈ 350px`, not `512px` (half of 1024). The element's left edge sits at 350px from the narrow column's left, then `translateX(-50%)` shifts it left by half its own width. **The math does not center the wide media on the outer container's centerline; it centers it on the narrow column's centerline.** Since the narrow column IS already `mx-auto`-centered inside the outer container, the centerlines coincide — but only because the narrow column is itself centered. This is correct only by an unstated assumption. State it: "this works because the inner `max-w-prose` div is itself centered via `mx-auto`; if the inner div is ever left-aligned, the escape becomes visually broken." Add a regression test for the visual centering.

- **[Novel] Challenge the `max-width: min(100%, var(--outer-width, 1024px))` line.** The `--outer-width` CSS variable is declared NOWHERE in `projects.css` or the JSX. The `var(--outer-width, 1024px)` syntax falls back to the literal `1024px`. So the rule effectively says `max-width: min(100%, 1024px)` where `100%` is the parent's (`.prose`, ~700px) width. **`min(700px, 1024px) = 700px`** — the wide-media element never exceeds the narrow column's width. The escape is intent-broken: the element is shifted via translate but capped at the narrow width. Verify by computing: on a viewport at `lg` breakpoint, the outer container is 1024px, the narrow column is ~700px, the wide-media `max-width` resolves to 700px (since `100%` of the narrow parent is 700px). **The image never spans 1024px.** Either declare `--outer-width: 1024px` on the outer container and use `width: var(--outer-width)` instead of `max-width: 100%`, or scope the rule's `100%` reference using a fixed `width: min(1024px, 100vw)` directly. The `100%` semantics under nested containers is the bug.

- **[Novel] Stress-test the `width: 100%; max-width: min(100%, ...)` interaction on viewports below `lg` (1024px).** On `sm`/`md` viewports the outer container itself is narrower than 1024px (it has `max-w-5xl` plus `px-4`, so on a 640px viewport the container content is ~608px). The narrow `max-w-prose` is ~640px source-width but capped at 100% of parent. `width: 100%` on a wide-media child resolves to whatever the parent (`.prose`) renders. The translate-X(-50%) still shifts it left by half — but the shift relative to a 608px container with a ~600px narrow column is a few pixels of horizontal jiggle, not a meaningful escape. State the responsive behavior: at what breakpoint does the escape actually visually fire? Probably only at `lg`+ where outer (1024px) > narrow (~700px). Below that, the escape is a no-op. Author doc §6 must say this.

- **[Novel] Challenge `transform: translateX(-50%)` against `position: sticky` / `position: relative` children.** The `prose` rule does not set `position`, so the transform creates a new stacking context AND a new containing block for `position: absolute` descendants. If an author embeds an `<svg>` with absolutely-positioned overlay text (a common diagram pattern), the overlay's positioning anchor flips from the document to the transformed element — likely correct here, but unstated. Also, `transform` on a `<pre>` block disables `position: sticky` for any descendant inside the pre (rare, but a syntax-highlighter UI may use sticky line-number rails). Document the side effects.

- **[Compounding] Challenge the descendant selector trade-off acceptance.** v3 documents that nested wide-media (e.g., `<iframe>` inside `<figure>`) also escapes. The doc says "fine for the launch use cases." But a `<figure><img><figcaption>` triplet from a standard MDX image-with-caption pattern — the `<img>` escapes AND the surrounding `<figure>` ALSO escapes (it's in the selector list). **Two nested escapes apply two `translateX(-50%)` transforms compounding via transform inheritance** (transforms on parent + child don't truly compound on translateX, but the child's reference frame changes). At minimum the `<figcaption>` lives inside an escaped `<figure>` and is laid out against the wide width, breaking the narrow-text rhythm for the caption. Either exclude `<figure>` (let the contained `<img>` escape but keep the figure narrow), or document that `<figcaption>` will render wide.

## Attack 2 — `getProjectBySlug()` re-runs the guard 4N×slugs times (Component 3)

v3 specified `getProjectBySlug(slug) → getPublishedProjects().find(...) ?? null`. This is correct but unstudied for cost.

- **[Novel] Stress-test the per-detail-page invocation cost.** Every detail page render calls `getProjectBySlug()` from BOTH `generateMetadata` AND the default page export. Each call invokes `getPublishedProjects()`, which (a) runs the env-var guard, (b) iterates ALL projects to filter drafts, (c) iterates again to emit the warning loop, (d) clones via `[...filtered]`, (e) sorts. **For N projects with M detail pages, the build does N × 2M filter+sort passes** (each detail page does two — `generateMetadata` + page body). The memoization is on the WARNING stderr only, not on the filtered-sorted result. Either memoize `getPublishedProjects()`'s return at module-scope (single sort per process) or accept that build time scales as O(N × M) where it could be O(N + M). At N = 5, M = 5, this is 50 sorts of a 5-item array — fine. At N = 50, M = 50, this is 2500 sorts. State the scaling limit.

- **[Novel] Challenge the guard-throw vs. warning-emit ordering for `getProjectBySlug`.** The body is `getPublishedProjects().find(...)`. `getPublishedProjects()` THROWS on production guard. So `getProjectBySlug` in production with `PROJECTS_INCLUDE_DRAFTS=1` throws — `notFound()` is never reached because the throw happens first. This is correct behavior (the build should fail), but the design documents `getProjectBySlug() → null → notFound() → 404` as the "404 path" without distinguishing the throw path. State: "in production with drafts enabled, the guard throws before any 404 logic runs." Author doc should mention.

- **[Novel] Stress-test the module-scope `__warnedDraftSlugs` against Next.js's per-worker module isolation.** Next.js's build process forks workers for `generateStaticParams` page generation. Each worker has its own module instance, hence its own `__warnedDraftSlugs` Set. **A multi-worker build still emits one warning per draft slug per worker, not one per build.** With 4 workers and 3 drafts, that's 12 warnings, not 3. The memoization is per-process, not per-build. Either accept this and rename the variable to reflect "per-process," document the multi-worker behavior, or move the warning to a build-time mechanism (Velite transform) that runs once.

- **[Novel] Challenge `__resetWarnedDraftSlugs()` as a test-only export.** Adding a test-only export to a production module pollutes the public API. The chokepoint scanner does NOT check for test-only naming conventions; any consumer can call `__resetWarnedDraftSlugs()` in production code. Either prefix-protect via a separate `projects-internal.ts` module that the scanner's allowlist permits, OR use Vitest's `vi.resetModules()` to clear the module cache between tests (heavier but no production-surface leak), OR use a `WeakRef`-based Set that is reachable only via a Symbol export. The current approach is the simplest but lets production code reset the warning state.

- **[Compounding] Challenge the `vitest` `process.env.VITEST` claim.** v3 says "Vitest sets `process.env.VITEST = "true"` automatically — verified at `node_modules/vitest/dist/index.d.ts`." `index.d.ts` is a TypeScript declaration file; it does NOT contain runtime env-var setting code. The verification citation is wrong. The actual source is somewhere in Vitest's runner code (`@vitest/runner` or similar). **Cite the actual source file and line, not the `.d.ts`.** Also: `VITEST=true` is set by the test runner's Node.js process. If a child process spawned by a test does NOT inherit this env var (e.g., a subprocess test), the gate fires `process.exit(1)` in the child. Probably fine, but document the inheritance assumption.

## Attack 3 — `next.config.ts` extension: import-graph and contract drift (Component 15)

The v3 design imports both `blog-errors.ts` AND `project-errors.ts` at `next.config.ts` top level. This makes `next.config.ts` depend on the contract of two separate modules.

- **[Novel] Stress-test the named-import contract drift.** `next.config.ts` imports `BLOG_DRAFT_LEAK_GUARD_MSG_PREVIEW`, `BLOG_DRAFT_LEAK_GUARD_MSG_PRODUCTION`, `checkVercelDraftGuard as checkBlogDraftGuard`. If `src/lib/blog-errors.ts` is later refactored to rename `checkVercelDraftGuard` (e.g., to `checkBlogVercelDraftGuard` for clarity post-unification), `next.config.ts` breaks at TypeScript-compile time — but the breakage is in a build-tooling file, not in a tested path. **Add a contract test** that `next.config.ts`'s imports resolve. Vitest's `import("./next.config")` is the cheapest version. The unification deferral (#1) WILL rename these exports eventually; the contract drift is a near-term risk.

- **[Novel] Challenge the audit step as documentation, not enforcement.** v3 says "a one-shot manual audit during the implementation task verifies `next.config.ts` is NOT transitively imported by any test fixture." A manual audit at one point in time does not prevent a future test from accidentally importing `next.config.ts` (e.g., via a `next/server`-shim that loads config). **Replace the audit with a permanent CI check**: a Vitest setup file that asserts `next.config.ts` is not in the module graph when tests run, OR a static check (grep) that no `*.test.ts` file imports `next.config.ts`. The VITEST gate is the safety net but the audit is the prevention; the prevention is currently doc-only.

- **[Novel] Stress-test the early-stderr ordering against Next.js's own logging.** `next.config.ts` top-level executes BEFORE Next.js initializes its logger. The stderr writes succeed but their formatting (no color codes, no `▲ Next.js` prefix) makes the messages look like raw error output, not configuration warnings. Compare: when `vercel build` fails on the guard, the developer sees an unformatted line at the start of stderr, then Next.js's exit-1 propagation. The error message constant includes a `Fix on Vercel:` instruction — good. But the absence of a leading marker (`ERROR:`, `[BLOCKED]`) means CI log parsers that scan for known prefixes miss it. Either prefix the message with an unambiguous severity marker or rely on the non-zero exit code alone (the message becomes nice-to-have).

- **[Novel] Challenge the `process.stderr.write(... + "\n")` pattern.** Manual `\n` concatenation is fragile (forget once and lines merge). Use `console.error(...)` which adds the newline. The reason to prefer `process.stderr.write` is async-flushing — `console.error` is synchronous in Node.js, AND it routes through the same fd. `console.error` is the conventional choice. Either justify the choice (e.g., "bypass console hijacking by Next.js's logger") or use `console.error`.

- **[Compounding] Challenge the dual-import diff size against current `next.config.ts`.** The v2/v3 design shows `next.config.ts`'s new top-level as ~30 lines of guard wiring. The current `next.config.ts` (per `7b8d11f` commit message) already has a `__draftGuard` block for blog. The v3 diff adds another guard import + 4 if-blocks (8 lines per guard × 2 guards = 16 lines of repetition). DRY this: a single `runGuard(guard, msgProd, msgPreview)` helper at the top of `next.config.ts`. Otherwise adding a third content type means 8 more lines of copy-paste.

## Attack 4 — The `pnpm-overrides` exact pin and lockfile reality (Component 17)

v3 adopted `pnpm-overrides` for an exact Velite pin. The mechanism does what's claimed but not for the reason claimed.

- **[Novel] Challenge the rationale "transitively-required higher version" for `pnpm-overrides`.** v3 says "a dependency declared as `velite: 0.3.6` can still be hoisted to a transitive higher version if another package depends on Velite." This is **factually wrong** for pnpm. pnpm does NOT hoist transitively to violate the root `package.json` declaration. The root `dependencies` entry IS the version for the root project; transitive demands are resolved separately in pnpm's content-addressable store. **The override is only needed if a hoisted transitive Velite version is loaded by the application code via Node's module resolution** — which requires symlinking/hoisting that pnpm explicitly avoids. The override is belt-and-suspenders that adds maintenance cost (override syntax must be re-applied on every pnpm update) without solving a real problem in pnpm's resolution model. Reconsider: a plain `"velite": "0.3.6"` (exact, no `^`/`~`) in `dependencies` IS the pin. The lockfile commit + `--frozen-lockfile` enforces it. Drop the override.

- **[Novel] Stress-test "`<exact-current-patch-version>` resolved during the implementation task."** The design ships a `package.json` snippet with a placeholder. The implementation task is expected to resolve the placeholder. But the version pin should be in the design AS A NUMBER — if the design is approved against a different version than the implementer chooses, the spec drifts. Either (a) pin to the current `velite` version at design-time and commit that string to the design, or (b) define the resolution rule ("whatever `pnpm view velite version` returns at PR-creation time") and check it against the lockfile in CI.

- **[Novel] Challenge the regression-test re-run as upgrade gate.** v3 says "Upgrades require an intentional `package.json` and lockfile change AND a re-run of the regression test." Re-running tests is what CI does on every PR. There's no special "re-run" — the test runs on every change. The intent is "the regression test MUST pass on the upgrade PR" — which it does by virtue of CI running it. **The actual upgrade gate is: when the regression test fails on an upgrade PR, do you update the test or revert the upgrade?** That's an editorial policy, not a mechanism. State the policy: "the regression test asserts current Velite output; if a Velite upgrade changes the output, the test must be updated AND the consumers (`projects.ts`, `<MDXContent />`, etc.) must be updated in the same PR. Test failure on upgrade = upgrade is breaking; assess impact before bumping."

- **[Novel] Stress-test the `pnpm-overrides` JSON shape.** v3 shows `"pnpm": { "overrides": { "velite": "<...>" } }` — this is the correct shape. But pnpm v8+ also supports a separate `pnpm` field with a `peerDependencyRules` sibling block; if the repo's `package.json` already has a `pnpm` block (e.g., for `onlyBuiltDependencies`), the override block must merge, not replace. Verify the repo doesn't already have a `pnpm` block whose deep-merge with the override is non-trivial.

## Attack 5 — Per-route layout for CSS scoping (Component 16)

v3 introduced `src/app/(site)/projects/layout.tsx` solely to import `projects.css`. The mechanism is correct; the side effects are unstated.

- **[Novel] Challenge the "scoped per-route" CSS claim.** Next.js App Router CSS imports are NOT scoped by file location — `import "@/styles/projects.css"` in a layout file causes the CSS to be included in the route's bundle. Other routes do not parse it, correct. But **CSS specificity is global**: if `.prose` is later styled differently in `src/app/globals.css`, the `.projects-article .prose` selector has the same specificity weight regardless of which CSS file declared it. Importing `projects.css` only on `/projects/*` means the rules are not LOADED for `/blog/*`, but if `/blog/*` ever loads `projects.css` (via a future shared layout import), the `.projects-article` selector becomes a global concern. State: "the per-route scoping is a load-time decision, not a CSS-module scoping mechanism." Use a top-level `[data-page-type="projects"]` attribute selector instead if true scoping is needed.

- **[Novel] Stress-test the layout's effect on the route segment cache.** Next.js App Router segment cache uses the layout boundary for partial-rerender decisions. Adding a new layout at `/projects` creates a new segment boundary — navigation between gallery and detail page is now a "same segment" transition (fast) but navigation from `/blog` to `/projects` crosses one more boundary than before. Probably imperceptible, but the architecture diff is one more layout file in the route tree. Document the rationale beyond "smaller CSS blast radius" — name the navigation behavior.

- **[Novel] Challenge the `<>` fragment return.** `export default function ProjectsLayout({ children }) { return <>{children}</>; }` — wrapping children in a Fragment is a no-op but Next.js's layout type signature does NOT require returning ONLY children. A future need to add a sidebar/header to projects pages requires touching this layout, and the fragment-only pattern conceals that the layout has a real visual role. Either (a) name the function `ProjectsCSSImportLayout` and add a comment "intentionally empty, exists solely for CSS scoping," or (b) skip the layout entirely and import `projects.css` at the top of `[slug]/page.tsx` and `page.tsx` (CSS imports in page files work in App Router). The page-import variant requires no new file. Justify the layout-file choice.

- **[Compounding] Stress-test the path-resolution claim in Component 10's code snippet.** The snippet shows `import "./../../../styles/projects.css";` with a comment "imported via layout instead — see Component 16." But the snippet still has the literal `import` line. **Remove the import line from the page snippet** to match the design's stated decision. As written, the snippet contradicts itself — it shows the import AND says it's elsewhere.

## Attack 6 — Empty-state fixture and E2E coupling unresolved (Component 9)

v3 documents the empty-state JSON file as "documentation only" with the mock returning a literal `[]`. The clarification creates a new contradiction.

- **[Novel] Challenge the "documentation only" claim against the chokepoint scanner.** `src/__fixtures__/projects-empty/projects.json` is in `src/__fixtures__/`. The scanner walks all `.ts`/`.tsx` files under `src/` — JSON is excluded. Fine. But IF any test ever does `import projects from "../__fixtures__/projects-empty/projects.json"`, that import resolves via Node's JSON-import resolution, not via the `#site/content` alias — the scanner won't flag it. The fixture is correctly out of scope. **But the design says "future contributors searching for 'how to test the empty state' find both the mock and the example shape side-by-side."** A contributor reading the JSON file does NOT discover the mock unless the JSON has a comment pointing at it. Verify the JSON file's content includes a comment block (JSON doesn't allow comments — JSON-with-comments or a sibling `README.md` is needed). State the actual discoverability mechanism.

- **[Novel] Stress-test the canonical-empty-array shape.** The mock returns `vi.mock("#site/content", () => ({ projects: [] }))`. The real `#site/content` barrel exports `projects`, `pages`, `profile`, `posts`. The mock returns ONLY `projects: []` — any test code path that ALSO touches `pages`/`profile`/`posts` via `#site/content` gets `undefined`. The empty-state test's import graph must not touch other collections. **Verify by listing what the gallery page transitively imports** — if it touches `blog.ts` (which imports `posts` from `#site/content`), the mock breaks `blog.ts`. The mock scope is per-test-file (`vi.mock` hoists), so a test that ONLY imports the gallery page is safe IF the gallery page doesn't transitively import blog. Confirm the import graph.

- **[Novel] Challenge the E2E "BUILD-TIME content set" coupling.** v3 says "the E2E counts cards rendered against the BUILD-TIME content set." The mechanism for the E2E to know the expected count is unstated. Does the E2E read `content/projects/*.mdx` from disk and count `draft: false` files? If yes, that's a duplicate parse of the frontmatter (the E2E re-implements Velite's filter). Does it read `.velite/projects.json`? If yes, it depends on a build artifact path that's `.velite`-implementation-specific. Spec: which mechanism? Probably "read `.velite/projects.json` after build; filter by `!p.draft` if `PROJECTS_INCLUDE_DRAFTS !== "1"`; count length; assert against rendered card count." State it explicitly.

- **[Compounding] Stress-test the dual-build CI matrix vs. E2E flake.** v2/v3 accept the E2E content-coupling because "dual-build CI controls the env consistently." But the gallery E2E runs ONCE per CI invocation — against the "publish drafts" build OR the "no drafts" build. The E2E count assertion must match the build flavor. If the test is parameterized by env, it has two expected values; if not, it runs only against one flavor. The dual-build matrix in `7b8d11f` is enough OR not — state which build the gallery E2E runs against.

## Attack 7 — The `formatPostDate === formatProjectDate` triangle is over-asserted (Component 4)

v3 added the third edge of the parity triangle in response to Attack 4. The addition is correct but inverts a concern.

- **[Novel] Challenge the test's actual coverage value.** The three assertions:
  - `formatPostDate === formatContentDate`
  - `formatProjectDate === formatContentDate`
  - `formatPostDate === formatProjectDate`

  By transitivity, the third assertion is provable from the first two. A test suite with all three is no stronger than a test suite with the first two — they fail in lockstep. The v2 Attack 4 finding said "verify the literal `const = formatContentDate` pattern survives — and add a single transitive assertion to lock down the pattern." The transitive assertion catches a SPECIFIC bug class: where `formatContentDate` itself is mutated between imports (e.g., a module-level reassignment). **Test that bug explicitly**: `expect(typeof formatPostDate).toBe("function") && expect(formatPostDate.toString()).toEqual(formatProjectDate.toString())` proves the function-body identity beyond reference identity. Or, more honestly, drop the third assertion as redundant.

- **[Novel] Stress-test the parity tests against `src/lib/blog.ts`'s migration.** v3 says `blog.ts`'s inline formatter at lines 81–94 is replaced with `export const formatPostDate = formatContentDate;`. The actual file's current line range may differ once edited. The design pins the LINE RANGE which becomes stale immediately after the implementation lands. **Either remove the line-range citation OR convert it to a logical citation** ("the existing formatter literal — the function declared and assigned to `formatPostDate`"). Same for the `82–86` citation in Component 4's "reuses" entry.

- **[Compounding] Challenge the parity test's failure mode on Vitest module reset.** If Vitest's `vi.resetModules()` is called between tests (per the new `__resetWarnedDraftSlugs()` need), module instances are reset and identity comparisons across modules become false even when the source is identical. The parity tests then false-fail. The tests must run with the same module instance — verify `vi.resetModules()` is NOT called in the test file (or test ordering avoids it). State the test isolation requirement.

## Attack 8 — Cumulative coverage matrix expansion is self-defeating (Component 11)

The scanner coverage matrix grew from 4 rows (v1) → 8 rows (v2) → 17 rows (v3). Each review adds rows. The pattern itself is the issue.

- **[Novel] Challenge the matrix's signal-to-noise ratio.** Of 17 rows: 11 "Covered," 6 "Out of scope." The "Out of scope" rows are documented bypasses. A motivated maintainer reading the matrix learns the bypass patterns AS A MENU. The matrix is a public API for circumvention. State the threat model: who is the scanner defending against? Accidental import (most likely) — the matrix overcovers. Hostile import (least likely in a single-author repo) — the matrix undercovers because of the bypasses. Pick a threat model and right-size.

- **[Novel] Stress-test the "follow-up spec" deferral for sub-path imports.** v3 says "If a future Velite version exposes sub-paths, the scanner is extended in a follow-up spec." But the trigger for that follow-up is unstated — a Velite upgrade that EXPOSES sub-paths is a silent capability addition, not a forcing function. Unless the Velite-upgrade workflow (Component 17) includes a step "check if sub-path exports were added," the trigger is invisible. Add a manual checkpoint to the upgrade workflow: "verify `node_modules/.velite/index.d.ts` does not declare sub-path exports; if it does, file a follow-up to extend the scanner."

- **[Novel] Challenge the canary fixture regex assertions for maintainability.** The v3 canary test embeds 10 regex literals matching the fixture file's contents. If the fixture is intentionally extended (e.g., to cover a new import shape), the test must be updated in lockstep. The test now has TWO failure modes: (a) the scanner regresses, (b) the fixture is edited without updating the test. **Mode (b) is a maintenance trap** — a contributor adds a new fixture line, the test fails on the unrelated line's regex, and the contributor learns the convention only after debugging. State the maintenance protocol in author doc §9: "when extending the canary fixture, update BOTH the regex list AND the expected-kinds set in the test."

- **[Novel] Stress-test "sentinel regex per pattern" against MDX-embedded examples in author doc.** If `docs/projects-authoring.md §9` contains code examples of the scanner-triggering patterns (for illustration), the structural test that scans `docs/` may pick them up as "found in repo," yielding false positives. Confirm the doc scanner's path scope excludes docs OR the canary regex is unique enough that doc examples don't match.

## Top 5 Risks/Gaps

1. **The `translate-X(-50%)` media-escape math is wrong relative to the actual nested-container geometry.** `margin-left: 50%` references the IMMEDIATE PARENT (`.prose`, ~700px), not the outer container (1024px). The `max-width: min(100%, var(--outer-width, 1024px))` falls back to `min(700px, 1024px) = 700px` because the `100%` is relative to the narrow parent. **The wide-media element never spans 1024px** despite the design's intent. The escape compiles and runs without error but produces an off-center, narrow rendering instead of a wide one. Build the page and visually verify; fix by declaring `--outer-width` on the outer container AND switching `max-width: 100%` to a viewport-relative or fixed-width expression that doesn't inherit the narrow parent's width.

2. **`pnpm-overrides` rationale is factually wrong and adds maintenance cost.** v3 claims pnpm hoists transitively to a higher version, justifying the override. **pnpm does not do this** — the root `dependencies` entry is the resolved version for the root project; transitive demands resolve separately. The override is a no-op safety net that adds a maintenance surface (a JSON block to keep in sync on every pnpm update). A plain `"velite": "0.3.6"` (exact, no operator) + `--frozen-lockfile` is the entire enforcement. Drop the override and update Component 17.

3. **Module-scope memoization assumes single-process build.** Next.js's build forks workers for parallel page generation. Each worker has its own `__warnedDraftSlugs` Set, so a multi-worker build emits N warnings per draft × number-of-workers, not N warnings per build. The unit test passes (single process); the real build is noisier than promised. Either accept multi-worker noise and document, or move warning emit to Velite's build-time transform (one process, one log per draft slug per build).

4. **`getProjectBySlug()` re-runs `getPublishedProjects()`'s filter+sort on every detail-page render.** The body `getPublishedProjects().find((p) => p.slug === slug)` does a full filter+sort+find per call. Each detail page calls it twice (`generateMetadata` + page body), so an M-detail-page build does 2M filter+sort passes over N projects. At N=5, M=5 this is 50 sorts of a 5-item array — trivial. At N=50, M=50 this is 2500 sorts. Memoize `getPublishedProjects()`'s result at module scope (single sort per process) OR document the O(N×M) scaling limit.

5. **`__resetWarnedDraftSlugs` test-only export leaks into production module surface.** A test helper exported from `src/lib/projects.ts` is callable from any consumer; the chokepoint scanner doesn't enforce naming conventions. A future contributor calling `__resetWarnedDraftSlugs()` in production clears the deduplication mid-build. Move the reset to a separate `src/lib/projects-internal.ts` (allowlisted in the scanner) OR use Vitest's `vi.resetModules()` mechanism (heavier but no surface leak).

## Top 3 Conclusions to Challenge or Reverse

1. **Reverse the per-worker memoization design in favor of a build-time-transform warning.** The module-scope `Set<string>` solves the "4N stderr lines per render" case but does not solve the multi-worker case (each worker emits its own N). The CORRECT location for a "warn once per draft slug per build" emit is in Velite's transform step — Velite runs once per build, regardless of Next.js worker count. Move the warning emit back to `velite.config.ts` (it lived there in v1; v2/v3 moved it for "after guard passes" ordering) AND check the guard from inside the velite transform. Velite has access to the same env vars. This collapses the per-worker noise to a single emit.

2. **Reverse the `pnpm-overrides` mechanism in favor of a plain exact pin + lockfile.** As detailed in Risk 2, the override solves a problem pnpm doesn't have. The exact pin in `dependencies` plus `--frozen-lockfile` plus the lockfile commit IS the enforcement. The override adds JSON surface and a maintenance hazard without strengthening any constraint. The "belt-and-suspenders" framing is wrong — the suspenders are doing nothing.

3. **Reverse the per-route CSS layout file in favor of a page-level CSS import.** Next.js App Router supports CSS imports in page files. A page-level import (`import "@/styles/projects.css"` at the top of `[slug]/page.tsx` and `page.tsx`) achieves the same per-route scoping without introducing a layout file whose only purpose is the import. Two import lines vs. one new file + import — the file is the bigger surface. The layout's claimed advantages (segment-cache boundary, future sidebar) are speculative; commit to the smaller change now.

## What's Missing — Work Before Acting

1. **A computed-style measurement test for the wide-media escape.** Playwright must measure the rendered `<img>` width at the `lg` breakpoint (viewport ≥ 1024px) and assert it equals the outer container width (within rounding tolerance). The current E2E spec lists this assertion but does not state the expected value or the tolerance. Without empirical measurement, Risk 1 (the `100%`-relative-to-narrow-parent math bug) ships uncaught.

2. **A multi-worker memoization decision.** Either accept worker-multiplied warnings and rewrite the test assertion ("at most W × N stderr writes for W workers and N drafts"), or move the emit to a single-process location (Velite transform). The current spec assumes single-process and will mismatch real builds.

3. **A `pnpm-overrides` reality check.** Test the override claim empirically: temporarily install a package whose transitive demands include Velite, then verify whether pnpm hoists. Update Component 17's rationale to match observed behavior.

4. **A `getPublishedProjects()` memoization decision.** Either memoize the filter+sort result at module scope (cheap, transparent) or document the O(N×M) scaling and the project count at which it becomes a concern.

5. **Removal of the `__resetWarnedDraftSlugs` public export.** Either co-locate with a test-only module file behind a separate allowlist entry, or use module-cache reset in tests.

6. **A single empirical render of the detail-page two-div pattern.** All of Risk 1 (math), Attack 1 (geometry), and the wireframe ambiguity collapse if a real render exists. Build one MDX fixture, render at `lg` breakpoint, screenshot, paste in the design (or attach). The "specify in prose" approach has not converged across three reviews because the visual primitive is asserted but never observed.

7. **A `next.config.ts` test-import contract.** Add a Vitest test that imports `next.config.ts` under `VITEST=true` and asserts no process exit. This locks the VITEST gate in place AND surfaces breakage if a future refactor removes the gate.

8. **Decisions on whether the parity test triangle's third assertion adds value, or whether to replace it with a `toString()`-based body-identity check.** Either is fine; the current state asserts a transitively-provable claim.
