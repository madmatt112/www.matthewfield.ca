### WARNING: AC2 plain-div test is tautological — inline styles win regardless of isolation
- **File:** e2e/tests/playground-isolation.test.ts:70
- **Issue:** Test 1 sets style={{ color: 'red', fontFamily: 'serif' }} on the target element and then asserts those exact values come back from getComputedStyle (e2e/tests/playground-isolation.test.ts:70-81; src/app/(playground)/spike/page.tsx:11). Inline style attributes have higher cascade priority than every author rule (layered or unlayered, :root or otherwise), so this assertion would pass even if .playground-container were deleted entirely and the test ran on the bare host page. The spike-summary acknowledges this (e2e/spike-summary.txt:26-31) and points to Test 5 as the real AC2 evidence, but the AC2 deliverable as written is still a non-test. Either change the fixture to use a non-inline class/selector that actually conflicts with site globals, or remove Test 1 and explicitly re-anchor AC2 on Test 5.
- **Task Requirement:** R11 AC2

### WARNING: EXPECTED_* constants encode Lightning-CSS serialization quirks that will silently break
- **File:** e2e/tests/playground-isolation.test.ts:35
- **Issue:** Constants like 'lab(7.78201% -.0000149012 0)' (with a leading-zero-stripped negative near-zero a-channel) and the dual %/no-% forms (EXPECTED_PRIMARY_LIGHT vs EXPECTED_PRIMARY_LIGHT_VAR) at e2e/tests/playground-isolation.test.ts:35-44 are byte-exact Lightning CSS output. A bump in Lightning CSS, the Tailwind v4 oklch palette, or browser CSSOM serialization will flip these to slightly different strings (e.g. 'lab(7.78201% 0 0)' vs 'lab(7.78201% -0.0000149012 0)') and every assertion that uses .toBe() will fail with a near-incomprehensible diff. Consider parsing the lab() output and comparing channel values numerically with a small tolerance, or at least asserting on canonical-form RGB after a known transform — otherwise this suite is a weekly maintenance trap.
- **Task Requirement:** R11 AC5 / R11 AC7

### INFO: EXPECTED_CONTAINER_COLOR comment claim is suspicious
- **File:** e2e/tests/playground-isolation.test.ts:47
- **Issue:** Line 47-51 of e2e/tests/playground-isolation.test.ts claims Lightning CSS collapses 'oklch(0.145 0 0)' to 'rgb(0, 0, 0)'. oklch L=0.145 is roughly a dark gray (~rgb(35, 35, 35)) in sRGB, not pure black. If the production build really outputs rgb(0, 0, 0), the cause is more likely a fallback ordering issue (Lightning CSS emitting an rgb() fallback before lab(), and the browser using the fallback) than 'collapse to sRGB'. Worth a quick recheck — if rgb(0, 0, 0) is actually being asserted because the lab() form is being shadowed by an rgb fallback, then the test isn't measuring what the comment claims.
- **Task Requirement:** R11 AC3

### INFO: Test 5 assertion on inherited tokens does not exercise the cascade-layer hypothesis
- **File:** e2e/tests/playground-isolation.test.ts:170
- **Issue:** Test 5 (e2e/tests/playground-isolation.test.ts:170-212) reads var(--primary) on a descendant. Because the playground.css token redeclarations live inside @layer playground (lowest priority) and tokens.css :root is unlayered (highest priority), one might expect the descendant to actually resolve var(--primary) from the inherited :root rather than from the container's layered redeclaration. It happens to work because the layered redeclaration is applied directly to .playground-container (which beats inherited values when computing custom properties on that element), but the test cannot distinguish 'layered redeclaration won' from 'inherited :root value happened to match in light mode'. Adding an assertion on a descendant of .playground-container while the host site is in dark mode where the values genuinely diverge (Test 5 already toggles .dark, so just expand the assertion to read a token whose .dark value differs from :root, e.g. --background) would close that loophole and make Test 5 a real isolation proof rather than a sympathetic-magic check.
- **Task Requirement:** R11 AC3 / R11 AC5
