# Requirements Document

## Introduction

The contributions-and-resources spec delivers two single-page, YAML-driven sections of matthewfield.ca:

1. **`/contributions`** — a single page rendering curated open-source contributions as cards. Each card shows the upstream repo identity, what Matthew contributed, a short description, the contribution date, and one or more typed links (PR, commit, issue, release notes, writeup, or discussion). Data lives in `content/contributions.yaml`. No per-contribution subpages.
2. **`/resources`** — a single page rendering curated bookmarks/links grouped by category (e.g. "DevOps Tools", "Blogs & Feeds", "Reading", "Fun Stuff"). Each entry is title + URL + short description. Data lives in `content/resources.yaml`. No per-entry subpages.

Both pages are statically generated server components. Both data files are processed by **new Velite collections** (`contributions` and `resources`) that this spec adds to `velite.config.ts`. **YAML is handled by Velite's built-in `yaml_default` loader** (registered by default in Velite 0.3.x); the schema attached to each collection is a top-level array load, shape `s.array(s.object({...}).strict())` — see Req 1.1 and Req 4.1 for the precise envelope. Both collections are content-typed (TypeScript types are generated by Velite and consumed at the page level via the `#site/content` chokepoint already established by site-foundation).

After this spec ships, Matthew can add or update either section by editing the corresponding YAML file in his editor, committing, and letting CI redeploy — no React changes required.

**Explicitly in scope at launch**:
- Two YAML data files: `content/contributions.yaml` and `content/resources.yaml`, each shaped as a top-level YAML array (possibly empty).
- Two Velite collections (`contributions`, `resources`) using the built-in YAML loader plus an explicit `s.array(s.object({...}).strict())` schema.
- Two route files (`/contributions/page.tsx`, `/resources/page.tsx`) — server components, `export const dynamic = 'force-static'`, no client JS beyond what Next.js's layout pulls in.
- Cards for contributions (no subpages, no detail routes).
- Category grouping and intra-category ordering for resources.
- Empty-payload handling: missing file and `[]` are valid empty states; zero-byte file and `null` literal payload are explicit build errors with a named diagnostic (Req 1.6, Req 4.6).
- Inclusion in the existing XML sitemap via `src/app/sitemap.ts`.
- A pinned authoring contract documented at `docs/contributions-and-resources-authoring.md` covering frontmatter conventions, the category enum and its extension workflow, link-type semantics, the forge-mapping convention, the seed-date pattern for the initial bookmark import, the UTC-timezone semantics of the `added` field's upper-bound refinement, the deep-link-anchor non-stability for both pages, and the no-draft policy rationale.
- A standalone CI step that verifies the authoring doc still contains every canonical section heading. Wiring is `package.json scripts.check:authoring-docs` invoked from the existing CI workflow at a documented position (Req 8.2). The earlier-draft "Velite `prepare` hook" wiring was rejected after verifying `velite.config.ts:400-458`: `checkProjectHeadings` runs inside the per-entry `projects` collection `transform`, NOT in `prepare`, and `prepare` has no API for reading arbitrary sibling docs.
- Two `src/lib/` helpers — `src/lib/contributions.ts` and `src/lib/resources.ts` — owning queries, sorting, grouping, and category-label maps. Page components SHALL import from these helpers only, never from `#site/content` directly.

**Explicitly out of scope at launch (deferred to later specs or future enhancements)**:
- **Per-contribution detail subpages**: out of scope.
- **Per-resource detail subpages**: out of scope.
- **Any `data-pagefind-body` markup on `/contributions` and `/resources`**: out of scope. Whichever spec adds Pagefind crawl extension to these pages will also add the appropriate body markers in the same change.
- **Search or filtering UI on either page**: out of scope.
- **Tags or cross-linking** between contributions and projects/posts: out of scope.
- **External link health-checking in CI** (`lychee`, `linkinator`): out of scope at launch.
- **A `draft` flag on either collection**: out of scope. Rationale per Req 10.7.
- **A quick-takedown mechanism with sub-CI-deploy latency**: out of scope (Req 10.7).
- **An "updated" timestamp on individual entries**: out of scope.
- **Pagination**: out of scope.
- **Sort controls / user-selectable ordering**: out of scope.
- **OpenGraph share images per page or per entry**: out of scope; both pages use the site default OG image from site-foundation.
- **RSS feed for contributions**: out of scope.
- **Importing contributions automatically from GitHub**: out of scope.
- **Resource voting, comments, or external submission form**: out of scope.
- **Stable-anchor URL contract for `/resources#cat-<slug>` and `/contributions#contrib-<n>`**: explicit non-feature for both pages (Req 10.6). Both anchors MAY shift on entry add/remove or sort-position change; the disclaim is scoped to those causes (not "any reason on any deploy" — v3's overly-broad disclaim is narrowed in v4).
- **Locked empty-state copy text**: out of scope as requirements content. The empty-state STRUCTURE (h1, h2, p) is locked; the prose inside is owned by the page component and may evolve without a requirements amendment (Reqs 2.9, 5.7).
- **A Levenshtein "did you mean?" hint** on category-typo errors: not at launch; noted as a candidate enhancement once the `category` enum grows past ~8 members (Req 4.2 documentation note).

## Alignment with Product Vision

- **Builder credibility** (business objective #2): The contributions gallery surfaces tangible open-source work — repo + PR + description — without forcing visitors to dig through GitHub profiles.
- **Personal expression / curated reference** (business objective #3 and product feature #6): Resources is Matthew's curated reading + tooling list, including a "Blogs & Feeds" blogroll category.
- **Markdown-first / data-first content** (product principle #2): Both pages are data-driven from YAML files Matthew edits.
- **Simple to maintain** (product principle #3): A new entry is a YAML edit + commit.
- **Independence from platforms** (business objective #4): Contributions are hosted on matthewfield.ca with links back to upstream.
- **Wide and spacious** (product principle #1): Card grid for contributions; clean section-grouped list for resources.
- **Responsive** (product principle #6): Contribution cards reflow from multi-column to single-column on mobile. Resources groups stack vertically at every breakpoint.
- **Accessible** (product principle #7): Both pages use semantic landmarks, `<h2>` for both per-card titles on `/contributions` and per-category headings on `/resources`, `<ul>/<li>` list semantics for resource entries, keyboard-navigable links with grouped semantics on multi-link cards, sufficient color contrast in both themes.
- **Performance** (success metric #4): Static generation, zero client JS beyond layout, no images on either page at launch.

## Shared Build-Time Error-Message Contract (referenced by Reqs 1.4, 3.1, 4.4)

Both collections share a single error-message contract. Defined here once, referenced by anchor from individual Reqs.

For any schema validation failure on a YAML entry, the error message SHALL include all of the following, in order:

1. The source file name (e.g. `contributions.yaml`).
2. An **entry locator** — either the entry's identifier field value (the `repo` for contributions, the `title` for resources) IF the identifier field's value parsed as a non-empty string after trim AND the validation failure being reported is on a NON-identifier field; otherwise the entry's zero-based array index in the form `entry[<n>]`. (v3's `MIN_DISPLAY = 2` floor is dropped — it was dead code under any valid schema configuration; the simpler "non-empty after trim" rule is sufficient.)
3. The failing field path in dot-and-bracket notation (e.g. `links[2].kind`).
4. The offending value, with the following serialization rules:
    - **Strings**: rendered with explicit surrounding double-quotes (e.g. `"my title"`).
    - **Numbers / booleans / `null`**: rendered bare (e.g. `42`, `true`, `null`), so they are visually distinct from quoted strings.
    - **Multi-line strings or strings containing `\n`**: newlines SHALL be replaced with the literal escape sequence `\n` (two chars: backslash + lowercase n) BEFORE the truncation step.
    - **Truncation**: AFTER newline escaping, if the rendered value (including surrounding quotes for strings) exceeds 80 chars, truncate to 80 with a `…` suffix preserved INSIDE the closing quote for strings.
5. For enum-type failures, a parenthesized list of valid enum members, comma-separated.
6. **Optional appended guidance** ("extension point"): individual Reqs MAY append one-line forge-specific or per-collection hints AFTER the enum-members list. Appendix format is LOCKED: each appended hint is on its own line, prefixed with the literal text `Hint: `, with no comma or colon inside the hint (since the parent error line uses both as delimiters). At most three hints may be appended per message.

The contract applies uniformly to `.strict()` rejection of unknown keys (the locator + field-path format covers `entry[3]: unknown key 'repoURL' (did you mean 'repoUrl'?)`).

## Requirements

### Requirement 1: `contributions` Velite collection

**User Story:** As Matthew, I want to add an open-source contribution by appending an entry to `content/contributions.yaml`, so that the contributions gallery card appears after the next CI deploy with no React changes.

#### Acceptance Criteria

1. The Velite configuration (`velite.config.ts`) SHALL define a new collection named `contributions` with:
    - `pattern: "contributions.yaml"` — matched by `fast-glob` from the content root; the built-in `yaml_default` loader (Velite 0.3.x — already registered, no `loaders` override required) handles `.yaml` files and returns the parsed array as `file.records`.
    - `schema: s.array(s.object({ ... }).strict()).min(0)` where the inner object is the per-entry schema defined in Reqs 1.2 and 1.3.
    - **No `single` flag is set** (the default `false` is what we want — Velite iterates each array element through the inner schema; this matches the precedent set by `posts` and `projects`, both `single: false` collections).
    - The existing `pages`, `profile`, `posts`, and `projects` collections SHALL remain unchanged. The collection registration is additive.

2. The per-entry schema SHALL require:
    - `repo` (string, 1–80 chars; regex `^[a-zA-Z0-9][a-zA-Z0-9._-]*\/[a-zA-Z0-9._-]+$` — GitHub-compatible `owner/name` format; per Req 1.7 this same format is used for GitLab/Codeberg/Sourcehut entries even though their canonical separators may differ, with the forge identity carried by `repoUrl`'s host).
    - `repoUrl` (string, URL-parseable, `http:` or `https:` only) — canonical URL of the upstream repo. Host MAY be any forge.
    - `title` (string, 5–100 chars after trim — schema applies `.transform()` to trim leading/trailing whitespace before length validation).
    - `description` (string, 30–280 chars after trim).
    - `date` (ISO 8601 date — when the contribution landed/merged; if not yet merged, the submission date). **Future-dated `date` IS permitted** — this represents PRs not yet merged. This asymmetry with resources' `added` (Req 4.2 — future-dated rejected) is editorially intentional: `date` represents "when the contribution happened OR will happen" while `added` represents "when I added this resource to my list", which is necessarily in the past.
    - `links` (array of typed link objects — see Req 3; **minimum 1, maximum 5** entries; the 5-entry cap exists because the link-kind enum has 6 members (Req 3.1) and uniqueness-per-kind (Req 3.2) means at most one member is unused. The cap is enum-cardinality minus one — explicitly the same arithmetic as Req 3.2's "at most one slot is unused").

3. The per-entry schema SHALL support these optional fields:
    - `language` (string, 1–24 chars) — primary language of the upstream repo, used as a textual badge on the card (e.g. "Rust", "TypeScript").

4. WHEN the build runs AND any entry violates the schema THEN the Velite build SHALL fail with a named error following the **Shared Build-Time Error-Message Contract** section above. Failure cases include but are not limited to: missing required field; invalid datetime; string length out of bounds; invalid URL or non-http(s) scheme; invalid `repo` format; **unknown frontmatter key under `.strict()`**; invalid `links[]` entry (Req 3); empty `links` array; `links` array with more than 5 entries.

5. The schema SHALL use `.strict()` mode at every object boundary (top-level entry AND nested link entries). Unknown keys SHALL be build errors per the shared contract.

6. **Empty-payload handling** — the four observable file states and the required build behavior:
    - File does not exist on disk — Velite emits `contributions: []`. Build succeeds.
    - File exists with explicit `[]` literal — Velite emits `contributions: []`. Build succeeds.
    - File exists with zero bytes (`""`) — the YAML loader returns `null`; this SHALL be a named build error: `"contributions.yaml is empty or null. To represent zero contributions, write the explicit empty list literal: []"`.
    - File exists with `~` or `null` literal payload — same error as the zero-byte case.
    - Implementation note for the design phase: the build-error case is detected by a Velite collection-level `transform` that asserts the parsed value is an array; this transform runs before the per-entry schema parse.

7. **Cross-forge precedent**: although the `repo` regex and the link-kind enum are GitHub-flavored, the spec MAY carry GitLab MRs (mapped to `kind: pr`), Codeberg patches, Sourcehut patches, etc. The author doc (Req 8) SHALL document this forge-mapping convention. No schema change is required.

8. The Velite output type for `contributions` entries SHALL be generated and surfaced via `#site/content`. Direct `JSON.parse` of `.velite/contributions.json` outside `src/lib/contributions.ts` is prohibited. **No new lint rule is added by this spec**: the existing site-foundation lint rule already exempts `src/lib/*.ts` from the `#site/content` import restriction (verified against the existing `src/lib/projects.ts:1` and `src/lib/blog.ts:1-4` import patterns).

9. **Order-of-operations**: The schema definition, the data file (with at least an empty-list placeholder if no real entries exist), the route file, the helper module, and the author doc with all canonical headings SHALL land in the SAME commit (or a sequence where every intermediate commit leaves CI green).

### Requirement 2: `/contributions` gallery page

**User Story:** As a visitor, I want to land on `/contributions` and see a card-style gallery of Matthew's open-source contributions.

#### Acceptance Criteria

1. WHEN a visitor navigates to `/contributions` THEN the page SHALL render a reverse-chronological grid of contribution cards, sorted by **`date` desc, `repo` asc, `title` asc** (three keys, deterministic). The comparator `byDateDescRepoAscTitleAsc` lives once in `src/lib/contributions.ts`.

2. WHEN the page is rendered THEN it SHALL be a statically generated server component with `export const dynamic = 'force-static'`.

3. **Page heading structure**: the page renders `<h1>Contributions</h1>` directly inside `<main>`. Each card's heading is `<h2>`. The `<h1>` → `<h2>` chain is WCAG 2.1 SC 1.3.1 compliant. The card grid's `<ul role="list">` wrapper carries `aria-labelledby="page-heading"` (where `page-heading` is the `<h1>`'s id), so screen-reader users hear "Contributions, list of N items" when entering the grid.

4. WHEN the page is rendered THEN each card SHALL include, in DOM order:
    - The contribution `title` (PR/contribution title) rendered as the card's `<h2>`. The heading carries a stable `id="contrib-<n>"` (zero-based index of the sorted output, NOT YAML index — sort first, then assign). **Anchor stability is disclaimed in Req 10.6** — adding or removing a contribution that affects the sort position shifts subsequent `<n>` values; external deep-linkers are warned in the author doc.
    - The `repo` rendered below the title as a `<code class="contrib-repo">` element. **`<code>` is chosen over `<span>`** because a repo identifier (`owner/name`) is a code-style string and `<code>` carries that semantic; user-agent stylesheets render `<code>` in monospace by default, which matches the editorial intent of "this is a repo path." Visual styling refinements remain a design-phase concern; the element choice is locked.
    - The `description` paragraph (`<p>`).
    - The `date`, formatted via `formatContentDate(iso)` from the existing `src/lib/format-date.ts` module.
    - A `language` textual badge iff `language` is present.
    - A typed-link rail (Req 3) wrapped in an element with `role="group"` and `aria-labelledby="contrib-<n>"`.

5. **No nested anchors / no whole-card-as-link**: each card is an `<article>` element wrapping its heading and content. The links inside the rail are independent `<a>` targets. Rationale: each card has multiple distinct external destinations.

6. **Link grouping for keyboard / screen-reader navigation**: the typed-link rail inside each card SHALL be wrapped in an element with `role="group"` and `aria-labelledby="contrib-<n>"`, so screen readers announce the card's `<h2>` (the contribution title) as the group's accessible name before each link. The card itself does NOT receive `tabindex="0"`. **Accepted tradeoff (not a requirement)**: the repo identity (rendered as `<code class="contrib-repo">`) is NOT a heading landmark and is not directly reachable via screen-reader heading-jump navigation. The title is the editorial signal that warrants heading-jump access; the repo identity is contextual sub-line content.

7. **Link attributes**: every external `<a>` inside a card SHALL have `rel="noopener"` and SHALL render same-tab (no `target="_blank"`). No per-link override.

8. WHEN the page is rendered THEN its `<title>` SHALL be "Contributions" composed through the site-foundation `%s | matthewfield.ca` title template. Meta description is a short author-curated string in the page component, 50–160 chars. OG image is the site default.

9. **Empty state**: WHEN `contributions` is `[]` THEN the page SHALL render `<main>` containing `<h1>Contributions</h1>` (same h1 as the populated state) followed by a `<section aria-labelledby="empty-state-heading">` containing `<h2 id="empty-state-heading">` and a `<p>`. **The exact prose text of the h2 and p is owned by the page component and is NOT specified at requirements level.** Acceptance tests assert on the structural skeleton (h1 retained, sectioned empty state with its own h2, explanatory p, `aria-labelledby` wiring) and on the meta description's resolution to the same curated string as the populated branch (so the SEO surface is consistent regardless of empty-vs-populated state). The v2 `role="status"` aside is retracted: `role="status"` is for transient live-region updates, not for a permanent-empty landing state. The page MUST NOT 404, MUST NOT render an empty `<main>`.

10. **Responsive breakpoints**: WHEN viewport &lt;640 px THEN single-column. WHEN 641–1023 px THEN two-column. WHEN ≥1024 px THEN at least two-column; finer escalation is a design-phase concern.

### Requirement 3: Typed-link rail on contribution cards

**User Story:** As a visitor reading a contribution card, I want to find the PR, commit, issue, release notes, writeup, or discussion in one predictable place, with a clear indication of what each link points to.

#### Acceptance Criteria

1. The `links` field on each contribution entry SHALL be an array of objects of shape `{ kind: "pr" | "commit" | "issue" | "release" | "writeup" | "discussion"; label?: string; url: string }`.
    - `kind` (required; CLOSED ENUM — the SIX literal strings above. `writeup` matches the existing project-showcase `linkSchema` precedent; any other string value is a build-time error).
    - `url` (required) — validated per Req 3.3.
    - `label` (optional, 1–60 chars). When omitted, the rendered text is the `kind`'s default label. **Note (out of acceptance-test scope)**: the default-label table (e.g. `pr → "Pull request"`) is owned by the page component, not by requirements; design phase finalizes the table.
    - **Error messages** for `kind` rejection MUST follow the Shared Build-Time Error-Message Contract above. An invalid `kind` value SHALL be reported with the file name, the entry locator, the field path (`links[<i>].kind`), the offending value, and the parenthesized list of valid enum members. The forge-mapping hint MAY be appended per the contract's "Hint:" extension point (e.g. `Hint: map GitLab MRs to pr`).

2. **Uniqueness per kind**: at most ONE entry per `kind` value per contribution. Duplicate `kind` within a single entry is a build error. With 6 enum members and a per-entry cap of 5 (Req 1.2), the schema cap and the unique-per-kind constraint are mutually consistent — at most one enum member is unused per contribution.

3. Each entry's `url` SHALL be validated in two stages: (a) `new URL(url)` parse — invalid is a build error; (b) protocol check — only `http:` and `https:` are accepted; all other schemes (`mailto:`, `tel:`, `javascript:`, `data:`, `file:`, etc.) are rejected per the shared error contract.

4. **Display order is array order**. Authors choose link prominence by reordering the array.

5. **At least one link is required** (per Req 1.2). A contribution with no link is not a contribution worth listing.

6. **Link attributes**: every link in the rail SHALL render with `rel="noopener"` and same-tab. No per-link override. Same as Req 2.7.

7. The rail SHALL be server-rendered. Each link is a plain `<a>`. The rail wrapper carries `role="group"` and `aria-labelledby="contrib-<n>"` per Req 2.6.

### Requirement 4: `resources` Velite collection

**User Story:** As Matthew, I want to add a bookmark by appending an entry to `content/resources.yaml`, so that it appears under its category on `/resources` after the next CI deploy.

#### Acceptance Criteria

1. The Velite configuration (`velite.config.ts`) SHALL define a new collection named `resources` with:
    - `pattern: "resources.yaml"`.
    - `schema: s.array(s.object({ ... }).strict()).min(0)` mirroring Req 1.1's envelope.
    - Same `single: false` defaulting and same built-in YAML loader as `contributions`.
    - Additive registration; existing collections unchanged.

2. The per-entry schema SHALL require:
    - `title` (string, 2–80 chars after trim — schema applies `.transform()` to trim leading/trailing whitespace before length validation).
    - `url` (string, URL-parseable, `http:` or `https:` only). Two-stage validation per Req 3.3.
    - `description` (string, 20–200 chars after trim).
    - `category` (string — CLOSED ENUM at the schema level; canonical category list pinned in the schema. Initial set: `devops-tools`, `blogs-and-feeds`, `reading`, `fun-stuff`. **Extension workflow**: adding a category requires editing `velite.config.ts` AND `src/lib/resources.ts`'s display-label map AND the author doc in a single PR. **Expected cadence**: zero to ~2 additions per year; if the enum grows past 8 members, evaluate adding a Levenshtein "did you mean?" hint via the shared contract's appendix (out of scope at launch). **Tradeoff acknowledged**: a category typo in YAML breaks the entire build, including unrelated changes in the same commit; same blast radius as project-showcase's `status` enum, accepted on the same grounds.).
    - `added` (ISO 8601 date — required). **Upper-bound refinement**: the schema SHALL `.refine((d) => Date.parse(d) <= buildStartUtc)` where `buildStartUtc` is the build process's start time (UTC, captured once at schema-module load). ISO dates without explicit time components are interpreted as UTC midnight per ECMAScript spec. **Wall-clock vs UTC failure mode acknowledged**: an author in a non-UTC timezone setting `added` to their local "today" can produce a value that is "tomorrow" in UTC; when the build runs before UTC midnight of that day, the refine rejects the entry. The author doc (Req 8.1's `## Resources YAML shape` section) documents this with a one-line UTC-comparison note. Future-dated values are universally rejected — this prevents AI-tool seeding hallucinations (a 2027 date sorting to top of category forever); the editorial intent (`added` represents "when this was added to my list", necessarily past) supports this rule.

3. The per-entry schema has **no optional fields**.

4. WHEN the build runs AND any entry violates the schema THEN the Velite build SHALL fail with a named error following the **Shared Build-Time Error-Message Contract** section above. Failure cases include: missing required field; invalid URL or non-http(s) scheme; string length out of bounds; unknown frontmatter key under `.strict()`; invalid `category` (not in enum); invalid `added` (not ISO 8601 date OR future-dated per Req 4.2 refinement).

5. The schema SHALL use `.strict()` mode at every object boundary.

6. **Empty-payload handling** mirrors Req 1.6 exactly, substituting `resources.yaml` for the file name in the error message.

7. The Velite output type SHALL be surfaced via `#site/content`. Direct `JSON.parse` is prohibited outside `src/lib/resources.ts`. Same lint-rule note as Req 1.8 — no new rule needed.

### Requirement 5: `/resources` page

**User Story:** As a visitor, I want to land on `/resources` and see Matthew's curated bookmarks grouped by clear categories, with each entry presenting a title, link, and short description.

#### Acceptance Criteria

1. WHEN a visitor navigates to `/resources` THEN the page SHALL render entries grouped by `category`, with category sections in the canonical order defined by the closed enum from Req 4.2. Display labels (e.g. "DevOps Tools", "Blogs & Feeds") are author-curated and live in `RESOURCE_CATEGORY_LABELS` in `src/lib/resources.ts`, NOT in the YAML.

2. WHEN the page is rendered THEN it SHALL be a statically generated server component with `export const dynamic = 'force-static'`.

3. **Intra-category order**: within a category, entries SHALL sort by **`added` desc, `title` asc, `url` asc** (three keys, deterministic). Comparator `byAddedDescTitleAscUrlAsc` lives once in `src/lib/resources.ts`. **Seed-date degenerate case acknowledged**: WHEN the initial bookmark-import seeds many entries with the same `added` date (per Req 8.1's documented seed pattern) THEN those entries SHALL sort alphabetically by `title asc` within category — i.e., "most recently added first" reduces to "alphabetical within category" for the seed set. This is a known degenerate case; the author doc explains it.

4. **Page heading structure**: the page renders `<h1>Resources</h1>` directly inside `<main>`. Each category section's heading is `<h2>` with stable `id="cat-<category-slug>"`. The `<h1>` → `<h2>` chain is WCAG 2.1 SC 1.3.1 compliant.

5. WHEN the page is rendered THEN each category section SHALL include, in DOM order:
    - The category heading (`<h2>`) per Req 5.4.
    - A `<ul>` of entries.
    - Each entry is a `<li>` containing, in DOM order, an `<a>` (the title link with `href=url`, `rel="noopener"`, same-tab) followed by a `<p class="resource-note">` containing the description.
    - **The v2 `<dl>/<dt>/<dd>` structure is retracted**: `<dl>` is for term-definition pairs (HTML spec); resource entries are link-annotation pairs. `<ul>/<li>` is semantically correct AND avoids the `<dl>`-vs-Pagefind-extractor conflict surfaced in v2 review.

6. **Empty categories**: categories with zero entries SHALL NOT render a heading or an empty `<ul>` — they are silently omitted.

7. **Empty page state**: WHEN `resources` is `[]` THEN the page SHALL render `<main>` containing `<h1>Resources</h1>` (same h1 as the populated state) followed by a `<section aria-labelledby="empty-state-heading">` containing `<h2 id="empty-state-heading">` and a `<p>`. **As with Req 2.9, the exact prose is owned by the page component.** Acceptance tests assert on the structural skeleton AND on the meta description's resolution to the same curated string as the populated branch.

8. WHEN the page is rendered THEN its `<title>` SHALL be "Resources" composed through `%s | matthewfield.ca`. Meta description is a short author-curated string in the page component, 50–160 chars. OG image is the site default.

9. **Responsive**: category sections stack vertically at every breakpoint. Within a category, entries are always single-column.

10. **In-page nav (anchor links)**: AT LAUNCH, the page SHALL NOT render a sticky table-of-contents or floating in-page nav. Each `<h2>` retains its stable `id="cat-<slug>"`, so external deep links like `/resources#cat-reading` scroll to the target. **However, the category slug is NOT a stable URL contract** (Req 10.6).

### Requirement 6: Sitemap inclusion

**User Story:** As a search-engine crawler, I want both `/contributions` and `/resources` listed in the XML sitemap.

#### Acceptance Criteria

1. The existing `src/app/sitemap.ts` SHALL include `/contributions` and `/resources` as static URLs.

2. `lastModified` for each entry SHALL be derived from the most recent `date` (contributions) or `added` (resources) of any entry on that page. WHEN the corresponding collection is empty THEN `lastModified` SHALL fall back to the build timestamp.

**Cross-spec note (NOT a requirement of this spec)**: the HTML sitemap page `/sitemap` is owned by the slash-pages spec (not yet written at the time of this spec). When that spec is implemented, its `tasks.md` will include adding `/contributions` and `/resources` to the HTML sitemap.

### Requirement 7: Helper modules

**User Story:** As a future maintainer, I want each content type's query / sort / display-label logic in one obvious place.

#### Acceptance Criteria

1. `src/lib/contributions.ts` SHALL export:
    - `getAllContributions(): ReadonlyArray<Contribution>` — returns the Velite-typed array, already sorted by `byDateDescRepoAscTitleAsc`. Pages import from here, NOT from `#site/content` directly.
    - `byDateDescRepoAscTitleAsc(a, b)` — the comparator (Req 2.1).
    - Type re-exports for `Contribution` and `ContributionLink` from the Velite-generated types.

2. `src/lib/resources.ts` SHALL export:
    - `getAllResources(): ReadonlyArray<Resource>` — Velite-typed array.
    - `getResourcesGroupedByCategory(): ReadonlyArray<{ category: ResourceCategory; label: string; entries: ReadonlyArray<Resource> }>` — pre-grouped, pre-sorted by `byAddedDescTitleAscUrlAsc` within group, category order matching the canonical enum order. Groups with zero entries are omitted (Req 5.6).
    - `byAddedDescTitleAscUrlAsc(a, b)` — the comparator (Req 5.3).
    - `RESOURCE_CATEGORY_LABELS: Record<ResourceCategory, string>` — the enum-to-display-label map (Req 5.1).
    - Type re-exports for `Resource` and `ResourceCategory`.

3. **Test coverage**: both helpers SHALL have unit tests (`*.test.ts` colocated, matching the pattern set by `src/lib/blog.test.ts` and `src/lib/projects.test.ts`). Tests cover:
    - All three comparator-key branches for each comparator.
    - Group-omission of empty categories.
    - The seed-date degenerate case (Req 5.3).
    - Stability of the comparators against identical-key inputs.

4. **`#site/content` chokepoint** — fact: the existing site-foundation lint rule already exempts files under `src/lib/`. The new files `src/lib/contributions.ts` and `src/lib/resources.ts` fall under that exemption automatically. **No rule edit is required by this spec.** Route files MUST NOT import from `#site/content` directly; this is enforced by the existing rule.

### Requirement 8: Author-facing documentation and build-time heading check

**User Story:** As Matthew authoring contributions or resources later, I want a single doc that tells me the YAML shape, the available link kinds, and the available resource categories.

#### Acceptance Criteria

1. The spec SHALL produce `docs/contributions-and-resources-authoring.md` covering, at minimum, these canonical sections (canonical headings must match exactly for the build check in Req 8.2). **Canonical headings MUST be single-line, MUST NOT contain commas (per Req 8.2's annotation-format constraint), and MUST NOT contain colons within the heading text itself.** The canonical headings are:
    - `## Contributions YAML shape` — required fields, optional fields, the `repo` regex and its GitHub-compatibility rationale.
    - `## Link kinds` — the typed-link table with `kind` enum, default labels, and a forge-mapping subsection (GitLab MR → `pr`, etc.).
    - `## Resources YAML shape` — required fields, the `added` semantics including the UTC-timezone wall-clock note (Req 4.2), the rationale for `added` being mandatory and future-blocked while contributions' `date` is past-or-future-allowed.
    - `## Resource categories` — the canonical category list, the display-label-vs-slug separation, and the extension workflow.
    - `## Seeding added for legacy bookmarks` — the documented pattern that the initial bookmark import MAY share a single `added` date (e.g., the YAML's first-commit date), with explicit acknowledgement that this produces alphabetical-within-category order for the seed set.
    - `## Sort order` — how each page orders entries, including all three tiebreakers for each page, and the seed-date degenerate case for resources.
    - `## Empty-file behavior` — the missing-vs-`[]`-vs-zero-byte distinctions and which fail the build.
    - `## No-draft policy and removal latency` — why neither collection carries a `draft` flag, the feature-branch workaround AND its limitations, AND the explicit "removal latency = one CI+deploy cycle" limitation.
    - `## Deep-link anchor stability` — both `/resources#cat-<slug>` AND `/contributions#contrib-<n>` anchors are NOT a stable URL contract under specific listed conditions (Req 10.6).
    - One concrete example entry for each collection.

2. **A standalone CI step SHALL verify the author doc still contains each canonical heading exactly.** Implementation:
    - **Wiring**: a new `package.json` script `check:authoring-docs` (sibling to `lint`, `test`, etc.) invokes `node scripts/check-authoring-docs.mjs` (new file). The script is invoked from the existing CI workflow at the following position: **after the existing `Lint` step and before `Build 1`**, co-located with the other `Verify-*` script steps. The exact slot is documented in the design phase but MUST be before Build 1 so author-doc drift fails the deploy. The `scripts/*.mjs` location convention matches the existing precedent (`scripts/check-vercel-auto-deploy.mjs`, `scripts/warn-no-pagefind.mjs`, etc.).
    - **Script behavior**:
        - Reads `docs/contributions-and-resources-authoring.md`.
        - For each canonical heading from Req 8.1, asserts the doc contains an exact-match line (the canonical heading string, not a fuzzy match).
        - **Annotation form**: in any environment (CI or local), missing headings emit a bare `::warning::<message>` line on stdout. The repo's existing precedent (`scripts/check-vercel-auto-deploy.mjs:128`, `scripts/warn-no-pagefind.mjs:103`) uses bare `::warning::` not file-scoped `::warning file=...::` — v4 aligns with that precedent rather than introducing a new format. (The earlier v3 file-scoped form had escape-rule complications around commas/colons in headings that the v4 canonical-heading constraint above sidesteps; bare `::warning::` has no parameter-parsing surface.)
        - **Exit-code behavior — same in CI and local-dev**: missing headings cause the script to exit non-zero. The v3 dev/CI asymmetry (local-dev exit 0, CI exit non-zero) is retracted: the only consumer of this script is the author-doc check, so there is no "unrelated local workflow" to protect from friction. Aligning exit codes prevents the silent-fail path where Matthew sees a local warning, dismisses it, pushes, and gets CI-blocked.
        - **Edge cases — explicit**:
            - Doc file missing → exit non-zero, error to stderr, no GHA annotation (no file to scope to).
            - Doc file exists but is zero bytes → treated identically to "file missing all canonical headings" — emit warnings for each missing heading, exit non-zero.
            - Doc file exists with all canonical headings present → exit 0, no output.
        - **Unit test coverage**: `scripts/check-authoring-docs.test.mjs` (sibling, matching the existing `scripts/check-velite-output.test.mjs` pattern) covers: all-headings-present → exit 0; one-heading-missing → exit non-zero + GHA warning on stdout; doc-file-missing → exit non-zero + stderr error; doc-file-zero-bytes → exit non-zero + warnings for every canonical heading.
        - **Integration coverage**: the existing CI workflow's invocation of `pnpm check:authoring-docs` against the actual `docs/` directory IS the integration test. A separate fixture-based integration test in CI is NOT required — the unit tests above exercise the script's logic, and CI invocation exercises wiring.

### Requirement 10: Lifecycle and editorial workflow

**User Story:** As Matthew editing either YAML file, I want predictable failure modes when I make a typo, and predictable rollback when an entry turns out to be wrong.

#### Acceptance Criteria

1. **Typo → build fail**: every kind of schema violation is a CI-blocking build error, surfaced per the Shared Build-Time Error-Message Contract.

2. **Closed-enum blast radius — acknowledged tradeoff**: a typo in a closed-enum field (`kind` or `category`) fails the Velite build, which blocks the entire deploy — including unrelated changes in the same commit. This is the same tradeoff project-showcase's `status` enum makes; it is accepted on the same grounds. **Fix-forward runbook**: revert the offending commit OR push a fix-up commit correcting the YAML.

3. **Renaming a contribution / resource**: there is no concept of "the URL of an entry," because neither page has per-entry subpages. Renaming has no SEO consequence — the entry's `title` / `repo` changes, but no route changes. No redirects needed.

4. **Removal**: removing an entry from the YAML SHALL remove it from the page on the next deploy. No tombstone, no redirect.

5. **Rollback**: a wrong commit is rolled back by `git revert`. There is no per-entry "unpublish" flag.

6. **Deep-link anchor non-stability — narrowed disclaim** (both pages):
    - `/resources#cat-<category-slug>` anchors MAY change if the `category` enum is edited to rename or remove the slug. They do NOT change for unrelated reasons.
    - `/contributions#contrib-<n>` anchors MAY change if a contribution is added or removed in a way that shifts the sort position, OR if the comparator (Req 2.1) is changed in a future spec. They do NOT change for unrelated reasons.
    - The disclaim is narrowed from v3's "MAY change for any reason on any deploy" because that wording was so broad as to make the anchor effectively useless. Under v4's wording, callers can reasonably expect anchors to remain stable across deploys that don't add, remove, or re-sort entries.
    - The author doc (Req 8.1's `## Deep-link anchor stability` section) documents these conditions and warns external deep-linkers.
    - **External `#cat-<old-slug>` links break silently** on a rename (no 301 redirect, no soft fallback). This is an accepted consequence of the category-rename workflow.

7. **No draft state — rationale and limitations**:
    - Neither collection carries a `draft` flag, diverging from the `posts` and `projects` precedent. Rationale: these entries have no per-entry route, no MDX body, no SEO-indexed standalone URL.
    - **Staging-an-entry workflow**: Matthew holds the YAML edit on a feature branch until the companion blog post drops. **Known limitation #1**: rebase friction every time `main`'s YAML changes during the embargo window. A `draft: true` flag would be lower-friction.
    - **Removal-an-entry workflow** (quick-takedown case): removal is a YAML delete + commit + CI + Vercel deploy. **Known limitation #2**: this incurs a full CI+deploy cycle of latency. A `draft: true` flag would NOT solve this — toggling `draft` is also bottlenecked on CI+deploy. Sub-cycle takedown latency requires a separate mechanism (out of scope).
    - The author doc explains both limitations and the workarounds.

8. **Internationalization** — explicit non-feature for v1: `title`, `description`, and `category` slugs are documented as English-only. Unicode IS permitted in the free-form `title` and `description` fields (no schema regex restricts them); category slugs are ASCII kebab-case. The schema regex on `repo` reflects GitHub-username conventions and is ASCII-only.

## Non-Functional Requirements

### Code Architecture and Modularity
- **Single Responsibility Principle**: `src/lib/contributions.ts` owns contribution queries; `src/lib/resources.ts` owns resource queries. Page route files own only rendering + metadata. Velite config owns schema definition and entry-level validation. `scripts/check-authoring-docs.mjs` owns the author-doc heading-drift check.
- **Modular Design**: The contributions schema, the resources schema, the typed-link helper, the empty-payload behavior, and the author-doc check are each independently testable.
- **Dependency Management**: Page route files MAY import from `src/lib/contributions.ts`, `src/lib/resources.ts`, `src/lib/format-date.ts`, shared UI primitives, and Next.js. Page route files MAY NOT import from `#site/content` directly.
- **Clear Interfaces**: All public exports from `src/lib/contributions.ts` and `src/lib/resources.ts` SHALL be typed; comparators SHALL be `(a, b) => number` matching the existing convention in `src/lib/blog.ts` and `src/lib/projects.ts`.

### Performance
- Both pages are statically generated at build time. Zero client JS is added by this spec beyond what the existing site layout already includes.
- No images on either page at launch.
- **Lighthouse performance target: 90+ on both pages**, with the following re-verification cadence:
    - Manually verified at launch.
    - **Count-based cadence (mirrors `scripts/check-lighthouse-cadence.mjs`)**: re-verified every Nth entry addition with **N = 10**, where the count is `contributions.length + resources.length` summed across both YAML files (the same cadence-guard infrastructure used by project-showcase is reused with `N = 10` instead of project-showcase's `N = 3`, because individual contribution/resource entries are smaller editorial events than full project additions, so a larger N matches the editorial-weight asymmetry).
    - Re-verification entries SHALL be appended to a runs-log doc (`docs/contributions-and-resources-lighthouse-runs.md`) following the existing per-run-count convention in `docs/projects-showcase-lighthouse-runs.md`. WHEN a count-triggered check fails the 90+ bar THEN the failure SHALL be triaged within one week.
    - **The v3 "quarterly cadence" framing was retracted** — it cited time-based semantics that the existing cadence-guard infrastructure does not support (the existing guard is count-delta-based, not time-based), and the cited commit `72462c5` was a parser-bug fix, not a pattern introduction. v4 aligns with the actual count-based mechanism.

### Security
- All external links carry `rel="noopener"`.
- All external URLs are validated at build time (`new URL()` parse + http/https-only protocol check) in both collections.
- No user input is ever rendered.

### Reliability
- Empty YAML files (`""` or `null`) SHALL be a build error with a clear, named diagnostic — NOT a silent fallback to `[]`. The "missing file" and "explicit `[]`" cases ARE valid empty states.
- A schema violation is a build error per the shared message contract.
- A failed CI build SHALL NOT leave production broken — the existing Vercel build-and-promote flow does not promote a failed build.

### Usability
- Cards and category sections are keyboard-navigable in source order. Multi-link cards use `role="group"` + `aria-labelledby` (Req 2.6) so screen readers preserve card context across the link rail.
- Color contrast targets WCAG 2.1 AA in both themes.
- Both pages render correctly in dark and light themes.
- `/contributions` and `/resources` are reachable from the landing page hero cards AND from the top nav (Req 9.1).
- Empty states render a sectioned `<section aria-labelledby="empty-state-heading">` containing the page's `<h1>`, an `<h2>` for the empty-state message, and a `<p>` explanatory line. **Empty-state prose text is owned by the page component, not by requirements** (Reqs 2.9, 5.7).

### Maintainability
- The category enum on resources is intentionally closed — adding a category requires editing the schema AND the display-label map AND the author doc (Req 4.2, Req 8.1). This is the documented extension workflow.
- The link-kind enum on contributions is similarly closed (Req 3.1).
- The authoring doc (Req 8) is the single source of authoring truth; the schema is the single source of validation truth. Both live in version control. The build-time heading check (Req 8.2) surfaces drift as CI failures; local-dev runs use the same exit-code behavior, preventing the dev/CI silent-fail path.
- The "no draft state" policy is documented (Req 10.7); both the staging-friction limitation and the takedown-latency limitation are spelled out.
- Cross-document citations use stable references (symbol names, file paths) rather than line ranges (which drift on unrelated edits). Req 9.1 was updated in v4 to cite `src/config/site.ts` by symbol rather than by `:33-72` line range.
