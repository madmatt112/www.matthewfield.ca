# Adversarial Analysis — project-showcase/requirements (v2)

Role: senior technical product manager. The v2 doc absorbed most of the v1 critique — `description`/`summary` split is now schema-enforced, `links` is an array, `featured` is accent-only, alt-text and `<h1>`-in-body are closed, the chokepoint is a real test, the date module is shared, lifecycle and author docs exist. That work is real. What follows is what v2 still gets wrong, what it papered over, and what new problems it created by adding constraints.

Findings are tagged **[Novel]**, **[Compounding]** (deepens prior), **[Recurring]** (unresolved from v1).

---

## Attack surfaces

### A. Req 1.3 — The `description ≤ 160` / `summary` mandatory split

- **[Novel] Challenge the 160-character ceiling on `description` as the SEO-tuning lever.** The v2 contract says: if `description > 160`, you must split. But the *good* SEO meta description is often 140–160; the *good* card body is 60–110. The split fires only when authors write a long description — it does NOT fire for the dominant case where the author writes a 130-char description that's perfect for SERPs and overweight on a card, or a 80-char description that's tight on a card and a wasted SERP opportunity. The schema enforces "split when long" but the failure mode "one mediocre string under 160" is still legal. The v1 finding ("description is overloaded") is only half-resolved. Either require `summary` always, or accept the split is opportunistic, not principled.
- **[Novel] Stress-test the 160 boundary as a magic number with no doc anchor.** Req 1.3 cites "150–160 chars" as the SERP clip zone but pins the schema at exactly 160. Google's actual pixel-width clipping is device- and query-dependent; 160 is a common heuristic, not a contract. When (not if) the author writes a 161-char description that renders fine on every SERP they care about, the build fails and they have to either pad to a `summary` split or trim. The author-facing doc (Req 11) does not currently explain *why* 160 — authors will hit this and assume it's arbitrary.
- **[Novel] Challenge the implicit assumption that `summary ≤ 160` is appropriate for cards.** The whole rationale for `summary` is that card body copy works at 60–110. Capping `summary` at 160 (same as the SERP threshold) doesn't enforce the card-friendly range — it just enforces "shorter than the description's tolerated max." A 155-char `summary` is still overweight on a card. If the spec is going to enforce a relationship, enforce the one that matters: `summary` should target the card range (e.g., ≤ 140), not echo the SERP cap.
- **[Compounding] Stress-test what happens when the author updates `description` later.** Author ships with `description: 130 chars` (no `summary` required). Six months later, edits `description` to 165 chars. Build fails. Author must now either trim or write a `summary` from scratch — and the diff/commit window is a typo fix, not a content rework. The schema's constraint-on-edit will surprise authors mid-edit. Document this explicitly in Req 11 or relax to a warning.

### B. Req 3.1 — Cover image dimension band

- **[Novel] Challenge the 1.4–2.4 aspect-ratio band as overspecified.** v1 had no constraint; v2 swings to a precise inclusive band. The band rules out 4:3 (1.33), which is a perfectly common screenshot aspect — a Mac desktop screenshot at default resolution is 16:10 (1.6), but a windowed-app screenshot may be 4:3 or even 5:4. Authors who take screenshots with their OS's default tools will hit "your cover ratio 1.33 is below the 1.4 floor" and have no clear remediation other than "crop or pad it." That's a real friction tax for a cover-image rule.
- **[Novel] Stress-test `width >= 1200` as the minimum for a cover.** Modern displays render the gallery card at ~400-600 px wide on desktop; the detail page renders the cover at maybe 1000-1280 px (per the `max-w-7xl` outer container). A 1200 px source for a 600 px display target is 2x — exactly right for Retina, but the OG-image use case (1200×630) means the SAME asset is also being asked to serve 1200×630 share previews. A 1200×600 cover (the minimum) is BELOW the 1200×630 OG target by 30 px vertically — Twitter/LinkedIn/Slack will letterbox or crop. The minimum doesn't satisfy the fallback path it claims to satisfy.
- **[Novel] Challenge the "±10% of 1.91:1" rule for explicit `ogImage`.** 1.91:1 ±10% is roughly 1.72–2.10. The cover ratio band (1.4–2.4) is WIDER than the ogImage band — which means a cover that passes the cover check can fail the OG check when used as the OG fallback. Wait — the cover IS the OG fallback (Req 6.4). So a 1.5-ratio cover (passes cover check) becomes the OG image and fails the implicit OG constraint, but there's no schema check that fires because the fallback path doesn't re-validate. The two bands need to be reconciled: either the cover band must be a subset of the OG band, or the fallback needs its own check, or the doc must admit "fallback OG previews may look bad if cover ratio is outside 1.72–2.10."
- **[Novel] Stress-test build-time enforcement of image dimensions across Velite versions.** Velite's `s.image()` emits `width`/`height` based on what the underlying image processor (probably `sharp`) reports. If a future Velite version changes the metadata shape, the schema check (`width >= 1200`) silently passes `undefined >= 1200` (false in JS) and rejects every image. There's no version-pin or contract-test for the Velite output shape. Add a smoke test or pin the version range.
- **[Novel] Challenge the absence of file-size constraints.** Req 3.8 explicitly disclaims an upper bound on dimensions but says nothing about file size. A 5 MB PNG cover passes the schema (dimensions are fine, ratio is fine) and degrades first paint dramatically. The "trust the author" hand-wave from v1 is now codified — but a single 5 MB cover on the gallery is a Lighthouse failure waiting to happen, and Req 12 Performance claims a 90+ Lighthouse target.

### C. Req 5 — Links rail (post-array reversal)

- **[Novel] Stress-test the array-of-objects schema's loss of v1's structural guarantees.** v1's keyed map gave you "at most one demo, at most one repo." v2's array gives you "up to 10 of anything." An author with two demos (staging, prod) or three repos (api, frontend, infra) is now valid — but the visual contract for "two `demo` entries side-by-side" is undefined. The schema permits duplicates of any `kind`; the rendering rule (Req 5.4) says "render in array order" but doesn't say how to disambiguate visually when two entries share an icon. Add either a uniqueness constraint per `kind` (e.g., at most one `demo`) or an explicit "duplicate kinds render with the icon and the label disambiguates them" contract.
- **[Novel] Challenge the cap of 10 entries as a sensible heuristic.** Ten is many. A project rail with 8–10 entries is a rail that visually competes with the cover image and pushes the MDX body below the fold on a laptop screen. The cap prevents pathology but doesn't shape good behavior. Either lower the cap (5–6 is a more honest "this is too many") or surface a soft warning at, say, 7+.
- **[Novel] Stress-test `kind` as "kebab-slug, max 24 chars, unrecognized values render without icon."** The schema accepts any kebab-slug for `kind` — `linkedin-post`, `show-hn`, whatever — but Req 5.1 says only `demo`/`repo`/`docs`/`package`/`writeup` get icons at launch. Authors who type `kind: showhn` (no hyphen) versus `kind: show-hn` versus `kind: hn` get the SAME rendering: no icon, just the label. There's no warning, no log, no "did you mean." Adding a typo in `kind` is silently accepted and silently iconless. Add either a warning surface or accept that `kind` is effectively a label-only field for non-built-in kinds.
- **[Novel] Challenge the omission of `rel="noreferrer"` as a "builder credibility" win.** The spec says noreferrer is intentionally omitted to preserve `Referer` for attribution. But the modern browser landscape sends `Referer` with the origin only (not the path) under default Referrer-Policy — so even WITHOUT `noreferrer`, the destination sees `matthewfield.ca` as the referrer, not the specific `/projects/<slug>` URL. The attribution gain is marginal; the tabnabbing protection is unaffected by noreferrer's absence (that's noopener's job). The reasoning in Req 5.5 conflates "preserving Referer at all" with "preserving rich Referer paths" — only the former survives modern browser defaults. Either restate the rationale or drop it.
- **[Compounding] Stress-test the same-tab default for outbound links.** v1 challenged this; v2 doubled down with "new-tab-by-default confuses non-power-users." That assertion is unsupported by any cited research. Portfolio sites are not a controlled population — the visitor IS the power user (recruiter, fellow engineer, HN reader). The rigid uniform policy still doesn't earn its rigidity.
- **[Novel] Challenge Req 5.4's "rail appears ABOVE the MDX body."** The intro defends short writeups (Req 6.10 anticipates them); a 6-entry rail above a 200-word body produces a page that is 70% navigation and 30% content above the fold. There's no contract for "rail below body when body is short" or "rail collapses if rail entries exceed body word count." The fold-eating failure mode v1 raised is unresolved.

### D. Req 6 — Detail page, container widths, MDX restrictions

- **[Novel] Stress-test Req 6.7's `max-w-7xl` (1280 px) outer container.** The doc claims wide screenshots/videos need the wide outer. But a 1280-px outer with a `max-w-prose` (~65ch ≈ 580–680 px depending on font) inner means the wide outer has ~600 px of *whitespace* on either side of the prose column. On a 1280-px viewport (a common laptop), the outer container fills edge-to-edge and the prose is centered with huge margins. Is that the intended visual? The "design phase" hand-wave covers this, but the contract is non-trivial: most prose-heavy sites use a narrower outer with full-bleed escape hatches for media, not a wide outer with always-narrow prose.
- **[Novel] Challenge the "wide media may escape the prose column" pattern as implementation-deferred.** Req 6.7 names it as "the design's responsibility." But the *contract* for what counts as "wide media" is undefined: does every `<img>` in the MDX body escape? Only those with a `wide` class? Only those above a certain intrinsic width? The MDX author has no way to express "this image stays narrow" vs. "this image goes wide" — and there's no custom-component path (Req 6.9.b forbids that). The pattern as specified is unimplementable without either a custom component (forbidden) or a CSS heuristic on plain `<img>` (unspecified).
- **[Novel] Stress-test Req 6.9.a's build-time `<h1>` rejection across MDX/Markdown forms.** The rule rejects "any heading of depth 1." A remark/rehype AST check catches `# Heading` and `<h1>` JSX. But what about an HTML-in-markdown `<H1>` (capitalized) or an embedded `<header><h1>...` block? Or a `<div role="heading" aria-level="1">`? The rule is straightforward for the common case but the doc says "parallel to the heading-depth check the posts collection already enforces" — verify the existing check actually catches all variants, or constrain the rule to "depth-1 headings emitted by the MDX AST."
- **[Novel] Challenge Req 6.9.b's "no custom MDX components" as a permanent ergonomic tax.** The spec acknowledges (via Req 11) that authors will hit this rule. The remediation is "documentation." But the implicit consequence — authors cannot use ANY of the MDX features they're conditioned to expect (callouts, code-with-filename, video embeds via component) — pushes them to either inline `<video>`/`<iframe>` HTML in MDX (which works but is verbose) or write their own bespoke markdown patterns. A spec that ships explicitly markdown-only is a spec that materially differs from "MDX" in user expectation. Rename the file extension and the user model, or accept components and provide a registry.
- **[Novel] Stress-test Req 6.1's DOM order against accessibility heading flow.** The spec says the detail page renders: `<h1>`, date, "Updated on …" badge, status badge, cover image, link rail, MDX body, "Back to all projects." The link rail (Req 5) contains anchors with text labels. If the MDX body's first content is an `<h2>`, the heading order is fine. But if the MDX body starts with a paragraph (common), the screen reader flow is: h1 → date → badges → image → rail-anchors → paragraph → h2. The first `<h2>` is far from the `<h1>` in reading order, and screen-reader users who jump by headings get a sparse landmark structure. Document the heading-flow expectation in the author doc (Req 11), or require body MDX to start with an `<h2>`.
- **[Novel] Challenge the missing contract for `<h2>` and `<h3>` nesting.** Req 6.6 says h2/h3 get anchored IDs via rehype-slug. But there's no contract preventing `<h3>` before `<h2>` (which is an a11y violation) or `<h4>+` (skipping levels). The blog-core spec may or may not enforce this; the projects spec doesn't restate it. With a "no custom components" rule, all structure must come from headings — making heading hygiene more important here than in a blog post.

### E. Req 7 — Draft handling, env disambiguation, and chokepoint test

- **[Novel] Stress-test Req 7.2.c's `NODE_ENV` discriminator under `next build && next start`.** The spec says `NODE_ENV=development` → drafts visible, `NODE_ENV=production` → drafts excluded. But what about `next build && next start` (production-mode runtime serving)? `NODE_ENV=production`, no VERCEL var — by Req 7.2.b, drafts are excluded. Fine. But the build was static; `next start` serves the build artifact. The "guard fires at build time" model assumes the guard ran when the static pages were generated. If an author runs `PROJECTS_INCLUDE_DRAFTS=1 pnpm build` and then `pnpm start`, the drafts ARE in the static output — `start` has no env-var contract to re-exclude them. The doc doesn't address build-time-vs-runtime separation for static sites; it assumes build = serve.
- **[Novel] Challenge the chokepoint test's regex/AST scan approach.** Req 7.4 says the test scans `src/**/*.{ts,tsx}` and fails on `import ... projects ... from '#site/content'`. A regex/AST scan over source text is brittle: `import { posts, projects } from '#site/content'` matches; `import * as content from '#site/content'; content.projects` does NOT match. Re-exports through a barrel (`export * from '#site/content'`) also evade. The contract is "no direct collection access outside src/lib/projects.ts" — the test as specified catches the named-import shape but not the destructure-after-namespace-import or barrel-re-export. The chokepoint claim is "mechanically enforced" but the mechanism has known gaps.
- **[Novel] Stress-test the env-var name `PROJECTS_INCLUDE_DRAFTS=1`.** Blog-core likely has its own `BLOG_INCLUDE_DRAFTS` (or similar). An author running `INCLUDE_DRAFTS=1 pnpm build` (forgetting the prefix) gets blogs but no projects, or vice versa, or neither. The two-env-var pattern is correct for separation of concerns but creates a small footgun. The author-facing doc (Req 11) needs to address this with the blog spec's counterpart.
- **[Novel] Challenge the absence of a test for the chokepoint test itself.** The chokepoint test scans source files for forbidden patterns. Who tests the test? If the regex is wrong and accepts a forbidden import, the test passes and drafts leak. Add a meta-test or a known-bad fixture file that the test SHOULD reject — a "canary" pattern that proves the scanner works.
- **[Compounding] Stress-test the rollback story.** v1 noted no rollback contract; v2 added Req 10.5 with two paths (fix-forward or revert). But the "during the window, bad content IS live" admission is the actual contract — and the doc doesn't quantify the window. CI deploy takes minutes; the window between bad-publish and fix-deploy is the same minutes. Document an expected upper bound on that window (e.g., "publish fixes typically deploy in <5 minutes per the CI duration target") or accept the window is unbounded.

### F. Cross-cutting — Req 9 module placement, Req 11 doc, and silent contradictions

- **[Novel] Challenge Req 9.1's module path `src/lib/format-date.ts` as the right home.** The doc says "shared module" — but it's a one-function module. A 3-line export is module overhead. If the formatter belongs anywhere, it belongs in `src/lib/utils.ts` (which already exists, per the directory listing) or co-located with the only two consumers (blog, projects) as a tiny shared helper. Creating a new file for one function with one export adds a maintenance edge.
- **[Novel] Stress-test Req 11's "or, if site-foundation's CI link checker would treat that as a content file."** That's an unresolved decision masquerading as a requirement. The doc says "the filename is a design-phase decision." But the filename has real consequences: `content/projects/README.md` IS scanned by Velite's glob pattern (`projects/*.mdx` — wait, that's only `.mdx`, so `.md` is fine; but the next dev who adds `**/*.md` in another tool will trip). The decision should be made now, not deferred.
- **[Novel] Challenge Req 11.2's "launch gate" status.** It says the spec is "not complete until Req 11.1 is met." But "the doc exists" is not the same as "the doc is correct." There's no acceptance test for the doc's coverage — no checklist verifying it actually covers all eight bullets. The doc can ship as a 3-line stub and the spec passes.
- **[Novel] Stress-test the intro's expanded "in scope" list against requirements.** The intro now says "author-facing MDX contract documentation (Req 11)" and "a shared date-formatting module the blog also consumes" are in scope. The latter is a cross-spec change — modifying `src/lib/blog.ts` to re-export from a new module. That's a refactor of an already-shipped spec, not a project-showcase concern. The risk: a regression in the blog's date formatter is introduced by this spec, and the blame trail goes to project-showcase. State this risk explicitly or scope the shared module as a follow-up.
- **[Novel] Challenge Req 12 Performance's 90+ Lighthouse claim without an enforcement path.** Lighthouse targets without CI checks are aspirational. The blog-core spec presumably has the same target; does CI run Lighthouse? If not, "SHALL meet 90+ Lighthouse" is a hope, not a contract. Either cite the CI check, defer the target to a manual verification step, or drop the requirement.
- **[Novel] Stress-test the empty-gallery contract against the homepage.** Req 2.9 says the empty gallery renders with "No projects published yet." The intro says the site's nav MAY link to `/projects` even when empty. But the site's homepage probably has a "recent projects" or "see my work" link. What happens to that link target — does it disappear? Show a placeholder? Render a teaser of zero items? Cross-spec link integrity is unaddressed.
- **[Novel] Challenge the missing user story for `featured` setting/unsetting.** Req 2.7 / Req 1.3 / Req 12 all mention `featured`, but no user story narrates "Matthew wants to highlight a recent project — what's the operational contract for setting featured: true, and when should he unset it?" Without that story, `featured` is a frontmatter flag with no editorial guidance. Add a sentence in Req 11 or write the user story.
- **[Recurring] Challenge the absence of a `noindex` mechanism for in-progress projects.** Drafts are excluded; archived/concept projects are indexed. There's no path for "published but don't index" — e.g., a project that's public-for-direct-link but shouldn't appear in search results. Not raised in v1; raising now. May be out-of-scope, but should be acknowledged.

## Top 5 risks/gaps

1. **The 160-char `description` cap is opportunistic, not principled.** v2 enforces a split only when `description > 160`, but the dominant failure mode — "author writes one 130-char description, mediocre on card AND on SERPs" — is still legal. The schema fires at the long-description case but not at the more common compromise-string case. Either always require `summary`, or accept that the constraint is opportunistic.

2. **The cover-image aspect-ratio band (1.4–2.4) doesn't include the OG-image band (~1.72–2.10).** A cover that passes the cover check can produce a bad OG preview via the fallback path. The two bands need to be reconciled — either narrow the cover band, widen the OG band, or re-validate covers when they're used as OG fallback.

3. **The chokepoint test's scan approach has known evasions** (namespace imports, barrel re-exports, dynamic imports). The doc claims "mechanically enforced" but the mechanism is a regex/AST scan that doesn't catch all the shapes the failure mode can take. Either ship an ESLint custom rule with semantic resolution or document the scanner's known gaps.

4. **`max-w-7xl` outer + `max-w-prose` inner produces a wide outer with mostly-empty whitespace on common laptop viewports.** The "wide media escape" pattern is named but its mechanism (which images escape, how authors signal escape) is "design phase." Without a custom-component path (forbidden by 6.9.b), authors have no way to mark an image as wide vs. narrow. The container contract is unimplementable as stated.

5. **The author doc (Req 11) is a launch gate but has no completeness check.** "The doc exists" passes the gate; "the doc covers all eight bullets correctly" is unverified. Authors will encounter undocumented edges (e.g., the `PROJECTS_INCLUDE_DRAFTS` vs. blog's equivalent, the `kind` typo silent-accept, the 160 boundary's rationale) and learn them by breaking the build.

## Top 3 conclusions to challenge or reverse

1. **Reverse: make `summary` always required, not conditionally required.** The conditional split (Req 1.3) is half-resolved v1 critique. The principled stance is that meta description and card body are different surfaces with different optimal lengths; the schema should reflect that always, not opportunistically. The migration cost (one frontmatter field on each project) is one-time and small.

2. **Reverse: drop the cover-image aspect-ratio band entirely; require a separate `ogImage` when an author wants a sharp share preview.** The current band-checked-at-build approach pretends to validate share appearance but the bands don't match the share targets. Either accept that covers and OG images are different concerns (require `ogImage` explicitly for projects that want good shares) or generate the OG image from the cover with a sharp pipeline (out of scope for this spec, but more honest than a band that doesn't match the requirement).

3. **Reverse: allow custom MDX components via a small launch registry.** The "no components" rule (Req 6.9.b) is a permanent ergonomic tax to avoid building the registry. A 3-component registry (`<Aside>`, `<Figure>`, `<Video>`) at launch costs ~50 lines of code and removes the entire class of "author hit a wall and broke the build." If the spec actually wants the headline goal — "drop an MDX file and ship" — then giving authors basic MDX components is more aligned than enforcing markdown-only and calling it MDX.

## What's missing — pre-action work

- **A concrete decision on the `description`/`summary` split:** opportunistic (current) or always-required. Pick one with rationale.
- **A reconciliation of the cover-band (1.4–2.4) and OG-band (1.72–2.10):** either narrow the cover band, validate the fallback path, or accept and document that fallback OG previews may letterbox.
- **A test for the chokepoint test itself** — a known-bad fixture that proves the scanner rejects the patterns it claims to reject.
- **A worked example of the wide-outer/narrow-inner container** showing how a wide screenshot ACTUALLY renders given the "no custom components" constraint. Either show the CSS pattern that lets a plain `<img>` escape, or admit that wide-image escape requires either a custom component or an MDX-pipeline rewrite (which Req 3.7 forbids).
- **A completeness checklist for Req 11's doc** — eight bullet items mapped to acceptance, so "doc exists" doesn't pass the launch gate without actual coverage.
- **A decision on `featured` editorial guidance** — when to set, when to unset, how many features at once, whether unsetting after a year is correct or revisionist.
- **A cross-spec audit for env-var naming** (`PROJECTS_INCLUDE_DRAFTS` vs. blog's equivalent) and a unified pattern, OR an explicit doc statement that each content type has its own draft-include flag.
- **An OG-image strategy that doesn't depend on the cover being share-shaped.** Either generate or require, but not "fallback and hope."
- **A heading-hygiene contract for MDX bodies** — minimum first heading depth (h2), no skip from h2 to h4, etc. With custom components forbidden, structural authoring relies entirely on heading discipline.
