# Adversarial Analysis — contributions-and-resources / tasks.md (v1)

Reviewer stance: tear-down. The tasks were produced from a strong, much-reviewed design (v4, post-r3). The decomposition is genuinely good — atomicity is mostly right, the DAG is mostly self-consistent, and the three load-bearing Velite corrections are pinned hard in both prose and `Restrictions:`. But there are real gaps: a few requirement-coverage holes the matrix papers over, one ordering hazard that can leave an intermediate commit red, several `Success:` lines that reduce to "looks right," and one scanner-allowlist omission that mirrors a real pattern in the existing `projects` infra. Findings below are grounded against the live repo.

## 1. Task ↔ design fidelity (the load-bearing mechanisms)

**Verdict: strong. The three corrections are pinned as enforceable `Restrictions:`, not just prose.**

- **No `s.array(...)` regression.** Task 2's `Restrictions:` explicitly say "Per-entry object schema only (no `s.array(...)` wrapper)" and the `Success:` checks both modules export cleanly for Task 5. This is enforceable: Task 5's `Success:` (`pnpm exec velite build` exits 0 and emits both JSON files) would fail loudly if Task 2 had shipped an `s.array` wrapper, because Velite applies the collection schema to each *element* (design correction #1, verified at the design's cited `chunk-4HFW4XPZ.js:38005-38019`). So the prohibition is backed by a downstream gate. Fine.

- **No `.transform()` on `isoDate()`.** Task 1's `Restrictions:` say "No `.transform()` on `isoDate()`" and its `Success:` requires "calendar-invalid dates produce aborted ZodIssues (no thrown RangeError)." This is the single best-pinned decision in the document — it has a direct unit test (`2026-02-30`, `2026-13-45`, non-leap `2026-02-29`) AND a restriction AND a success criterion that mechanically catches the regression. Good.

- **No global `strict:true` / no native errorMap path.** Task 2's `Restrictions:` say "No per-field `errorMap`"; Task 5's say "Additive only — do not modify existing collection definitions." Neither task touches `defineConfig`'s `strict` key (it stays unset → `false`). The loader-as-validator is the only hard-fail hook, and Task 4 pins `throw new Error("\n" + messages.join("\n"))`. **Gap (minor):** no task or restriction explicitly forbids a future implementer from adding `strict: true` to `defineConfig` as a "belt and suspenders" — the design's "Rejected alternative" reasoning lives only in design.md prose, not in any task restriction. An over-eager implementer of Task 5 could add it and silently convert currently-warning `posts`/`projects` content into a hard failure (the exact blast radius the design rejected). **Recommend:** add to Task 5 `Restrictions:` an explicit "do NOT set `strict` in defineConfig."

- **Task 3 schema-walk specificity.** Task 3 reproduces the unwrap table verbatim (`ZodEffects→_def.schema`, `ZodPipeline→_def.out`, etc.) and names the exact target path `["links",0,"kind"]` through the `superRefine` `ZodEffects`→`ZodArray`→element `ZodObject`→`.shape.kind`. It also pins the defensive fallback ("OMIT the member list rather than throw"). A unit test for that exact traversal is required in the test bullet. This is specific enough that an implementer would reproduce it rather than ship a thrower. **One residual risk:** the `ZodPipeline` row says "`_def.out` (then `_def.in` if needed)" — "if needed" is the only vague clause in the table, and which of in/out you want depends on whether you're walking toward the *input* shape (for `unrecognized_keys` `.shape` matching) or the *output*. For `trimmed()` (`transform(trim).pipe(string.min.max)`) the `unrecognized_keys` never fires on a string field anyway, so this ambiguity is harmless in practice — but the `Success:` line does not test a pipeline-traversal case, so an implementer could pick the wrong branch and no test would catch it. Low severity (no field combination actually exercises it), but flagged.

- **Task 4 "throw propagates to non-zero exit" — asserted, not verified in-task.** Task 4's tests call `makeContentYamlLoader({...}).load(fakeVFile)` and assert it *throws* — they do NOT assert the throw becomes a non-zero process exit through Velite. That end-to-end claim is only verified in **Task 26** (the throwaway-branch build). So between Task 4 landing and Task 26 running, the "hard build failure" property is asserted by design prose + unit-level `throws`, never integration-tested. This is acceptable (Task 26 is the integration test and is on the critical path to done via the DAG), but it means **Task 4's `Success:` overstates coverage** — it says the loader "delivers the hard build failure the requirements demand" in its Purpose, while the tests only prove `load()` throws. The actual hard-fail is a Task-26 deliverable. Not a defect, but the matrix marks 1.4/4.4 as "I + V" against Tasks 3/4/26 — the **V** genuinely lives in 26 alone.

## 2. Atomicity and sizing

- **Task 3 is the one oversized bucket.** It bundles SEVEN distinct pure-function surfaces (`formatZodIssues`, `serializeValue`, field-path builder, locator chooser, `formatEnumMembers`, schema-walk-with-unwrap-table, nearest-key matcher) plus all their tests, in ONE file (`content-error-format.ts`) under ONE checkbox. The design itself lists these as seven contract items. This is the highest-complexity single task in the spec and the hardest to review as a unit — a reviewer cannot track "is the unwrap table done" separately from "is the locator chooser done." It is technically one file / one concern ("the error contract"), so it does not violate the 1–3-file atomicity rule, but it hides the most defect-prone sub-work (the v3 schema-walk, which r3 flagged as previously unspecified) inside a single binary checkbox. **Recommend:** either split into 3a (serialize/field-path/locator — the "easy" formatting) and 3b (schema-walk + unwrap table + enum-member derivation + did-you-mean — the "hard" introspection), OR add explicit per-sub-function checkboxes to the task body so the reviewer can verify each contract clause independently. As-is, the `Success:` line ("every contract-clause unit test passes") is the only thing standing between this task and a partial implementation.

- **Task 2 bundling both schema modules is fine.** Two small files, same pattern, single concern (per-entry schemas). Atomic enough.

- **Too-granular candidates:** Task 14 (CSS) and Task 25 (hero-card copy) are each a single tiny edit. Task 25 is even labeled "optional polish." These are arguably below checkbox-worthiness, but they carry distinct DAG dependencies (14 ← 12,13; 25 ← 17,19) and distinct requirement IDs, so keeping them separate is defensible for traceability. Not a defect; leave them.

- **Hidden merge couplings (files touched by >1 task):**
  - `eslint.config.mjs` is edited by **both Task 7** (importNames + helper allowlist) **and Task 9** (canary off-list). This is a genuine shared-file coupling. The tasks don't flag this. **Severity: low** (trivial merge), but it is an undeclared coupling — worth a one-line note in both tasks.
  - `tsconfig.json` is touched only by Task 9. Fine.
  - `velite.config.ts` only by Task 5. Fine.
  - `.github/workflows/ci.yml` only by Task 24. Fine.
  - `package.json` by Task 22 (check:authoring-docs script) only. Fine.

## 3. Ordering, dependencies, and the chokepoint cluster

This is where the most concrete hazard lives.

- **Task 7 vs Tasks 12/13 — the eslint additive edit can leave an intermediate commit RED, in one direction.** Task 7 adds `contributions`/`resources` to `importNames` AND adds `src/lib/contributions.ts`/`resources.ts` to the exemption allowlist, in the same change. The DAG correctly draws `7 → 12` and `7 → 13`.
  - **If 7 lands before 12/13 (the DAG order):** `importNames` now restricts `contributions`/`resources`, and the two helper files are allowlisted — but the helper files **do not exist yet**. eslint's `no-restricted-imports` allowlisting a non-existent file is harmless (it's just a `files:` glob that matches nothing). No real file imports the new symbols yet. **Lint is green.** Good.
  - **If 12 lands before 7 (DAG-violating order):** `src/lib/contributions.ts` imports `contributions` from `#site/content`, but `importNames` does not yet restrict it AND the file is not yet allowlisted — so no rule fires. **Lint is green.** So the dependency edge `7 → 12` is about *correctness of the guard*, not about lint-greenness: 12-before-7 leaves the chokepoint temporarily unenforced but not red. The `_Depends on: 5, 7` on Task 12 is therefore slightly stronger than strictly necessary for CI-greenness, but it correctly preserves the *guard-is-active* invariant. **No Req 1.9 violation in either order.** Fine — but note the edge is a correctness edge, not a build-green edge, and the task prose doesn't say so.

- **The canary three-exemption cluster (Tasks 8, 9) — a real intermediate-red window.** Task 9 creates `src/__fixtures__/content-chokepoint-canary.ts` carrying intentional raw `#site/content` imports, and must add it to (i) `tsconfig.json` exclude, (ii) eslint off-list, (iii) the scanner allowlist (which is Task 8's file). Task 9 `_Depends on: 8`. The hazard: **all three exemptions must be in the SAME commit as the fixture**, or:
  - Fixture without tsconfig-exclude → `pnpm typecheck` (ci.yml:51) **fails** on the intentional violations (the design explicitly cites this as r3 finding #5: "otherwise `pnpm typecheck` fails").
  - Fixture without eslint-off → `pnpm lint` (ci.yml:45) **fails**.
  Task 9's `Success:` line does require "`pnpm typecheck` and `pnpm lint` both pass with the new fixture present," which forces both (i) and (ii) into the task. **But (iii) the scanner allowlist is Task 8's responsibility, and Task 8 lands first** — Task 8 must path-exempt a fixture file that does not yet exist when Task 8 lands. That is fine (it's just a path string in an allowlist). The real risk is the reverse: **if Task 8's allowlist forgets the fixture path, Task 10's scanner test will flag the canary as a violation** — but that's caught by Task 10's `Success:` ("authorized helpers + the canary path are NOT flagged" is in Task 10's body). So the cluster is self-consistent **provided Task 9 is a single atomic commit**. The tasks say so implicitly via the `Success:` lines. **Recommend tightening:** add to Task 9 `Restrictions:` the explicit "fixture + tsconfig-exclude + eslint-off MUST be one commit (never split)" — Req 1.9's intermediate-green invariant depends on it and it's currently only implied by the success line.

- **The new scanner test file is NOT in the scanner allowlist — coverage parity gap with `projects`.** I verified that `src/lib/projects.test.ts` IS in the projects scanner's `PRODUCTION_ALLOWLIST` (`projects.test.ts:315-318`), alongside the canary and `projects.ts`. Task 8 says it path-exempts only "the new canary fixture path." Task 10's `check-content-chokepoint.test.ts` will own regex *sentinels* — and I confirmed those sentinels in `projects.test.ts:372+` are **RegExp literals** (`/^import \{ projects \} from "#site\/content";$/m`), not real import statements, so an AST-based scanner would NOT flag them. **So the omission is probably harmless** (the test file has no real imports for the AST walk to catch). BUT: the existing `projects` infra defensively allowlists its test file anyway, and the design claims "true parity with `projects`." If the implementer writes the new test to read the canary via `fs.readFileSync` (the projects pattern) the test file is clean; if they instead inline a fixture string that happens to AST-parse as an import, the scanner self-test (Task 10) would flag its own test file. **Severity: low**, but it is a parity deviation the design's "zero changes to projects infra / full parity" framing glosses over. **Recommend:** Task 8's allowlist should mirror projects and include `src/lib/build/check-content-chokepoint.test.ts`, OR Task 10's restrictions should pin "read the canary via fs only; no inline import-shaped strings outside RegExp literals."

- **Task 24 (CI wiring) implicit dependencies.** Task 24 `_Depends on: 11, 22, 23`. It inserts three steps and re-runs `verify-ci-topology.mjs`. **Question from the prompt: does it also need the helpers/pages to exist for the build steps to pass?** Task 24 only ADDS steps to the workflow; it doesn't run the full CI. The new cadence step (Task 23's script) reads `.velite/*.json` which exist after any `velite build` — but the cadence script's "two-file-missing → fail hard" semantics mean that if Task 24's CI edit is exercised before Task 5's collections are registered, `.velite/contributions.json` won't exist and the cadence step fails. However, Task 23 `_Depends on: 5`, and Task 24 `_Depends on: 23`, so transitively 24 depends on 5 — the files will exist. **No gap.** The `verify-ci-topology` re-run is a real action (its `Success:` requires exit 0), not a hope. Good.

- **DAG vs `_Depends on:` footer consistency.** I cross-checked every edge in the mermaid graph against the per-task footers:
  - Graph has `T2 → T4` and `T3 → T4`; Task 4 footer `_Depends on: 2, 3`. ✔

## 5. Completion criteria and verifiability

- **Several `Success:` lines reduce to "renders the documented structure":** Tasks 15, 16, 18 all have `Success:` of the form "renders the documented structure; typecheck/lint clean." **None of these three component tasks has a test file.** "Renders the documented structure" is verified by no automated check — it's manual inspection. That is consistent with the existing repo's `projects` components if those also lack render tests (not verified here), but the spec's own Testing Strategy admits it ("manual review"). **The weakest verifiability cluster in the spec.**

- **Task 26 (end-to-end) leans on implementer discipline, and at least one listed malformed class needs scrutiny.** Task 26 enumerates malformed classes and says "do not commit." Two concerns:
  1. **"zero-byte file"** as a malformed class: the loader throws "empty or null" on `yaml.parse("") === null`. ✔ Reproducible.
  2. **"top-level mapping"**: loader throws "must be a top-level YAML list." ✔
  3. **"future-dated `added`"**: the `added` refine is `Date.parse(d) <= BUILD_START_UTC`. `BUILD_START_UTC = Date.now()` captured at module load. A future date like `2027-01-01` reliably exceeds it. ✔ **BUT** — the design's `added` is `isoDate().refine(...)` and `isoDate()` aborts *fatally* on bad calendar dates, so the refine only runs on valid dates. A future-dated-but-calendar-valid date correctly fires the refine. ✔ Reproducible.
  4. **"calendar-invalid `date`" (contributions)**: `date: isoDate()` with NO upper bound. `2026-02-30` → round-trip rejects. ✔
  - **The one to scrutinize: "duplicate `kind`".** `uniqueByKind` is a `superRefine` on the `links` array. Task 26 says introduce a duplicate-`kind` entry and confirm hard-fail. This works **only if** `links` has ≥2 entries with the same kind AND the array otherwise passes `.min(1).max(5)`. The `superRefine` is reachable. ✔ Reproducible. No false assertion found here.
  - **Real weakness:** Task 26 is a manual checklist on a throwaway branch with "DO NOT commit" — there is **no committed regression test** that any of these eight malformed classes hard-fails. Once Task 26 is checked off, nothing in CI re-verifies the hard-fail for these specific classes (the loader unit tests in Task 4 cover *a* bad enum / oversize / unknown-key / dup-kind / future-`added` / calendar-invalid-`date`, which IS the committed regression layer — so this is less bad than it first looks). The loader tests (Task 4) ARE the durable regression for most classes; Task 26 is a one-time integration confirmation. **The matrix should make clear that the durable V for 1.4/4.4/10.1 is Task 4's loader tests, not Task 26.** As written the matrix lists 3,4,26 — fine, but the emphasis on 26 as the verifier slightly overstates a non-committed task.

- **`_Prompt` self-sufficiency:** the prompts are unusually thorough — each restates role, restrictions, leverage, requirements, and a concrete `Success:`. A fresh-context implementer could execute Tasks 1, 2, 4, 5, 7, 12, 13, 22, 23 from the prompt alone. **Task 3 is the exception** — its prompt says "exactly per the design's seven contract items and the unwrap table" — this is a hard dependency on reading design.md (the prompt does not inline the unwrap table). That's acceptable (the prompt names the design section), but it means Task 3 is NOT self-sufficient from the prompt text alone; it requires design.md §"Schema-walk unwrap table" open alongside. Given Task 3's complexity, that's appropriate, not a defect — but it's the one task where "the prompt assumes context only the author has" is closest to true.

## Top 6 risks/gaps (ranked)

1. **Rendering layer (Tasks 15–19) ships with ZERO render tests; Req 2.6/3.7 a11y wiring (`aria-labelledby` ↔ `id`) is verified only by manual review.** Failure scenario: implementer writes `<h2 id={\`contrib-${index}\`}>` in Task 16 but passes `labelledBy={\`contrib_${index}\`}` (underscore) to the rail in Task 15. Both `Success:` lines ("renders the documented structure; lint clean") pass. The rail's `aria-labelledby` dangles, screen readers announce no group name, and nothing catches it until a human runs a screen reader. Responsible: Tasks 15+16 split ownership of a single id↔aria contract with no joining test. **Fix: add a DOM/`toHaveAccessibleName` assertion to Task 16.**

2. **Task 5 has no restriction forbidding global `strict: true` in `defineConfig`.** Failure scenario: an implementer "hardening" the build adds `strict: true` to `defineConfig`. Every currently-warning `posts`/`projects` entry becomes a hard build failure — the exact unassessed cross-spec blast radius the design explicitly rejected (design lines 27-28). Lands green for contributions/resources, breaks an unrelated `posts` deploy. Responsible: Task 5, missing restriction. **Fix: add "do NOT set `strict` in defineConfig" to Task 5 restrictions.**
