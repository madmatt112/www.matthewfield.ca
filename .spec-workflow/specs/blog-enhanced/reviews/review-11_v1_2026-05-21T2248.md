## Findings

### WARNING: Fragment fallback does not decompress gzipped .pf_fragment files
- **File:** scripts/verify-pagefind-no-drafts.mjs:70
- **Issue:** collectIndexedUrls() reads each fragment/*.pf_fragment file via readFileSync then casts the buffer to a UTF-8 string and applies a `"url":"..."` regex. Pagefind 1.x .pf_fragment files are typically gzip-compressed binary blobs; the inline comment even acknowledges this (`Fragments may be gzipped or plain JSON`) yet no zlib.gunzipSync is invoked. Against a real Pagefind output, the regex will find zero URL matches when fragments are compressed, the fallback returns urls=[], and the non-empty assertion will fire with a misleading diagnostic ("index has 0 entries...") despite the index actually being healthy. Decompress before scanning, or pin a manifest source (e.g. parse pagefind-entry.json + a sibling URL-listing file) that does enumerate URLs in plaintext.
- **Task Requirement:** 1.12

### INFO: Primary pagefind-entry.json path is effectively dead code per design
- **File:** scripts/verify-pagefind-no-drafts.mjs:45
- **Issue:** Design line 1222 documents pagefind-entry.json as containing only `version + language list` — no `pages`/`urls`/`entries` array. The script reads the file and looks for those fields, but per the design contract they will never be present, so the code path always falls through to the fragment fallback (the only real source). Not incorrect, but the defensive-first ordering misleads readers about which path actually executes in production. Consider either (a) removing the dead primary branch, or (b) pinning a different manifest source that genuinely enumerates URLs in plaintext.
- **Task Requirement:** 1.12

### INFO: Generalization from `+1 fixture-search` to `+ hidden.length` deviates slightly from spec letter
- **File:** scripts/verify-pagefind-no-drafts.mjs:133
- **Issue:** Tasks.md line 278 and design line 1032 pin the expected count as `getVisiblePublishedPosts().length + 1` (the +1 dedicated to fixture-search). The script generalizes to `visible.length + hidden.length`, partitioning by `hiddenFromLists: true`. This is a sensible generalization (and the implementation log declares it as such), but it depends on hiddenFromLists semantics matching the +1 carve-out. If any future hiddenFromLists post is NOT actually crawlable, the assertion will over-count. Acceptable today; document the coupling.
- **Task Requirement:** 1.12
