# Adversarial Analysis: Technology Stack Steering Document

---

## 1. Next.js Over Simpler Alternatives — Justify the Complexity Budget

### Do playground items actually need SSR or API routes?

The product document describes playground items as "self-contained mini-apps, toys, games, curiosities, and small tools." The overwhelming majority of things fitting this description are purely client-side: canvas animations, WebGL demos, JavaScript games, CSS art, interactive visualizations. None of these need server components or API routes.

The tech document's justification — "the playground requirement for dynamic, potentially server-backed experiments makes Next.js the better fit" — is speculative. The product doc's "Future Vision" mentions "lightweight serverless options" as a potential enhancement, not a launch requirement. Choosing the framework based on hypothetical future needs that the product document itself defers is a weak basis for the decision.

The one concrete server-side need is the contact form, which calls Resend's API. This is a single API route. Astro supports API routes (endpoints). So does any static framework paired with a serverless function on Vercel. This does not require Next.js.

### The complexity tax is real

Next.js App Router adds meaningful overhead to a static-first site:

- **Mental model cost**: Server components vs. client components, the `"use client"` boundary, rules about what can import what, serialization constraints on props passed from server to client. For a site where most pages are static markdown, this is overhead with no payoff on those pages.
- **Baseline JavaScript**: A Next.js App Router page with zero client components still ships the React runtime (~40-45KB gzipped) plus the Next.js client-side router (~15-20KB gzipped). Astro ships zero JS by default. Eleventy ships zero JS by default. For the blog listing, the profile page, the resources page, the contributions page — all static content pages — Next.js ships ~60KB of JavaScript that does nothing useful.
- **Hydration on static pages**: Every Next.js page hydrates on the client to activate the router, even if there are no interactive elements. This is wasted CPU on the user's device and delays time-to-interactive.

This is not a theoretical concern. The document targets "90+ Lighthouse performance score" and "no unnecessary JavaScript on content pages." Next.js structurally contradicts the second goal on every page.

### Playground isolation: is it actually simpler in Next.js?

The document proposes style-reset boundaries and iframe fallback within a single Next.js app. Compare the alternative: a static site (Astro/Eleventy) for content pages, with playground items as independent mini-apps deployed to subpaths or subdomains.

With the alternative approach:
- Content pages ship zero JS and trivially hit 100 Lighthouse performance.
- Each playground item is truly isolated by default — separate build, separate dependencies, no leakage risk.
- No need for "style-reset boundaries" or iframe hacks.
- Adding a new playground item with weird dependencies never risks breaking the main site's build.

The single-Next.js-app approach creates coupling that requires engineering effort to undo (isolation boundaries, iframe fallback, potential pnpm workspace extraction). The multi-app approach starts isolated and only creates coupling if you choose it.

**However, the DX argument for Next.js has genuine merit** — though the document doesn't make it. Running playground items as separate apps means separate build configs, separate deployments, and cross-app navigation friction. For a solo maintainer, having one `next dev` process with hot reload across the whole site, including playground items, is genuinely simpler day-to-day than coordinating multiple apps. The document should have made this argument instead of the SSR argument.

### Vercel coupling

The document chooses Vercel specifically because it's "zero-config for Next.js" and dismisses Cloudflare because "the OpenNext adapter introduces friction." This is the definition of vendor coupling.

The product principle "independence from platforms" is directly at odds with choosing a framework whose deployment story is optimized for, and in some features dependent on, a single commercial platform. If Vercel changes its pricing, migration requires either adopting the OpenNext adapter (the friction dismissed as a reason not to choose Cloudflare) or self-hosting Next.js with a Node.js server, losing edge deployment.

A truly static site generated by Astro or Eleventy is a folder of HTML/CSS/JS files deployable to any CDN with zero adapter, zero config, zero lock-in.

**That said, the coupling is proportional for a personal site.** The code is a standard Next.js app in a Git repo. Moving to another Next.js host (Netlify, self-hosted) is a weekend migration, not a rewrite. The content (MDX files) is fully portable. This is not the kind of platform dependence the product principle is primarily addressing (leaving WordPress.com). The concern is real but not catastrophic.

**Verdict**: The Next.js decision is defensible but the document overstates the technical case and understates the costs. The honest justification is DX simplicity (single dev server, single build, single deployment) and framework familiarity, not SSR requirements. The document should acknowledge the ~60KB JavaScript tax on every page and the vendor coupling as accepted tradeoffs.

## 2. Content Pipeline — Overengineered for the Actual Content Model

### MDX: where is the concrete use case?

The document calls MDX "zero-cost optionality." This is not accurate. The costs of MDX over plain markdown:

- **Build-time cost**: MDX compilation is slower than markdown parsing. Not dramatically so for a small site, but it is not zero.
- **Tooling friction**: MDX files require an MDX-aware editor setup. Standard markdown previewers (GitHub, VS Code's built-in preview) render MDX component syntax as broken text.
- **Error surface area**: An MDX file with a syntax error in a JSX expression fails at build time with a React compilation error, not a helpful "your markdown is broken" message. Plain markdown is far more forgiving.

The product document describes no content type that requires embedded React components at launch. Blog posts, the professional profile, project descriptions, contribution entries, resources — all are text and images.

**However**: the cost is genuinely small for a solo developer comfortable with JSX. If Matthew understands he's paying a small tooling tax for optionality he may never use, this is an acceptable decision. It is not zero-cost, but it is low-cost. The document should say "low-cost optionality" not "zero-cost."

### Velite: appropriate or replaceable?

Velite provides typed content schemas, build-time validation, and typed JSON output. The alternative is gray-matter (frontmatter parsing) + zod (schema validation) + a ~50-line glue script.

The document's claim of "~15 minutes of setup" for Velite is reasonable for initial setup. But the "15 minutes" framing is misleading — it doesn't account for debugging time when Velite conflicts with Next.js's build pipeline, when its types don't align with component expectations, or when you need to customize its output shape. The alternative (gray-matter + zod) takes longer to set up initially but has zero dependency surface beyond two extremely stable libraries.

The real risk is Velite's ecosystem longevity. It's a relatively niche tool. Contentlayer's abandonment is instructive — it filled the same niche and died. If Velite is abandoned, migrating off it means rewriting the content pipeline. The document should note this risk explicitly.

### rehype/remark plugin chain

Auditing against launch requirements from the product doc:

| Plugin | Product doc requirement | Needed at launch |
|--------|------------------------|------------------|
| Table of contents | "auto-generated table of contents from headings" | Yes |
| Footnotes | "footnotes/sidenotes" | Yes |
| GFM | Tables, strikethrough, task lists for a technical blog | Yes |
| Heading anchors | Not explicitly mentioned but standard for technical blogs | Nice-to-have, trivially added later |

Three of four are directly justified. Heading anchors are a single plugin addition. **This is fine.**

### Shiki vs. Prism

Shiki produces build-time highlighted HTML with zero client JS. Prism requires a client-side runtime. For a site that explicitly wants no unnecessary client JavaScript, Shiki is the correct choice. The dependency weight is borne at build time only.

**This decision is correct. Moving on.**

## 3. Playground Architecture — Unresolved Structural Risks

### "Style-reset boundary" is undefined and that's a real problem

The document uses "style-reset boundary" without specifying what it means in implementation. The options and their failure modes:

1. **CSS reset stylesheet**: Resets inherited properties on the playground container. Does NOT prevent the main site's Tailwind utilities from being available in the playground scope. Does NOT prevent the playground's CSS from leaking upward into the site chrome. If a playground item sets `body { background: red }` or uses global class names that collide with the site's, the site breaks. This is essentially meaningless isolation.

2. **CSS `@layer`**: Provides cascade ordering, preventing the main site's styles from overriding playground styles. But layers do not prevent leakage — playground styles in a higher-priority layer affect the rest of the page. Requires careful layer ordering and authoring discipline.

3. **Shadow DOM**: True CSS encapsulation in both directions. Styles inside don't leak out, styles outside don't leak in. But React's event system has historically had issues with Shadow DOM boundaries (event delegation, portal rendering). Global styles don't pierce it, so no shared design tokens. Requires extra framework plumbing.

4. **Scoped class naming (CSS Modules, BEM)**: Relies on convention, not enforcement. A playground item that writes global CSS rules will still leak.

The document doesn't specify which approach is intended. The failure mode: playground item #3 has a CSS rule that bleeds into the site nav, and no one notices until it's deployed because dev testing only looked at the playground page in isolation. **This decision should be made now, not discovered during implementation.**

### Dependency conflict: when do you pull the eject handle?

The document says conflicting items "can be extracted into a pnpm workspace." This is presented as a simple escape hatch, but the migration involves:

- Decoupling the playground item's imports and build configuration from the main app
- Rewriting any usage of Next.js features (dynamic imports, API routes, Image component)
- Setting up iframe integration (a new route that serves the workspace's output)
- Updating CI/CD to build both packages
- Ensuring preview deployments work for both packages

This is a half-day to full-day migration per item, not a configuration change. More importantly, there is no guidance on when to make this decision. The first time you hit a dependency conflict mid-implementation is the worst time for architecture decisions.

**The document should include a simple decision rule**: "If a playground item requires a dependency that conflicts with the main app's dependency tree, use iframe isolation from the start. Workspace extraction is a deliberate architectural decision, not a casual fallback."

### Dark/light mode exclusion

The product document explicitly states playground items "control their own presentation." This is documented, intentional, and makes sense — playground items are creative experiments that may have their own visual identity. A WebGL demo or a retro game doesn't need to respect the site's theme.

**However, the transition is unaddressed.** A user in dark mode navigating to a playground item with a white background will experience a jarring visual shift. The playground listing page (which IS part of the main site) should use the site's theme, and individual item pages should have a clear visual transition indicating the user has entered a different context. The tech document doesn't address this transition, and the product document doesn't either. This is a UX gap for the design phase to resolve.

### Persistent state and backend APIs are genuinely unaddressed

The tech document is silent on how playground items handle:
- Local persistent state (localStorage is the obvious answer, but it's not mentioned)
- Server-side state or databases
- External API credentials that shouldn't be exposed to the client
- CORS considerations for cross-origin requests

The contact form already establishes the pattern: Next.js API route + external service. The document should extend this pattern explicitly: "Playground items needing server-side capabilities use Next.js API routes under `/api/playground/[item]/`. External service credentials are stored in Vercel environment variables. At launch, playground items are client-side only — server-side capabilities are evaluated per-item as needed."

## 4. Testing and Quality Strategy — Gaps in Coverage

### The highest-risk failures are not tested

For a markdown-driven static site, the things most likely to break are:

1. **Broken internal links**: A blog post links to `/projects/foo` but the project was renamed to `/projects/foo-bar`. This is the single most common failure mode on content-driven sites.
2. **Missing referenced images**: An MDX file references `./images/screenshot.png` but the file was moved or renamed.
3. **Frontmatter values that pass schema validation but produce bad output**: A date in the future causing the post to appear at the top of a reverse-chronological list, or a tag typo creating a tag page with one post.
4. **MDX syntax errors**: A file with malformed JSX that passes Velite's frontmatter validation but fails during rendering.

The testing tools listed (Vitest + Playwright) are poorly matched to these failure modes:

- **Vitest unit tests** are good for testing utility functions (reading time calculation, date formatting, tag normalization). They don't catch content-level issues.
- **Playwright E2E tests** could catch rendering failures and broken links, but running a full browser to validate that `/blog/my-post` renders is heavy machinery for something a link-checking script does faster.

**What's missing**: A build-time or CI-time content validation step that checks all internal links against the set of generated pages, verifies all referenced images exist, and detects orphaned tags as warnings. This can be as simple as running `lychee` or a custom crawler against the built static output. This is the single highest-value quality gate for a markdown-driven site and it's absent from the plan.

### Playwright: justified but needs scope

Playwright is justified for:
- Contact form submission flow (form validation, success/error states)
- Theme toggle (no flash of incorrect theme, correct persistence)
- Search functionality (Pagefind integration)
- Playground item loading (isolation boundaries work)

Playwright is overkill for:
- Checking that blog posts render (a build-time check is sufficient)
- Validating links (a crawler is cheaper)
- Verifying RSS feed generation (a file existence check is sufficient)

That's 4-6 E2E tests, not a comprehensive suite. The document lists Playwright without scoping what it tests, creating risk of either over-testing (high maintenance burden for a solo maintainer) or under-testing (covering the wrong things).

## 5. Security Model — Thin for a Site Accepting User Input

### Contact form: XSS via email

The contact form accepts user input (name, email, message) and sends it to Matthew's email via Resend. The document says "server-side validation" without specifying what is validated.

**Failure scenario**: A user submits `<img src=x onerror=alert(1)>` in the message field. The API route passes this to Resend. If Resend's email template renders the message field as raw HTML (not escaped text), the malicious HTML is in Matthew's email. Most modern email clients strip dangerous tags, but not all strip all HTML — malicious HTML/CSS in emails can be used for phishing layouts, tracking pixels, or rendering hijacking.

**Minimum needed**: The API route should:
1. Validate input against a zod schema (string lengths, email format)
2. Sanitize or HTML-escape all user-provided fields before passing to Resend
3. Send the email as plain text, or use a Resend template that escapes all interpolated values

This is straightforward but must be specified, not hand-waved as "server-side validation."

### CSP headers: unspecified and will conflict with playground

The document says "CSP headers configured for production" without specifying the policy. For the main site, a strict CSP is achievable:
- `script-src 'self'` (no inline scripts with build-time Shiki highlighting)
- `style-src 'self' 'unsafe-inline'` (Tailwind may need inline style support)
- `img-src 'self' data:` (local images and inline SVGs)

For playground items using the default isolation (regular Next.js routes), they inherit the site-wide CSP. A playground item using:
- External API calls → needs `connect-src` entries
- Third-party scripts → needs `script-src` entries
- Canvas/WebGL → likely fine
- Inline styles (common in creative coding) → needs `style-src 'unsafe-inline'`

**This is a structural conflict**: The default playground isolation model is incompatible with a strict site-wide CSP. The solution is route-level CSP headers: strict policy for `/blog/*`, `/profile`, `/projects/*`, and a relaxed policy for `/playground/*` routes. Vercel supports path-based headers in `vercel.json` or `next.config.js`. This is solvable but needs to be planned upfront, not discovered when a playground item breaks in production but works in dev (where CSP headers aren't typically enforced).

### Rate limiting: application-level gaps

Vercel's built-in protection covers DDoS at the edge. It does not cover application-level abuse:
- **Form spam**: Automated submissions that don't exceed Vercel's request rate limits but fill Matthew's inbox with junk.
- **Resend quota exhaustion**: Each form submission costs an API call. Resend's free tier is 100 emails/day. An attacker sending 100 form submissions exhausts the daily quota, preventing legitimate contact.

**Minimum needed**: A honeypot field (hidden form field that bots fill but humans don't) and server-side rate limiting per IP (e.g., 5 submissions per hour). Both are trivial to implement. CAPTCHA is overkill for a personal site.

## 6. Performance Claims vs. Architectural Choices

### Next.js baseline JavaScript

A Next.js App Router page with zero client components ships approximately:
- React runtime: ~42KB gzipped
- Next.js client router + framework code: ~18-25KB gzipped
- **Total baseline: ~60-67KB gzipped JavaScript**

An Astro page with zero client components ships **0KB JavaScript**.

For a blog post page — static HTML with syntax-highlighted code blocks — this JavaScript provides zero user-facing benefit. The page doesn't need client-side routing (the user navigated via a link), doesn't need React hydration (nothing is interactive), and doesn't need the RSC payload mechanism (content was statically generated).

**However, 90+ Lighthouse performance is still achievable.** Lighthouse penalizes JS that blocks rendering or extends Time to Interactive. Next.js defers its runtime scripts and they don't block initial paint. A statically generated Next.js page with no client components will score 90+ in practice — the ~60KB loads asynchronously after the HTML renders. The stated performance target is achievable; the "no unnecessary JavaScript" claim is not.

### shadcn/ui + Radix UI bundle impact

Radix primitives only load on pages that import them. A blog post page doesn't import the dialog or dropdown components. The pages that use Radix (nav with mobile menu, theme toggle) are interactive by nature and already expect JS. The key is ensuring Radix components are only imported via client components and not accidentally pulled into server component bundles.

For navigation and theme toggle components present on every page, estimated Radix overhead is ~15-20KB gzipped. Combined with the Next.js baseline, content pages ship ~75-85KB of JavaScript.

**shadcn/ui is still the right choice** — accessible, customizable components without design system lock-in. The Radix overhead is the cost of correct accessibility on interactive elements, and that cost is worth paying. But the document should acknowledge this JS budget rather than implying content pages will be JS-free.

### Image optimization on Vercel Hobby tier

Vercel Hobby tier provides 1,000 source images optimized per month, cached after first optimization. For a personal site with project screenshots, blog images, and a profile photo, this is well within limits. A blog with 50 posts averaging 3 images each = 150 source images. **This is fine.**

## Deliverables

### Top 5 Risks or Gaps

1. **"Style-reset boundary" is undefined and will fail during implementation.** The document's default playground isolation model has no concrete implementation plan. The first playground item with custom CSS will force a design decision that should have been made upfront: CSS reset (insufficient), CSS layers (requires discipline), Shadow DOM (requires framework plumbing). Without this decision, the first playground implementation will involve unplanned architecture work and potential rework.

2. **No content validation beyond frontmatter schemas.** Broken internal links, missing images, and orphaned tags are the highest-probability failures on a markdown-driven site, and nothing in the testing plan catches them. A renamed blog post slug will create a 404 that persists until someone clicks the broken link and reports it.

3. **Contact form input reaches Matthew's email unsanitized.** The API route sends user input to Resend without specified sanitization. HTML in the message body will be rendered by the email client. This is both a security issue (potential email-based attacks in vulnerable clients) and a quality issue (spam rendering as formatted HTML). The 100 email/day Resend quota is also exhaustible by trivial scripting with no application-level rate limiting.

4. **CSP policy will break playground items unless route-scoped.** A single global CSP policy cannot be both strict enough to protect content pages and permissive enough to allow playground items to use inline styles, external resources, and dynamic code execution. This will surface during implementation as "why does my playground item break in production but work in dev."

5. **Playground dependency extraction is understated as an escape hatch.** The document presents pnpm workspace extraction as a casual fallback when it's actually a half-day to full-day migration per item. There is no decision rule for when to trigger this migration, meaning it will happen mid-project under pressure when a dependency conflict is discovered.

### Top 3 Conclusions to Challenge or Reverse

1. **Challenge: "Next.js over Astro because playground items need SSR."** The product document describes no playground item that requires server-side rendering at launch. The only server-side need is the contact form, which Astro also supports. The actual reason to choose Next.js is DX simplicity (single dev server, single build) and framework familiarity — which is a valid reason, but the document should own it rather than citing a speculative technical requirement. As written, the rationale overstates the technical need and understates the cost (~60KB JS tax on every page, vendor coupling).

2. **Challenge: "Single-package structure with extraction as escape hatch."** The document should establish iframe as the first-line isolation for incompatible playground items, not workspace extraction. Iframe isolation provides CSS/JS/dependency isolation for free, enables per-item CSP headers, and removes the risk of playground items breaking the main site's build. Workspace extraction should be a deliberate architectural decision with a documented threshold, not a casual "we can always do that later."

3. **Challenge: "No unnecessary JavaScript on content pages."** This claim is structurally false with Next.js. Every page ships ~60-85KB of JavaScript (React runtime + router + navigation components) regardless of content interactivity. The document should replace this with a realistic statement acknowledging the baseline and confirming that 90+ Lighthouse scores are achievable despite it. Stating an impossible goal creates confusion during implementation.

### What's Missing

1. **A concrete specification for playground item style isolation.** Pick a mechanism (CSS `@layer` + scoped class prefix, Shadow DOM, or iframe-only), document its limitations, and specify what playground authors must avoid (e.g., "no global style rules, no unscoped class names").

2. **A CI-time content validation step.** A link checker and image reference validator that runs against the built static output. This is the single highest-value quality gate for a markdown-driven site and it's absent from the plan.

3. **Route-scoped security headers.** The CSP, rate limiting, and security headers need to be specified per route group: strict for content pages, relaxed for playground routes, specific policies for the contact form API route.

4. **Contact form API route specification.** Input schema (field types, max lengths), sanitization approach (HTML-escape or plain-text encode message body), rate limiting mechanism (honeypot + per-IP limiting), and error response format.

5. **Playground server-side convention.** A statement covering: API route naming convention for playground backends (`/api/playground/[item]/`), environment variable scoping, and the explicit constraint that playground items at launch are client-side only with no server-side state or credentialed API access.

6. **Decision rule for playground iframe isolation.** A simple heuristic: "Use iframe isolation if the playground item requires conflicting dependencies, custom CSP directives, or global CSS that could leak. Use same-page rendering for simple items with scoped styles."
