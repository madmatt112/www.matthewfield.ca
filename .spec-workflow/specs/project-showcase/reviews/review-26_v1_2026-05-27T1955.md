## Summary

Test geometry math omits the outer `px-4` (16px each side) padding: at 1280 viewport the outer `max-w-5xl px-4` produces a 992px content box, not 1024px. ## Findings

### CRITICAL: h1 width assertion is off by ~22px (padding ignored)
- **File:** e2e/tests/projects-detail-layout.test.ts:44
- **Issue:** `src/app/(site)/projects/[slug]/page.tsx:74` wraps the article in `mx-auto w-full max-w-5xl px-4 ...`. At 1280×720 the rendered content box is 1024 - 2*16 = 992px, not 1024px. The h1 (a block-level element with no width set) will boundingBox to ~992px, but the test asserts `±10px of EXPECTED_OUTER_CONTENT_WIDTH = 1024` (line 44 + 96-99). Off by ~22px → assertion fails on first run with the current page implementation. Either lower EXPECTED_OUTER_CONTENT_WIDTH to 992 (recommended — matches actual content box) or widen tolerance, but ±10 is the spec-mandated tolerance per Task 26 restriction. The comment at line 41 derives `min(1280-32, 64rem) = 1024px` for the OUTER box but then mis-applies it to the inner content width.
- **Task Requirement:** 6.7

### WARNING [hygiene]: Cover-image selector is fragile under Next/Image rendering changes
- **File:** e2e/tests/projects-detail-layout.test.ts:80
- **Issue:** Line 80 selects the cover via `article > header + img, article > header ~ img`. The `+` (adjacent sibling) variant requires the cover img to be the immediate next sibling of header; the `~` (general sibling) variant matches but `.first()` would still find the cover. In newer Next.js, `<Image>` can render an `<img>` directly OR (when `fill` etc.) with a wrapping span. Today it's a bare img so it works, but a Next/Image regression to a wrapper would silently make `.first()` match the wide body img instead (which has the wrong alt) — the assertion at line 81 would then fail mysteriously instead of skipping a missing cover. Consider a `data-testid` or `[alt="<coverAlt>"]` selector for resilience.
