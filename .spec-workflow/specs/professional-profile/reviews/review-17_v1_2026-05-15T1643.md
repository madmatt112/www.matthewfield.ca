## Findings

### WARNING: Honeypot input missing aria-hidden="true"
- **File:** src/components/shared/contact-form.tsx:294
- **Issue:** Design §Component: ContactForm (line 233) specifies that the honeypot <input> itself carry aria-hidden="true" in addition to the wrapper div's aria-hidden. Implementation set aria-hidden only on the wrapper. Display:none + parent aria-hidden already hides it from AT in practice, but the design is explicit. ACTIONED: added aria-hidden="true" to the input.
- **Task Requirement:** Req 3.2; Design §Component: ContactForm honeypot block

### WARNING: LinkedIn recovery CTA fails 44x44 tap-target requirement
- **File:** src/components/shared/contact-form.tsx:218
- **Issue:** Req 4.11: "any interactive target (button, link, form control) ... SHALL have a minimum hit area of 44x44 CSS pixels." The server-error LinkedIn <a> was rendered with only `text-sm underline underline-offset-4` — no min-height enforcement. Recruiters on touch viewports hitting the server-error path would have a sub-44px tap target. ACTIONED: added `inline-flex min-h-11 items-center px-1` to clear 44px hit area while keeping the underlined text style.
- **Task Requirement:** Req 4.11

### INFO: Layout-shift container height (28rem) is by-inspection, not measured

### INFO [hygiene]: Retry-After parser only handles delta-seconds, not HTTP-date
- **File:** src/components/shared/contact-form.tsx:171
- **Issue:** RFC 7231 defines Retry-After as either a delta-seconds integer OR an HTTP-date. The code parses only the integer form. In this spec the only Retry-After ever sent is the literal `60` from Req 3.8, so delta-seconds is correct for all paths exercised in this codebase. Logging here only — no fix needed.

### INFO [hygiene]: isFieldErrors type predicate is structurally loose
- **File:** src/components/shared/contact-form.tsx:60
- **Issue:** The function signature claims `value is Partial<FieldErrors>` but the body only verifies plain-object-ness, not that name/email/message values are strings or undefined. Downstream consumption coerces via raw.name/email/message reads, so an attacker-crafted 400 body with non-string field error values would flow into setState as-is. Real risk is near-zero (server is our own zod-driven route), but the predicate is misleading. Acceptable as-is for this task.
