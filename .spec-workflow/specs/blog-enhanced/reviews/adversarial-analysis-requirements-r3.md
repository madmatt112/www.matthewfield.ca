# Adversarial Analysis — blog-enhanced/requirements.md (v3)

Primary attack surface: **completeness, ambiguity, scope**. v3 explicitly responds to v2's five top risks: the `DEPLOY_VIA_CI` flag, the `sha256sum` artifact verification, the `PAGEFIND_ENABLED` kill-switch, `RelatedPostMeta` via type composition, the Playwright slug-parity DOM read, and the `isVisibleInLists()` filter for `fixture-search`. Most of those fixes land cleanly. The new surface area they introduce — feature-flag interactions, dual-filter consumers, h4 build-time rejection, the slug regex contract, and operator-procedure ordering — is where v3 leaves residue.

Each finding is classified **Novel** (not in v1 or v2), **Compounding** (deepens a prior finding), or **Recurring** (prior finding not actually resolved — severity escalated).

---

## Section A — Req 0.3 v3 feature-flag migration — new race surface, not eliminated

The v3 response replaces v2's "two-step coordinated migration" with `DEPLOY_VIA_CI`, a GitHub Actions repository variable. The flag is a real improvement. The accompanying text, though, materially understates the residual coupling between the GitHub variable and the Vercel-dashboard switch.

- **[Novel] Challenge Req 0.3 v3's claim that "either order is safe within a single browser session" for the dashboard-disable + variable-flip sequence.** The text says GitHub-flip-first leaves a "few-seconds window where CI tries to deploy AND Vercel still auto-deploys — both targeting the same commit, both succeeding, with LAST-WRITE-WINS semantics" and asserts this is safe because Vercel deployments are content-addressed. **This is wrong on two counts.** First, "content-addressed" is overstated: Vercel deduplicates *build outputs* by hash but assigns each deploy its own `*.vercel.app` URL and its own promotion-to-production event. Two deploys of identical content produce two deployment records, two log streams, and (if both promote to prod) a momentary domain alias flip-flop. Second, the trigger surfaces are not commit-identical: Vercel auto-deploy ships from the GitHub integration's view of the repo at trigger time; CI ships `.vercel/output/` after running Pagefind. These are NOT byte-identical artifacts (one has `public/pagefind/`, the other does not). The race is between "site without Pagefind index" and "site with Pagefind index" — which one wins is operator-timing-dependent. Either acknowledge that "safe" means "no data loss, but the search UI may flap between working and broken for one promotion cycle," or require the operator to verify (via the Vercel dashboard's deployment history) that the post-migration deploy on `main` came from the CI path before declaring the migration done.
- **[Novel] Stress-test Req 0.3 v3's "Pre-deploy auto-deploy detection" sub-bullet that logs a warning but does not fail.** The rationale ("failing on it would block legitimate deploys during the migration window before the operator has flipped the dashboard") is internally inconsistent with Req 0.3 v3's own migration sequence, which says the variable flip and the dashboard flip happen "in a single browser action." If the migration is single-session, the detection-check can fail-loud after the first successful CI deploy — there is no legitimate steady-state in which BOTH auto-deploys are on AND `DEPLOY_VIA_CI=true`. The warning-only stance creates a permanent quiet failure mode: a future operator who re-enables Vercel auto-deploys from the dashboard (e.g., to test something) re-introduces the dual-deploy race AND the CI run logs only a warning. Either escalate the detection to a blocking check after a documented grace period (e.g., 7 days post-migration), or remove the check entirely as misleading.
- **[Novel] Attack the "Pre-merge feasibility check" workflow_dispatch dry-run as a merge precondition.** Req 0.3 v3 says the dry-run job is "a merge precondition" — but `workflow_dispatch` jobs are not native merge-blocking checks in GitHub. They do not appear in the PR checks panel unless wired as a required status check, and required-status-check configuration is a repo-settings action separate from the PR. The "merge precondition" is enforced socially (Matthew remembers to run it), not technically. The spec implies enforcement that does not exist. Either specify how the dry-run becomes a required check (e.g., via branch protection rules added in the same PR, with the rule name pinned), or downgrade the language from "merge precondition" to "recommended pre-merge action."
- **[Novel] Challenge Req 0.8 v3's "weekly auth check workflow" for `VERCEL_TOKEN` rotation monitoring.** The bullet says "AND/OR" — calendar reminder OR scheduled workflow, Design pins which. This is a defer that hides the load-bearing decision. A calendar reminder in Matthew's calendar has zero CI-side enforcement and is the failure mode the requirement was meant to prevent (the v2 review said tokens expire silently; CI starts failing with 401). A scheduled workflow that runs weekly and alerts on failure is the only mechanism that actually catches silent expiry. Drop the calendar-reminder option; require the scheduled workflow; pin the alert destination (the spec says "GitHub Actions email-on-failure to Matthew" but does not say whether email-on-failure is enabled by default on this repo OR requires a `notifications` configuration). Without that, the rotation monitoring is performative.
- **[Compounding/v2 Section A fifth bullet] Stress-test Req 0.2 v3's `sha256sum` artifact-preservation check.** The check compares `public/pagefind/pagefind-entry.json` (pre-`vercel build`) against `.vercel/output/static/pagefind/pagefind-entry.json` (post-`vercel build`). This catches the failure mode where `vercel build` strips `public/pagefind/`. It does NOT catch the failure mode where `vercel build` strips a subset of the directory: a partial copy (e.g., `pagefind-entry.json` survives but `pagefind.wasm` or `wasm/*.pf_fragment` files do not). The Pagefind index is a directory of many files; matching one file's hash does not verify all files survived. Either widen the check to compare a directory-recursive checksum (e.g., `find public/pagefind -type f -exec sha256sum {} \; | sort | sha256sum` vs the same against `.vercel/output/static/pagefind/`), or document that the entry-json check is a smoke check and acknowledge the residual risk of partial-copy regressions.

## Section B — Req 1.4 v3 `PAGEFIND_ENABLED` kill-switch — new coupling, new ambiguity

The `PAGEFIND_ENABLED` flag is a clean improvement over v2's "comment out the crawl step." It introduces new gate-interaction surface that v3 does not fully close.

- **[Novel] Challenge the interaction between `PAGEFIND_ENABLED=false` and `DEPLOY_VIA_CI=true`.** Req 1.4 v3 says "the site continues to deploy without search when the flag is flipped off" and that the deployed `.vercel/output/static/` "simply lacks the `pagefind/` directory." But the `"Verify Pagefind artifact in .vercel/output"` step (Req 0.2 v3) is gated `if: vars.PAGEFIND_ENABLED != 'false'` — so it skips when Pagefind is off, which is fine. The `"Vercel deploy (Build 2)"` step is gated `if: vars.DEPLOY_VIA_CI == 'true'` and explicitly NOT gated by `PAGEFIND_ENABLED`. **What happens when `PAGEFIND_ENABLED=false` AND a subsequent CI run is the first one with `DEPLOY_VIA_CI=true`?** The deploy ships a site without `public/pagefind/`. The search dialog hits the Req 1.9a v3 graceful-failure path. That is the intended behavior — but the spec does NOT include an acceptance criterion that the CI log emits a visible warning when deploying without Pagefind. An operator who flipped `PAGEFIND_ENABLED=false` six months ago and forgot will silently ship Pagefind-less deploys forever. Add a CI step that fails-loud OR logs a HIGH-VISIBILITY warning ("Deploying without Pagefind index — search UI will show 'unavailable' state") when `PAGEFIND_ENABLED=false` AND `DEPLOY_VIA_CI=true`.
- **[Novel] Stress-test Req 1.9a v3's Playwright test for the graceful-failure state.** The test uses `route.fulfill({ status: 404 })` on `/pagefind/pagefind.js` to simulate the missing-index state. This verifies the dialog handles a 404 on the script. It does NOT verify the handling of: (a) script loads but `pagefind-entry.json` 404s; (b) script loads, entry-json loads, but a fragment file (`wasm/*.pf_fragment`) 404s mid-query; (c) script loads, all files load, but the index is corrupt (Pagefind throws during query); (d) CSP blocks the dynamic import (different DOM exception than 404). The spec uses 404 as the canonical failure mode, but the real failure surface is wider. Either expand the test matrix to cover at minimum (a) and (d) — both realistic post-rollback states — or document the test as covering "script-load failure only" and accept the residual fault tolerance gaps.
- **[Compounding/v2 Section B first bullet, recurring concern] Re-examine the rollback claim "ONE click. ALL four steps skip on the next run. NO `ci.yml` edit, NO PR revert."** The four gated steps will skip. But Req 1.4 v3 also says the deploy step is NOT gated by `PAGEFIND_ENABLED`, so the deploy continues. **What ships on that "rollback" deploy?** The `.vercel/output/` directory was produced by a prior `vercel build` that ran against `public/pagefind/` (when the flag was true). When the flag is flipped false and the next CI run is triggered (the only way the gate takes effect), the next CI run produces a `.vercel/output/` without Pagefind. The rollback is one click ONLY if the operator then triggers a new CI run (e.g., re-runs the failed workflow, or pushes an empty commit). Until a new CI run completes, the most recent deploy still has the (broken or flaky) Pagefind output. The spec text "single-action" undersells the operator's mental model: it is "single click + wait for next CI run + verify deploy." Document this OR specify that the rollback procedure includes a manual `workflow_dispatch` re-run as part of the single action.

## Section C — Req 4 v3 weighting + type composition — new residues

v3 escalated tags-over-categories from 2:1 to 3:1 and consolidated `RelatedPostMeta` via type composition. Both are improvements. Three follow-ups remain.

- **[Novel] Challenge Req 4.1 v3's 3:1 ratio as "deliberate over-correction."** The spec proves monotone dominance for the *current* category cardinality but does not state what the maximum category count is or commit to a constraint preventing it from growing. If a post can legitimately carry 4+ categories (no schema cap currently — blog-core Req 4 schema permits an array), then a category-only score of 4 ties a one-tag score of 3 + 1-category (4) and beats one-tag-only (3). The over-correction is monotone *only* if categories-per-post stays ≤ 3. Either add an explicit cap to the categories array in the schema (and reject builds that exceed it), or document that the dominance proof is conditional on author discipline. Currently the math depends on a constraint that does not exist in the schema.
- **[Novel] Stress-test Req 4.4 v3's `RelatedPostMeta = PostMeta & Pick<Post, 'description' | 'date'>` type composition.** The composition is structurally sound, but the bullet "A future helper that needs `{slug, title, description}` without `date` SHALL compose its own type (`Pick<RelatedPostMeta, 'slug'|'title'|'description'>`)" prescribes a coding pattern via the requirements doc. This is a Design/code-style decision masquerading as a SHALL. Code review enforcement of "compose, don't widen" is not testable. The requirement either belongs in `design.md` as a convention OR needs a mechanical check (e.g., an ESLint rule, a `eslint-plugin-import` restriction, a CI grep for `extends PostMeta`). Without enforcement, the SHALL is aspirational. Move the convention to `design.md` and remove from `requirements.md`, OR add a mechanical check as an acceptance criterion.
- **[Compounding/v2 Section C second bullet] Re-examine the v3 "launch-corpus expectation" addition to Req 4.6.** The text says "MANY post pages will have a no-rail state because tag/category overlap is sparse on a young blog" and frames adding fallback copy as "a future polish, not a launch concern." This locks in a reader experience where most launch-era posts have no visible cross-post discovery affordance below the prose. The spec does not specify a corpus-size threshold at which the fallback becomes a concern, does not require revisiting the decision when the corpus grows, and does not add a code comment or follow-up issue. This is a deliberate deferral that has no trigger for re-evaluation. Either pin a corpus-size threshold (e.g., "when published-post count exceeds 20 AND >30% of post pages still have no-rail, file a follow-up spec") OR accept that the no-rail state is permanent and document the rationale once in `design.md` rather than embedded in a requirement.

## Section D — Req 7 v3 — Playwright parity + h4 loud-failure — new dependencies, new gaps

The Playwright DOM-read for slug parity (Req 7.4 v3) and the h4-rejection in the Velite transform (Req 7.10 v3) are the right fixes. Both introduce dependencies the spec does not fully pin.

- **[Novel] Challenge Req 7.4 v3's reliance on `fixture-toc` being reachable in CI Build 1.** The test loads `/blog/fixture-toc` against "the CI Build 1 server" where `BLOG_INCLUDE_DRAFTS=1`. `fixture-toc` is `draft: true` per the Fixture Roster. This works in Build 1, but Build 1 does NOT deploy to Vercel (per Req 0.4 v3). So the slug-parity test runs against a `pnpm start` server that exists only inside the CI runner for the duration of the test. **The test environment IS NOT the production environment.** A future change that makes `s.mdx()`'s heading output environment-dependent (e.g., a NODE_ENV-gated rehype plugin, a production-only minifier that strips `id` attributes from headings under some condition) would produce a passing test against the Build 1 server AND broken anchors in production. Either add a SECOND parity check that runs against the Build 2 server (with `fixture-toc` excluded from the production index per the `isVisibleInLists` filter — wait, the fixture filter excludes from LISTS but the page is still reachable; the test could still load it directly), OR document that the parity test covers Build 1's MDX pipeline only and that Build 2 is assumed to produce identical heading output.
- **[Novel] Stress-test Req 7.10 v3's h4-rejection in the Velite transform as a "loud failure" mechanism.** The error message is named and the build fails — good. But the rejection happens at Velite build time, which is BEFORE blog-core's existing axe/Lighthouse/e2e gates run. An author who introduces an h4 sees a Velite-stage error with no context for WHY h4s are banned. The named error message ("If h4 substructure is genuinely needed, file a spec extension before adding it.") helps, but the author's likely first action is to delete the h4 OR demote it to a bolded paragraph — neither of which preserves the semantic structure the author was trying to express. The rejection trades silent-flatten (v2's footgun) for build-blocking with no escape hatch. Authors who genuinely need h4 must wait for a spec extension. **For a personal blog where Matthew is both author and spec owner, this is a high-friction loop for the cost of "TOC doesn't render h4 entries." The cost-benefit assumption is undefended.** Either reduce the friction (e.g., allow h4 with a build-time warning when `BLOG_ALLOW_H4=1`, OR generate a TOC that includes h4 entries flat at the bottom — explicit non-hierarchy), or accept the friction with a stated rationale that "personal blog discipline" is the goal.
- **[Compounding/v2 Section D third bullet] Re-examine Req 7.5 v3's orphan-h3 handling.** v3 specifies that orphan h3s render as a flat list and `extractToc()` returns them as flat entries. This is a clear improvement over v2's ambiguity. But the spec does NOT specify: (a) what `extractToc()` returns when a post has h2-then-h3-then-h2-then-h3 — does it nest, or stay flat? The text says "no nesting" for orphan h3s but is silent on whether h3-under-h2 nests in the data structure or also renders flat; (b) what the `TocEntry` type's shape is regarding hierarchy (a flat `{id, text, depth}[]` vs a tree `{id, text, children: TocEntry[]}[]`). Design will pick one. The choice determines whether the TOC's rendered indentation can ever reflect h2 vs h3 — a UX decision currently buried inside an implementation choice. Either pin the `TocEntry` shape in requirements (with rationale) OR pin the rendered-indentation contract (e.g., "h3 entries SHALL render with visual indentation under their preceding h2") and let Design pick the data shape.

## Section E — Fixture-visibility filter `/^fixture-/` — over-broad, contract-coupled

v3's `isVisibleInLists()` filter solves the v2 "permanently visible production fixture" problem. It introduces a load-bearing slug regex that the spec does not protect against drift.

- **[Novel] Challenge the `/^fixture-/` regex as the slug-naming contract.** The filter excludes any slug matching `/^fixture-/`. This means:
    - A future author who writes a post legitimately titled "Fixture Patterns in Test Suites" with slug `fixture-patterns-in-test-suites` is silently excluded from `/blog`, RSS, sitemap, and taxonomy pages. The author sees the post page render fine on `/blog/fixture-patterns-in-test-suites`; they do NOT see why it's missing from `/blog`. The discovery is delayed and the cause is non-obvious.
    - The filter is a global side-effect of a slug convention with no schema enforcement. Velite does not validate that `fixture-*` slugs are also `draft: true` OR meet any other test-fixture criterion. The convention is enforced socially.
    - Either move the filter from a slug-pattern match to an explicit frontmatter flag (e.g., `hiddenFromLists: true`) with schema validation, OR add a schema-level constraint that `fixture-*` slugs MUST be either `draft: true` OR have an explicit `__test_fixture: true` field, OR document the slug-prefix as a reserved namespace and add a Velite warning when a non-fixture-purpose slug starts with `fixture-`.
- **[Novel] Stress-test the consumer-by-consumer filter application.** Req 4 enumerates five consumers that must apply the filter: `/blog` index, RSS, sitemap, two taxonomy routes, plus `getAllTags()` and `getAllCategories()`. Future consumers (a hypothetical archives page, a "Recent posts" widget on `/profile`, a yearly-summary page) must remember to apply the filter. The spec does not require an ESLint rule, a wrapper function (`getVisiblePosts()`), or a code-review checklist. **This is the same drift vector v2's `derivePostSlug` consolidation fixed for slug derivation, reintroduced for list filtering.** Either consolidate by introducing `getVisiblePublishedPosts()` as the new canonical list-context API (and deprecate direct `getPublishedPosts()` calls outside list contexts), or accept that future consumers will forget the filter and `fixture-search` will leak through whichever surface gets added next.
- **[Compounding/v2 Section E third bullet] Re-examine the residual "fixture-search appears in real search results" failure mode that the spec explicitly does not solve.** The v3 text says: "complete elimination would require a `data-pagefind-ignore` on the fixture body (which would defeat its purpose — the keyboard test needs the index to contain it)." This is correct IF the keyboard test queries against the production-mode crawled index. But Req 10.3 says "The test SHALL run against the production-mode CI Build 2 index" — the test runs in CI, where the index is freshly built and contains `fixture-search`. **What if the keyboard test ran against a TEST-ONLY index that DOES include fixture-search, while the PRODUCTION-deployed index excludes it?** Pagefind supports multiple indexes; the spec does not consider a two-index architecture (production index without fixtures + test index with fixtures). The current single-index design forces fixture-search into production search results. Either accept the residual indexing trade-off explicitly with a "we evaluated and rejected a two-index design because [reason]" note, or revisit the architecture. The current spec says the trade-off is acceptable; it does not show the alternatives were considered.

## Top 5 risks/gaps

1. **[Novel] `PAGEFIND_ENABLED=false` deploy state is silently persistent.** No CI warning when deploying without the index; no scheduled re-evaluation; an operator who flips the flag once may forget it is flipped. **Failure mode: Pagefind is disabled "temporarily" during a debugging session, the operator forgets to re-enable, every deploy for the next six months ships without search, the dialog shows "unavailable" indefinitely, the broken state is invisible to the operator unless they happen to open the dialog.**
2. **[Novel] `isVisibleInLists()` filter is consumer-by-consumer rather than encapsulated in a `getVisiblePublishedPosts()` API.** Future list-context features (archives, related-tags widget, "Latest" home-page block) will reach for `getPublishedPosts()` and forget the filter. **Failure mode: a future spec adds a "Latest 3 posts" widget to `/profile` using `getPublishedPosts()`, `fixture-search` appears as one of the three, the regression is invisible until a reader notices.**
3. **[Novel] `sha256sum` artifact preservation check verifies one file out of a multi-file index directory.** Partial-copy regressions (where some Pagefind files survive `vercel build` and others don't) pass the check but produce a broken deployed index. **Failure mode: a Vercel CLI version that preserves top-level files in `public/pagefind/` but skips subdirectories ships a "looks deployed" index that crashes the WASM loader on first query.**
4. **[Novel] Req 7.10 v3's h4-rejection is build-blocking with no escape hatch for the author who is also the spec owner.** Matthew writing an essay with legitimate h4 structure must amend the spec before he can write the post. **Failure mode: friction discourages writing posts that warrant h4 depth; either the post is published with a degraded structure (h4s demoted to bold paragraphs) or the post is not published at all.**
5. **[Novel] Req 0.3 v3's "Pre-deploy auto-deploy detection" warning-only check is a permanent quiet failure mode.** A future operator who re-enables Vercel auto-deploys (e.g., for a one-off test) re-introduces the dual-deploy race; CI only logs a warning. **Failure mode: dual-deploy races re-appear silently months after the migration; the operator who originally migrated has no recollection of the warning's significance; debugging the racy promotion behavior is detective work against scrollback.**

## Top 3 conclusions to challenge or reverse

1. **Reverse: "The `isVisibleInLists()` slug-pattern filter is the right encapsulation."** The filter is currently a free function applied by N consumers. The spec already learned this lesson in v2 with `derivePostSlug` (centralized to prevent drift). The same pattern should apply here: replace the per-consumer filter with `getVisiblePublishedPosts()` as the canonical list-context API, and have `getPublishedPosts()` either be deprecated for list contexts OR explicitly documented as "use ONLY when fixtures must appear (i.e., the slug-direct page route)." Reasoning: the spec's own v2-era anti-drift principle applies here too; not applying it is internally inconsistent.
2. **Reverse: Req 7.10 v3's "loud-failure on h4+ with no opt-out."** The build-blocking failure is a stronger mechanism than warranted for a personal blog whose author is also the spec owner. A `BLOG_ALLOW_H4=1` escape hatch (with a corresponding build-time warning and a follow-up issue auto-filed) achieves the same "no silent flatten" goal without imposing spec-amendment overhead on every author who legitimately needs h4. Reasoning: the v3 rationale frames this as "author discipline," but in this codebase the author IS the spec owner, so the discipline mechanism is paying the cost of a constraint it should not have to enforce against itself.
3. **Reverse: Req 0.3 v3's "either order is safe within a single browser session."** The text claims content-addressed safety that does not hold for the actual artifact difference (with vs without Pagefind index). Replace with: "The dashboard flip and the variable flip SHALL be performed in this exact order: (1) variable flip to true, (2) verify next CI run completes successfully, (3) verify the deployed `/pagefind/pagefind-entry.json` is reachable on the production URL, (4) THEN flip the Vercel dashboard switch to disable auto-deploys." Reasoning: pinning a verification gate between the two operator actions converts "trust the operator's timing" into "verify the new path works before disabling the old path" — which is the standard cutover pattern and matches the spec's own preference elsewhere for verify-then-cut.

## What's missing — work to do before acting

- **A `getVisiblePublishedPosts()` consolidation** (or a documented decision to keep the per-consumer filter despite the drift risk). Without it, the `isVisibleInLists` filter is one forgotten import away from leaking fixtures to readers.
- **A directory-recursive checksum for the `sha256sum` artifact-preservation step**, OR an explicit acknowledgment that the check is a smoke check and partial-copy regressions are not caught.
- **A spec-level decision on the `BLOG_ALLOW_H4` escape hatch** (or a written rationale for why an author-is-spec-owner setup requires the higher-friction loop).
- **A verification gate in Req 0.3 v3's migration sequence**: specifically a "verify deployed `/pagefind/pagefind-entry.json` returns 200" step between flipping the GitHub variable and flipping the Vercel dashboard. The current "either order is safe" claim is unverified.
- **A `PAGEFIND_ENABLED=false` deploy-warning step in CI**: when the flag is false AND a deploy ships, the CI log MUST emit a high-visibility line indicating search is shipping disabled. Optionally a comment on the deploy URL via `gh pr comment` for PRs.
- **A `VERCEL_TOKEN` rotation monitoring choice pinned in requirements** (not deferred to Design via "AND/OR"). The calendar-reminder option does not address the silent-expiry failure mode the requirement exists to prevent.
- **A slug-prefix reservation mechanism for `fixture-*`**: either a Velite warning when a slug starts with `fixture-` AND `draft: false` AND no `__test_fixture: true` flag, or a frontmatter-driven hidden-from-lists flag replacing the slug-pattern match.
- **A `TocEntry` shape decision in requirements** (flat vs nested), or an explicit Design defer with a rendered-indentation contract that constrains the choice.
- **A pinned rationale for the single-index Pagefind architecture** — at minimum a sentence acknowledging that a two-index (prod / test) split was considered and why it was rejected, so the residual "fixtures in real search results" trade-off is documented rather than implied.
