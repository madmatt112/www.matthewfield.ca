# Adversarial Analysis — blog-core/tasks (v2)

Reviewer stance: senior delivery lead, post-r1 sweep. The v2 tasks doc absorbed nearly every r1 finding at the structural level — Task 4 split into 4.1–4.4, helpers moved to `src/lib/build/`, comment carve-out promoted into the rejection visitor (4.2), CDATA dual-assertion pinned (14), Shiki variable names pinned literally (9), env-var step-scoping pinned (20), siteConfig audit added (5), fixture image committed (6), and `node-html-parser` pinned (27). The r1 prompt-only `]]>` substitution is now a body bullet (4.4). What follows is what v2 did not surface, plus what the v2 edits themselves introduced.

Citations are to line numbers of `tasks.md` (v2, post-r1).

## Attack surface 1 — Task 6 fixture content vs. Task 7 query layer drift (novel)

Task 6 (lines 101–112) commits all three fixtures with `draft: true`. Task 7 (lines 114–125) implements `getPublishedPosts()` which excludes drafts unless `BLOG_INCLUDE_DRAFTS=1` is set at call time. Task 11 (line 167) commits the index empty-state to `"No posts yet — check back soon."`.

- **Challenge the implicit assumption that `pnpm dev` (no env vars) renders something useful for the implementer.** Without `BLOG_INCLUDE_DRAFTS=1`, the index, all taxonomy pages, both detail routes — every route added in Tasks 11–13 — render either the empty-state or `notFound()`. The implementer working through Tasks 11–14 has no visible signal that their route code is correct unless they remember to set the env var. Demand the task body for 11/12/13 pin the dev-loop env-var contract: a multi-line comment in each route file's PR description (or the implementation log) reminding the implementer that "drafts visible only with `BLOG_INCLUDE_DRAFTS=1`."
- **Stress-test Task 6's "Success" criterion against Task 4.1's `.strict()` mode.** Task 6 line 112 says "rejection visitor does not throw on any fixture." But Task 4.1 (line 53) declares `.strict()` rejects unknown frontmatter — and Task 6 line 104 says fixtures use the same frontmatter shape (title, description, date, tags, categories, draft). Nothing pins that the fixture frontmatter's exact key set matches the v4.1 schema's exact key set; if Task 6 is implemented before Task 4.1 is finalized (the doc ordering allows this — Task 6 lists schema sub-task 4.1 as a dependency only via the design refs, not a structural ordering pin), the fixtures could fail strict validation on unknown keys before the rejection visitor even sees them. Pin: Task 6 MUST run after 4.1 lands, and Task 6's success criterion MUST run `pnpm velite build` against the 4.1-built schema, not against a partially-implemented Task 4.
- **Tear apart Task 6's `<!-- FIXTURE-NOTE: ... -->` claim against 4.2's carve-out regex.** Task 4.2 (line 65) carves out HTML nodes WHERE `value.trimStart().startsWith('<!--')` AND `value.trimEnd().endsWith('-->')`. A FIXTURE-NOTE comment that spans multiple lines, or one that an editor reflows to wrap mid-comment (`<!-- FIXTURE-NOTE: this fixture\nis referenced ... -->`), still satisfies the trimmed-bounds check — but only because `value` is the entire HTML node's text including newlines. Demand the carve-out's regex be tested against a multi-line comment as a fixture in Task 4.2's success criterion (the current "test post with `<!-- FIXTURE-NOTE: ... -->` does NOT throw" assertion only covers the single-line case). One newline inside the comment is an unsurprising authoring outcome; the visitor's behavior on it is unspecified.
- **Demand explicit pinning of Task 6's image alt text.** Task 6 line 105 says "one image `![alt text](./fixture-image.svg)`" — the alt text is the literal string `"alt text"`. Task 27 (line 334) asserts `<img src>` URL absolutization parity between bodyHtml and the rendered page. If the implementer writes `![](./fixture-image.svg)` (empty alt), `countWordsFromMdast`'s `includeImageAlt: true` produces zero added words; if they write a long alt, the reading-time word count drifts. The reading-time test (Task 22 line 290) asserts identity against the observed count, not a band — so any drift is caught — but the implementer reading Task 6 alone cannot predict the downstream coupling. Pin alt text literally in Task 6.

## Attack surface 2 — Task 7's runbook comments and Task 16's stderr guard double-encode the same operator UX (compounding)

Task 7 (line 117) declares Layer-2 guards inside `getPublishedPosts()` with multi-line runbook comments. Task 16 (lines 221–229) declares a Layer-1 stderr guard at the top of `next.config.ts` with its own multi-line runbook comment. Both fire on the same condition class.

- **Challenge the claim that both layers are independent defenses.** They are not — they are the same `process.env.VERCEL === '1' && ...` predicate, evaluated at two different stages of the same deploy. Task 16's `next.config.ts` guard fires first (module load). If it `process.exit(1)`s, Task 7's runtime guard never runs. The Layer-2 throw is dead code in any deploy where Layer-1 already exited the process. Pin: either accept Layer-2 as defense-in-depth for the case where `next.config.ts` is bypassed (e.g., a custom server bootstrap), or admit that Layer-2 is functionally unreachable in the CI/Vercel path and document it as such.
- **Stress-test the divergence risk between the two runbook comments.** Task 7 line 117 says the runbook includes "the verbatim error substring." Task 16 line 225 says "Multi-line runbook comment above the check." Neither task pins that the two comments must contain the SAME guidance, the SAME error substring, or the SAME runbook URL. A future edit to one without the other produces two diverging operator-facing messages for the same condition. Demand: pin a single shared constant string (e.g., `MSG_VERCEL_DRAFT_LEAK` exported from `src/lib/blog-errors.ts`) imported by both `getPublishedPosts()` and `next.config.ts`, so the source of truth lives once.
- **Stress-test the Vercel-detection assumption.** Both guards check `process.env.VERCEL === '1'`. This works on Vercel today. It does not work on (a) self-hosted deploys, (b) Vercel preview environments where the env var has been overridden, (c) Vercel feature flags that may rename the detection variable in a future platform revision. Tasks 7 and 16 both depend on this string being the canonical Vercel marker — pin a source citation (Vercel docs URL) in at least one of the two tasks, and document the fallback path if Vercel renames the variable.
- **Tear apart Task 16's `process.exit(1)` against Vercel build telemetry.** A `process.exit(1)` from `next.config.ts` produces a non-zero exit before Next.js's normal error formatter runs. Vercel's build log may surface this as "Command failed with exit code 1" with no stack trace, defeating the purpose of the named stderr write. Demand Task 16's success criterion include a manual verification that the named error string appears in the Vercel build log, not just in local-shell stderr. This is the same staleness pattern as the design's launch-time-verification finding from design-r3.

## Attack surface 3 — Task 20's "topology contract" recurring procedural-as-structural pattern (recurring, escalated)

Task 20 (lines 260–272) extends `.github/workflows/ci.yml` with a single CI job containing two sequential build sequences, gated by `rm -rf .velite .next` between them. Task 18 (lines 239–248) asserts `.velite/.build1-sentinel` absent. This is the same procedural pin design-r3 flagged.

- **Recurring (escalated): challenge whether tasks should encode CI topology defense at all if the design already admits the pin is procedural.** Task 20 line 268 says "Topology contract for draft-isolation + step-scoped env-var contract (closes r1 review Attack Surface 6 env-scoping gap)." The contract still lives in markdown + YAML comments — there is no CI lint rule, no schema check. A future maintainer who edits `ci.yml` to "simplify" by promoting `BLOG_INCLUDE_DRAFTS` to job-level env breaks the draft-isolation guarantee silently. Task 17 (lines 232–237) added an ESLint chokepoint rule for the `#site/content` import — the same defense pattern (mechanical, code-enforced) is missing for the env-var scoping. Demand a parallel structural defense: e.g., a `scripts/verify-ci-topology.mjs` that parses `ci.yml` (YAML), asserts (a) no job-level `BLOG_INCLUDE_DRAFTS`, (b) Build-2's build step has no `BLOG_INCLUDE_DRAFTS` in its `env`, (c) the `rm -rf` step's `if: always()`. Run it as the first step of the job so a topology break fails CI before Build 1 runs.
- **Stress-test Task 20's "defense-in-depth" framing for the e2e step's step-scoped env var.** Line 267 declares the e2e step's `BLOG_INCLUDE_DRAFTS=1` is "defense-in-depth for any future scenario where a draft-aware code path is evaluated at server-runtime." This is honest but exposes the gap: there is no test today that exercises a draft-aware server-runtime path. Demand either (a) drop the defense-in-depth pin and document that drafts are entirely build-time, or (b) add a task to write a single integration test that asserts the e2e server's runtime env contains `BLOG_INCLUDE_DRAFTS=1` (read via a debug route or a header), so the contract is mechanically verified, not just documented.
- **Tear apart Task 20's silence on Build 1's failure-cascade behavior.** Lines 263–265: Build 1 runs `pnpm build`, then `pnpm test:e2e`, then `validate-feed.mjs`, then `touch sentinel`. Build 2 begins with `rm -rf` (`if: always()`). What happens if `pnpm test:e2e` fails? The cleanup runs (good), Build 2 runs (per `if: always()` on Build-2 steps, line 265). But the sentinel is touched only at the END of Build 1's sequence (line 263 last step) — so if e2e fails before the touch, the sentinel never exists, the cleanup removes a non-existent file, and Build 2's verify-production-build.mjs asserts "sentinel absent" — which is trivially true. The sentinel check provides NO signal when Build 1's e2e fails early. Demand: move the `touch sentinel` to the FIRST step of Build 1 (just after `pnpm build` succeeds), so its presence signals "Build 1 reached the cleanup step" rather than "Build 1 completed every step." The current ordering inverts the diagnostic value.

## Attack surface 4 — Task 9's "no TODO" pin is contradicted by Task 28's "patch + document" (novel)

Task 9 (lines 137–146) pins the literal Shiki variable names (`--shiki-light`/`--shiki-dark`) and explicitly prohibits TODOs: line 145 — "NO TODO comments. Do NOT defer the variable-name decision — pin literally." Task 28 (lines 341–350) then says "Spot-check Task 9's literal pinned variable names ... If reality differs ... patch globals.css with the actual variable names and document the discovery in the implementation log."

- **Challenge the consistency of the closing-task patch path.** If Task 9 pins the names with no deferral, and Task 28 explicitly accommodates "if reality differs, patch globals.css," then Task 28 IS the deferred verification — relabeled. The r1 review's Attack Surface 3 found that "verification belongs in the closing task, not as a TODO in Task 9." Task 9's body now repeats that framing (line 140: "Task 28 (final integration smoke) spot-checks the rendered output and any unforeseen plugin behavior gets caught there") while simultaneously claiming "NO TODO comments." These are the same deferral pattern with a different label.
- **Stress-test the "patch + document" path against the dual-build CI.** If Task 28 discovers the variable names are wrong and patches globals.css, Tasks 11–13's routes were built against the wrong cascade. Task 26 (lines 320–327) asserts color values against the cascade. A Task-28 patch invalidates the prior tasks' "Success" claims retroactively. Demand: either Task 9 SHOULD have a TODO acknowledging post-Task-28 verification, OR Task 28's patch path should require re-running Tasks 26 (theme test) and 24 (axe) against the patched cascade. The current shape lets a Task-28 patch ship without a re-verification of the affected downstream tasks.
- **Tear apart the documentation-as-mitigation framing.** Task 28 line 345 says "document the discovery in the implementation log." Implementation-log entries are write-only artifacts; nothing forces a re-review of the patched cascade. Pin a structural defense: if Task 28 modifies any file Tasks 9–26 wrote, the implementation must explicitly re-run the affected `pnpm test` / `pnpm test:e2e` and the implementation log must cite the re-run output, not just describe the patch.

## Attack surface 5 — Task 22's "end-to-end identity assertion" carries the entire reading-time correctness load (compounding)

Task 22 (lines 281–296) describes the Vitest suite for `src/lib/blog.ts`. The reading-time coverage is split across three assertions: pure-function `wordsToReadingTime` for `N ∈ {0,1,237,238,239,1000,10000}`, plus "End-to-end identity assertion using shared `countWordsFromMdast` ... against `fixture-reading-time` body."

- **Compounding (escalates design-r3 Attack 3): challenge the end-to-end identity assertion's stability against fixture edits.** The assertion asserts that `Math.max(1, Math.round(countWordsFromMdast(parsedFixture) / 238))` equals the Velite-transform-emitted `readingTime`. Both sides use the same `countWordsFromMdast` function (Task 22 line 291: "imported from `@/lib/build/word-count`") — so the identity holds tautologically as long as the function is deterministic and the fixture parse is stable. The assertion does NOT verify the word count is correct; it verifies the function is consistent with itself. If `countWordsFromMdast` has a bug (e.g., off-by-one on whitespace handling), the bug is invisible to this test. Demand a separate fixed-input unit test: `countWordsFromMdast(known-input-mdast)` returns `<exact pinned count>`, where the input is a synthetic 100-word mdast tree built in-test, not the fixture file. The current suite has the pure-function conversion test for `wordsToReadingTime` but no equivalent for `countWordsFromMdast` itself.
- **Stress-test the test against fixture frontmatter changes.** `countWordsFromMdast` walks the mdast tree — does it include or exclude frontmatter-derived content? The Velite transform parses `meta.content` which is body-only (frontmatter stripped). If the test imports the body differently — e.g., reading `.velite/posts.json`'s `body` field, or re-parsing the .mdx file from disk — the two sides may walk different trees. Pin the substrate explicitly: the test reads `post.body` (or whichever Velite-emitted field) from `#site/content` for fixture-reading-time, NOT the raw .mdx file.
- **Tear apart the test ordering against Tasks 11–13.** Task 22 imports `src/lib/blog.ts`, which (Task 7) imports from `#site/content`. The test runs against the built `.velite/` content. If Tasks 4–6 have not run a build before Task 22's test runs, `#site/content` is empty or stale. Demand Task 22's success criterion include "depends on `pnpm velite build` having run with the fixtures present" — or wire Vitest's `globalSetup` to run Velite before the test suite. The current task body assumes the content exists at test time.

## Attack surface 6 — Coverage gap: Requirement 6.5 references Task 22 but the linkage is one-directional (novel)

Several tasks list `_Requirements:` footers that name specific Req numbers. Spot-check: Task 22's `_Requirements: 6.0, 6.5, 7.5, 7.6, 7.12, 8.0` (line 294). Task 6's `_Requirements: 6.5, 7.13, 7.14, 9.2, 11.9, 11.11` (line 110). Task 27's `_Requirements: 11.11` (line 337).

- **Challenge the one-directional traceability.** Each task claims to satisfy a set of requirements, but no inverse mapping exists in the tasks doc itself — there is no "Req 11.11 is covered by Tasks 6 and 27." A reviewer cannot tell at-a-glance whether all reqs have at least one covering task without building the mapping by hand. Demand either: (a) a final "Requirements coverage matrix" section at the bottom of tasks.md listing each Req number and the tasks covering it, (b) a separate `tasks-coverage.md` artifact, or (c) the requirements doc itself lists "covered by Task X" inline. As written, a quietly-orphaned requirement (one with zero covering tasks) is invisible.
- **Stress-test specific potential orphans.** Spot-check: Req 7.11a appears in Tasks 11 and 16 only. Req 11.10 appears in Tasks 4.4 and 14 only. Req 13.5 appears in Task 21 only. Req 13.7 in Task 26 only. The tasks doc has 28 tasks (4 split to sub-tasks) and the design references reqs through 13.x — a reviewer cannot tell without a matrix whether Reqs 1.1–1.4, 3.1–3.5, 3.8, 4.1, 4.3–4.5, 4.7, 5.1–5.2, 6.2–6.4, 7.0–7.4, 7.9–7.10, 8.1–8.x, 9.3–9.4, 10.x, 11.1–11.3, 11.6, 12.3–12.x, 13.0–13.1, 13.3, 13.6 are all covered. Demand the matrix.
- **Tear apart Task 13's coverage of Req 4.0.** Task 13 lists `_Requirements: 4.0, 4.2, 4.6, 4.8`. Req 4.6 (kebab-slug regex) is implemented by Task 4.1, not Task 13 — the linkage in Task 13 is at best "depends on" rather than "covers." Pin the semantics: are `_Requirements:` footers expressing "this task partially or fully implements these reqs" or "this task transitively depends on these reqs"? The current usage mixes both.

## Top 5 Risks/Gaps

1. **Task 6 fixture authoring vs. Task 4.1 strict-mode timing (novel).** Fixtures committed in Task 6 may fail Task 4.1's `.strict()` validation if implemented in the wrong order, or if frontmatter keys drift between the two task bodies. The doc lists no structural ordering pin between 4.1 and 6, and the `_Leverage:` footer in Task 6 doesn't reference 4.1. **Severity: medium.** Catches as a Velite-build failure when an implementer takes Task 6 before 4.1 lands.

2. **Task 16's `process.exit(1)` vs. Vercel log surfacing (novel).** Layer-1 guard exits before Next.js's error formatter runs; Vercel may render this as a generic "Command failed with exit code 1" with no stack trace. The named error string the runbook comment promises may never appear in the operator-facing log. **Severity: medium.** Catches as a launch-time UX regression that no test exercises — same pattern as design-r3's launch-verification staleness finding.

3. **Task 20's sentinel ordering inverts diagnostic value (novel).** Sentinel is touched at the END of Build 1's sequence; an early failure (e.g., e2e flake) means the sentinel is never created, Build 2's "sentinel absent" assertion is trivially green, and the topology contract provides zero signal. Move the `touch` to immediately after `pnpm build` succeeds. **Severity: medium.** Catches as silent CI greenness on a partial Build 1.

4. **Task 9's "no TODO" pin + Task 28's "patch + document" path is the same deferral with different labels (novel).** If Task 28 patches globals.css, Tasks 11–13 and especially Task 26 were built against the wrong cascade — the patch path lacks a re-verification requirement on the downstream tasks. **Severity: low–medium.** Catches as a green CI hiding a cascade regression that only manifests on a specific theme path.

5. **Task 22's end-to-end identity assertion is tautological without a separate fixed-input test for `countWordsFromMdast` (compounding from design-r3 Attack 3).** Both sides of the identity use the same function; a bug in the function is invisible. Add a synthetic-input unit test for the walker itself. **Severity: low–medium.** Catches as a silent reading-time computation bug surviving review.

## Top 3 Conclusions to Challenge or Reverse

1. **Reverse: "Task 17's ESLint chokepoint rule is sufficient mechanical defense, but Task 20's CI topology can stay procedural."** The same code-enforced defense pattern that closed the `#site/content` import gap should close the env-var scoping gap. Add a `scripts/verify-ci-topology.mjs` that YAML-parses `ci.yml` and asserts the structural pins (no job-level `BLOG_INCLUDE_DRAFTS`, no Build-2 step env, `rm -rf` has `if: always()`). Run as Build 1's first step. **Reasoning:** the asymmetry — mechanical defense for the import chokepoint, procedural defense for the CI topology — is the same gap r1's Attack 6 surfaced. v2 closed half of it.

2. **Reverse: "The runbook comments in Task 7 and Task 16 can live independently."** Pin a single shared error-message constant (e.g., `BLOG_DRAFT_LEAK_GUARD_MSG` in `src/lib/blog-errors.ts`) imported by both `getPublishedPosts()` and `next.config.ts`. Both tasks must reference the constant by name in their `_Restrictions:`. **Reasoning:** otherwise the two operator-facing messages drift over time and the runbook diverges from itself across two files.

3. **Challenge: "Task 28's verification + patch path is acceptable closure for Task 9's pinned variable names."** Either (a) Task 9 should explicitly accept the post-Task-28 verification as a real deferral (with a TODO comment in globals.css naming Task 28 as the verifier), OR (b) Task 28's patch path must require re-running Task 26 (theme E2E) and Task 24 (axe) against the patched cascade, with re-run output cited in the implementation log. The current shape pretends the verification is closed at Task 9 while reserving the right to patch at Task 28 — that is the same TODO pattern under a different name. **Reasoning:** consistency requires either calling it a TODO or pinning the re-verification requirement explicitly.
