## Findings

### WARNING: HTML-comment carve-out predicate accepts mixed comment+HTML payloads
- **File:** velite.config.ts:138
- **Issue:** The carve-out at velite.config.ts:138 checks only `value.trimStart().startsWith('<!--')` AND `value.trimEnd().endsWith('-->')`. A node value like `<!-- a --> <aside>x</aside> <!-- b -->` satisfies both predicates and would slip through the rejection visitor, defeating the FIXTURE-NOTE-only intent. Whether this is reachable depends on how `mdast-util-from-markdown` chunks adjacent html — but the predicate is overly permissive. Tighten by either (a) asserting no `-->` followed by non-whitespace before the next `<!--`, or (b) requiring the entire trimmed value match `/^<!--[\s\S]*-->$/` with NO unescaped `-->` inside.
- **Task Requirement:** 3.7, 11.7a

### WARNING [hygiene]: Scope creep: shared remark/rehype plugin infrastructure added in Task 4
- **File:** velite.config.ts:29
- **Issue:** The diff adds `sharedRemarkPlugins`/`sharedRehypePlugins` constants and wires them into both `mdx` and `markdown` top-level Velite config blocks (velite.config.ts:29-34, 204-211), including `rehype-pretty-code`, `rehypeAbsolutizeUrls`, and `siteConfig.url` imports. None of this is in Task 4's stated scope (which is schema + transform + registration). This appears to pre-stage Task 6/7 work. Recommend reverting these changes from this commit and adding them under their proper task; at minimum, surface in the implementation log.

### WARNING [hygiene]: Unrelated devDependencies added to package.json
- **File:** package.json
- **Issue:** package.json gains `feed`, `fast-xml-parser`, `node-html-parser`, `reading-time`, `rehype-pretty-code`, `shiki`, `mdast-util-to-string`, `@types/hast`, `@types/mdast`, and an `engines.node >=24` block. Only `unified`, `unist-util-visit`, `remark-parse`, `remark-gfm`, `remark-mdx` are actually consumed by Task 4 code. The rest look like pre-staging for downstream tasks (RSS = `feed`, syntax highlight = `shiki`/`rehype-pretty-code`) and inflate the dependency footprint of this task's commit. The unused `reading-time` package is particularly notable since the implementation correctly uses a hand-rolled calculation per design intent — including the lib invites future regression to using it.

### INFO [hygiene]: `readingTime` is attached to transform output but not declared in schema
- **File:** velite.config.ts:165
- **Issue:** velite.config.ts:165 computes `readingTime` and returns it spread alongside schema fields. This works because Zod transforms can widen the output type, and `.velite/index.d.ts` derives `Post` from `_output`, so the generated type does include `readingTime`. Just be aware that adding it to the schema explicitly (e.g. via a separate field or via making the transform's return shape declared) would make the contract more discoverable. Non-blocking.

### INFO [hygiene]: Rejection visitor uses `node: any`
- **File:** velite.config.ts:132
- **Issue:** velite.config.ts:132 types the visitor parameter as `any`, losing the discriminated-union narrowing that `unist-util-visit` provides via overloads. Switching to the typed visit form or `Node` from `unist` keeps type safety while not changing runtime behavior.

### INFO [hygiene]: Two separate parse passes over `meta.content`
- **File:** velite.config.ts:160
- **Issue:** The transform parses `meta.content` twice — once with remark-mdx for rejection (line 122) and once without for reading-time (line 160). This is correct per the design (different parser stacks) but doubles parse work per post. Acceptable at build-time scale; flagging only because if post count grows large, caching the first parse's word-count via an mdx-aware filter could halve the work.
