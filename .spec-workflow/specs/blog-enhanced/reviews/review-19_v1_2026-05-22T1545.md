## Summary

Implementation meets most Req 1.9/1.10/1.11/1.13/1.14/1.15/10.7 surface requirements but has two material spec-compliance gaps: (1) PagefindUI is not re-mounted on subsequent dialog opens — Radix unmounts DialogContent on close, leaving the cached PagefindUI instance attached to a detached node and rendering an empty dialog on reopen; (2) Req 1.9a failure mode (b) entry-json 404 is not actually collapsed to the unavailable state — PagefindUI fetches entry.json asynchronously after its constructor returns, so the try/catch around construction does not observe that failure and state stays "ready".

## Findings

### CRITICAL: PagefindUI does not re-mount on subsequent dialog opens — second open renders an empty dialog
- **File:** src/components/blog/site-search.tsx:47
- **Issue:** Radix DialogContent unmounts when the dialog closes (no forceMount). On close, the <div ref={mountRef}> element that PagefindUI was mounted into is destroyed. On reopen, the mount-effect early-returns because initializedRef.current === true and state === 'ready', so PagefindUI is never reattached. The orphaned instance is bound to a detached node; the freshly-rendered mountRef div stays empty. Observable result: clicking the trigger a second time shows an empty dialog (no input, no results). Fix: either render with forceMount on DialogContent, or scope initialization to per-open lifecycle (reset initializedRef on close / re-construct PagefindUI on each open after the first lazy load).
- **Task Requirement:** 1.9

### CRITICAL: Failure mode (b) entry-json 404 is not collapsed to the unavailable state
- **File:** src/components/blog/site-search.tsx:57
- **Issue:** Req 1.9a v4 requires that failure modes (a) script-404, (b) entry-json-404, and (d) CSP-block all render the same observable unavailable state. The implementation wraps only the dynamic imports and the synchronous `new PagefindUI({...})` call in try/catch. PagefindUI fetches /pagefind/pagefind-entry.json asynchronously after the constructor returns; that fetch failure is not observable by this try/catch. State transitions to 'ready' even when entry.json 404s, and PagefindUI renders its own internal error UI rather than the spec-mandated 'Search is temporarily unavailable' copy with the aria-live announcement and blog-index link. Mitigation likely requires probing /pagefind/pagefind-entry.json (HEAD or fetch) prior to constructing PagefindUI, or hooking into a PagefindUI error callback if one exists, and routing those errors to setState('unavailable').
- **Task Requirement:** 1.9a

### WARNING: / shortcut does not check for the search dialog being open via aria-modal'd descendants
- **File:** src/components/blog/site-search.tsx:32
- **Issue:** Req 1.10 says `/` is ignored when the search dialog is already open. The implementation checks `if (open) return;` which is correct for this dialog's own state. However, if a Radix Dialog has stolen focus and the document-level keydown handler still fires before Radix intercepts, the scoping is correct — this is mostly defensive. Less critical: shortcut also fires while focus is inside the dialog input because Radix's input receives `/` and the handler's INPUT check filters it. Acceptable but worth a Playwright assertion.
- **Task Requirement:** 1.10

### WARNING: Req 1.13 filter excludes /blog/ (with trailing slash) but Pagefind result URLs for /blog index typically have no trailing slash
- **File:** src/components/blog/site-search.tsx:80
- **Issue:** The predicate is `r.url.startsWith('/blog/') && r.url !== '/blog/'`. The startsWith check already excludes `/blog` (no trailing slash) entirely because '/blog' does not start with '/blog/'. The `!== '/blog/'` clause filters the trailing-slash form, but if Pagefind emits the index URL as `/blog` (no trailing slash), it is already excluded. Either form is filtered; the spec wording (`r.url !== '/blog'`) and the implementation (`r.url !== '/blog/'`) differ by trailing slash — confirm Pagefind's actual URL output to ensure the index page is excluded regardless of which form Pagefind uses.
- **Task Requirement:** 1.13

### WARNING: Loading state hidden once state becomes 'ready' but PagefindUI's own input/empty state may not be present yet at the moment React flips state
- **File:** src/components/blog/site-search.tsx:161
- **Issue:** The 'Loading search…' paragraph renders while state is 'opening' or 'closed'. As soon as PagefindUI constructor completes and setState('ready') runs, the loading copy disappears and PagefindUI's UI fills mountRef. This sequence is fine for the success path. For Req 1.9 the dialog must show (e) an initial state before the user types — relies entirely on PagefindUI rendering its initial empty state synchronously after construction. Not a defect — flagged because the spec's 'Initial' empty state copy is delegated to PagefindUI, and Design pins the copy 'Type to search posts'. Verify PagefindUI's default initial copy matches Design's pinned copy or override via UI translations.
- **Task Requirement:** 1.9

### INFO [hygiene]: ESLint disable comment for next/no-html-link-for-pages
- **File:** src/components/blog/site-search.tsx:145
- **Issue:** The /blog index link in the unavailable state uses a plain <a> with an eslint-disable-next-line directive. This is intentional per the inline comment (degrades without JS) and acceptable, but worth noting that an alternative is to use Next.js <Link> — which also renders an <a> at runtime and is functionally equivalent for no-JS degradation (Next renders the anchor in initial HTML). The current choice is defensible.
