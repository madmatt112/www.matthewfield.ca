## Context
Requirements v9 is approved and hard-capped, so the criterion cannot be amended. Req 10.4 states: "IF the evaluated record's latest status is a terminal non-`success` state (`failure`, `error`, or `inactive`) THEN the run SHALL fail immediately under Req 9 with that status as the named cause". Combined with Req 10.3's "latest SHALL mean the status with the greatest `created_at`", this means a deployment that succeeded and was then marked `inactive` reads as a failure. GitHub's `auto_inactive` behaviour marks a *superseded* production deployment `inactive` when a newer one takes over, so a successful deploy that is immediately superseded would be reported as `deploy-not-success`. Measured during design review r1: across all 159 status objects in this repository's 156 deployments there is exactly one `inactive` (deployment 4811291063), and it follows a `failure` at 15:55:11 with `inactive` at 16:13:25 — a superseded failure, not a superseded success. So the requirements' own r7 measurement ("no deployment has ever transitioned from a non-`success` status to `success`") still holds and Req 10.4's list is empirically safe in this repository today. The race window is roughly the interval between the sync's production deploy completing and a newer production deploy superseding it; Req 11.1's concurrency group prevents the sync from racing itself, and a human push landing a production deploy inside that window is the only way in. Alternatives considered: (a) evaluate the greatest-`created_at` *`success`* status rather than the greatest status overall - rejected as a direct contradiction of Req 10.3's definition of "latest"; (b) treat `inactive` as non-terminal and keep polling - rejected as a direct contradiction of Req 10.4's enumeration; (c) record and monitor - chosen, on the measured base rate and the loudness of the failure.

## Decision Deferred
github-activity-sync will implement Req 10.4's terminal-status list verbatim, including `inactive`, and will read the latest status strictly by greatest `created_at` per Req 10.3. The known consequence — a successful production deployment that is superseded within the poll window is reported as `deploy-not-success` — is accepted rather than designed around.

## Revisit Criteria
Revisit when EITHER: (1) a sync run fails with `deploy-not-success` whose named status is `inactive`, which distinguishes this case from a genuine build failure with no ambiguity; or (2) `vars.DEPLOY_VIA_CI` is set to `true`, enabling the CI-driven deploy path gated at `.github/workflows/ci.yml:110-137` and creating a second producer of production deployments that could supersede the sync's own within the poll window.
