# Adversarial Analysis — project-showcase/requirements (v1)

Role: senior technical product manager. Focus: completeness, ambiguity, scope. The document is long, dense, and frequently anticipates its own critics — but "anticipating" is not "resolving." Below are the load-bearing weaknesses.

---

## Attack surfaces

### A. Req 1.2 / Req 1.5 — Schema field set and the `updated` divergence rationale

- Challenge the claim that `description` (1–300 chars) serves both as meta description AND default card body. Meta descriptions clip in SERPs around 150–160 chars; card body copy thrives at 60–110. A field that is "good enough for both" is a field that's mediocre for both — the optional `summary` override is acknowledged but the spec does not require it where it materially matters, so the *default* failure mode (lazy author writes one `description`, gets a weak SERP snippet AND a weak card) is the *most likely* mode in practice.
- Stress-test the assumption that the `updated` field will be authored honestly and consistently. Req 1.5 prohibits git-derived `updated` precisely because typo fixes shouldn't surface as updates — but the spec offers no operational definition of "meaningful to readers" and no lint/check. The first time Matthew fixes a real bug in a project and forgets to bump `updated`, the badge silently misrepresents the page. The mirror failure (bumping `updated` on a screenshot swap) is equally unguarded.
- Stress-test the absence of a `cover` *aspect ratio* or *minimum dimension* constraint. Req 3.8 explicitly disclaims any upper bound, but provides no lower bound either. A 200x100 cover and a 4000x2250 cover both pass the schema; the gallery grid will render them at wildly different perceived quality. "Authors are trusted" is fine for one author, but the spec is the only contract between today's Matthew and 2027's Matthew.
- Challenge the decision to make `coverAlt` a separate required field rather than embedding it in the `cover` object. Velite's `s.image()` could plausibly co-locate alt text; splitting them means a future cover swap requires editing two fields and risks alt-text drift (new image, old description). The spec doesn't address how to keep these in sync at review time.
- Challenge the implicit claim that `tags` (0–8, kebab-slug) without navigation has any user-visible value. Req 2.5 forecloses clickable tags; Req 5 doesn't surface them; Req 8 doesn't index them. What does a visitor *do* with a tag chip that is not a link? The requirement reads as "future hook" rather than "launch value" — say so, or cut it.

### B. Req 2 — Gallery contract and the empty/featured/sort interactions

- Challenge the claim in Req 2.7 that `featured: true` is a "presentation hint, not a sort key" while simultaneously permitting "larger grid span." A larger grid span in a CSS grid IS a sort-adjacent property — it changes visual prominence and the order in which the eye scans cards. The spec says order is preserved but does not address that featured cards in mid-chronology will visually dominate older work. Either commit to "featured = visual weight only, never repositioned" with concrete constraints, or admit that featured IS partial sort.
- Stress-test Req 2.3's DOM-order list against Req 2.6's "single anchor wraps the whole card." The list specifies title, body, date, tags, status badge all inside one anchor. Per Req 5.5/5.6 the link rail is excluded, but an anchor wrapping *tag spans plus a status badge plus body text* produces a verbose accessible name unless the title is explicitly marked as the link name. Req 2.3 hand-waves this with "image carries empty alt if the same card surface also surfaces the title text within the link" — the alt-text trick handles the image but not the cascade of additional text content collected into the link's accessible name. Concrete failure: VoiceOver reads "image, project title, project body, date, tag1, tag2, Archived, link" as the link name.
- Stress-test the empty-gallery contract (Req 2.9). The copy "No projects published yet." ships in production. If Matthew launches this spec and ships zero projects on day 1 (likely, given the placeholder.mdx pattern in Req 1.10), the live site briefly advertises an empty gallery — which contradicts the "builder credibility" objective the introduction cites. The spec needs either a "do not link `/projects` from the nav until N≥1" rule or an acceptance that the empty state IS the initial production state.
- Challenge Req 2.10's "single column on <640px" without specifying intermediate breakpoints. The requirement guarantees mobile correctness but provides zero contract for tablet (641–1024px), where a single-column gallery looks wasteful and a four-column gallery looks crowded. "Design-phase concern" defers the failure mode rather than addressing it.
- Stress-test the date-formatting parity claim in Req 2.3 ("same Intl DateTimeFormat the blog uses"). If blog-core's formatter is later refactored to support timezones or relative dates, this spec inherits silent breakage unless the shared formatter lives in a shared module. Req 6.3 mentions `formatProjectDate` *in `src/lib/projects.ts`* — that's a parallel implementation, not a shared one, and the parity will drift.

### C. Req 5 — Links rail (key set, ordering, future extensibility)

- Challenge the closed key set (`demo`, `repo`, `docs`, `package`, `writeup`) as "permitted at launch." The strict-mode schema (Req 5.2) makes adding a sixth key a schema-change commit, not a content-change commit — which directly violates the spec's own headline goal ("never edit React code to launch or update a project"). A project with a Figma file, a YouTube demo, a Loom walkthrough, or a Show HN thread has no key — the author edits velite.config.ts, the page component (for the visible label), and possibly an icon map. This is a self-inflicted scope problem.
- Stress-test the ordering claim. Req 5.4 lists keys in a fixed visible-label order but does not specify the *display* order. Is it the order keys appear in YAML? Insertion order in JS objects? A canonical order baked into the component? The acceptance criteria are silent. Failure: author lists `repo` before `demo` in YAML, expecting that order; component renders alphabetical or schema-declaration order; bug filed.
- Challenge the uniform `rel="noopener noreferrer"` + same-tab policy in Req 5.5. "noreferrer" strips the referrer from outbound traffic — which means when a visitor clicks through to the project's live demo, the demo's analytics shows the click as direct traffic, not as "from matthew-field.ca." For a site whose business objective #2 is "builder credibility," voluntarily erasing the attribution path on outbound clicks is a value-misaligned default. State this as a deliberate trade-off or reconsider.
- Stress-test the same-tab default against user expectation. Most portfolio sites open demos in new tabs; same-tab forces back-navigation through the demo's history stack, which often breaks (SPAs, login walls). Req 5.5 declares this a uniform policy with "authors are not given a per-link override" — a rigid stance unsupported by user-research justification in the document.
- Challenge Req 5.4's positional claim ("ABOVE the MDX body"). For a long writeup the rail-above-body pattern is conventional, but for a short project page (Req 6.10 explicitly anticipates these) the rail dominates the visible content. No acceptance criterion handles short-body pages where the rail eats the fold.

### D. Req 6 — Detail page contract and MDX limitations

- Challenge Req 6.9's "no custom component registry" framed as a feature. The document acknowledges that `<Screenshot />` would throw a ReferenceError caught by 6.8(c)/(d) — but the actual *failure mode* is silent: an author writes `<Demo url="..." />` thinking it's syntax sugar, the build fails, the author has to debug. The spec frames this as "correct behavior" but offers no author-facing documentation, no warning in CONTRIBUTING-equivalent, no example MDX to copy. Authors will write component-tag MDX and break the build.
- Stress-test Req 6.7's `max-w-5xl` (1024 px) container reuse from `/profile`. Profile is a resume — a single-column document with mostly text and a few structural blocks. A project page may contain wide screenshots (1600px+), video embeds, terminal recordings. A 1024px container forces those into a smaller frame than the source — defeating the spec's own "wide and spacious" justification in the introduction.
- Challenge the absence of any heading-hierarchy contract for MDX bodies. Req 6.1 specifies the page's `<h1>` is the title; Req 6.6 anchors h2/h3. But there is no acceptance criterion forbidding an author from putting an `<h1>` inside their MDX body (which would create two h1s on the page — an a11y violation that the spec ostensibly cares about). Blog-core may have this contract; the spec doesn't restate it, doesn't reference it, doesn't enforce it.
- Stress-test Req 6.4's OG-image-from-cover claim against Velite's output. Velite's `s.image()` emits dimensions for layout stability — but OG images have their own dimension requirements (1200x630 typical). A vertical or square cover image will preview poorly on Twitter/LinkedIn/Slack unlinks. The spec inherits cover dimensions as OG dimensions with no warning, validation, or remediation.
- Challenge Req 6.10's "no prev/next" justification. The asserted reasoning is "project visitors are looking for a specific project." But the gallery is the entry point for many visitors who *don't* know what they want — they came from the homepage hero or a Hacker News thread. Once on a detail page, the only way back to other projects is the browser back button or finding the nav link. This is a real UX cost asserted away rather than measured.

### E. Req 7 — Draft handling, environment scoping, and the leak guard

- Stress-test the layered draft-leak guard's assumption that `VERCEL_ENV` is reliable. On a local `pnpm build` (not preview, not production, no `VERCEL` set), Req 7.2 says drafts are excluded UNLESS `PROJECTS_INCLUDE_DRAFTS=1`. But `pnpm dev` and `pnpm build` are different code paths in Next.js — does the guard fire in dev mode? Does HMR re-evaluate the env var? The spec assumes a single "local build" model and doesn't disambiguate dev/build.
- Challenge Req 7.6's test contract. It mirrors blog-core's tests, but the *interesting* failure case for a leak guard is the one neither codebase has hit yet: a misconfigured CI env where `VERCEL=1` is set but `VERCEL_ENV` is unset or has a typo. The test list as specified (production excludes drafts, guard throws on misconfig, env flag works locally) does not cover the "looks-like-prod-but-isn't" intermediate state.
- Stress-test the claim that `getPublishedProjects()` is the single chokepoint. Req 7.4 prohibits direct collection imports outside `src/lib/projects.ts`, "enforced by code review." Code-review enforcement is not enforcement — it's a hope. The non-functional section restates this as "a future ESLint rule could mechanize it." Either ship the lint rule now or accept that drafts WILL leak the first time someone imports `#site/content` directly to "just write a quick script."
- Challenge the publish-by-frontmatter-flip model in Req 7.5. There is no rollback story. If Matthew flips `draft: false`, commits, deploys, and immediately realizes the writeup has an error — what's the contract? Revert the commit, redeploy, the URL 404s briefly, sitemap drift. The spec does not articulate this lifecycle.

### F. Cross-cutting — scope creep risk, contradictions, missing user stories

- Stress-test the introduction's "explicitly out of scope" list against subsequent requirements. The intro says cross-linking from blog posts is out of scope, but Req 5.1 includes a `writeup` key for "a related blog post." That IS cross-linking — just unidirectional and author-curated. Either align the intro or align the requirement.
- Challenge the missing user story for *editing* an existing project. All user stories are framed as launching or adding new projects. The acceptance criteria for `updated` exist but no story narrates "Matthew updates an existing project after a year — what does the gallery / detail page / sitemap reflect, in what order, with what badges visible?"
- Challenge the missing user story for *unpublishing* a project (deleting the MDX file or flipping draft back to true). Req 7 covers draft-on-launch but not "this project was live; now it is not." The sitemap re-generation handles this implicitly, but the URL goes 404 with no redirect, and the spec does not discuss whether that's acceptable.
- Stress-test the no-RSS-feed omission. Posts have a feed; the spec says nothing about a projects RSS/Atom feed. Either the explicit "out of scope" list should include it, or it's an oversight.
- Challenge the absence of a contract for *case sensitivity* on slugs. The kebab-slug regex permits only lowercase, but Next.js routes on case-insensitive filesystems (Windows, macOS default) versus case-sensitive (Linux CI) can produce subtle "works locally, 404s in CI" failures. The spec inherits this from blog-core silently.

## Top 5 risks/gaps

1. **The `description` field is overloaded.** It serves SEO meta and default card copy; the optional `summary` exists but is opt-in. The dominant failure mode is "author writes one OK string, gets two mediocre surfaces." Make `summary` required when card copy and meta description would diverge, or split the schema fields explicitly.

2. **The links rail's closed key set is a self-inflicted scope wound.** Adding a sixth link type requires schema + component + label changes — directly violating the spec's own "no React edits to launch a project" promise. The five-key allowlist will need its sixth entry within months.

3. **The `featured` flag's "presentation only, not sort" contract is logically incoherent.** A larger grid span IS a visual reordering of attention. Either define exact constraints ("featured cards retain row position; only the card's own cell dimensions change") or admit `featured` partially overrides chronology.

4. **The draft-leak guard depends on code-review enforcement of "no direct collection imports."** The spec acknowledges this isn't mechanically enforced. The first script or one-off page that imports `#site/content` directly will bypass the guard. Either ship the ESLint rule with this spec or accept the leak risk.

5. **Card link semantics produce a verbose accessible name.** Req 2.6 wraps the entire card surface (image + title + body + date + tags + status badge) in a single anchor. The acceptance criteria do not establish how to scope the link's accessible name to just the title — VoiceOver will read the entire card content as the link name. The "empty alt" trick handles the image but not the text content.

## Top 3 conclusions to challenge or reverse

1. **Reverse: `links` should be `links: Array<{ label, url, kind? }>`, not a fixed-key map.** The keyed-map model assumes a stable taxonomy of project link purposes. It doesn't exist. Authors will hit the wall by project #4. An array with author-supplied labels and an optional `kind` for icon lookup degrades gracefully and never requires schema changes for new link types. The fixed-label "Live demo / Repository / Docs / Package / Writeup" set can be the *default* visible label when `kind` matches, not the *only* possibility.

2. **Reverse: `summary` should be required when `description.length > 160`.** The spec's split exists to allow SEO-tuned descriptions, but the schema doesn't enforce when the split is actually needed. A 280-char description guarantees a card that's either truncated or visually overweight. Validate the relationship between fields, not just each field independently.

3. **Reverse: drop tag display at launch.** The introduction defers tag *navigation* and Req 2.5 enforces non-interactive tag chips. The combination produces visual noise with no user affordance. Either include the tag-routing infrastructure or omit tag rendering until that spec lands. Storing tags in frontmatter is fine; rendering chips that do nothing is not.

## What's missing — pre-action work

- **Concrete card and detail page wireframes** (or low-fidelity mocks) for: empty gallery, single-project gallery, multi-project gallery with one featured, detail page with rail, detail page without rail, archived badge on card, concept badge on card. The current acceptance criteria specify many invariants in prose but the geometric interactions (featured-card span vs. responsive grid, rail-above-body for short writeups, status badge placement within a single-anchor card) need visual confirmation.

- **An author-facing writeup of "what MDX you can use in a project body"** — the unspoken contract that custom components throw, image references work, headings are sluggified, the prose container is 1024px. Without this, authors learn the contract by breaking the build. The spec frames build failures as "loud" — they're loud *to the build*, not to the author writing the MDX.

- **A migration / lifecycle section** covering: editing a published project, unpublishing (delete file vs. flip draft), renaming a slug (URL break, redirect strategy), and the order of operations when bulk-updating multiple project files. The current spec is comprehensive about *adding* projects and silent about *maintaining* them.

- **An ESLint rule or a documented decision to defer it.** The Req 7.4 "code review enforces no direct collection imports" claim needs either mechanization or an explicit acknowledgment that the leak guard is best-effort. Right now the spec asserts both "the chokepoint is mandatory" and "it's enforced by review" — those are contradictory in any team larger than zero.

- **An OG-image strategy** that doesn't assume the cover image is share-shaped. Either Velite should derive a 1200x630 crop, the schema should require a separate `ogImage`, or the spec should document that share previews will look poor for non-landscape covers.

- **Decision on tags-at-launch:** render or omit. The current "render but inert" middle ground is the worst of both options.
