# Adversarial Analysis — blog-core/requirements.md (v3)

**Reviewer stance:** senior technical PM, directive, no validation. Primary attack surface: completeness, ambiguity, scope.

**Prior-review status (one-line):** v2's eight headline gaps (Req 8.4↔3.10 contradiction, preview-draft public-internet, no-JS Shiki theme parity, `s.markdown` plugin alignment, regex prose-extraction brittleness, excluded-tag-class enumeration, CI orchestration, All-Environments guard) have all been substantively addressed. This review concentrates on **novel issues introduced by the v2→v3 fixes** and on **compounding gaps** the fixes leave open.

---

## Targeted attacks

### 1. Req 9.2's two-selector union overrides an explicit user theme choice — a new bug introduced by the v2 fix

- **Stress-test the cascade between the `.dark` attribute selector and the `@media (prefers-color-scheme: dark)` fallback.** Req 9.2 says both selectors SHALL produce the same dark-variant code-block colors, then leaves their cascade unpinned. Consider the user with a dark-mode system who explicitly toggled the site to light mode via the theme button. `next-themes` removes `.dark` from `<html>`. The `@media (prefers-color-scheme: dark)` query *still matches* and lights up the dark-variant code blocks against a light-themed page body. This is worse than the original no-JS bug — it is an explicit-user-choice contradiction visible to every dark-system user who prefers light reading.
- **Challenge the symmetric inverse case.** A user with a light-mode system who toggled the site to dark gets `.dark` on `<html>` → dark code blocks correctly. But a CSS that selects on `.dark, @media(prefers-color-scheme: dark)` (the simplest reading of "two selectors, both required") will produce light code blocks for a dark-system + light-toggle user. The spec asserts equivalence; it does not pin the precedence rule (`@media` only applies when the attribute is absent — e.g. via `:not(.dark):not(.light)` ancestor, or by next-themes setting an explicit `.light` class the spec does not require).
- **Attack the silence on the third-state class.** `next-themes` typically writes `.dark` and removes it; some configurations also write `.light` for symmetric tooling. The spec assumes the binary "dark class present / absent" model but does not pin the ThemeProvider config to write a paired `.light` class — without which the precedence-fix above (`:not(.light)` guard on the @media query) is not implementable.
- **Stress-test the no-JS Playwright test in Req 13.7.** The test launches with `javaScriptEnabled: false` and `emulateMedia({ colorScheme: 'dark' })`, then asserts "the rendered code block's effective text color matches the dark-variant Shiki token color." With JS off, no class is on `<html>`, so the @media query alone resolves the color. Fine. But the test never exercises the JS-on + system-dark + user-toggled-light failure case from the first bullet — the exact regression the cascade ambiguity allows. The test verifies the documented happy path and ignores the dangerous edge.

### 2. Req 7.11's noindex protects the post detail page; Req 2 and Req 4 leave the index and taxonomy pages indexable on preview deploys

- **Challenge the per-page robots scope.** Req 7.11 says draft *post pages* emit `noindex,nofollow` unconditionally. The preview deploy also includes `/blog` (Req 2), `/blog/tags/<tag>` (Req 4.1), and `/blog/categories/<category>` (Req 4.2), all of which list drafts when `BLOG_INCLUDE_DRAFTS=1`. These pages render the draft's title, description, and tag chips. A crawler that reaches the preview deploy's `/blog` indexes the draft title + lede + tag taxonomy without ever crawling the detail page. The noindex directive on the detail page never fires for this leak surface.
- **Stress-test the realistic disclosure scenario.** Hypothetically: a draft titled `"Embargoed: ACME acquisition timeline"` with description `"How the deal closed and what changes Monday"`. On a preview deploy this title and description render as a Card on `/blog` (indexable), a chip-link to `/blog/tags/acme` (the taxonomy page is indexable and lists the same Card), and a sitemap entry — wait, sitemap is gated by `getPublishedPosts()` per Req 12.3, so that surface is closed. But the rendered HTML on `/blog` itself is indexable and contains the title and description. The "anti-disclosure NOT covered" guidance in Req 7.10 is honest, but Req 7.11 implies a stronger posture than it delivers.
- **Attack the cleaner site-wide alternative.** The standard Vercel pattern for preview deploys is a site-wide `X-Robots-Tag: noindex` header when `VERCEL_ENV === 'preview'`, configured in `next.config.ts` headers or `middleware.ts`. This covers the index page, taxonomy pages, post pages, AND any future surface added without per-page noindex discipline. The spec instead requires per-page directives that depend on author compliance and consumer-side memory. Recommend: replace Req 7.11's per-page approach with a preview-env-scoped site-wide noindex, and keep the per-page draft directive only as a redundant belt for production-shipped drafts (which by Req 7.1 cannot exist anyway, making the per-page directive structurally dead code).
- **Challenge the dead-code observation.** Req 7.11 says "set the directive unconditionally for drafts — independent of whether the deploy is production (impossible per Req 7.1 since the post would not be in `generateStaticParams()`)..." The spec itself acknowledges the production-draft case is impossible. So the per-page noindex directive only ever fires on preview and dev. On preview, the index/taxonomy leak above is the real risk; on dev, no crawler reaches localhost. The directive's actual job is "redundant safety belt on a surface that cannot happen." That is fine as defensive coding but is not where the leak risk actually lives.

### 3. Req 11.7a pins shared plugin registration but introduces a Shiki highlighter cost the build-time-cost note (Req 11.7) does not account for

- **Challenge the "30ms per post" cost estimate.** Req 11.7 estimates the dual-pipeline overhead as "~30ms per post." This assumes the shared `[rehypePrettyCode, prettyCodeOptions]` tuple in Req 11.7a actually shares a single Shiki highlighter across both Velite pipelines. `rehype-pretty-code` instantiates the highlighter via `shiki.createHighlighter()` on first use; that initialization is ~500–1000ms (theme/grammar/wasm load). If Velite invokes the plugin tuple in two distinct contexts — once for `mdx.rehypePlugins`, once for `markdown.rehypePlugins` — the highlighter is created twice unless the plugin caches the instance globally. The shared array does NOT guarantee shared instances; it guarantees shared configuration. The cost estimate is off by an order of magnitude for the cold-cache case.
- **Stress-test the "single named constant" mechanism.** Req 11.7a says "define a single named constant ... and register that exact array under BOTH" pipelines. This shares the configuration. Whether the *plugin instance* (the function rehype-pretty-code exports) is invoked once per file or memoizes its highlighter across calls is plugin-internal behavior the spec does not verify. The contract should be: "the design phase SHALL verify the Shiki highlighter is instantiated exactly once across both pipelines (via plugin caching, an explicit `createHighlighter()` call shared via module-level memo, or equivalent)." Without this, the dual-build cost claim is unbacked.
- **Attack the deferred-to-Design `markdown.rehypePlugins` API existence question.** Req 11.7a hedges: "confirm during Design that `defineConfig` accepts a `markdown.rehypePlugins` option (Velite v0.3.x — if the option's name differs in the installed Velite version, pin the actual key in Design)." This is a *requirements-blocking question* — if the option does not exist, the entire shared-plugins mechanism is unimplementable and the spec's RSS-parity contract collapses. Bouncing this to Design risks discovering the spec is unbuildable after task decomposition. Resolve in requirements: check the Velite version in `package.json` and the actual API surface NOW, pin the key (or, if the API does not exist, fork to one of the documented alternatives: post-process `bodyHtml` after `s.markdown()` runs, or stop using `s.markdown()` and hand-roll the markdown→HTML pipeline with the shared plugin array).
- **Challenge the plugin-state-across-pipelines assumption.** `rehype-pretty-code` and `rehype-slug` are stateless across files in practice. But the absolutization step (`rehypeAbsolutizeUrls`, Req 11.8) is described as "a rehype-urls-style step (or hand-rolled HAST visitor)." A hand-rolled visitor that closes over per-file state (e.g. tracks already-rewritten URLs) and is registered as a single shared instance across two pipelines and N files could exhibit cross-file contamination. Pin: plugin instances in the shared array MUST be stateless across `(pipeline, file)` tuples. Add it as an acceptance criterion on Req 11.7a.

### 4. Req 6.4's AST-based extraction closes regex bugs but introduces parity-with-page-pipeline and visitor-configuration gaps

- **Challenge the unpinned remark-gfm parity.** Req 6.4 says "and `remark-gfm` if the page pipeline uses it; pin during Design." This is the same deferral pattern as Req 11.7a — punt to Design a question the spec contract depends on. If the page MDX compile uses `remark-gfm` (it does — `velite.config.ts:79` registers it) and the reading-time AST extraction does NOT, then a post body with a GFM table (`| col | col |`) is parsed by `remark-parse` alone as a paragraph containing pipes and dashes (different node structure, different word count). A 50-row table renders identically on the page (with GFM) but the reading-time estimate inflates because every `|` and `-` becomes a "word" in the non-GFM parse. Pin: the AST extraction pipeline SHALL register the same `remarkPlugins` array used by `mdx.remarkPlugins` (analogous to Req 11.7a's shared rehype array).
- **Stress-test the mdast-util-to-string visitor configuration.** The library has options like `includeImageAlt: true|false` and behavior differences between versions for footnote definitions, link references, and inline images. The spec does not pin these. A post with `![hero photo of CN tower](/img/cnt.jpg)` either contributes "hero photo of CN tower" (4 words) or contributes 0 words, depending on `includeImageAlt`. The reading-time tolerance fixture (Req 6.5) cannot catch this without a fixture that exercises image alt text — which the spec does not require. Pin the visitor's configuration and add image alt to the fixture coverage.
- **Attack the JSX self-closing tag interpretation.** Req 6.4(b) says "drop JSX wrappers but recurse into children." A self-closing tag (`<Image src="..." alt="hero" />`) has no children — the alt text inside the attribute is dropped. For accessibility prose (`<Image alt="diagram showing the request flow">`), this is real prose discarded. Less serious now (Req 3.7 forbids JSX in launch bodies), but the contract is being written for the future-spec MDX-component world where this matters. Pin: when MDX components are introduced (future spec), the AST extractor SHALL be revisited; capture this as a forward-looking constraint, not an "approximately correct" rule.
- **Challenge the silent dropping of `type: 'html'` nodes.** Req 6.4(b) says raw HTML nodes are "dropped entirely" because "raw HTML in a markdown body is rare and counting it as prose is more wrong than dropping it." This pre-decides a judgment call. A post that uses `<aside>` or `<details>` blocks inline (legitimate markdown that authors sometimes reach for) drops the entire aside content from the word count. The page renders the aside as prose; the reading time underreports. Either forbid raw HTML in post bodies (add to Req 3.7's plain-markdown-equivalent constraint) or recurse into the HTML node's text content.
- **Stress-test Req 6.5's tolerance against fixture length.** The ±20% bound + ±1-minute floor: for a 1-minute post (~200 prose words), the floor wins and allows 0–2 minutes. A regression that inflates a 1-min post to 2 mins (33% bound from v2) passes. The fixture must be long enough that the ±20% bound dominates the floor — at 5+ minutes (~1200 prose words), ±20% is ±1 minute, where the bounds tie. Below that, the floor lets regressions through. Pin: the fixture SHALL contain ≥1000 prose words (≥5 min at 238 wpm) so the percentage bound actually exercises the contract. Otherwise the bound is decorative.

### 5. Req 7.14's single-build CI strategy leaves the production-exclusion path without E2E coverage; Req 7.12's guard is asymmetric

- **Challenge the "Vitest unit-level coverage of `getPublishedPosts()` is sufficient" claim.** Req 7.14 retires the dual-build approach in favor of one Playwright build (`BLOG_INCLUDE_DRAFTS=1`) and Vitest unit tests for the "drafts excluded" path. The spec's reasoning: "the helper is the single chokepoint per Req 7.4." But the assertion "every consumer calls the helper" is enforced by code review, not by any test. A future PR that adds, say, an "all posts" JSON dump for AI search and imports `#site/content` directly bypasses the helper. The Vitest unit test on `getPublishedPosts()` still passes (the helper still works in isolation), but the new consumer ships a draft to production. Add an integration test: read `#site/content.posts` directly, identify the fixture-draft entry, then assert it is absent from every documented consumer surface (RSS XML output, sitemap output, `/blog` HTML, taxonomy page HTML, `generateStaticParams()` for `/blog/[slug]`).
- **Stress-test the Req 7.12 build-time guard's asymmetry.** The guard catches `BLOG_INCLUDE_DRAFTS=1 + VERCEL_ENV=production` and throws. It does NOT catch the symmetric misconfiguration: Preview scope without `BLOG_INCLUDE_DRAFTS=1`. The operator misconfigures the Vercel UI by scoping the env var to Production only instead of Preview only; the next PR preview deploy builds successfully but excludes the fixture draft. Matthew shares the preview URL with a reviewer expecting to see drafts, sees no drafts, then debugs Vercel UI for 20 minutes. There's no positive assertion ("if `VERCEL_ENV === 'preview'`, then `BLOG_INCLUDE_DRAFTS` SHALL be `'1'`, else throw with a configuration-help message"). Add the symmetric guard.
- **Attack the missing fixture-draft 404 verification under production-mode build.** The strongest test of "production excludes drafts" would be: run a production-mode build (no `BLOG_INCLUDE_DRAFTS`), then a Playwright test hits `/blog/fixture-draft` and asserts a 404 response. The Req 7.14 single-build approach makes this impossible without dual builds. Either (a) accept the gap explicitly ("no E2E verification of 404 on production; trust the chokepoint pattern"), or (b) add a separate lightweight CI step: a second `next build` invocation without `BLOG_INCLUDE_DRAFTS`, then a Node script that lists `.next/server/app/blog` and asserts `fixture-draft` is not in the generated route manifest. The latter avoids a second Playwright run but covers the regression class the chokepoint pattern cannot structurally enforce.
- **Challenge the fixture-draft permanent slug occupation.** Req 7.14's "Fixture post location" pins `content/posts/fixture-draft.mdx`. This permanently occupies `/blog/fixture-draft` in the preview namespace AND in any future consumer that bypasses the helper. If Matthew later wants to publish a real post about a draft fixture meta-discussion under that slug, it collides. The spec accepts this trade-off but does not capture it as a *durable constraint* — future-spec authors should know the slug is reserved. Add a one-line note on the chosen filename: "the slug `fixture-draft` is reserved for the testing fixture and SHALL NOT be reused for published content."

### 6. Fixture roster is implied across multiple requirements but never enumerated; tests reference fixtures that the spec does not concretely list

- **Challenge the missing fixture inventory.** The spec references at least three fixture posts implicitly: (1) `content/posts/fixture-draft.mdx` (Req 7.14, the draft fixture), (2) "the code-fixture post from Req 9.6" (Req 6.5, Req 11.11, Req 13.7), (3) "a-known-fixture-slug" / "a-known-fixture-tag" / "a-known-fixture-category" (Req 13.2's axe pass). These may be one post or three — the spec does not pin. The axe pass needs a non-draft fixture with at least one tag and one category to exercise four routes. The code fixture needs fenced code blocks of both fence flavors (Req 6.5). These could be the same post or not. Pin the fixture roster: which slug(s), what frontmatter, what body shape, what tags/categories.
- **Stress-test the "fixture is also test infrastructure" pattern.** Fixture posts are committed to the repo and shipped in production builds (per Req 7.14's discussion of fixture-draft). A non-draft code fixture (call it `content/posts/code-fixture.mdx`) is therefore a real, live, public-internet post on `matthewfield.ca/blog/code-fixture` with title, description, and body visible to every visitor and indexed by Google. Either the fixture is also legitimate content (a sample post Matthew is happy to have indexed), or the fixture must be marked `draft: true` and only exist on preview deploys — but then the axe pass in Req 13.2 cannot find it in production. Pin: are non-draft fixture posts intended to be public, or is there a third class (test-only-but-not-draft)?
- **Attack the Req 13.2 axe-pass route enumeration.** The four routes "`/blog`, `/blog/<a-known-fixture-slug>`, `/blog/tags/<a-known-fixture-tag>`, `/blog/categories/<a-known-fixture-category>`" presuppose fixtures with specific slugs/tags/categories that the spec does not list. If the test is run before fixtures are authored (i.e. on the first task that wires up Playwright), the test fails for "fixture not found" — a setup ordering problem the task decomposition will hit. Pin the fixture roster early so decomposition tasks have stable filenames.

## Top 5 risks/gaps

1. **Req 9.2's `@media` fallback overrides explicit user theme choices.** A dark-system user who toggles the site to light still gets dark code blocks against a light body, because the `@media (prefers-color-scheme: dark)` selector matches regardless of the user's explicit override. The v2 fix solved one bug (no-JS dark-system gets light code) by introducing another (JS-on dark-system + light-toggle gets dark code on light body). The spec asserts equivalence between selectors but never pins their precedence.
2. **Req 7.11's per-page noindex misses the leak surface.** Drafts leak via `/blog` and taxonomy pages, which list draft titles + descriptions on preview deploys and have no noindex. The cleaner fix — a `VERCEL_ENV === 'preview'`-scoped site-wide `X-Robots-Tag` — covers every current and future surface; per-page directives leave consumer-side gaps.
3. **Req 11.7a's "markdown.rehypePlugins" API existence is unverified and deferred to Design.** If Velite's installed version does not expose that key, the shared-plugin mechanism — the structural fix for the v2 plugin-pipeline alignment finding — is unimplementable. Verify against `package.json`'s actual Velite version in the requirements doc, not in Design.
4. **Req 7.14's single-build strategy + Req 7.12's asymmetric guard leave both ends of the env-var matrix without E2E coverage.** The "drafts excluded in production" path has no E2E test (Vitest unit-only); the "drafts present in preview" path has no positive guard (only `Production+drafts=1` throws, not `Preview+drafts≠1`). Both the leak failure mode and the not-shown-on-preview failure mode are unverified.
5. **Req 6.4's remark-gfm parity is unpinned and Req 6.5's tolerance fixture lacks a length floor.** Without a shared remarkPlugins array between the page and reading-time pipelines, a GFM table inflates reading time silently. Without a ≥1000-prose-word fixture, the ±1-minute floor swamps the ±20% bound on short fixtures and lets regressions through.

## Top 3 conclusions to challenge or reverse

1. **Reverse: Req 7.11's per-page noindex in favor of a preview-env site-wide robots header.**
   The per-page directive only fires on the post detail page. The leak risk lives on `/blog` and the taxonomy pages, which the per-page directive does not cover. Set `X-Robots-Tag: noindex, nofollow` site-wide on every response when `process.env.VERCEL_ENV === 'preview'`, configured in `next.config.ts`'s `headers()` (or `middleware.ts` if `headers()` cannot read env vars at request time). The per-page directive becomes structurally dead code (Req 7.11 admits the production case is impossible); the site-wide header covers every surface without consumer discipline. Move the per-page directive to "defense in depth only" status.

2. **Reverse / harden: Req 9.2's two-selector union cascade.**
   The spec must pin which selector wins when both apply. The correct rule: the `@media (prefers-color-scheme: dark)` selector activates the dark variant ONLY when the JS-driven attribute is absent. Implementations: (a) require ThemeProvider to write a paired `.light` class symmetrically, and scope the @media selector with `:not(.light)`; (b) or use the cascade ordering rule where `.dark` and `.light` selectors win over @media via specificity. Add an acceptance criterion: a Playwright test with JS enabled, dark-system, and a programmatically-set light theme MUST render light-variant code blocks. Without this, the v2 fix produces a regression worse than the bug it solved.

3. **Reverse: Req 7.14's "Vitest unit-level coverage is sufficient for production-exclusion."**
   The Vitest unit test verifies the helper in isolation. The production-exclusion contract depends on every consumer calling the helper. A consumer regression (a future PR that imports `#site/content` directly) passes the unit test and ships a draft. Add a lightweight integration check: a Node script that runs `next build` without `BLOG_INCLUDE_DRAFTS`, then asserts `fixture-draft` is absent from `.next/server/app/blog/*` route manifest, the generated `feed.xml`, and the generated sitemap. This is a no-Playwright, no-second-Playwright-build solution that catches the chokepoint-bypass class of bug.

## What's missing — work that should be done before acting on this document

- **Pin Req 9.2's two-selector cascade rule.** Add a concrete CSS-selector spec and a Playwright acceptance criterion for the JS-on + dark-system + light-toggle case.
- **Replace Req 7.11's per-page noindex with a `VERCEL_ENV === 'preview'`-scoped site-wide `X-Robots-Tag` header.** Move per-page directive to defense-in-depth status.
- **Verify Velite's `defineConfig.markdown.rehypePlugins` API in the installed version.** If the key is wrong or the option does not exist, refactor Req 11.7a's shared-array mechanism now, not at Design time. The shared-plugins contract is the spec's structural answer to the v2 plugin-alignment finding; if it is unbuildable, the whole `bodyHtml` story is unbuildable.
- **Add a symmetric Req 7.12 guard for `VERCEL_ENV === 'preview' && BLOG_INCLUDE_DRAFTS !== '1'`.** Throw with a configuration-help message that points at the Vercel env-var scoping UI. Same shape as the existing guard, opposite condition.
- **Add a production-mode build smoke check** (Node script over `.next/` route manifest, RSS XML, sitemap XML — no second Playwright run) that asserts `fixture-draft` is absent from every output. Codify in Req 7.14 as the gap-closing test for production exclusion.
- **Pin Req 6.4's remark plugin parity.** Require the AST extraction pipeline to share the page's `remarkPlugins` array (mirror Req 11.7a's shared rehype mechanism for the remark side). Otherwise GFM-only constructs (tables, task lists) inflate reading time silently.
- **Pin mdast-util-to-string visitor options** (image alt text inclusion, footnote handling) and extend the Req 6.5 fixture to exercise image alt text and at least one GFM construct (table or task list).
- **Set a Req 6.5 fixture-length floor.** ≥1000 prose words (~5 min) so the ±20% bound dominates the ±1-min floor. Below that, regression detection is decorative.
- **Enumerate the fixture roster.** List every fixture post the spec assumes (the draft fixture, the code/parity fixture, the axe-pass fixture set). Decide whether non-draft fixtures are public production content or a separate test-only class. Pin slug names, tags, categories so the Req 13.2 axe-pass route list resolves.
- **Reserve the `fixture-draft` slug explicitly in Req 7.14.** One-line note that the slug is permanently reserved for the testing fixture and SHALL NOT be reused for published content.
- **Add a stateless-plugin-instance acceptance criterion to Req 11.7a.** Shared plugin instances in the array MUST NOT carry state across `(pipeline, file)` invocations. Required because the `rehypeAbsolutizeUrls` hand-rolled visitor (Req 11.8) is a likely state-carrying suspect.
- **Reconsider the Req 11.7 "~30ms per post" build-time cost note.** Either verify the Shiki highlighter is genuinely shared across pipelines (via plugin caching) and document the mechanism, or remove the cost estimate and replace with "build-time cost not characterized; expected to scale linearly with post count and remain acceptable through tens of posts."
- **Extend Req 6.4(b)'s raw-HTML node handling.** Either forbid raw HTML in post bodies (add to Req 3.7) or recurse into HTML node text content. The current silent-drop produces wrong reading times for posts using `<aside>` or `<details>`.
