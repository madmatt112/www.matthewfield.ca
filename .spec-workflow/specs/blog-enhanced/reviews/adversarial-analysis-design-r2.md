## Selected attack surfaces

### 1. wget mirror crawl (`scripts/run-pagefind-crawl.mjs`, v2 §"Crawl orchestration")

The v1 "HTTP-`--site` ambiguity" is replaced with `next start → wget --mirror → pagefind --site ./out`. v2 calls this "Pinned, no verify-during-implementation hedge." It is not pinned in any way that survives a first run.

- **(Novel) Stress-test the wget asset-reject list as a Pagefind-input contract.** The script invokes `wget --reject="*.css,*.js,*.png,*.jpg,*.jpeg,*.svg,*.ico,*.webp,*.wasm" --exclude-directories=/_next,/static`. Pagefind's content extractor reads `<body>` HTML but Next.js routes hydration data, RSC payloads, and inline preload tokens through `/_next/...` URLs. Excluding `/_next` is correct for crawl efficiency BUT the rendered HTML still contains `<link rel="preload" as="script" href="/_next/...">` and `<script src="/_next/...">` tags — wget will print 404-warnings for those (they are in the rejected directory) yet still write the HTML. The `--quiet` flag suppresses these. So far OK. **But:** Next.js 15 with App Router and the `app/(site)/blog/[slug]/page.tsx` server component emits a self-hydrating script chunk that the production build needs to render correctly under JS — and Pagefind reads the SERVER-RENDERED HTML, not the hydrated DOM. Confirm that the SSR HTML reaching wget contains the full prose body, NOT a streaming shell awaiting RSC payload completion. Next.js 15 with React 19 streams progressively; a wget HEAD-then-GET sees the initial flush, which may be a skeleton if the page suspends. Without an explicit assertion that the post page never suspends past the prose, the crawl can index `<article>...loading...</article>`.
- **(Novel) Challenge the assumption that wget reaches all routes.** wget `--mirror` walks links from `/`. The crawl entry point is `http://localhost:${PORT}/` — the site homepage. The homepage in this project (per `src/app/(site)/page.tsx`) is the bio/profile page; it links to `/blog`. From `/blog`, wget can find each `/blog/{slug}`. But will wget reach pages that are ONLY in the sitemap (e.g. a fixture-search post that's `hiddenFromLists: true` and excluded from `/blog`)? The whole point of `fixture-search` is "reachable as a static page so Pagefind can index it, invisible on `/blog`." If `fixture-search` is excluded from `/blog`, from `/feed.xml`, from `/sitemap.xml`, and from taxonomy pages — wget will NEVER discover it. The crawl will not index `fixture-search`. The whole search smoke test (`MATTHEWFIELD-SEARCH-SMOKE`) will fail in CI. This is a P0 bug in the v2 crawl mechanism.
- **(Novel) Stress-test wget's link-following against hash-only anchors and relative URLs.** The blog post body emits absolute URLs via `rehypeAbsolutizeUrls({ baseUrl: siteConfig.url })`. `siteConfig.url` in `src/config/site.ts` is `https://matthew-field.ca` (or similar). wget started against `http://localhost:3013/` will see absolute links pointing at `https://matthew-field.ca/...` in body HTML — wget treats those as off-host links and `--no-host-directories` doesn't help; cross-host links are skipped by default unless `--span-hosts` is set. Result: wget follows the navbar/header links (relative) but NOT body-internal links between posts (absolutized). For Pagefind indexing this may be acceptable since each post page is reached via the nav/index — but verify that the absolutize plugin doesn't rewrite SITE-NAV anchors too (it shouldn't, but the design doesn't pin which links get rewritten).
- **(Novel) Challenge the wget HTML output's URL-vs-filename mapping.** wget writes `http://localhost:3013/blog/foo` to a file `./out/blog/foo` (no extension) or `./out/blog/foo/index.html` depending on flags. `pagefind --site ./out` reads HTML files from that directory tree. Pagefind 1.x expects `index.html` files (or files with `.html` extension) for URL discovery. The design uses `--no-host-directories` but does NOT set `--adjust-extension` (which would append `.html` to extensionless responses). Result: Pagefind sees `./out/blog/foo` (no extension) and may skip it as a non-HTML file. Add `--adjust-extension` OR pin Pagefind's file-discovery rules.
- **(Recurring, escalated) The "pinned, no verify-during-implementation hedge" framing is recurring untruth.** v2 trades one unverified pipeline (`pagefind --site URL`) for a second unverified pipeline (`wget → pagefind --site dir`) that has not been demonstrated against Next.js 15 SSR output. The v1 reviewer's point was: VERIFY against real Pagefind+Next docs before locking. v2 locked a new mechanism without verifying. Escalate severity: do a 10-minute spike running the proposed pipeline against the existing `main` branch BEFORE merging the design. If wget+pagefind doesn't produce a usable index, the design needs a third revision.

### 2. The `Metadata.robots` SEO fix (v2 §Integration Points; `[slug]/page.tsx`)

v2 closes the SEO leak by setting `Metadata.robots = { index: false, follow: false }` in `generateMetadata()` when `hiddenFromLists === true`. Plus the Pagefind crawl is `data-pagefind-body` based, which is unaffected.

- **(Novel) Stress-test the `noindex` vs `data-pagefind-body` contradiction.** A page with `<meta name="robots" content="noindex, nofollow">` is, in Google's view, a page that should not appear in search results. Pagefind's `data-pagefind-body` attribute tells Pagefind to index THAT page's content. So `fixture-search` will be: noindex'd for Google AND indexed by Pagefind. That works for the smoke test. But the contract is brittle: any future "hidden post" added for an OPERATIONAL reason (e.g., a private "thanks for subscribing" page) will be auto-indexed by Pagefind because the design hard-couples `hiddenFromLists` to "still in Pagefind." Pin a SECOND flag for "exclude from Pagefind too" OR pin an explicit policy that `hiddenFromLists` ALWAYS means "in Pagefind."
- **(Novel) Challenge whether `Metadata.robots` actually emits the meta tag in App Router.** Next.js 15 App Router `Metadata` API does emit `<meta name="robots" content="noindex, nofollow">` for `robots: { index: false, follow: false }` — confirmed against Next.js docs. **But the `X-Robots-Tag` HTTP header is NOT auto-emitted by Next.js;** it requires `headers()` config in `next.config.ts`. The existing `next.config.ts` already emits `X-Robots-Tag: noindex, nofollow` for the `preview` environment globally, but does NOT have a per-route header for hidden posts. Google treats `<meta>` and `X-Robots-Tag` equivalently when present, but if the HTML response is fetched without rendering (e.g., a curl from another bot), only the header layer enforces. Add a per-route `X-Robots-Tag` for hidden posts, OR document that `<meta>` alone is sufficient and accept the residual surface.
- **(Compounding) Stress-test the migration runbook step 1's "no behavior change" framing as recurring untruth.** v2's changelog says "step 1 acknowledges the ~40-90s CI duration delta." It does, but the runbook ALSO acknowledges a new behavior consequence: existing `getPublishedPosts()` callers (in `sitemap.ts`, `feed.xml`, `blog/page.tsx`, `getAllTags`, `getAllCategories`, `getPostsByTag`, `getPostsByCategory`) need to be flipped to `getVisiblePublishedPosts()`. The design says "one-line change" for each. But these flips happen in the SAME PR as the schema add (`hiddenFromLists?: boolean`). Step 1 says "merge with `DEPLOY_VIA_CI` UNSET, no behavior change [other than CI duration]." This is false for any reader looking at `/blog`, `/feed.xml`, `/sitemap.xml`, or tag pages — those routes will start filtering `fixture-search` out (which is fine because `fixture-search` will be in the PR's content as a new fixture). The behavior change is internally consistent but it's still a behavior change. Tighten the runbook claim.

### 3. `getPublishedPosts` allow-list verifier (`scripts/verify-getPublishedPosts-callers.mjs`)

v2 introduces a 15-line `git grep` script with a hard-coded `ALLOWED_CALLERS` set to enforce that list-context code uses `getVisiblePublishedPosts()`.

- **(Novel) Challenge the ALLOWED_CALLERS set as incomplete on day 1.** The script lists `src/lib/blog.ts`, `src/lib/blog.test.ts`, `src/app/(site)/blog/[slug]/page.tsx`. But `getPublishedPosts()` is ALSO called by:
  - `src/app/(site)/blog/page.tsx` (line 26) — wait, v2 says "Switches its single `getPublishedPosts()` call to `getVisiblePublishedPosts()`. One-line change." So this caller goes away. OK.
  - `src/app/feed.xml/route.ts` (line 22) — same flip.
  - `src/app/sitemap.ts` (line 28) — same flip.
  - The taxonomy helpers `getAllTags`, `getAllCategories`, `getPostsByTag`, `getPostsByCategory` in `src/lib/blog.ts` call `getPublishedPosts()` directly (`blog.ts` lines 76, 82, 87, 91). The script's allow-list includes `src/lib/blog.ts` so these pass the verifier — BUT the design says "The taxonomy and tag enumeration helpers (`getAllTags`, `getAllCategories`) are updated to source from `getVisiblePublishedPosts()` so `fixture-search`'s `search-test` tag doesn't generate a `/blog/tags/search-test` static page." So the design WANTS them flipped, but the verifier doesn't enforce the flip because the file is allow-listed at the FILE level not the FUNCTION level. The allow-list mechanism cannot enforce "this file may call X but only in certain functions." A future contributor adding a new `getPostsByYear()` helper in `blog.ts` will call `getPublishedPosts()` and skip the visibility filter; the verifier passes; the leak ships.
- **(Novel) Stress-test the verifier under the regex `git grep -lE "getPublishedPosts\\(\\)"`.** The `-l` flag returns file names only. The regex matches `getPublishedPosts()` with literal empty parens — but a future contributor passing an argument (e.g., a hypothetical `getPublishedPosts({ includeHidden: true })`) escapes the grep. Less likely but possible. More importantly, the regex matches comments and JSDoc references — the JSDoc warning ABOVE `getPublishedPosts` itself contains the literal substring `getPublishedPosts()`, so EVERY file with the comment matches. The script will flag any file that merely references the function in a comment. Use `-w` (word boundary) and a more precise pattern; better, use an AST-based check (`tsc --noEmit` + a transform, or `@typescript-eslint` custom rule).
- **(Novel) Challenge wiring the verifier "BEFORE Build 1." Build 1 is the pre-CI verification gate. The proposed step name is `Verify getPublishedPosts callers`. The design says "Wired into CI as a new step BEFORE `Build 1 (with drafts)`." But `verify-ci-topology.mjs` (Req 12.2) enforces ordered step name literals — adding a step requires updating BOTH `ci.yml` AND `verify-ci-topology.mjs`'s allow-list, AND `verify-requirements-coverage.mjs`. The design lists `scripts/verify-ci-topology.mjs` extension for "the seven new step name literals in order" — but this new verifier is an EIGHTH step that isn't enumerated. Pin the exact step ordering including this new step, or the implementer will guess.

### 4. The `aria-live="polite"` per-button regions (v2 `<CopyButton />` §A11y)

v2 reverses the v1 shared-live-region pattern in favor of one `<span aria-live="polite" className="sr-only">` per button.

- **(Novel) Stress-test the per-button live-region count on a code-heavy post.** A long post may have 10-15 code blocks. Each `<CopyButton />` renders its own `aria-live` region. Screen readers (NVDA, JAWS, VoiceOver) cache live-region elements at page load and watch for mutations on EACH. The overhead is small per region but the count is N. More importantly: when a reader navigates the page with a screen reader, every empty `aria-live` region is an empty announcement candidate. Most SRs ignore empty regions, but the test surface is now N×accessibility-tools. The v1 shared-region pattern was wrong for state-collision reasons, but the v2 fix swings to the other extreme. The proper pattern: a single `aria-live` region OWNED BY THE BUTTON THAT WAS LAST CLICKED — i.e., the button writes to a SHARED region but the region's text is debounced/queued. Per-button is correct under ARIA spec but operationally inelegant.
- **(Novel) Challenge the "sr-only" class assumption.** The design uses `className="sr-only"` for the live region. `sr-only` is a Tailwind utility class that visually hides but keeps in the accessibility tree. Verify it exists in the project's Tailwind config / globals.css — the project uses Tailwind v4 (per `package.json`) and `sr-only` is a built-in utility, so this should be fine. **But:** an `aria-live` region with `display:none` or `visibility:hidden` is NOT announced by some screen readers (the W3C spec says regions need to be in the accessibility tree, which `sr-only` preserves via `clip-path`/`position:absolute` rather than `display:none`). Confirm the project's `sr-only` implementation uses the modern clip-path pattern, not the legacy `display:none`.
- **(Compounding) Stress-test the `<CopyURLButton />` "same pattern" claim.** The design says `<CopyURLButton />` follows the same per-button `aria-live` pattern. Good. But the share bar contains FOUR icon links + the Copy URL button. The Copy URL button is the only stateful one. A reader hitting the share bar with TAB will move through five focus targets, one with a live region attached. The other four are plain anchors. This is consistent but the visual/spatial coupling between the announcement and the focused element is not strong — when a reader clicks Copy URL, the announcement fires AFTER focus has stayed on the button. Some SRs interrupt the focus announcement with the live region update. Verify against NVDA at minimum.

### 5. Velite `safeBodyHtml` regex strip of `data-copy-source` (v2 §`<CopyButton />`)

v2 strips `data-copy-source` from `bodyHtml` via a regex on the serialized HTML before RSS render.

- **(Novel) Challenge the regex `/\sdata-copy-source="[^"]*"/g` against base64 content containing `"`. Base64 alphabet is `[A-Za-z0-9+/=]` — no `"` characters. The regex is safe AGAINST current Buffer.toString('base64') output. **But:** if a future contributor changes the encoding to URL-safe base64 (`[A-Za-z0-9_-]`) or adds an `data-copy-source-format` attribute, the regex anchor changes silently. Pin the regex with a test that asserts the post-RSS `bodyHtml` does NOT contain `data-copy-source` for a fixture with non-ASCII source. Without the test, the strip can silently break.
- **(Novel) Stress-test regex strip ordering vs CDATA wrap.** The current `safeBodyHtml`:
  ```ts
  data.bodyHtml
    .replace(/<p>\{\/\*[\s\S]*?\*\/\}<\/p>\s*/g, "")  // strip MDX comments
    .replace(/\sdata-copy-source="[^"]*"/g, "")        // v2 — strip from RSS
    .split("]]>")
    .join("]]]]><![CDATA[>");                          // CDATA escape
  ```
  The order is: MDX-comment strip → attribute strip → CDATA escape. If a code block contains the literal text `]]>` (unlikely but legal in `<pre>` text content), the CDATA-escape pass handles it. But the `data-copy-source` value is base64; base64 doesn't contain `]]>`. The current ordering is correct. **But** the regex `[^"]*` is non-greedy by default with `g` flag — it does not span across attributes. Good. Verify in test.
- **(Novel) Challenge the rehype plugin order's interaction with rehype-pretty-code's `<code class="language-...">` extraction.** v2 says `rehypeCopyButton` runs BEFORE `rehype-pretty-code` so it reads the plain `<code>` text via `hast-util-to-text`. The plugin extracts language from `codeChild.properties?.className` as the first `language-*` entry. But rehype-pretty-code MAY rewrite that className during its own processing. After pretty-code runs, the `<code>` element gets a `data-language` attribute AND its className changes to highlight-related classes. So the `data-code-language` attribute on the wrapper `<div>` (set BEFORE pretty-code) and the `<code data-language="...">` set BY pretty-code may agree or disagree on language. Verify with a test: pin one source of truth.

### 6. `next start` lifecycle vs `wget --mirror` (v2 §Crawl orchestration)

- **(Novel) Challenge the wget timeout / retry behavior.** `wget --mirror` has default timeouts (300s connect, no read timeout). If `next start` hangs serving a request mid-mirror (e.g., a route triggers an unhandled-rejection that leaves the response hanging), wget waits indefinitely. The script has no overall timeout — only the readiness poll has 180s. A hung mirror = a hung CI step until GitHub's job timeout fires (default 6 hours). Add `--timeout=30` to wget invocation OR wrap the whole script in a `Promise.race` against a master timeout.
- **(Novel) Stress-test the "wget walks links from /" assumption against the existing site nav.** `src/components/layout/site-header.tsx` is the nav. wget can only reach pages whose href is rendered in HTML that wget receives. If the nav uses client-side routing for some links (Next.js `<Link>` renders `<a href>` server-side, so this is fine), wget sees the hrefs. **But** the new `<SiteSearch />` trigger is added to the header — and clicking it opens a Dialog. The trigger button isn't a link; wget doesn't reach the dialog content. Not a problem for crawl (dialog is search itself, not content), but verify that the SEARCH TRIGGER doesn't render as a `<a href="#">` that wget tries to follow back to `/#` and creates a self-loop.
- **(Novel) Challenge SIGTERM forwarding on macOS dev environments.** The user runs on Linux/WSL2 (per env). But `pnpm build:search` may be run by contributors on macOS. `node_modules/.bin/next` is a symlink/script on macOS that may or may not forward SIGTERM cleanly. The design picks the binary path "so signals propagate cleanly" — good — but this hasn't been verified against macOS. Low priority; document as "Linux CI runners only" OR test.

## Top 5 risks/gaps

1. **(Novel, P0) `fixture-search` cannot be reached by wget — search smoke test will fail.** The post is excluded from `/blog`, sitemap, feed, taxonomy. wget `--mirror` walks from `/`. There is no link path FROM the navigable site TO `/blog/fixture-search`. Pagefind will not index the fixture; `MATTHEWFIELD-SEARCH-SMOKE` will return zero results; the smoke test FAILS. **Action:** EITHER add an explicit wget URL list (`wget -i list.txt` with `/blog/fixture-search` enumerated) OR generate a hidden sitemap-for-crawl (`/sitemap-crawl.xml`) that wget consumes via `--input-file` OR add an unstyled link from the homepage that says "Hidden test fixture (do not index)" — none of these are in the design. Without this, the entire Pagefind smoke check is dead on arrival.

2. **(Novel, P0) wget output may not be HTML-extension'd, so `pagefind --site ./out` silently indexes nothing.** Pagefind's CLI looks for `.html` files (or directory `index.html` patterns) in the source dir. `wget --mirror --no-host-directories` writes `./out/blog/foo` (extensionless) when the response Content-Type is `text/html` but the URL has no extension. Without `--adjust-extension`, Pagefind sees no `.html` files and produces an empty index. **Action:** add `--adjust-extension` to the wget invocation, verify Pagefind 1.x recognizes the resulting `.html` files, AND assert in `verify-pagefind-no-drafts.mjs` that the index has ≥ 1 entry (it currently only asserts no DRAFT entries appear, not that ANY entry appears).

3. **(Novel) ALLOWED_CALLERS allow-list operates at FILE granularity, not FUNCTION granularity.** Adding a new function to `src/lib/blog.ts` that calls `getPublishedPosts()` passes the verifier because the file is allow-listed. The fixture-search-list-leak prevention is therefore brittle. **Action:** either move taxonomy helpers OUT of `blog.ts` into a new file that is NOT allow-listed (forcing them to use `getVisiblePublishedPosts()`), OR use an ESLint rule that checks the import chain rather than file-level grep.

4. **(Novel) `hiddenFromLists` is overloaded as "exclude from lists" AND "include in Pagefind."** The design hard-couples these two semantics. The flag's name is `hiddenFromLists`; its observable behavior is "hidden in lists, present in search." A future operational hidden post (e.g., a `/blog/thanks-for-subscribing` page) will be Pagefind-indexed by default, surfacing in `MATTHEWFIELD-SEARCH-SMOKE`-style result lists. **Action:** add a second optional flag `excludeFromSearch?: boolean` (default false), OR rename `hiddenFromLists` to `searchOnlyVisible` (more accurate). Either way, document the coupling.

5. **(Novel, recurring-pattern) "Pinned, no verify-during-implementation hedge" is repeated in v2 without verification.** v2 explicitly criticizes v1 for "verify during implementation" hedging on the Pagefind crawl mechanism — then pins a NEW mechanism (`wget + pagefind --site`) that has not been verified against Next.js 15 SSR output, Pagefind 1.x's HTML-discovery rules, OR the actual `fixture-search` reachability problem above. **Action:** run a 10-minute spike: on the current `main` branch, run `next build && next start &; wget --mirror --no-host-directories --adjust-extension http://localhost:3013/; pagefind --site ./out --output-path /tmp/pf` and confirm (a) wget produces .html files, (b) pagefind produces a non-empty index, (c) the resulting index contains at least one known post. If any step fails, the design needs a third revision before tasks land.

## Top 3 conclusions to challenge or reverse

1. **REVERSE: "wget --mirror is the canonical Pagefind input pipeline."** wget's link-walking heuristics, extension-handling, and asset-rejection rules are unverified against Next.js 15's RSC streaming output. A more direct path: keep `next start`, run Pagefind in HTTP mode via `pagefind --site http://localhost:3013` IF that's documented for Pagefind 1.x, OR use Next.js's `output: 'export'` to produce a static-HTML directory directly, eliminating the wget step. The "static export" path is a one-line `next.config.ts` addition (`output: 'export'`) and produces a clean static directory `out/` that Pagefind reads natively. The wget step is engineering overhead for a problem `next export` solves directly. Reverse to: `next build` with `output: 'export'` → `pagefind --site out --output-path public/pagefind`. Verify the existing dynamic routes (none in this project per `force-static`) and edge runtimes (none) tolerate static export.

2. **REVERSE: "per-button `aria-live` regions for `<CopyButton />`."** The v2 fix swings from "shared region with state collision" to "N regions with N×SR overhead." The correct pattern is a single shared region that DEBOUNCES updates (clear region → set after 100ms) so consecutive clicks each announce, OR a single shared region with `aria-atomic="true"` that re-announces on every text change. ARIA spec supports both. Per-button is technically correct but operationally wasteful. Reverse to: single shared `<output aria-live="polite" aria-atomic="true">` element rendered ONCE in the page (e.g., in `[slug]/page.tsx`), updated by all copy buttons via a shared DOM-ref hook.

3. **REVERSE the "noindex meta is sufficient" implicit assumption.** The v2 fix sets `Metadata.robots = { index: false, follow: false }` on hidden posts. This emits a `<meta name="robots">` tag in the HTML. It does NOT emit `X-Robots-Tag` HTTP header. A bot fetching `/blog/fixture-search` via raw HTTP and parsing only headers (not body) misses the noindex signal. Add a `next.config.ts` `headers()` entry that emits `X-Robots-Tag: noindex, nofollow` for `/blog/fixture-search` AND any future hidden post. Pattern: parse the Velite content list at build time, generate the header rules dynamically. Or simpler: hard-code the headers for the KNOWN_FIXTURE_SLUGS set.
