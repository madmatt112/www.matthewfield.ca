# Adversarial Analysis — Playground Design (v2, round 2)

Reviewer stance: principal Next.js/React platform engineer, tasked to break v2 before approval. Every claim verified against the live repo (`/home/mcf/repo/matthew-field.ca`, Next 16.2.2 / React 19.2.4, Tailwind v4 / Lightning CSS, Vitest 4). Round 1 found two hard blockers (sync `params`, `expectLabClose` on a real `color`) and seven softer findings (F3–F9); all were accepted and folded into v2.

**Bottom line up front: v2 genuinely closed both blockers and all seven softer findings — verified, not taken on faith.** The async-params rewrite matches the live `blog/[slug]` route exactly; the container-color flip matches the assertion mechanism already present at `playground-isolation.test.ts:286`. The residual exposure is thinner than round 1: three Novel findings, all Medium/Low, none of which prevent compilation. Two are "the design introduces new code (the sample items, the shared partition helper) but omits a constraint that code must satisfy." One is an overstated "empirically confirmed" claim. I looked hard for a new blocker and did not find one.

---

## Verification of the v2 blocker-fixes (Analysis dimension 1)

### Async `params` — LANDED, exact-match (Recurring → closed)
All three v2 route components and both `generateMetadata` now type `params: Promise<{ slug: string }>`, are `async`, and `await params`. I diffed them against the live sibling `src/app/(site)/blog/[slug]/page.tsx:36-41,65-70`, which uses precisely `params: Promise<RouteParams>` + `const { slug } = await params`. The v2 snippets match. `generateStaticParams` is correctly param-less (returns the array). No residual synchronous `params.slug` survives in any v2 snippet, prose, the integrity test, or the gallery. **Closed.**

### `EXPECTED_CONTAINER_COLOR_RGB = [10,10,10]` + `expectRgbEqual` — LANDED, and better than the design claims (Recurring → closed, with one honesty caveat)
The design's Blocker-2 fix is not merely correct — it matches a mechanism already in the live test. `playground-isolation.test.ts:286` already reads the container color as `expectRgbEqual(before.color, EXPECTED_CONTAINER_COLOR_RGB)` (NOT `expectLabClose`). So "use `expectRgbEqual`, keep the RGB tuple, flip the value" is a one-constant edit to existing, working assertion code. `parseLab` is never on this path. **The serialization claim checks out:** the test header (`playground-isolation.test.ts:17-19`) documents that this toolchain emits `color: #0a0a0a; color: lab(2.75381% 0 0);` for `oklch(0.145 0 0)`, and Chromium collapses the real `color` property to sRGB. `#0a0a0a` = `rgb(10,10,10)`. So `[10,10,10]` is the right value.

**Caveat (Novel, Low):** the design says `[10,10,10]` was "empirically confirmed against the prod build before pinning." There is **no `.next/static/css` build artifact in the tree right now** (`ls .next/static/css/*.css` → no matches), so that confirmation is not reproducible from the current repo state. The value is sound because it is grounded by the committed test-header comment — but the design overstates the provenance ("empirically confirmed … before pinning" implies a build was run and read). Reword to "pinned from the toolchain's documented fallback (`#0a0a0a`), to be re-confirmed against the prod build in the tasks phase," which is what actually has to happen.

### `landingParams`/`embedParams` pure helpers (F3 fix) — LANDED, but they introduced a coverage narrowing
See r2-N1 below. The mechanical fix (test imports `#playground/manifest` only, never a route `page.tsx`) is correct and removes the jsdom hazard r1 flagged. But the helpers are now **tautological** with the route, which under-covers Req 10.1's on-disk intent.

## Top 5 risks / gaps (ranked)

### 1. r2-N1 (Novel, Medium) — The integrity test is now tautological; on-disk route & embed-directory existence is no longer asserted by it.
`design.md:222-227, 547`. F3's fix made `landingParams(items)` / `embedParams(items)` pure functions that **both** the route `generateStaticParams` and the integrity test call. The test asserts `landingParams(playgroundItems)` equals all slugs and `embedParams(playgroundItems)` equals the iframe-only slugs — but it reconstructs that expectation from the **same** `playgroundItems` it is checking. It therefore proves the filter logic, not that `src/app/(playground)/playground/[slug]/embed/page.tsx` exists on disk, nor that the `[slug]` segment is wired.

Req 10.1 reads: "every slug resolves to a `/playground/[slug]` route; every `iframeIsolated: true` slug resolves to an embed route." Concrete failure: an author adds an iframe item, forgets to create (or typos) the `embed/` directory. `embedParams` still returns that slug; the integrity test still passes (it never touches the filesystem); the gap surfaces only at `next build` (the embed `generateStaticParams` enumerates a slug whose route file is absent → no page) and the E2E. The `[slug]` landing is a single dynamic file so it can't go "missing," but the **embed directory genuinely can**, and the test the design points at Req 10.1 won't catch it.

This is acceptable — `next build` + the E2E (`design.md:560-565`) do cover on-disk existence — **but the design presents the integrity test as satisfying Req 10.1's "resolves to a route," which it now does only tautologically.** Fix: add one sentence stating the coverage handoff ("on-disk route/embed existence is covered by `next build` + the gallery E2E; the integrity test covers slug uniqueness/kebab-case + the partition logic"). Tag: **Compounding** on F3.

### 2. r2-N2 (Novel, Medium) — SSR-prerender safety of the two NEW sample items is unspecified, and an SSR throw is a build failure the design doesn't name.
`design.md:320, 364, 374-379`; Error Scenario 1 (`design.md:511-513`). `dynamic(it.load)` is SSR-on (the only legal config in a server component, correctly chosen). At `next build`, the same-page route static-prerenders the `scribble-pad` client component and the embed route static-prerenders the `starfield` client component. Both samples are, by the design's own description, browser-dependent: `scribble-pad` is a `<canvas>` drawing toy; `starfield` is a `position: fixed`, animated, canvas visualization. If either touches `window`, `document`, `canvas.getContext`, `requestAnimationFrame`, or `useRef().current` at **module scope or render scope** (not inside `useEffect`), it throws during the static prerender → **`next build` fails**.

The design specifies these samples but never states the SSR-safety constraint they must satisfy. Error Scenario 1 covers "bad import, type/syntax error" failing the build; it does **not** cover an SSR-time browser-global throw, which is the more likely failure for a canvas toy written by someone who assumes client-only execution. Fix: add a one-line constraint to the sample-item section and the authoring doc — "same-page and embed items are SSR-prerendered; browser-global access MUST be guarded behind `useEffect`/refs, or the build fails." (Alternatively the design could note that an item needing to fully skip SSR has no escape hatch here, since `ssr:false` is illegal in the server-component host — worth stating so an author doesn't reach for it.) Tag: **Compounding** on F4.

### 3. r2-N3 (Novel, Low) — The embed inherits the site `<body>` theme; "standalone, no site chrome" is overstated.
`design.md:370` calls the embed a standalone document with "no site chrome." But `src/styles/globals.css:37-40` applies `body { background-color: var(--background); color: var(--foreground); }`, and the embed renders under the shared root `<body>` with `globals.css` loaded (it's in the root layout). So the embed's body background and default text color **follow the host site's light/dark theme** — it is not a neutral surface. For the `starfield` sample (paints its own full-bleed background) this is invisible, so no sample breaks. But the design's "standalone … no site chrome" framing is inaccurate: the embed has no *layout* chrome (header/footer) but does inherit *body theming* and the Geist font and provider context (the design even says so at `design.md:370` — the two statements are in tension). Fix: reconcile — either "inherits root-layout body theming + fonts + providers, but no header/footer chrome and no `.playground-container` reset," or pin the embed surface explicitly if a neutral background is intended.

(The companion full-bleed concern is **fine**: Tailwind v4 preflight zeroes `body` margin and there is no `max-width`/flex/grid on `<body>` in `globals.css`, so a `position:fixed`/`100vw`×`100vh` starfield fills the iframe viewport without constraint. Verified.)

### 4. F9 carryover (Recurring, Low) — The `#playground/manifest` subpath alias still has no resolving precedent in this repo.
`design.md:88, 233`. The design keeps F9's mitigation ("Vite prefix-substitution resolves subpaths; verified by running the integrity test in the tasks phase"). I re-checked the precedent it leans on: `#site/content` is used **only as a terminal import** repo-wide, and the two chokepoint checkers (`src/lib/build/check-content-chokepoint.ts:27`, `check-projects-chokepoint.ts:17`) **explicitly mark subpath `#site/content/foo` as out-of-scope / non-resolving.** So the repo has **zero** working examples of a `#`-prefixed *subpath* import. Vite `resolve.alias` bare-string prefix substitution does handle `#playground/manifest` → `<root>/playground/manifest`, so this will almost certainly work — but the design's claim that `#site/content` "proves `#` works" is doing more work than the evidence supports for the subpath case. The "verify by running, not just `tsc`" instruction is the correct and sufficient mitigation; keep it, and drop the implication that existing precedent already proves it. Not a defect — a residual implementation risk that must be discharged by running, not asserted.

### 5. First-of-kind-in-repo patterns are unflagged as such (Novel, Low — aggregate).
Three mechanisms the design treats as settled are correct per the framework but have **no existing instance in this repo**, so each is an untested-in-this-toolchain assumption: (a) the `_components` underscore-private App Router folder (`design.md:90, 145` — `find src/app -type d -name "_*"` → none); (b) `next/dynamic` anywhere (r1 already noted zero usage); (c) the `#`-subpath alias (#4 above). The design flags (b) for build-time verification but not (a) or (c) as first-of-kind. Underscore-private folders ARE a documented Next feature (opt out of routing) and will work; this is low risk. But the tasks-phase "verify by building/running" gate should explicitly enumerate all three, not just `next/dynamic`, so none is assumed.

## What checks out (so the implementer doesn't re-verify)

- **`@layer playground` ordering survives moving the CSS import into `PlaygroundFrame`.** This was the memory file's headline round-2 worry. It is sound: `@layer playground;` is **declared** in `globals.css:4` *before* `@import "tailwindcss"`, in the root layout, which always loads above any playground route. A cascade layer's position is fixed at its first *declaration*; `playground.css`'s `@layer playground { … }` only adds *rules into* that already-positioned layer. Importing it deep in the component tree (in `PlaygroundFrame`) does not re-order the layer — the layer still sits below Tailwind's layers, so utilities still win inside the container. No regression.
- **`dynamic(it.load)` type-checks under TS strict.** `next/dynamic` (`node_modules/next/dist/shared/lib/dynamic.d.ts`) is `dynamic<P={}>(opts: DynamicOptions<P> | Loader<P>)`, `Loader<P> = () => Promise<ComponentType<P> | { default: ComponentType<P> }>`. The manifest's `load: () => Promise<{ default: ComponentType }>` (bare `ComponentType` = `ComponentType<{}>`) satisfies `ComponentModule<{}>` with `P={}` inferred. No `ComponentType<{}>` vs `<any>` mismatch. Sound.
- **Relative import path** `../../_components/playground-frame` from `src/app/(playground)/playground/[slug]/page.tsx`: `..`→`playground/`, `../..`→`(playground)/`, so `../../_components/`→`(playground)/_components/`. Correct (off-by-one was the worry; it lands right).
- **`frame` union narrowing** `it.frame && "height" in it.frame` discriminates `{aspectRatio} | {height}` correctly under strict TS. The else-branch `as { aspectRatio: string } | undefined` cast is redundant (TS already narrows) and slightly over-defensive, but harmless.
- **Embed `generateMetadata` `{ title: it?.title }`**: `title: undefined` is valid `Metadata` → falls back to the root template; the component's `notFound()` then renders the 404. Sensible.
- **iframe ratio E2E**: Playwright runs `Desktop Chrome` (1280×720). The `max-w-3xl` (768px) column gives the iframe ~700px width — not clamped. `aspectRatio: "16 / 10"` (string) passes verbatim through React inline styles. The ratio assertion (height ≈ width×10/16 ± tolerance) is stable. F7 fix is sound.
- **Gallery `ThemeToggle`**: it's a client component (`"use client"` in `theme-toggle.tsx`); rendering it inside the server gallery is the standard RSC composition and needs nothing. `ThemeProvider` is in the root layout, wrapping all groups, so the context is present. The gallery does **not** need `"use client"`. Fine. (Minor: the gallery snippet omits the `import { ThemeToggle }` line; trivially correct in implementation.)
- **`notFound()` / `error.tsx` / `dynamicParams=false`**: r1 already confirmed `notFound()` renders `not-found.tsx`, not the segment `error.tsx`. No new interaction; `error.tsx` must be `"use client"` (the design says so), `loading.tsx` may be a server component. Fine.
- **`composes … from global` / `@import url(…)`** added to the leak guard (F8). Not re-mined.

## Top 3 conclusions to challenge / reverse

1. **"The integrity test satisfies Req 10.1 ('every slug resolves to a route')."** (`design.md:547`) — narrow this. Post-F3 it satisfies *slug uniqueness + the partition logic*, but NOT on-disk route/embed existence (which is now tautological with the manifest). State the coverage handoff to `next build` + E2E explicitly, or the design over-claims what the test proves.
2. **"`EXPECTED_CONTAINER_COLOR_RGB = [10,10,10]` … empirically confirmed against the prod build before pinning."** (`design.md:24, 556`) — the value is right, but no build artifact exists to back "empirically confirmed." Reword to "pinned from the toolchain's documented `#0a0a0a` fallback; re-confirm against the prod build in the tasks phase."
3. **"The embed is a standalone document with no site chrome."** (`design.md:370`) — partially reverse. It inherits the root-layout `<body>` theming (`globals.css:37`), Geist fonts, and provider context. Say "no header/footer chrome and no reset wrapper, but it DOES inherit body theming/fonts/providers from the shared root layout" — which is in fact what `design.md:370`'s second half admits, so the "no site chrome" phrasing should be tightened to match.

## What's missing before this design is implementation-ready

- **State the SSR-prerender constraint on the sample items** (r2-N2): same-page and embed items are statically prerendered; browser-global access must be guarded behind effects/refs or `next build` fails — and there is no `ssr:false` escape hatch in the server-component host. Add to the sample section and the authoring doc.
- **State the integrity-test coverage handoff** (r2-N1): one sentence clarifying that on-disk route/embed existence is covered by `next build` + the gallery E2E, not the (now-tautological) integrity test.
- **Reconcile the embed "no site chrome" claim with the inherited `body` theming** (r2-N3).
- **Soften the `[10,10,10]` provenance and the `#playground` subpath-precedent claims** to "verify in the tasks phase," and **enumerate all three first-of-kind patterns** (`_components` folder, `next/dynamic`, `#`-subpath alias) in the tasks-phase build/run verification gate — not just `next/dynamic`.

None of the above is a blocker. v2 fixed everything round 1 raised; what remains is precision on the *new* surfaces v2's relocations and the sample items introduce. If these four notes are folded in, the design is implementation-ready.
