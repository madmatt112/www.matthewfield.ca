## Summary

Implementation cleanly meets the v4 restrictions (two modes, step name exactly twice in ci.yml, three CI wirings, three fixtures, deferred stale-detection note present). Findings are advisory: a few edge-case and ergonomic gaps in the gate and self-tests.

## Findings

### WARNING [hygiene]: countCheckVeliteSteps does not restrict to the `ci` job despite the docstring claim
- **File:** scripts/check-velite-output.mjs:92
- **Issue:** The JSDoc on `countCheckVeliteSteps` says it counts steps 'under the `ci` job', but the implementation iterates `Object.keys(jobs)` and counts across ALL jobs. Today ci.yml has one job so behavior matches; if a future job is added (e.g. a release job) that legitimately also contains a 'Check velite output before tests' step, the invariant would silently accept >2 site-wide while the docstring still claims a per-job count. Either restrict to `jobs.ci.steps` to match the doc, or update the doc to reflect the actual whole-workflow scope.

### WARNING: Default-mode success criterion (`exits 0 against a real Build 1 output`) has no executable coverage
- **File:** scripts/check-velite-output.test.mjs
- **Issue:** Success criteria call out behavior against a real `.velite/projects.json` produced by Build 1, but the self-test suite only exercises `checkProjectsShape` on synthetic inputs and `verifyCiWiring` on yaml fixtures. The end-to-end default-mode path (cwd lookup of `.velite/projects.json`, JSON.parse failure branch, process.exit codes) is not test-covered. A small tmpdir-based test invoking the script via `child_process.spawnSync` would close this gap; otherwise the success criterion relies on a manual run that isn't documented anywhere.
- **Task Requirement:** 1.8

### INFO [hygiene]: `checkProjectsShape` accepts entries with required keys set to `undefined`/`null`
- **File:** scripts/check-velite-output.mjs:67
- **Issue:** The shape check uses `key in entry`, so `{slug: undefined, title: undefined, date: undefined, draft: undefined}` passes. Velite would never emit that, but if the contract is 'these keys exist with valid values', the check is weaker than it reads. Cheap fix: require `entry[key] !== undefined`. Leaving as info because the practical risk is low and the gate is intentionally narrow.

### INFO [hygiene]: Self-tests are not wired into any pnpm script or CI step
- **File:** scripts/check-velite-output.test.mjs:7
- **Issue:** `scripts/check-velite-output.test.mjs` exists but nothing in ci.yml runs `node --test scripts/check-velite-output.test.mjs`, and there is no package.json script for it (per the doc comment, Vitest's include pattern excludes it). The fixtures therefore don't protect the script in CI — only locally on demand. Consider adding a single CI step `node --test scripts/check-velite-output.test.mjs` near the other verifier invocations, or a `test:scripts` pnpm script.

### INFO [hygiene]: `--ci-file` flag is documented in the header but the success criteria don't reference it
- **File:** scripts/check-velite-output.mjs:186
- **Issue:** The CLI advertises `--ci-file path/to/ci.yml`, but no fixture invocation in the self-tests exercises it via the CLI (only the exported function is called directly). Not a defect — just noting that the surface area is slightly larger than the spec demanded; if the flag is load-bearing for future stale-detection it should get a CLI-level test, otherwise it could be removed to keep the script minimal.
