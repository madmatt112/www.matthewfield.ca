## Context
Surfaced by adversarial review r1 of profile-resume/design. Velite only throws on schema issues when `config.strict` is set; `makeContentYamlLoader` exists precisely to provide hard-fail validation for YAML content. Alternatives considered: (a) set `strict: true` globally — rejected for this spec because it changes failure behaviour for the four existing collections at once with an unmeasured blast radius; (b) route all new content through the loader — adopted for skills/education; (c) guard the one remaining frontmatter field with a module-load throw — adopted for profile.mdx `summary`.

DISPOSITION (profile-resume tasks v2, after adversarial r1 of the tasks doc): this deferral's revisit trigger reads "before adding any further constrained field to a plain collection's frontmatter", and profile-resume task 8 adds `summary` to profile.mdx frontmatter. The trigger is deliberately NOT tripped, because `summary` is declared `s.string().optional()` — it is not a constrained field in the schema. All validation lives in `getProfileSummary()` in application code, so no reliance is placed on frontmatter schema enforcement. This was itself a correction: an earlier draft made the field required, which would have aborted the profile collection parse on absence and produced velite's `no data resolved for 'profile' collection` before the guard could ever run.

DISPOSITION CONFIRMED AT IMPLEMENTATION (profile-resume task 8, 2026-08-06): task 8 shipped exactly as designed. velite.config.ts declares `summary: s.string().optional()` with an inline comment stating why, and `src/lib/profile-summary.ts` owns absence, blank, min-length (100) and max-length (600) validation, throwing at module load with the only error message — one that names `content/profile.mdx` and the field. `strict: true` was NOT set; `defineConfig` is untouched. The trigger stands as NOT tripped: no schema constraint was added, so nothing in this task relies on frontmatter schema enforcement. Verified empirically — with `summary` deleted from the frontmatter, `pnpm exec velite build` still exits 0 (confirming the warn-and-ship semantics this deferral records), and the guard is what fails, via Vitest at module load.

The general gap remains: any future frontmatter field that IS constrained in the schema silently inherits warn-and-ship semantics.

## Decision Deferred
Not decided: whether `defineConfig` in velite.config.ts should set `strict: true`. Today it is unset, so a zod failure in a plain (non-loader) collection warns and ships rather than failing the build. profile-resume works around this per-field rather than changing the global setting.

## Revisit Criteria
A `velite build` run has been done and the warning count across pages/profile/posts/projects is known, so flipping `strict: true` can be assessed as a bounded change rather than an open-ended one.
