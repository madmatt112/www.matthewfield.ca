# Adversarial Design Analysis — contributions-and-resources/design.md

Method: every Velite/eslint/CI claim below was verified against on-disk source, and the two load-bearing "corrections" plus the empty-payload mechanics were verified **empirically** by building Velite 0.3.1 against throwaway fixtures (`/tmp/velite-strict-probe`, since deleted). Citations are `file:line` against the actual installed sources.

---

## VERDICT UP FRONT

The design's two named "corrections" are **both correct** — confirmed against source and by execution. But the design rests them on a foundation that is itself broken: **Velite 0.3.1 does not fail the build on zod validation issues unless it runs in strict mode, and this repo runs it non-strict.** The design's entire error-message contract (Reqs 1.4, 3.1, 4.4, 10.1) is delivered through the zod-issue path, which under the repo's actual config produces a *warning and exit 0*, writing the invalid entry to JSON anyway. This single gap invalidates the build-time-validation guarantee that the whole spec is premised on. It is not mentioned anywhere in the design.

## Attack dimension 1 — Correction #1 (per-entry schema vs array schema): CORRECT

- `load` reads `file.records` raw and iterates element-wise: `const isArr = Array.isArray(file.records); const list3 = isArr ? file.records : [file.records];` then `list3.map((data, index2) => { const path2 = isArr ? [index2] : []; ... schema._parse({ data, path: path2, ... }) })` — `chunk-4HFW4XPZ.js:38005-38019`. **Confirmed**: the collection `schema` is applied to *each element*, with the issue path rooted at `[index]`. An `s.array(...)` schema would indeed validate each element against an array schema and fail every entry. Correction #1 is real, not hallucinated.
- Type generation: `dts.push(\`export declare const ${name2}: ${collection.name + (collection.single ? "" : "[]")}\`)` — `chunk-4HFW4XPZ.js:37937`. With `single` falsy, the generated type is `Contribution[]`. **Confirmed.** `single` is read off the collection object; `defineCollection` does not inject a default `single`, so `collection.single` is `undefined` (falsy) when omitted — the `? "" : "[]"` branch yields `[]`. Correct.
- `.min(0)` drop: harmless. Empirically, `[]` survives the loader and produces a written `[]` collection (TEST C below). `.min(0)` was always a no-op.
- No Req text asserts the schema object is literally `s.array(...)` in a test-observable way. The acceptance criteria assert *behavior* (typed array, per-entry validation). Per-entry schema satisfies them.

**Empirical (TEST C/D):** `[]` literal → exit 0, `.velite/things.json` = `[]`. Missing file → exit 0, `.velite/things.json` **still written as `[]`**. So the "file absent → cadence script read throws" worry (prompt dim 5) is **unfounded** — `outputData` only skips when `data == null` (`chunk-4HFW4XPZ.js:37952`), and a non-single collection always resolves to an array, never null.

## Attack dimension 2 — Correction #2 (custom loader for empty-payload): CORRECT

- `VeliteFile.create` fail path: `meta.data = await loader.load(meta); if (meta.data?.data == null) return meta.fail(\`no data loaded from '${path}'\`)` — `chunk-4HFW4XPZ.js:33320-33321`. A loader that returns `{ data: [] }` survives (`[]` is not null); a loader that `throw`s never reaches this line. **Confirmed.**
- A thrown error in `load` propagates: `meta.data = await loader.load(meta)` is un-try/caught; it rejects up through `load` → `resolve3` → `build(...).catch(err => { logger.error(err.message); process.exit(1) })` (`cli.js:59-63`). **Empirically confirmed (TEST B): zero-byte file → `yaml.parse` → null → loader throws → exit 1 with the named message.** The error is NOT swallowed, NOT turned into a per-file warning. Build exits non-zero with a usable diagnostic (the raw `err.message`, untruncated; full stack only with `--debug`).
- Loader resolution order: `loaders: [...loadedConfig.loaders ?? [], ...loaders]` (`chunk-4HFW4XPZ.js:37908`) prepends user loaders, and `config.loaders.find((l) => l.test.test(path))` (`chunk-4HFW4XPZ.js:33317`) takes the first match. The custom `/\.(ya?ml)$/` loader wins over the built-in `yaml_default`. **Confirmed.** The correction does not collapse.
- `yaml` dependency: **it IS a direct dependency** — `package.json:76` `"yaml": "^2.9.0"` (devDependencies, which is correct for build-time-only use; it's already imported by `scripts/check-velite-output.mjs` and `scripts/verify-ci-topology.mjs`). No hidden-dependency risk. The prompt's concern is resolved.
- Collateral YAML interception: `find content -name '*.y*ml'` returns nothing today — the only `.yaml` files will be the two this spec adds. **No existing collateral.** Forward-risk (one line, worth noting in the design): the loader matches ALL `.yaml`/`.yml` under `content/`; any *future* YAML collection added by another spec inherits this envelope contract (null/non-array → throw). That is probably desirable but is an undocumented coupling.

## Attack dimension 3 — Error-message contract and the dropped repo/title locator: PARTLY BROKEN

- `source` construction: `const source = issue.path.map((i) => typeof i === "number" ? \`[${i}]\` : i).join(".")` — `chunk-4HFW4XPZ.js:38023`. For a nested failure this yields `[3].links.2.kind` — **NOT `[3].links[2].kind`.** Array indices in the *middle* of a path are numbers, so they render as `.2.` not `[2]`, because `.join(".")` inserts a dot between every segment regardless of bracket. Only the *first* segment (the entry index) is bracketed-then-dot-joined. The design's claimed `[3].links[2].kind` form (design.md:195, 372) is **wrong**; the real output is `[3].links.2.kind`. Cosmetic, but the design states it as fact and a heading-check-style test asserting the bracket form would fail.
- Filename prepend: `message.name = this.path + ":" + message.name; message.file = this.path` — `chunk-4HFW4XPZ.js:33197-33199`. `this.path` is the **path passed to `load`**, which is `absolute: true` from fast-glob (`chunk-4HFW4XPZ.js:38044`). So `file.message` prepends the **absolute path**, e.g. `/home/.../content/contributions.yaml:[3]...`, NOT the bare basename. The design (design.md:194) claims "VFile.message prepends `contributions.yaml:`". **It prepends the absolute path** — noisy, and not the basename the contract item 1 specifies. The design's own loader works around this for the *loader* errors (it computes `basename` itself), but the *schema-issue* path the contract relies on does not get a basename.
- **The contract cannot be delivered by a per-field zod `errorMap`, and the design's `makeContentErrorMap(file)` signature is impossible.** A collection's `schema` is constructed once at config-module load, before any file is read. zod invokes the errorMap as `(issue, ctx)` during `_parse` (`chunk-4HFW4XPZ.js:38017,38019`) — it never receives the `file`. So `makeContentErrorMap(file)` **cannot close over `file`**; there is no `file` to pass at schema-construction time. The filename therefore *must* come from `file.message` (which gives the absolute path, see above), not from the errorMap. The design's interface `makeContentErrorMap(file)` (design.md:102, 198, 312) is not buildable as written.
- Which contract elements have a home, and which don't:
  - File name (item 1): comes from `file.message` — but as **absolute path**, not basename. **Partial.**
  - Entry locator (item 2): only the bare `[n]` index is reachable (see below). repo/title-preferred form dropped (design's stated decision).
  - Field path (item 3): from `source`, but in `.2.` not `[2]` form. **Partial.**
  - Offending value, enum members, hints (items 4-6): a per-field `errorMap` *does* see `issue.received`/`issue.options` for enum, and the bad value for other codes via `ctx.data` — **but only for the field the errorMap is attached to.** A `.strict()` unknown-key rejection (`unrecognized_keys`) is raised by the *object* schema, not any field, so it routes through the **object-level** errorMap or zod's default, not a per-field one. The design names per-field enum errorMaps and a `superRefine`, but never specifies an object-level errorMap to catch `.strict()` violations with contract formatting. **The `.strict()` unknown-key message (contract example `entry[3]: unknown key 'repoURL'`, requirements line 75) has NO home in the design.** It will emit zod's default `"Unrecognized key(s) in object: 'repoURL'"` with no contract formatting.
- repo/title locator drop: the design's justification ("a field-level zod errorMap has no access to sibling fields") is **true for a per-field errorMap** but the design's own *alternative* — a top-level `.superRefine` on the entry object — **does** see all sibling fields (it receives the whole parsed object). The design uses `superRefine` for `uniqueByKind` already. So the claim "delivering the preference would require a parallel full-entry validation pass duplicating the schema" is **overstated**: a single object-level `.superRefine` could read `repo`/`title` and emit the preferred locator for non-identifier-field failures. Dropping it is a *defensible scope cut*, but the stated technical impossibility is not accurate. The requirements (line 65) explicitly specify the index fallback, so the drop does not violate a test — but the design should justify it as a scope choice, not a Velite limitation.
- `uniqueByKind` superRefine routing: a `superRefine` issue is pushed into `ctx.common.issues` and flows through the same `source`/`file.message` machinery (`chunk-4HFW4XPZ.js:38022-38024`). **Confirmed** it produces a contract-shaped message — subject to the same `.2.`-vs-`[2]` and absolute-path caveats above, **and the same strict-mode gate (dim 4 below).**

## Attack dimension 4 — Chokepoint lint edit and other config edits: PREMISE RIGHT, LANDSCAPE MISCHARACTERIZED

- Current rule is `posts`-only with a hardcoded file allowlist (not a glob): `importNames: ["posts"]` (`eslint.config.mjs:30`) and `files: ["src/lib/blog.ts", "velite.config.ts", "src/__fixtures__/chokepoint-canary.ts", "src/lib/blog.test.ts", "src/app/feed.xml/parity.test.ts"]` with `"no-restricted-imports": "off"` (`eslint.config.mjs:39-49`). **Confirmed.** `src/lib/projects.ts:1` imports `projects` from `#site/content` and is NOT in the allowlist — it passes eslint only because `projects` is not in `importNames`. The design's premise (contributions/resources would be unguarded by eslint with no change) is **correct.**
- **But the design mischaracterizes how `projects` is actually guarded.** `projects` is protected by a *separate* AST-based scanner — `src/lib/build/check-projects-chokepoint.ts` (`const PROJECTS_NAME = "projects"`, line 45) — driven by `src/lib/projects.test.ts` Cases 8-11 with its own production allowlist (`projects.test.ts:312-317`: `src/lib/projects.ts`, `src/lib/projects.test.ts`) and a canary fixture (`src/__fixtures__/chokepoint-canary.ts`) covering 17 import shapes. This scanner is **hardcoded to the `projects` symbol** and does NOT cover `contributions`/`resources`. So the real enforcement story is: `posts` → eslint rule; `projects` → AST scanner + canary; the design's `contributions`/`resources` → eslint rule only. **This is strictly weaker enforcement than `projects` gets**, and the design neither acknowledges the scanner's existence nor explains why eslint-only parity is acceptable. A reviewer expecting parity with `projects` will flag this. (`projects.test.ts` Cases 8-11 are the "canary/sentinel test the design fails to account for" the prompt asks about — confirmed present, and they assert exact allowlist contents at lines 312-317; they will NOT break, because they scan only for `projects` and the design doesn't touch them. But the design should at least name them.)
- Adding `contributions`/`resources` to `importNames` does NOT break `velite.config.ts` — it is in the off-allowlist (`eslint.config.mjs:42`) AND it imports schemas, not collections, from `velite`, not `#site/content`. The new `src/lib/build/*` modules import from `velite`/`yaml`, not `#site/content`, so they are unaffected even without an allowlist entry. **No breakage.**
- Components receive data via props and do not import `#site/content` — confirmed by design intent; the chokepoint is enforced at the route layer. The only files needing the import (and thus the allowlist) are `src/lib/contributions.ts`, `src/lib/resources.ts`, and their `.test.ts` siblings — which the design adds. **Correct.** Note: the design's test files import the *real* collections, whereas `projects.test.ts` uses `vi.mock("#site/content", ...)` (projects.test.ts:4,42) and would not actually need the import at runtime; this is a minor divergence from precedent, not a bug.

## Attack dimension 5 — Sitemap, cadence, CI wiring: MOSTLY OK, ONE CORRECTNESS BUG

- Sitemap: current `routes` array lists `/contributions` (line 11) and `/resources` (line 13) as static `lastModified: now` (`sitemap.ts:7-28`). **Confirmed.** Moving them to computed entries is sound; `getAllContributions`/`getAllResources` have no draft guards or env coupling (unlike `getPublishedProjects`, which calls `checkVercelDraftGuard` and can *throw* in production — these helpers must NOT copy that, and the design correctly does not).
- **`maxOr` string-reduce is correct for ISO dates** *but the design's reduce picks the max while `new Date()` wraps it* — `dates.reduce((a, b) => (a > b ? a : b))` over ISO `YYYY-MM-DD` strings sorts lexicographically = chronologically. Fine. Empty → fallback to `now`. Fine. **However**: `maxOr` is called with `.map((c) => c.date)` — `s.isodate()` emits a date-only string (`YYYY-MM-DD`), and `new Date("2025-01-02")` parses as UTC midnight. Consistent with the rest of the codebase (`sitemap.ts:35` does the same `new Date(post.date)`). No bug.
- Cadence script: structural clone is faithful. `.velite/contributions.json` + `.velite/resources.json` **both exist after Build 2** as plain arrays (TEST C/D: even missing/empty → `[]` written), so `.length` works and the read never throws. The prompt's "file absent → throw" worry is **resolved by source** (`outputData` only skips on `null`, and arrays are never null). **One caveat the design copies from the original:** the existing `check-lighthouse-cadence.mjs:34-38` *fails* if the JSON is missing — but it never is, post-Build-2. Safe.
- **Author-doc check placement is safe**: it reads `docs/`, not `.velite/`. Confirmed it has no `.velite` dependency, so placing it after Lint / before Build 1 (where `.velite` may be stale or absent) is fine. Cadence check after Build 2 is correctly placed.
- **CI topology guards**: `scripts/verify-ci-topology.mjs` asserts an *ordered* list of step-name literals (`ENHANCED_STEPS_ORDERED`, lines ~60-71) each appearing after the previous, plus specific pins (Build 2 env, Clean-for-Build-2 `if: always()`, sentinel ordering). Inserting `check:authoring-docs` between `Lint` (ci.yml:45) and the first ordered literal (`Verify getPublishedPosts callers`) does **not** violate any "X after Y" pin and does not rename any matched literal. **Likely safe** — but the design must run `node scripts/verify-ci-topology.mjs` after the edit to confirm, because the verifier is FATAL on any missing/misordered literal and the design adds *two* new steps plus a self-test step. The design asserts co-location but does not commit to running the verifier.

## Attack dimension 6 — Rendering, a11y, gaps: SEVERAL UNHANDLED STATES

- `contrib-<n>` id uses sorted-output index — matches Req 2.4 "sort first, then assign." Empty branch uses `empty-state-heading`; populated `<h1>` uses `page-heading` — **no id collision** (the empty branch has no `page-heading`-labelled list; the populated branch has no `empty-state-heading`). OK.
- `<ul role="list">`: NOT harmful. `role="list"` is the standard defense against Safari/VoiceOver dropping list semantics when `list-style: none` is applied via CSS. Defensible, even recommended. The `aria-labelledby="page-heading"` wiring is valid and announces "Contributions, list, N items." OK. (Note: the existing `projects/page.tsx:34-35` uses `aria-label="Project gallery"` instead — the design introduces a *new* pattern, not the precedent it claims to "reuse." Minor.)
- Multi-link rail `role="group"` + `aria-labelledby` → the card's `<h2 id="contrib-<n>">`: valid ARIA, and the `<h2>` id is unique per card (index-based). OK.
- **Unhandled / under-specified states:**
  - `language` empty string after the optional pass: schema is `s.string().min(1).max(24).optional()` — `.min(1)` rejects `""`, so a present-but-empty `language` is a build error (correct). But `language: ""` only errors under strict mode (dim 4). Without strict, `""` is written and the card renders an empty badge. **Gap follows from the strict-mode hole.**
  - Two resources with identical `title`+`url`+`added`: the comparator `byAddedDescTitleAscUrlAsc` returns 0 (stable), so both render. No dedup. Acceptable, but undocumented.
  - Category valid but zero entries: `getResourcesGroupedByCategory` omits empty groups (design.md:228, Req 5.6). Confirmed in design; needs the helper to actually filter `entries.length === 0`. Specified, not yet a gap.
  - `links[].label` whitespace-only (e.g. `"   "`): schema is `s.string().min(1).max(60).optional()` with **no `.trim()`** (unlike `title`/`description` which use `.transform(trim).pipe(...)`). So `"   "` passes `.min(1)` and renders as a blank-looking link label. **Genuine gap** — `label` is not trimmed, inconsistent with `title`/`description`.
- Reqs with no corresponding design element:
  - **Req 1.4 / 3.1 / 4.4 / 10.1 (build fails on schema violation): the design describes the message but never wires the *failure* (strict mode). See dim 4 / Top Risk #1. This is the big one.**
  - **Contract item: `.strict()` unknown-key message has no formatting home (dim 3).**
  - Req 2.8 / 5.8 meta description length (50-160 chars): the design names `CONTRIBUTIONS_DESCRIPTION`/`RESOURCES_DESCRIPTION` constants but does not pin the 50-160 bound or any check. Minor.
  - Everything else (Reqs 2, 5, 6, 7, 8, 9, 10) has a corresponding design element.

## TOP 5 RISKS / GAPS (each with a concrete failure scenario)

1. **Non-strict Velite silently swallows every schema violation and ships the bad entry.** Verified empirically: with the repo's config (no `strict: true`, `velite build` with no `--strict`), a `s.string().min(5)` violation on `"x"` produced `[VELITE] issues: ... info String must contain at least 5 character(s)`, then **`build finished`, exit 0**, and wrote `{"title":"x"}` to the JSON. Failure scenario: Matthew commits a contribution with a 3-char `title` (or a 9-scheme `url`, or an unknown `.strict()` key). CI Build 1 and Build 2 both pass green, Vercel promotes, and the broken/under-validated entry renders in production. The design's "every malformed entry is a CI-blocking build error" (design.md:30) is false as built. Fix: set `strict: true` in `defineConfig` (or `--strict` on every `velite build` invocation incl. `postinstall` and ci.yml:119) — **and verify this doesn't start failing the build on *existing* posts/projects content that currently only warns.** This must be designed and the blast radius assessed before implementation.

2. **`.strict()` unknown-key rejections have no contract-formatted message home.** `unrecognized_keys` is raised by the object schema, not a field, so the design's per-field enum errorMaps and `superRefine` never see it. Failure scenario: author writes `repoURL:` (the exact typo in requirements line 75) → message is zod's default `"Unrecognized key(s) in object: 'repoURL'"`, missing the file name, locator, field path, and "did you mean" — directly violating the contract the design claims to satisfy. (And under non-strict, it doesn't even fail — see #1.) Fix: object-level errorMap or a post-parse check.

3. **The error message format the design promises does not match what Velite emits.** `source` renders mid-path array indices as `.2.` not `[2]` (`chunk-4HFW4XPZ.js:38023`), and `file.message` prepends the **absolute path**, not the basename (`chunk-4HFW4XPZ.js:33197-33199`). Failure scenario: a test or author-doc example asserting `contributions.yaml ... [3].links[2].kind` will not match the real `/abs/path/contributions.yaml:[3].links.2.kind`. The contract's item-1 (basename) and item-3 (`[i]` bracket form) are both unmet by the native machinery the design relies on.

4. **`makeContentErrorMap(file)` is not constructible.** The schema (and its errorMap) is built once at config load; zod calls the errorMap `(issue, ctx)` with no `file`. Failure scenario: implementer tries to write `makeContentErrorMap(file)` and discovers there is no `file` to pass — the interface in design.md:102/198/312 has to be redesigned (filename must come from `file.message`, which gives the absolute path, looping back to #3).

5. **Enforcement parity gap + unrun topology verifier.** `projects` is guarded by an AST scanner + 17-shape canary (`check-projects-chokepoint.ts`, `projects.test.ts` Cases 8-11); the design gives `contributions`/`resources` eslint-only protection and never mentions the scanner. Failure scenario: a future route does `import * as c from "#site/content"; c.contributions.map(...)` — eslint `no-restricted-imports` with `importNames` does **not** catch namespace-member access (only named imports of the restricted name), so the chokepoint silently leaks, exactly the shape the `projects` scanner exists to catch. Separately, adding two CI steps without running `verify-ci-topology.mjs` risks a FATAL ordered-literal failure that only surfaces in CI.

## TOP 3 CONCLUSIONS TO CHALLENGE OR REVERSE

1. **Reverse: "every malformed entry is a CI-blocking build error" / the build-time-validation guarantee.** Grounded in `chunk-4HFW4XPZ.js:38053-38056` (`if (config.strict) throw` — the ONLY throw for zod issues) and live execution (TEST A: same fixture exits 1 with `--strict`, exits 0 without). The design must add strict mode and treat it as a first-class, blast-radius-assessed decision, not an unstated assumption.

2. **Challenge: "a field-level zod errorMap has no access to sibling fields, so repo/title locator is impossible without duplicating the schema" (design.md:200).** A top-level object `.superRefine` (which the design already uses for `uniqueByKind`) receives the entire parsed entry and can read `repo`/`title`. The drop is a legitimate scope cut, but the stated *technical impossibility* is false and should be reworded — otherwise it reads as a verified fact that doesn't hold.

3. **Challenge: the implied claim that the existing chokepoint is eslint-only and `projects` is simply "unrestricted."** True for the eslint rule, but `projects` is in fact guarded by `check-projects-chokepoint.ts` + `projects.test.ts` Cases 8-11. The design should either replicate that scanner for `contributions`/`resources` (parity) or explicitly justify eslint-only as sufficient given the single-author threat model — and note that `no-restricted-imports`/`importNames` does NOT catch `import * as c` namespace access, which is the precise hole the scanner closes.

## WHAT'S MISSING (must be resolved before this design is safe to implement)

- **Strict-mode wiring.** Decide and document: `strict: true` in `defineConfig` vs `--strict` on every invocation (`postinstall`, ci.yml:119, and the `next build`-triggered path). Assess whether enabling it flips any *currently-warning* posts/projects content into a hard failure. Without this, the spec's core guarantee is absent. (Top Risk #1.)
- **An object-level error-message hook** that (a) formats `.strict()` unknown-key rejections per the contract, and (b) reconciles the basename/`[i]`-bracket mismatch (Top Risks #2, #3). The `makeContentErrorMap(file)` signature must be redesigned to not depend on a per-file `file` argument (#4).
- **Decision on chokepoint parity**: replicate the AST scanner for the two new collections, or document eslint-only as an accepted reduction — and address the `import * as` namespace-access hole in either case (Top Risk #5).
- **Run `verify-ci-topology.mjs` against the edited workflow** as part of the design's acceptance, since two steps + a self-test are being inserted into a verifier-guarded file.
- **`label` trimming** to match `title`/`description` (whitespace-only label gap), and a one-line pin for the 50-160-char meta description bound.
- **One-line note** that the custom YAML loader now owns the envelope contract for ALL `content/**/*.y(a)ml` files, binding any future YAML collection to the same null/non-array rules.
