# Adversarial Analysis — Playground Tasks (v1)

Reviewer stance: tear down, not validate. Every claim below is checked against the live repo at `/home/mcf/repo/matthew-field.ca` (Next 16.2.2, Vitest 4, the actual `ci.yml`, the actual `playground-isolation.test.ts`). The headline conclusion: the DAG is **mostly** sound and the red-by-construction story for Task 8 holds, but there are **two genuine execution-blockers** (a missing CI-file edit hidden inside "1–3 files," and a `data-testid` hook set that is two hooks short of what the migrated isolation test actually selects), plus several softer gaps. Ranked findings follow.

## Top 5 risks / gaps (ranked)

### R1 — Task 12 silently edits `.github/workflows/ci.yml`, an unnamed file; "1–3 files" and the `File:` list are both wrong (BLOCKER for the task's own `Success`/review)

Task 12 (`tasks.md:161-168`) declares `File: scripts/check-playground-css.mjs (new), scripts/check-playground-css.test.mjs (new), package.json` and its prompt says "a `check:playground-css` package script **wired into CI alongside check:authoring-docs**." But "wired into CI" is not a `package.json` edit. The live CI (`/.github/workflows/ci.yml`) has **no generic aggregator step** that would pick up a new package script for free — every gate is its own explicit step:

- `Check authoring docs` → `pnpm check:authoring-docs` (`ci.yml:48-49`)
- `Self-tests for check-authoring-docs` → `node --test scripts/check-authoring-docs.test.mjs` (`ci.yml:97-98`)

So "run it in CI alongside check:authoring-docs" requires **two new YAML steps** (the production run, and the `node --test` self-test) added to `ci.yml`, plus the `package.json` script. The task lists three files; the real count is four, and the fourth — `ci.yml` — is the one a fresh agent will miss because the body never names it. Concrete failure: the agent adds the script + self-test + `package.json` entry, marks the task `[x]`, and the leak guard **never runs in CI**. Req 10.6 ("leak guard CI") is then unsatisfied while the task reports green, because the task's own `Success:` line only checks `node --test …` and `pnpm check:playground-css` **locally** — it never asserts a CI step exists. This is the single most likely "passes review, doesn't actually do the thing" failure in the breakdown.

Fix: name `.github/workflows/ci.yml` in Task 12's `File:` list and `Success:`, and specify the two steps to add (mirroring `ci.yml:48-49` and `97-98`). Compare to how `check:authoring-docs` is wired — the design's "run in CI alongside check:authoring-docs" phrasing is precisely an instruction to replicate those two steps, but the task never says so.

### R2 — The `data-testid` hook set is two hooks short of what the re-pointed isolation test selects; Task 8 cannot mechanically pass as written (BLOCKER)

The live `playground-isolation.test.ts` selects **six** descendant `data-testid`s plus the container:

- `spike-plain-div-target` (`:185`)
- `spike-shadcn-button-target` (`:221`)
- `spike-tailwind-div-target` (`:245`)
- `spike-token-access-target` (`:314`)
- `spike-button-token-target` (`:370`)
- `spike-ac2-inherit-target` (`:404`)

The design's hook-mapping table (`design.md:415-420`) and Task 3 (`tasks.md:75`) provide **only three** sample hooks: `sample-font-target`, `sample-token-target`, `sample-leak-probe`. That covers `spike-shadcn-button-target`, `spike-token-access-target`, and `spike-ac2-inherit-target`. **Three live selectors have no replacement defined:**

1. `spike-plain-div-target` (`:185-194`) — the "plain div inline styles preserved" test, asserting `color: rgb(255,0,0)` and `fontFamily: "serif"` from an **inline-styled** fixture div.
2. `spike-tailwind-div-target` (`:245-264`) — "Tailwind utilities resolve inside @layer playground," asserting `bg-blue-500` → `EXPECTED_TAILWIND_BLUE_500`, `p-4` → 16px, `text-lg` → 18px/28px.
3. `spike-button-token-target` (`:370-387`) — the shadcn `<Button>` with inline `style={{ backgroundColor: var(--primary), color: var(--primary-foreground) }}`.

Task 8's body (`tasks.md:127`) says "move descendant selectors from `spike-*` to the sample's `sample-font-target`/`sample-token-target`/`sample-leak-probe`" — i.e. it assumes a 3-selector test. But the migration is not 3→3; it is 6→3 unless the scribble-pad sample carries six hooks **or** three of those tests are dropped. The tasks never decide which. A fresh agent doing Task 8 will hit `page.getByTestId("spike-tailwind-div-target")` (still in the file) → timeout/fail, or will delete those tests with no instruction to, eroding the very coverage Req 10.2 says "SHALL NOT regress." Either way Task 8's `Success:` ("the isolation suite passes on /playground/scribble-pad in both themes") is not mechanically reachable from Task 3's deliverable.

This is not hand-wavy: the design's own coverage note (`requirements.md:221`, "reset / token re-declaration / typography / leak behaviors SHALL NOT regress") is contradicted by a 6→3 hook reduction that silently drops the inline-style-preservation test, the Tailwind-utility-in-layer test, and the direct-component-token test. Fix: either (a) Task 3 must enumerate all six (or a justified reduced set with the dropped tests named and their coverage re-homed), or (b) Task 8 must explicitly list which spike tests are deleted vs. re-pointed. As written, the gap lives in the seam between Task 3 (defines 3 hooks) and Task 8 (re-points an unspecified number of tests).

### R3 — `applyDarkMode` hardcodes `localStorage.setItem("theme", …)`; the re-point introduces a latent coupling the tasks never reconcile

`playground-isolation.test.ts:160` sets `localStorage.setItem("theme", "dark")` with a literal `"theme"` key. The live root layout's `ThemeProvider` (`theme-provider.tsx:6,11`) uses `storageKey={THEME_STORAGE_KEY}` where `THEME_STORAGE_KEY = "theme"` — so the literal currently matches. Task 8 says "re-audit `applyDarkMode` for the next-themes hydration path" (`tasks.md:127`) but gives no concrete instruction, and the test's own comment (`:36-37`) still claims "`(playground)` is a route group … served at /spike" — stale once re-pointed onto `/playground/scribble-pad`, which **is** under the root `ThemeProvider` (the spike was too, but the comment's framing was written pre-ThemeProvider-integration).

The real risk: on the spike fixture, `applyDarkMode` was verified to work; on `/playground/scribble-pad` the same-page item is now SSR'd + hydrated under the live `ThemeProvider`, and the "stays light" assertion (`:300`) depends on the container's M1-fixed unlayered `color` winning over an actually-present `.dark` class. If the re-audit is non-trivial (a real hydration race), it is hidden inside Task 8's "re-audit" verb with no budget and no fallback — exactly the kind of open research question §3 warns about. Task 8 is already four edits; this is a latent fifth. At minimum the prompt should pin `THEME_STORAGE_KEY` (import it, as Task 16 is told to) rather than leaving the literal `"theme"` and a vague "re-audit."

### R4 — Task 8's `Success:` smuggles an open research question into a completion criterion (`[10,10,10]` "pin … if the toolchain differs")

Task 8 `Success:` (`tasks.md:132`): "confirm the live post-M1 container `color` serializes to `rgb(10,10,10)` and **pin the exact value if the toolchain differs**." The design is honest that `[10,10,10]` is "pinned from the toolchain's documented `#0a0a0a` fallback … re-confirmed against the prod build in the tasks phase" (`design.md:43,63,590`) — i.e. the value is *not* verified, and the test header itself (`playground-isolation.test.ts:16-27`) documents that Lightning CSS + Chromium serialization is exactly the kind of thing that drifts. So the criterion is: write the assertion, run the prod-build suite, and if it yields e.g. `rgb(10,10,11)` or `rgb(9,9,9)`, edit the constant to match. That is a **verify-then-edit loop inside one "atomic" task** whose four edits already "must all land in one commit." Concretely: the prod E2E run that confirms the RGB requires Tasks 6 (route builds), 8's own layout/CSS edits, and a full `next build` + `pnpm start` — so the agent can only discover the true value *after* doing the breaking edit, and if it differs there is no guidance on whether `expectRgbEqual`'s exact-integer match (`:134-138`, `toBe`, no tolerance) is still appropriate or whether a near-match helper is needed. `expectRgbEqual` uses `toBe` (exact), so a 1-LSB serialization difference fails hard. This is a real fragility, not a theoretical one — the whole point of the test file's 30-line serialization preamble is that this value is toolchain-sensitive. The criterion should be split: (a) implement the flip using `[10,10,10]` as the hypothesis, (b) a *separate, explicit* sub-step "run prod E2E, read the actual serialized `color`, pin it" with a stated tolerance policy.

### R5 — Req 1.2 "single source / no parallel list" has no task that would *catch* a future parallel list; the matrix overclaims coverage

The Requirements Coverage Matrix (`tasks.md:221`) maps Req 1.2 ("single source — gallery, both gSP, loader derive; no parallel hand-maintained list") to tasks 5, 6, 7, 9. But those tasks only *establish* the single source — none of them, nor the integrity test (Task 11), would **fail** if a future contributor hand-listed a slug in the gallery or sitemap instead of deriving it. The integrity test (Task 11, `tasks.md:154`) asserts slug uniqueness, kebab-case, the partition helpers, and `fs.existsSync` of each item folder — all *manifest-internal*. Nothing asserts that the sitemap, gallery, or `generateStaticParams` actually *derive* from `playgroundItems` rather than carrying a parallel list. So Req 1.2's "never a parallel list" is **asserted by construction, not gated** — honestly it is an "M"/convention, but the matrix lists four task numbers as if mechanized. This is the §4 "is there a task that would catch a future parallel list, or is it just asserted?" probe, and the answer is: just asserted. Low severity (the design is right that this is mostly a structural discipline), but the matrix should mark it partial/convention rather than implying four tasks gate it.

## Top 3 conclusions to challenge or reverse

### C1 — "Each task touches 1–3 files" is false for Task 12 and misleading for Task 8

Task 12 is four files once `ci.yml` is counted (R1). Task 8 is four files **plus** a 413-line test rewrite plus a verify-then-pin loop (R4) plus a possibly-nontrivial `applyDarkMode` re-audit (R3) — calling it one atomic task is *correct for the cascade reason* (the four edits genuinely must co-land, per `tasks.md:5,121-132`, and I verified `/spike` has no external importers — only its own `page.tsx → ./spike-overlays` and the isolation test's `SPIKE_PATH`, so deleting it breaks nothing else), but the "1–3 files" framing undersells the cognitive load and the hidden verify loops. The atomicity claim survives; the *sizing* claim does not. Recommend keeping Task 8 atomic but explicitly enumerating the test-rewrite as the dominant sub-effort and pulling the RGB-pin into a named verification step.

### C2 — "Task 8 is the only breaking change and the tree is green before/after every task" — true, but for a reason the doc half-states

§1's stress test: after Task 6 lands (`/playground/scribble-pad` route renders `<PlaygroundFrame>`) but before Task 8 (group layout still wraps), the same-page route is wrapped by **both** the group layout's `.playground-container` (`layout.tsx:5`) **and** `<PlaygroundFrame>`'s `.playground-container` — a double `all: initial` nest. Is that red? I checked: no test points at `/playground/scribble-pad` until Task 8 re-points the isolation suite (Task 16 also touches it but depends on 8). `next build` (Task 6 `Success`) only requires the route to *prerender without error* — nested `.playground-container` divs are valid CSS/HTML and SSR fine; `all: initial` on an inner div re-resets from the outer's baseline, which is cosmetically odd but **not a build error**. So the green-before/after claim holds. **But** the doc's justification ("no test points at it yet") is the load-bearing reason and it is only stated implicitly in the route↔E2E coupling note (`tasks.md:48`). One real wrinkle the doc misses: Task 6's `Success` says `next build` "prerenders both `/playground/scribble-pad` … with NO error — proving `next/dynamic` SSRs." Under the double-wrap, the scribble-pad *content* renders inside two resets — the SSR prerender still succeeds (the assertion is "no error," not "renders correctly"), so the criterion is technically met, but anyone eyeballing the page between Task 6 and Task 8 sees a doubly-reset surface. Not a blocker; worth a sentence so a reviewer doesn't flag the intermediate visual as a regression.

### C3 — Task 16's axe pass is in-scope, but the matrix mis-cites its requirement basis

Challenge from §2: does axe belong in Task 16, and did the spec mandate it as blocking? Yes — `requirements.md:288` ("WCAG 2.1 AA violations on the new playground pages are **blocking** issues (cross-spec accessibility convention)") and the NFR Accessibility row both make it blocking, and the design's Testing Strategy doesn't list axe explicitly but the NFR does. The task correctly scopes axe to gallery + iframe-landing and exempts the same-page toy surface (`tasks.md:205`), and the `blog-axe.test.ts` conventions it copies are real (verified: `AXE_TAGS` at `:24`, `setupTheme`/`assertTheme` local, `THEME_STORAGE_KEY` imported at `:4` from `theme-provider`, which exports it at `:6`). So the axe pass is legitimately mandated and the leverage is accurate — **do not** descope it. The challenge that *fails*: Task 16 bundling render + sizing-ratio + 404 + embed-a11y + console-clean + axe across five page types in two themes is a lot for "one reviewable task," but it is a single test file with cohesive setup; splitting it would fragment the shared `setupTheme`/prod-server fixture. Keep it whole. The only real defect is bookkeeping: the matrix (`tasks.md:273`) cites "NFR Accessibility → 16 (axe …)" correctly, but Task 16's `_Requirements` footer (`tasks.md:208`) lists "10.3, 3.2, 4.5, 4.6 (+ NFR Accessibility)" while its body also delivers 10.4 (prod-build) and the console-clean check that backstops 7.4 — minor under-citation, not a coverage hole.
