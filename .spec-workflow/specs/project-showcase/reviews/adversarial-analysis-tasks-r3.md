## Targets attacked

### Target 1 — Task 6.5's `verify-paired-merge.mjs` gate is itself enforcement-by-prose at the seam (**Compounding** — extends r2 Target 1)

V3 closes r2 Target 1 by adding Task 6.5: a CI script that reads `git diff --name-only origin/main...HEAD` and fails when a strict subset of `{src/__tests__/next-config-imports.test.ts, next.config.ts, src/lib/project-errors.ts}` is touched. This shifts paired-merge from prose to tool gate — a real improvement. But the gate itself depends on conventions that are not themselves gated.

- Challenge the claim that "all-or-none" closes the revert case. A `git revert` of Task 7's commit alone on `main` produces a new commit whose diff vs. its parent touches only `next.config.ts` (the revert's content). When that revert is pushed directly to `main`, the script's "non-PR push (e.g. push to main directly), the script no-ops with a one-line 'non-PR context — skipping' message" explicitly bypasses the check. The revert case the r2 review flagged — "a post-merge revert of Task 7's commit alone restores the red-on-main window" — is **not** closed by 6.5; it is explicitly excluded. The v3 revision history claims 6.5 closes r2 Target 1; the script's own no-op path concedes the closure is partial.
- Stress-test the file-set hard-coding. Task 6.5's script encodes THREE filenames literally: `src/__tests__/next-config-imports.test.ts`, `next.config.ts`, `src/lib/project-errors.ts`. If a future refactor renames any of these (e.g. moves `project-errors.ts` to `src/lib/errors/project.ts`), the script's "all-or-none" rule silently degrades — none of the three named files is touched, the rule's "none" branch fires, the gate exits 0 even though the test/config/errors trio is actually being modified at the new paths. The same enforcement-by-prose pattern r2 flagged (canary-regex pair-update) now lives inside the verifier itself: extending the verifier requires updating two literal arrays in lockstep.
- Stress-test the asymmetric pair definition. The script verifies a TRIPLE: test + config + project-errors. It omits `src/lib/blog-errors.ts` from the set, even though Task 6's contract test asserts blog-errors's named exports too (`BLOG_DRAFT_LEAK_GUARD_MSG_PRODUCTION` etc.). A PR that renames `BLOG_DRAFT_LEAK_GUARD_MSG_PRODUCTION` in blog-errors and updates the test in the same PR — but does NOT touch project-errors or next.config — passes the gate (only test file in the set is touched, "strict subset" rule fires, exits non-zero). Wait — re-reading: the rule is "ALL of {A, B, C} must be present, OR NONE." A blog-errors rename touches A (the test) only — strict subset → fails. Good, the rule catches it. But the diagnostic says "missing paths: `next.config.ts`, `project-errors.ts`" which is the WRONG diagnostic — the actual missing path is `blog-errors.ts`. Reviewer reading the failure may modify the wrong file. The gate's UX misleads on a real failure mode.
- Stress-test the merge-queue / squash-merge interaction. GitHub's squash-merge collapses a PR's commits into one before applying to `main`. The script reads `git diff --name-only origin/main...HEAD` — what is `HEAD` in the squash-merge preview? If a developer rebases the PR's branch and force-pushes, the diff base may move. The Task 6.5 body says "with `GITHUB_BASE_REF` to derive the base ref" but does not specify whether `GITHUB_BASE_REF` is set on `pull_request` events vs. `push` events vs. merge-queue events. In a merge queue, the gate may run against a base ref that already contains some of the changes (because the queue rebased intermediate PRs in), inverting the all-or-none result silently.
- Reject the claim that 6.5 closes r2 Target 1. It closes the merge-time case for the canonical file paths under non-rename conditions on standard `pull_request` events. It does NOT close: (a) post-merge reverts on direct push to main (explicit no-op), (b) file-rename refactors (silent degradation), (c) the blog-errors counterpart in the import surface (mis-diagnosed), (d) merge-queue / squash interactions (under-specified). The closure is real but narrower than the revision history claims.

### Target 2 — Task 14.3 Case 13 still under-specifies the bypass surface and over-relies on regex-on-source (**Compounding** — extends r2 Target 2)

V3 replaces v2's four-pattern regex with a paired assertion: (a) positive shape regex `/updated:\s*s\.isodate\(\)\.optional\(\)/` on `velite.config.ts` source, and (b) widened negative grep `/git[- ]?log|git\.log\(|simple-git|git-log-fast|child_process[^,]*git|require\(['"]git['"]\)|import\(.*git.*\)/i`. The positive shape assertion is the better closure direction; the negative grep widening is still bypass-able and bolts on more regex maintenance burden.

- Challenge the positive-shape regex's resilience. `/updated:\s*s\.isodate\(\)\.optional\(\)/` matches only the literal sequence `updated: s.isodate().optional()`. Acceptable variants that semantically do the same thing fail the regex: `updated: s.isodate ().optional()` (space before paren — uncommon but legal), `updated: s.isodate().optional().describe("...")` (chained `.describe()` — common Zod pattern, semantically equivalent, breaks the literal anchor), `updated: s.optional(s.isodate())` (different style — Zod allows it). The first time a reviewer adds `.describe()` to document the field, Case 13 fails and the developer's likely response is to weaken the regex — eroding the assertion.
- Stress-test the schema-block extraction. Case 13's prompt says "locate the `projects` collection's schema block (between `projects:` and the next top-level collection or the close of `defineConfig`)." The "next top-level collection or close of `defineConfig`" boundary is parsed by regex on `velite.config.ts` source. If `defineConfig` is wrapped (`export default withSomething(defineConfig({...}))`) or if `projects:` appears inside a comment or string elsewhere in the file, the boundary detection misfires. The task body does not specify whether the extraction is a Zod-AST walk (parses `velite.config.ts` with the TypeScript compiler) or a regex slice. Defaulting to regex slice repeats the v2 fig-leaf criticism inside the v3 closure.
- Stress-test the widened negative grep's coverage. The new regex `/git[- ]?log|git\.log\(|simple-git|git-log-fast|child_process[^,]*git|require\(['"]git['"]\)|import\(.*git.*\)/i` covers more shapes but still misses: dynamic `import` via variable (`const m = "git-log"; await import(m)` — the regex matches `import(.*git.*)` only when "git" appears literally in the import call expression's source text), `node:child_process` (the `[^,]*git` clause requires "git" within a non-comma-containing run after `child_process`, but `import { execSync } from "node:child_process"` followed elsewhere by `execSync("git log ...")` splits across two lines/expressions), `fs.readFileSync(".git/...")` (filesystem direct read of git metadata — not in regex), and arbitrary npm packages that wrap `git log` (`@some-org/git-history`, `isomorphic-git`, `nodegit`). Defense-in-depth widens but does not close.
- Stress-test the positive/negative tension. The task prompt says "Case 13 carries BOTH the positive shape assertion AND the widened negative grep." The positive shape catches "the schema field's declaration is not the literal we expect" — which is one signal. The negative grep catches "imports/calls of git-related packages exist" — a different signal. The positive shape's stronger framing (assertion about WHAT the schema is) suggests the negative grep should be retired, not paired. Keeping both encodes both a narrow positive signal AND a noisy negative signal; the test now fails when ANY change adds a comment containing "git log" (e.g., a developer comment `// see git log for historical context`) — false positive.
- Reject the framing that Case 13 verifies Req 1.5. Req 1.5 says `updated` is author-controlled — set in frontmatter, not derived from git history. The test verifies a proxy: "the schema declaration matches an expected string" plus "the config file does not import git packages." Neither verifies the AC at the build-output level. A genuine verification would: (a) build the fixture, (b) assert `.velite/projects.json`'s `updated` field for the published fixture equals the frontmatter value verbatim, (c) assert no transformation step ran (perhaps by mutating the fixture's git commit date and re-asserting `updated` unchanged). Case 13 verifies the implementation surface; the actual AC is one indirection removed.

### Target 3 — Task 28.4's GitHub Action firing mechanism is wired to the wrong trigger (**Novel**)

V3 pins Option C and ships three artefacts: `scripts/check-lighthouse-cadence.mjs`, `docs/projects-showcase-lighthouse-runs.md`, `.github/workflows/lighthouse-cadence.yml`. The workflow trigger is `push to main paths: 'content/projects/**/*.mdx'`. This is a real improvement over v2's prose pin — but the chosen trigger does not gate the cadence event correctly.

- Challenge the trigger choice. The cadence is "every 3rd published project triggers a Lighthouse re-run." A `push` event on `content/projects/**/*.mdx` fires on ANY mdx change — adding a project, editing a project's body, fixing a typo, renaming a slug. The script's check (`(current_count - last_count) >= 3 AND current_count % 3 === 0`) filters at counting time, not at trigger time — so the workflow fires for every mdx edit, runs the script, and exits 0 most of the time. Each non-cadence edit produces a green CI run for the cadence workflow. Over time the workflow's signal degrades because most runs are no-ops; reviewers ignore it.
- Stress-test the "draft: false" counting. The script counts `.mdx` files where `draft: false` or `draft:` absent. A fixture project (Task 19's `fixture-placeholder.mdx` is `draft: true`; `fixture-published-second.mdx` is `draft: false`) counts as 1 published. The launch state has 1 published fixture. Adding a real first project pushes the count to 2. Adding the second real project (count = 3) fires the cadence alert. But Task 19's fixtures live in `content/projects/` — the script does NOT exclude fixtures. The cadence counts fixtures as real projects. This is wrong on its face: a Lighthouse re-run should fire after the 3rd USER-FACING project, not after the 3rd file including the fixture. The task body does not address fixture exclusion.
- Stress-test the regex frontmatter parse. The script uses "regex grep on `draft:` line — a Node-builtin-only approach to avoid an external YAML dep." This is brittle: an mdx file with `draft: false` in a code fence (an author-doc example of how to write `draft: false`) counts as `draft: false`. An mdx file with `\ndraft: true\n` after the closing `---` (placed in the body by accident) gets miscounted. The fixture-published-second.mdx is `draft: false` — the script counts it. The author doc's `projects-authoring.md` is not in `content/projects/` so it's excluded from the readdir, but the precedent of regex-frontmatter-parsing is set, and future maintenance is exposed to the YAML-parsing brittleness the team chose to skip.
- Stress-test the workflow's first-run verification. Task 28.4 marks complete when "the workflow's first run on a `main` push completes (a one-line verification: paste the workflow-run URL into the implementation log)." First-run success means the script exited 0 (no cadence alert at launch with 1 published project). It does NOT verify the script EXITS NON-ZERO when the cadence should fire. A typo in the script's modulo arithmetic (`current_count % 3 === 0` vs. `current_count % 3 == 0` — both work in JS, but `(current_count - last_count) >= 3` is subtly different from "every 3rd published project") would not surface at first-run because count = 1 trivially exits 0. The success criterion does not include a positive-case test (manually push the count to 3 in a feature branch and verify the workflow fires red).
- Reject the framing that 28.4 closes r2 Target 4. r2 said the [x] should commit to a firing mechanism. v3 picks Option C and wires it. The wiring is real. But the trigger is over-broad (fires on every mdx edit, signal degrades), the count semantics include fixtures (off-by-N), and the first-run success criterion does not exercise the positive case. The closure is structural (an Action exists) but not functional (the Action fires correctly when the cadence event occurs).

V3 adds `fixture-published-second.mdx` (draft: false, earlier date) to give Task 25's reverse-chrono assertion a non-degenerate case. Task 27's draft-handling assertions are now parameterized on PROJECTS_INCLUDE_DRAFTS but the fixture set still under-exercises the contract.

Off-by-zero, but the grep-counts-frontmatter-occurrence approach is the wrong substrate for the assertion. ### Target 5 — Task 19.5's pretest gate runs in CI but tests the wrong invariant (**Compounding** — extends r2 Target 3)

V3 adds Task 19.5: a CI step that fails when `.velite/projects.json` is missing, paired with the v3 skip-if-absent gates `process.env.CI !== "true"`. The two-tripwire model is real defense-in-depth — but the script's invariant is narrower than the actual failure mode.

- Challenge the "parse-as-array" check. The script reads `.velite/projects.json` and "assert it is an array; if non-empty, assert each entry has the keys `slug`, `title`, `date`, `draft`." This catches a wholesale shape regression. It does NOT catch: (a) an empty `.velite/projects.json` written by a Velite build that completed successfully but had zero matching files (e.g., if `content/projects/` is empty due to a path-pattern regression, the file is an empty array — the script passes); (b) `.velite/projects.json` written by a stale build whose source files were since deleted — file exists, shape valid, but doesn't reflect current source; (c) a build that ran but emitted the file at a different path (e.g., a Velite config change moves outputs to `.velite/output/projects.json`) — the gate fails on absence, but the diagnostic blames the user ("run `pnpm velite build`") when the actual problem is config drift.
- Stress-test the dual-build CI step duplication. The task body says "add an identical step between Build 2 (production-mode) and the verify step." TWO identical steps in `ci.yml` — both named "Check velite output before tests." YAML uniqueness rules tolerate this (steps are list items, not keyed map entries), but the duplication is fragile: a future CI refactor that combines or reorders Build 1 / Build 2 stages may delete one of the two steps and not realize the other was the load-bearing one for the other build. The task does not pin "BOTH duplicated steps in CI" as a structural invariant verified by anything; it's two literal copy-paste lines.
- Stress-test the in-test second-tripwire. The skip-if-absent gates in Tasks 9, 25, 26, 27 are now gated on `process.env.CI !== "true"` — so under CI, absent file = loud failure. But the failure is `expect(fs.existsSync(...)).toBe(true)` (or equivalent) in each individual test suite. Each suite's failure produces its own error. If 19.5's pretest gate already failed (exit non-zero), the test step never runs — so the second tripwire is dead code under the canonical failure mode (the pretest gate caught it first). The "second tripwire is a tripwire for the case where a CI step deletes the file BETWEEN the gate and the tests" case is real but narrow; the bigger uncovered case is "the gate passed because the file exists but is stale" (gate passes, tests run, fixtures have rotated, assertions misfire).
- Reject the framing that 19.5 + the CI-gate-skip closes r2 Target 3. r2 Target 3's core concern was "skipped tests collapse to passed in CI summaries — operationally indistinguishable." v3's response makes the SUITE fail loud under CI (good). But it does NOT address the original signal-to-noise concern: CI summaries still show "test ran and passed" for tests that run; "the suite failed because a precondition was missing" is a DIFFERENT failure mode from "the test itself ran and verified the production behavior." The Lighthouse score for `/projects` being verified, for instance, requires the test to actually run — not for a pretest gate to fail. If the gate fails for an unrelated reason (e.g., a flaky CI step deleted `.velite/`), the actual production assertion was never exercised. r2's concern was about the green-when-broken WINDOW; v3 narrows it but does not eliminate it.
- Compounding consequence with Target 1: the verify-paired-merge gate (6.5) and the velite-output gate (19.5) are now BOTH CI-side scripts with hardcoded file paths. Each one extends the "enforcement-by-prose at the seam" pattern noted in Target 1. The pattern is now established for two gates; future specs will adopt it; rename-resilience is a known weakness without a closure plan.

## Top 3 conclusions to challenge or reverse

1. **Reverse the "r2 Target 1 closed by Task 6.5" framing.** The script's no-op on direct-push-to-main is an explicit concession of the revert case the r2 review flagged. Either (a) extend the script to also enforce the pair when a single-commit revert-shaped diff appears on `main` (touching one of the three paths without the other two AND being a revert per `git log -1 --grep=Revert HEAD`), or (b) update the revision history to acknowledge the closure is merge-time only and accept the residual revert-time risk explicitly.

2. **Reverse the "negative grep + positive shape catches Req 1.5" framing in Case 13.** The actual AC is build-output-level: `.velite/projects.json`'s `updated` for a fixture project equals the frontmatter value verbatim regardless of git history. Replace both regexes with a runtime assertion: write a fixture with `updated: "2025-01-01"`, run velite, assert `.velite/projects.json` shows `updated: "2025-01-01"`. Then mutate the fixture's git commit timestamp via `GIT_COMMITTER_DATE` and assert the value is UNCHANGED. This catches every bypass shape — the test is shape-agnostic about the implementation. Retain ONE of the regexes (positive shape preferred) as defense-in-depth, not as the primary signal.

3. **Reverse the Task 28.4 trigger choice.** `push to main` on every mdx edit fires too often. Replace with: (a) a `workflow_dispatch` trigger so the cadence is checked on-demand, plus (b) a step in the existing CI workflow (the same workflow that runs the dual-build + tests) that runs the cadence script as a final step — gating the cadence check on the same cadence as the build itself. The cadence alert appears in normal CI runs; no separate workflow that fires noisily on every edit.
