# Adversarial Analysis — blog-enhanced/requirements.md (v2)

Primary attack surface: **completeness, ambiguity, scope**. v2 has resolved most of v1's structural issues (Vercel topology pinned to Req 0, promotion mechanism dropped, slug-derivation centralized, fixture-search published). This review targets the NEW surface area v2 introduced and the residual ambiguity in clauses v2 touched but did not fully close.

Each finding is classified **Novel** (not in v1), **Compounding** (deepens a v1 finding), or **Recurring** (v1 finding not actually resolved — severity escalated).

---

## Section A — Requirement 0 (Vercel deploy migration) — NEW surface, NOT fully de-risked

Req 0 was promoted from NFR-defer to a top-level requirement in v2. That was the correct move. The remaining problem is that Req 0 was written as if "decide CI-driven deploy" closes the topology question — it does not. Req 0 introduces a one-way migration that the spec does not stage safely.

- **[Novel] Challenge the claim in Req 0.3 that disabling Vercel auto-deploys via the dashboard is a "one-time operator step" timed to the spec's PR merge.** The migration plan is: (a) merge the PR that adds `vercel deploy --prebuilt` to CI, (b) then disable auto-deploys. But on step (a) merge, BOTH CI's new deploy step AND Vercel's still-active auto-deploy will fire for the merge commit, racing each other. Whichever finishes last wins. There is no specified ordering — the spec must require disabling auto-deploys BEFORE the merge (which then breaks any pre-merge rollback because the dashboard switch is already flipped), or it must accept a race window. Neither is acknowledged.
- **[Novel] Stress-test Req 0.3's rollback procedure**: "re-enable Vercel auto-deploys via the dashboard AND comment out the `vercel deploy` step in `ci.yml`." This requires a human to perform TWO coordinated actions when CI deploys have just failed. The dashboard is a separate UI from the repo. There is no atomic rollback. If only one action is taken (dashboard re-enabled but `ci.yml` not edited; or vice versa), the result is either double-deploys or no deploys. Add a single-action rollback (e.g., a feature flag in CI that defaults to "use Vercel auto" and is flipped per-branch), or accept the manual-coordination risk explicitly.
- **[Novel] Attack Req 0.6's "no automatic failover to Vercel-direct-deploy" stance combined with Req 13.1's "pre-merge smoke check" pre-condition.** The pre-merge smoke check requires the `VERCEL_TOKEN`, `VERCEL_PROJECT_ID`, `VERCEL_ORG_ID` secrets to be set on a throwaway branch BEFORE merge. GitHub Actions secrets at the repository level are visible to PRs from forks only if the workflow opts in — but they're visible to branches in the same repo, which is the scenario here. The risk is: who creates these secrets, what's their rotation cadence, who's the recovery contact when the token expires? Req 0 and Req 13.1 require these secrets exist; neither specifies ownership or rotation. A Vercel token expiry silently fails every future deploy until detected. Add an ownership/rotation requirement or accept that secret expiry is an unmonitored failure mode.
- **[Novel] Challenge Req 0.4's "Build 1 preview path remains intact for draft-content preview but does NOT produce a Pagefind index."** Per Req 0.3, preview deploys now come from `vercel deploy --prebuilt` on non-`main` branches. But Build 1 ran in `BLOG_INCLUDE_DRAFTS=1` mode — what does Build 1 deploy TO? Before this spec, Build 1 was a CI verification step only (produced artifacts, no deploy). After this spec, the CI pipeline runs Build 1 + Build 2. Does Build 1 ALSO `vercel deploy --prebuilt`? If yes, two preview URLs ship per PR (with and without drafts) — Req 0 does not specify this. If no, then draft authors lost the Vercel-preview-on-PR affordance they had under the Vercel-auto-deploy model. The spec needs to state which Build deploys to the preview URL — currently silent.
- **[Compounding/v1 Section D] Stress-test Req 0.2's `vercel build` step.** The sequence is `next build → next start (bg) → pagefind crawl → kill next start → vercel build → vercel deploy --prebuilt`. The `vercel build` step internally runs `next build` AGAIN (it doesn't reuse the prior build output by default — `vercel build` is a full build that produces `.vercel/output`). So `next build` runs twice per CI run. The Pagefind index from the first build's `public/pagefind/` directory needs to survive the second `vercel build` (since `public/` is copied into `.vercel/output/static`). This may work — `vercel build` does copy `public/` — but the requirement does not specify it, does not verify it, and does not address what happens if `vercel build` clears `public/`. A 30-second test on a throwaway branch would falsify this. Without it, the entire deploy chain rests on undocumented Vercel CLI behavior.

## Section B — Requirement 1.4 v2 "BLOCKING from day 1" — rollback is not really one-line

v2 dropped the v1 promotion mechanism in favor of "ships blocking, revert PR if flaky." This is cleaner in theory; in practice the rollback claim is overstated.

- **[Novel] Challenge Req 1.4 v2's claim that the rollback is "revert this spec's PR (one-line change: comment out the crawl step in `ci.yml`)."** The spec's PR adds: Req 0 deploy migration, Pagefind crawl, draft-leak smoke check, Pagefind UI components, series UI, related-posts rail, share bar, reading progress, TOC, footnote styling, copy buttons, fixture posts, axe-pass extensions, Lighthouse threshold extension. Reverting the WHOLE PR throws out all eight features to recover one. Reverting JUST the crawl step requires editing `ci.yml` AND removing the smoke-check step (Req 12.1's `"Verify Pagefind index (Build 2)"`) AND removing `"Upload Pagefind manifest"` AND removing `"Vercel deploy (Build 2)"` if it depends on the crawl artifact. The "one-line" claim is false; the actual rollback is "comment out three or four sequential CI steps." Either the rollback is documented as a multi-step procedure with a verified runbook, or "ships blocking" loses its escape valve.
- **[Novel] Stress-test Req 1.4 v2's "search UI shows the empty-index state per Req 1.15" rollback behavior.** Req 1.15 specifies behavior when zero published posts exist (the index is empty but valid). The post-rollback state is different: the index file is MISSING from the deploy (Pagefind never ran), not empty. The Pagefind WASM module will throw or 404 on the fetch of `/pagefind/pagefind.js`. The search dialog will open and fail (Req 1.9's lazy import) — not gracefully degrade. The "rollback is safe because search degrades" claim requires the dialog to handle a missing index, not just an empty one. Add an acceptance criterion for "Pagefind script load fails → dialog shows a meaningful state" or accept that the rollback breaks the search UI visibly.
- **[Compounding/v1 Section A] Attack Req 1.4 v2's "blocking from day 1" combined with Req 0.6's "CI deploy failure fails the workflow loudly."** Two blocking failure modes now stack: Pagefind crawl can fail (blocking) AND `vercel deploy --prebuilt` can fail (blocking). A flaky Vercel CLI release can block ALL deploys without any Pagefind problem. The spec does not require pinning the Vercel CLI version (Req 0.2 says "Design SHALL pin the exact step sequence, the Vercel CLI version pinned in `devDependencies`") — Design is asked to pin a CLI version inside a `devDependencies` lockfile, but the requirement does not specify a pinning policy (exact version? caret range? auto-update via dependabot?). An accidental Vercel CLI minor-version bump can break the deploy gate. Either require an exact-version pin and a manual-bump-only policy, or accept this as a recurring break vector.

## Section C — Requirement 4 (Related posts) weighting — new ambiguity introduced by v2 fix

v2 changed the score from `|tags ∩| + |categories ∩|` to `2*|tags ∩| + |categories ∩|`. This addresses v1's "categories dominate" critique. v2 introduces new edge cases.

- **[Novel] Challenge Req 4.1 v2's claim that the 2:1 ratio "is conservative — not so strong that a single shared tag dominates two shared categories."** The arithmetic example given (`1-tag overlap scores 2; 2-category overlap scores 2; ties broken by recency`) is correct, but this is a NEW edge case the spec creates and does not handle well. Two posts sharing two categories AND nothing else now score IDENTICALLY to two posts sharing one tag AND nothing else. Ties are broken by recency — meaning the related rail will show "two-category, no-tag" posts before "one-tag, no-category" posts simply because they were posted more recently. The cosine of relatedness is not just a number; the rail conveys to the reader "these are like this post." A two-category overlap with zero topical tags is rarely actually related (it just means both posts are in the same coarse buckets). Either bump tags to 3:1, or accept that the 2:1 ratio still produces "looks related but isn't" results in the tie case.
- **[Novel] Stress-test the corpus-scale assumption.** At launch the site has ~5 published posts (NFR Performance). Many posts will have score=0 against each other (no shared tag, no shared category) → rail will not render (Req 4.1 last bullet). The "rail does not render" branch fires for most posts at launch. Req 4.6 v2 removed the rationale ("a reader doesn't need to know the absence") but the behavior remains: a launch post page silently lacks a related rail with no UI signal. Compare to "Related posts: nothing yet — see all posts on /blog" or similar. The spec deliberately chose silent-absence; verify that's intentional given the launch corpus size.
- **[Recurring/v1 Section B fourth bullet, escalated] Attack Req 4.4 v2's `RelatedPostMeta = { slug, title, description, date }` decision.** v1 noted the typed-API decision was deferred to Design. v2 commits to a NEW sibling type, NOT extending `PostMeta`. The escalation: the new type's shape DUPLICATES four fields that already exist on the Velite `Post` output. The spec also says (NFR) "the Velite typed output is structurally unchanged." Now there are TWO type contracts representing the same post data (`PostMeta` with `{slug, title}` and `RelatedPostMeta` with `{slug, title, description, date}`), plus the full `Post` from Velite. A caller that wants `{slug, title, description}` has no canonical type — they'll either widen `PostMeta`, use `RelatedPostMeta` and ignore `date`, or import the full `Post`. The "avoid breaking callers" rationale was correct; the consequence (three overlapping types) is new technical debt. Either consolidate via type composition (`type RelatedPostMeta = PostMeta & Pick<Post, 'description' | 'date'>`) or document why two distinct types is preferable.

## Section D — Requirement 7 (TOC) v2 hardening — leftover residues

v2 dropped scroll-spy (good), pinned in-flow (good), and unified slug derivation to read from `bodyHtml` (good). Three residues remain.

- **[Novel] Challenge Req 7.10's "corpus heading-depth audit" finding.** The audit captured today's snapshot. Req 7.10 acknowledges future posts may introduce h4: "WHEN a future post introduces h4 headings, the TOC SHALL silently flatten that information." Silent flattening is the failure mode v1 critiqued for being undetected. The spec accepts it explicitly now, but does not add a build-time signal (e.g., a console warning, a fixture test, or a "headings beyond h3 detected" annotation in `bodyHtml`). The author writing an h4-rich post will not learn the TOC is incomplete until they open the rendered page. Either add a lint-style warning at Velite build time OR accept that the silent-flatten contract is a permanent footgun authors discover by accident.
- **[Novel] Stress-test Req 7.3 v2's claim that "parsing `bodyHtml` with a HAST/HTML parser" is the slug-parity guarantee.** `bodyHtml` is produced by `s.markdown()`, NOT by `s.mdx()`. Per blog-core, the markdown pipeline is used for RSS output AND the MDX pipeline produces the rendered page. Are heading IDs identical between the two pipelines? They SHOULD be (both use `sharedRehypePlugins` per Req 11.1), but the requirement reads the IDs from `bodyHtml` (markdown) while the rendered page heading IDs come from `s.mdx()` output. If `s.markdown()` and `s.mdx()` produce different HAST for the same heading (e.g., because one strips an MDX expression the other preserves), the TOC slug `extractToc` returns will not match the page anchor. Req 7.4's test asserts ID equality, but the test sources both sides from `bodyHtml` per the v2 text ("from the `bodyHtml` field directly — same source"), making the test tautological by Req 7.3 v2's own admission. The test does not actually verify parity between TOC slugs and the rendered post page. Either source the test's "ground truth" side from the MDX-rendered page (Playwright DOM read), or accept that the test is not a parity test.
- **[Compounding/v1 Section C] Attack Req 7.2's "h2 and h3 only" combined with Req 7.5's "fewer than 2 entries → don't render."** A post with three h2s and zero h3s renders a TOC with three top-level entries (good). A post with one h2 and six h3s nested under it renders a TOC with seven entries (one h2, six h3s). A post with one h2 and zero h3s renders nothing (per Req 7.5 the threshold is `< 2`). A post with zero h2 and three h3s — does it render? The h3s without h2 parents would produce a flat list. Req 7.2 says "h2 and h3 only" without specifying hierarchy enforcement. The empty-rendering rule (Req 7.5) is by entry count, not by structure. Decide whether orphan-h3-only posts render a flat TOC or are skipped, or accept the current ambiguity.

## Section E — Fixture Roster v2 — `fixture-search` PUBLISHED introduces production-visible test fixture

v2's solution to the v1 contradiction ("fixture-search must be searchable but all fixtures are draft") was to publish `fixture-search`. This resolves the contradiction; it creates new visible-on-production surface area.

- **[Novel] Challenge the Fixture Roster's claim that `fixture-search` being published is "small visible 'search test' post — acceptable, low-noise."** The post is rendered on `/blog` (index page), in any tag/category page where its `search-test` tag or `search-fixture` category exists, in the Pagefind index for any search, in the RSS feed, and in the sitemap (per blog-core Req 7.16 `sitemap.ts` modification). The "low-noise" claim is undefended. A real visitor to `/blog` will see a card labeled "fixture-search" with the body "This page is a permanent fixture..." Acceptable for a personal site? Probably. But the spec asserts low-noise without any operator opt-out mechanism (e.g., an env var that excludes `fixture-*` slugs from production). If Matthew ever wants to hide the fixture from real visitors, the only path is removing it — which breaks Req 10.3's keyboard test. Either add an opt-out mechanism, or document that the fixture is permanently visible and will appear in production navigation.
- **[Novel] Stress-test the Fixture Roster's "dedicated `search-fixture` category keeps it from polluting related rails."** `fixture-search` has `tags: ['search-test']` and `categories: ['search-fixture']`. The OTHER real (non-fixture) blog posts have their own tags/categories. Under Req 4.1 v2's algorithm, `fixture-search`'s score against any non-`search-*` post is 0 (no shared tag, no shared category). So far so good. But: the related rail on `fixture-search` ITSELF — what does it show? `fixture-search` is published, so it appears on the production `/blog/[slug]/page.tsx` route. Visitors who navigate to `/blog/fixture-search` see the related rail. With no other post sharing `search-test` or `search-fixture`, the rail will be empty (per Req 4.1 last bullet, rail doesn't render). So the published fixture has a no-rail post page in production. This is the dead-zone v1 noted in a different form — verify the visitor experience on `/blog/fixture-search` is acceptable, OR exclude the fixture from real-visitor navigation (back to opt-out).
- **[Compounding/v1 Section E] Challenge the Fixture Roster's failure to address `fixture-search` appearing in the SEARCH RESULTS themselves.** The Pagefind index includes `fixture-search` (the whole point). Any real visitor typing into the search dialog who happens to query a term in the fixture's body ("MATTHEWFIELD-SEARCH-SMOKE" — unlikely, but the fixture body will also contain English copy explaining it's a fixture) will see the fixture as a result. The fixture body content is search-indexed; any common word in it (e.g., "fixture", "search", "permanent") will surface it in queries. Either accept that the fixture pollutes real search results for common words, OR add a per-page index opt-out (Pagefind supports `data-pagefind-ignore="all"` on the body but Req 1.6 contradicts this — the post page is the `data-pagefind-body` carrier).

## Top 5 risks/gaps

1. **[Novel] Vercel deploy migration (Req 0.3) has a race window on merge AND requires uncoordinated two-step rollback.** The spec specifies a migration sequence but not an ordering between "dashboard switch" and "PR merge." A real merge will produce duplicate or zero deploys depending on operator timing. **Failure mode: spec PR merges, Vercel auto-deploys ship the old (pre-spec) CI behavior, GitHub Actions ALSO deploys via `vercel deploy --prebuilt`, two deploys race, the loser's artifact is what users see.**
2. **[Novel] `vercel build` runs `next build` a second time after Pagefind has populated `public/pagefind/`.** The spec does not verify that the second build preserves the Pagefind artifact (likely it does — `public/` is copied — but not specified, not tested). **Failure mode: a Vercel CLI version that does cleanup on `public/` strips the index between build and deploy; deployed site has no `/pagefind/` directory; search UI fails to load on first open.**
3. **[Novel] `fixture-search` is permanently visible on production `/blog`, in RSS, in sitemap, in tag/category pages.** No opt-out mechanism. **Failure mode: Matthew is interviewing for a job, recruiter visits the blog index, sees "fixture-search — This page is a permanent fixture used by the site's search smoke test" alongside the real essay posts.**
4. **[Compounding/v1 #2] `RelatedPostMeta` is a new sibling type duplicating four fields that already exist on `Post` and partially on `PostMeta`.** v2 resolved the v1 ambiguity by creating duplication. **Failure mode: future helpers default to importing the full `Post` to avoid the type-zoo, undoing the typed-API isolation Req 4.4 v2 intended to preserve.**
5. **[Novel] Req 7.4's slug-parity test is tautological under Req 7.3 v2.** Both sides of the assertion read from `bodyHtml`. The test catches regressions in the test, not regressions in the page-rendering pipeline. **Failure mode: a future change to `s.mdx()` (page rendering) diverges from `s.markdown()` (bodyHtml), TOC links resolve to non-existent anchors on real post pages, fixture test continues to pass.**

## Top 3 conclusions to challenge or reverse

1. **Reverse: "Req 0 migration is operator-doable as a documented procedure."** The two-step coordination (dashboard switch + PR merge) and two-step rollback (dashboard re-enable + `ci.yml` edit) have no atomic primitive. Either build a feature-flag wrapper in `ci.yml` (e.g., `if: vars.DEPLOY_VIA_CI == 'true'` keyed to a GitHub Actions variable that's flipped in a single dashboard action) OR accept that the migration is a coordinated maintenance window, NOT a one-time operator step. Reasoning: the spec presumes the operator will perform steps in correct order, but provides no enforcement — the most common error mode (PR merges before dashboard switch flips) is unprotected.
2. **Reverse: "`fixture-search` published is acceptable low-noise."** The fixture appears in every reader-facing surface (index, RSS, sitemap, tag pages, search results) and the spec provides no opt-out. Either exclude `fixture-*` slugs from `getPublishedPosts()` at the `src/lib/blog.ts` layer (a single-line filter that production reads but tests bypass via a flag) OR accept the visibility. The current "small post — acceptable" claim is asserted without evidence. Reasoning: a personal site competing for reader attention should not advertise its test fixtures to readers.
3. **Reverse: "Req 7.4's slug-parity test verifies TOC anchors match rendered page anchors."** Per Req 7.3 v2's own text, both sides of the test now read from the same `bodyHtml`. The test is structurally incapable of detecting divergence between `s.markdown()` and `s.mdx()`. Either rewrite the test to source one side from a Playwright DOM read of the rendered page OR document the test as a regression guard against re-introducing a separate slugger, NOT as a parity verifier. Reasoning: the spec text claims parity verification while the mechanism makes parity verification impossible — that's worse than admitting the test's actual scope.

## What's missing — work to do before acting

- **A merge-sequencing decision for Req 0.3**: specify whether dashboard-disable happens BEFORE or AFTER PR merge, and what protects against the race. Add a CI-side guard (e.g., `vercel deploy --prebuilt` fails fast if Vercel auto-deploys are still enabled — Vercel API surfaces this).
- **A `vercel build` artifact-preservation verification**: run a dry-run on a throwaway branch confirming `public/pagefind/` survives the `vercel build` step. Document the Vercel CLI version under which the verification was performed.
- **A `fixture-search` visibility opt-out mechanism**: a single-line filter in `getPublishedPosts()` (e.g., excluding slugs starting with `fixture-` from non-test contexts) or an explicit acceptance that the fixture ships to readers.
- **A genuine slug-parity test for the TOC**: read one side from the rendered MDX page (Playwright DOM query for `<h2 id>` / `<h3 id>`) and one side from `extractToc(post)`. Asserting equality of two reads of `bodyHtml` proves nothing about the MDX pipeline.
- **A Vercel CLI pinning policy**: exact-version pin in `devDependencies`, manual-bump-only, owner specified.
- **A secret rotation / ownership note for `VERCEL_TOKEN`**: who created it, who rotates it, what monitoring fires when it expires. Tokens expire silently; CI starts failing 100% with a 401.
- **An orphan-h3 decision for Req 7.5**: does a post with three h3s under no h2 render a TOC or not? Currently ambiguous.
- **A `RelatedPostMeta` consolidation**: define as `PostMeta & Pick<Post, 'description' | 'date'>` so there's one canonical shape, or document why three overlapping types is acceptable.
