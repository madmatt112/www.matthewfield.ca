# Requirements Document

## Introduction

The professional-profile spec delivers the site's primary professional inbound funnel: a wide-layout `/profile` page driven by a single MDX file (visual resume / CV) with structured frontmatter metadata, a contact section with LinkedIn and GitHub links, a bot-protected email address, a contact form that delivers messages via Resend, and a standalone `/contact` slash page that reuses the same contact components. Employers, recruiters, and collaborators land on `/profile`, assess Matthew's experience, and reach out — either directly by email or through the form.

## Alignment with Product Vision

- **Professional inbound funnel** (product.md business objective #1): `/profile` and the contact form are the main mechanism by which employers and recruiters get in touch.
- **Markdown-first content** (product principle #2): Profile body content lives in `content/profile.mdx` and is rendered by React components — no CMS, no database, edits are a markdown commit.
- **Simple to maintain** (product principle #3): Matthew updates the profile by editing a single MDX file.
- **Wide and spacious** (product principle #1): `/profile` uses a wider layout than standard content pages to give resume-style content room to breathe.
- **Approachable and human** (product principle #5): The contact section uses the "Shoot me a message — I respond to every human :)" copy from product.md.
- **Accessible** (product principle #7): Form submission feedback, obfuscation interactions, and all controls meet WCAG 2.1 AA in both themes.
- **Slash pages convention** (product.md feature #8): `/contact` is a lightweight standalone page reusing the same contact components.

## Requirements

### Requirement 1: MDX-driven profile page

**User Story:** As a potential employer or recruiter, I want to view Matthew's professional experience on a dedicated profile page, so that I can quickly assess his fit for a role.

#### Acceptance Criteria

1. WHEN a visitor navigates to `/profile` THEN the page SHALL render MDX content from a single source file at `content/profile.mdx` with frontmatter-driven metadata.
2. The Velite configuration SHALL define a new top-level collection `profile` with `pattern: "profile.mdx"` and `single: true`, sourced from `content/profile.mdx`. This is separate from the existing `pages` collection, which remains unchanged. IF `content/profile.mdx` is missing at build time THEN the Velite build SHALL fail with a named error — the `profile` collection SHALL NOT silently emit `undefined` (which would otherwise cause an opaque crash during static generation of `/profile/page.tsx`).
3. The `profile` schema SHALL require the following frontmatter fields: `title` (page title), `description` (meta description, distinct from `/about`'s — see Req 6), `headline` (one-line role summary displayed under the name), `location` (city, country), `availability` (string describing openness to new opportunities). It SHALL support an optional `headshot` field typed as Velite's `s.image()` primitive, with a relative path value (e.g. `./headshot.jpg`) that Velite resolves and copies to the built asset output.
4. The `updatedAt` value SHALL NOT be authored in frontmatter. It SHALL be derived at build time by a Velite transform reading `git log -1 --format=%cI content/profile.mdx` and exposed on the parsed document. This removes the human-error class of stale dates.
    - **Shallow-clone remedy**: Vercel's default build clone has limited depth. Since `content/profile.mdx` will be edited rarely (resume edits happen quarterly at most), the file's last-touching commit is likely to fall outside a shallow clone window after ~10 intervening commits. The build pipeline SHALL unshallow the repository before the Velite build runs — concretely, `vercel.json`'s `buildCommand` (or an equivalent pre-build hook) SHALL invoke `git fetch --deepen=1000` (or `git fetch --unshallow`) prior to `velite build`.
    - **Transform failure contract**: IF the `git log` command returns an empty string (indicating the file's history is not present in the clone despite the unshallow step) THEN the Velite transform SHALL throw a named error that fails the build with a diagnostic pointing at the shallow-clone cause. It SHALL NOT coerce to `Invalid Date`, a zero timestamp, or any silent placeholder.
    - **Local-build quirk (acknowledged, not fixed)**: Running `pnpm build` locally with uncommitted edits to `content/profile.mdx` will show the *previous* commit's timestamp (not the on-disk mtime), because `git log` reports committed state. This is a dev-loop quirk, not a production bug.
5. The headshot, when present, SHALL be rendered by the `/profile` page component in a layout position adjacent to the headline area (above the MDX body in DOM order). The MDX body SHALL NOT be expected to reference the headshot directly. The responsive layout — stacking behavior at narrow breakpoints, side-by-side vs. stacked at wide breakpoints, and explicit pixel sizing — is deferred to the Design phase. This requirement guarantees data plumbing only.
6. The MDX body structure SHALL be at Matthew's editorial discretion — no required section headings enforced by the spec.
7. WHEN `content/profile.mdx` is updated and the site is rebuilt THEN the rendered `/profile` page SHALL reflect the new content with no React component changes required.
8. WHEN the profile page is rendered THEN it SHALL use the `max-w-5xl` Tailwind utility (1024px / 64rem) as its content container width — wider than the standard prose column, narrower than full-bleed.
9. WHEN the profile page is rendered THEN it SHALL be a statically generated server component (no per-request rendering). To enforce this (and prevent silent degradation to dynamic rendering if an implementer accidentally calls `headers()`, `cookies()`, or another dynamic API), both `/profile/page.tsx` AND `/contact/page.tsx` SHALL declare `export const dynamic = 'force-static'`.
10. WHEN the profile page is rendered THEN its `<title>` and meta description SHALL come from the MDX frontmatter, composed through the site-wide `%s | matthew-field.ca` title template defined in `src/app/layout.tsx`.
11. IF the author includes h2 or h3 headings in the profile MDX body THEN each SHALL render with an anchor ID (via a rehype plugin such as rehype-slug — exact plugin selection deferred to Design) so that `/profile#some-heading`-style deep links work. Deep-link *targets* are the author's responsibility; the spec guarantees the *mechanism*, not specific anchors.
12. WHEN the build runs THEN it SHALL fail loudly on ANY of the following conditions: (a) frontmatter schema violations (Velite), (b) MDX compile errors, (c) references to undefined MDX components, (d) render-time exceptions during static generation of `/profile`. No error class SHALL degrade to runtime SSR or a blank page.
13. The profile MDX body has NO custom component registry at launch. The existing `<MDXContent />` component in `src/components/shared/mdx-content.tsx` renders MDX via `new Function(code)(runtime)` with no `components` argument, so capitalized-tag references (e.g. `<Timeline />`, `<Callout />`) in `content/profile.mdx` WOULD produce a `ReferenceError` at static-generation time (which Req 1.12(c)/(d) then surfaces as a build failure, correctly). Matthew SHALL author the profile body as plain-markdown-equivalent MDX — no custom component tags. Future specs MAY introduce a registry; this one does not.
14. **Order-of-operations for landing the schema and content**: Implementation SHALL land the new Velite `profile` collection schema (in `velite.config.ts`) and the initial `content/profile.mdx` file in the SAME commit. Splitting them across two commits creates a window where CI is broken: schema-first leaves Req 1.2's missing-file failure firing; content-first leaves the `profile` collection unregistered (Velite ignores the file silently and `/profile/page.tsx` references an undefined collection). Tasks decomposition SHALL respect this constraint.

### Requirement 2: Contact section on the profile page

**User Story:** As a visitor on the profile page, I want to see how to contact Matthew at the bottom of the page, so that I can reach out after reviewing his experience.

#### Acceptance Criteria

1. WHEN the profile page is scrolled to the bottom THEN the contact section SHALL display links to Matthew's LinkedIn and GitHub profiles as accessible external links with appropriate `rel="noopener"` and `aria-label` attributes. These links SHALL be server-rendered (no JS required to display or follow them).
2. WHEN the contact section is rendered THEN Matthew's email address SHALL be displayed via `react-obfuscate` (click-to-reveal) so that the plain address does not appear in the raw HTML of the rendered page.
3. The `<ObfuscatedEmail />` wrapper SHALL apply `min-height: 44px`, horizontal padding, and a flex layout (`display: inline-flex; align-items: center`) so that the pre-click tap target meets the 44×44 CSS px requirement in Req 4.11 regardless of the rendered font size or line-height.
4. The `<ObfuscatedEmail />` wrapper SHALL carry an `aria-label` naming the reveal action (e.g. `"Reveal Matthew's email address"`) so that screen-reader users encounter an accessible name independent of the obfuscated visible text (which `react-obfuscate` renders as a reversed or otherwise garbled string that screen readers would otherwise enunciate as meaningless syllables).
5. WHEN the contact section is rendered THEN the copy "Shoot me a message — I respond to every human :)" SHALL be visible above the contact form. The page owns this tagline copy (not the form component).
6. WHEN the contact section is rendered THEN the contact form (Requirement 3) SHALL be embedded inline, not behind a modal or separate navigation step.
7. The LinkedIn URL, GitHub URL, and email address SHALL be sourced from `src/config/site.ts` (extended with a `links` object containing `linkedin`, `github`, and `email` fields). Contact components SHALL NOT hard-code these values.
8. The `siteConfig.links.email` value (e.g. `hello@matthew-field.ca`) is accepted as plaintext in the public source tree. `react-obfuscate` protects the rendered HTML only; the source file is public. The spam defense for this alias is per-address filtering at the mail provider (see Req 3.5), not source-code obfuscation.

### Requirement 3: Contact form submits and delivers email via Resend

**User Story:** As a visitor, I want to fill in and submit a contact form with my name, email, and message, so that I can reach Matthew without needing my own mail client.

#### Acceptance Criteria

1. WHEN the form is rendered THEN it SHALL include three visible fields — `name`, `email`, `message` — each with an associated `<label>`, PLUS one invisible honeypot field.
2. The honeypot field SHALL use the exact name attribute `url_secondary` (chosen to avoid password-manager autofill patterns). Its container SHALL be hidden via `display: none`, and the input itself SHALL carry `tabindex="-1"`, `aria-hidden="true"`, and `autocomplete="off"`. Off-screen positioning (e.g. `.sr-only`, `position: absolute; left: -9999px`) SHALL NOT be used.
3. The form SHALL NOT use a client-stamped submission-timing heuristic. (A prior revision proposed one; it was rejected because it is trivially bypassable by any bot that parses the form, and it creates a silent-drop trap for password-manager users whose autofill beats the threshold.)
4. WHEN the user submits the form with valid data THEN the client SHALL POST the payload as JSON to a Next.js route handler at `/api/contact`. JavaScript is required to submit the form; the no-JS fallback is the LinkedIn/GitHub/email affordances in Req 2 (all server-rendered).
5. WHEN the `/api/contact` handler receives a request THEN it SHALL apply the following steps in order. The handler SHALL read the raw request body first (as bytes, for size enforcement), then parse JSON, then run the downstream checks against the parsed object.
    - a. **Size cap**: Raw body size ≤ 32 KB. Oversize requests SHALL return HTTP 413 with a JSON body `{ error: "Message is too long. Please shorten and try again." }` that the client can render to the user. (32 KB is sized to accommodate 5000 UTF-8 characters at up to 4 bytes/char for CJK + emoji content, plus JSON envelope overhead and headroom. Next.js App Router does not cap body size by default — this cap MUST be explicit in the route handler.)
    - b. **Origin-matching**: The request SHALL be accepted when the `Origin` header is present and matches the site's production origin; when `Origin` is absent, the handler SHALL fall back to checking `Referer`; when both are absent, the request SHALL be allowed. The handler SHALL NOT log this fallback firing — IP, user-agent, or any other request metadata in a `console.*` call would be captured by Vercel Function Logs (~1 day retention on Hobby) and become an undisclosed persistence channel in tension with Req 3.9. The signal of interest ("how often does this fallback fire") is reconstructable downstream from invocation count vs. body-validation success count if it ever becomes operationally relevant. Rejecting legitimate Safari / Lockdown-Mode / strict-privacy-browser traffic on a weak signal is worse than letting the remaining defenses (honeypot + zod) catch any corresponding bots. Mismatched `Origin` or `Referer` SHALL return HTTP 403.
    - c. **JSON parse**: `JSON.parse` the body. A parse failure SHALL return HTTP 400 with a JSON body `{ error: "Malformed request." }`. The handler SHALL NOT throw or allow an unhandled exception (which would surface as a 500 and pollute Vercel function logs).
    - c2. **Parsed-body type guard**: After successful JSON parse, the handler SHALL verify the parsed result is a non-null plain object — concretely, `typeof parsed === 'object' && parsed !== null && !Array.isArray(parsed)`. Bodies of `null`, `[]`, `"string"`, `42`, or `true` parse successfully but would otherwise throw `TypeError: Cannot read properties of null` at the honeypot read in (d), or pass through to zod which already rejects them. The handler SHALL respond HTTP 400 with `{ error: "Malformed request." }` for any non-plain-object parsed body. This clause closes the unhandled-500 path that would otherwise contradict (c)'s no-throw guarantee.
    - d. **Honeypot check**: Read `parsed.url_secondary` off the parsed object (before any zod step, so a strict zod schema cannot reject it first). Populated honeypot SHALL return HTTP 200 without invoking Resend (silent bot suppression — indistinguishable from success).
    - e. **Body schema validation**: Apply a zod schema of shape `z.object({ name, email, message }).strip()` to the parsed object. The `.strip()` mode is REQUIRED so that extra fields (`url_secondary`, `source`) do not cause validation failure. Field bounds:
        - `name`: 1–100 characters, trimmed. (Note: `.trim()` strips leading/trailing whitespace only, not embedded CRLF. CRLF-header-injection risk is neutralized via Req 3.6's bare `reply_to` policy, not here.)
        - `email`: valid email per zod's `.email()`, length ≤ 254 characters (RFC 5321 envelope limit). Note: zod's `.email()` regex rejects internationalized email (IDN / non-ASCII local parts). This limitation is acknowledged; IDN users can reach out via LinkedIn or the obfuscated email. Swapping to an IDN-aware validator is explicitly out of scope for this spec.
        - `message`: 10–5000 characters, trimmed.
    - f. **Body-schema validation failures** SHALL return HTTP 400 with a structured JSON body of shape `{ errors: { field: string } }` so the client can display field-level error text.
    - g. **`source` normalization**: After body-schema validation passes, the handler SHALL normalize `parsed.source` via `z.enum(['profile', 'contact']).optional().catch(undefined)`. Invalid or missing values silently become `undefined`; this is NOT a 400 — bad values indicate client tampering that should be invisible to the attacker, not surfaced as feedback. The normalized value is what flows into email construction (Req 3.6).
6. WHEN validation passes and the honeypot is empty THEN the API SHALL send an email via the Resend API.
    - The **production** `from` address SHALL be an email at a custom domain verified in Resend (target address: `hello@matthew-field.ca` or a comparable alias). Deliverability depends on a verified domain with SPF, DKIM, and DMARC configured. The required DNS posture:
        - **SPF**: the Resend-provided SPF include (or a TXT record authorizing Resend to send on behalf of `matthew-field.ca`).
        - **DKIM**: the CNAME records Resend generates for DKIM signing (typically one or two `resend._domainkey.<subdomain>` records).
        - **DMARC**: a TXT record at `_dmarc.matthew-field.ca` with at minimum `v=DMARC1; p=none; rua=mailto:<monitoring-address>` at launch. Alignment mode SHALL remain at the DMARC default (relaxed) for both DKIM and SPF; the `adkim` and `aspf` tags SHALL NOT be set to `s` (strict). Resend's DKIM signs at `resend._domainkey.<subdomain>`, which aligns with the parent `From:` domain only under relaxed alignment; switching to strict would cause Resend-sent mail to fail DMARC and bounce. **Do not change the alignment mode in any future hardening pass without first re-verifying Resend's `d=` tag against the production From: domain.** Matthew SHALL set a 14-day post-launch calendar reminder to review DMARC aggregate reports; tighten to `p=quarantine` (and later `p=reject`) only after observing clean alignment for at least two weeks. DMARC tightening is an operational duty, not a CI-enforced gate — failure to tighten is an acknowledged residual launch risk (spoofed `From: matthew-field.ca` mail remains deliverable to recipients).
        - **DNS verification is a launch prerequisite**: the funnel SHALL NOT be considered shipped until the custom-domain `from` address is verified in Resend and SPF/DKIM/DMARC records resolve correctly from public DNS.
    - The **preview and local-development** `from` address MAY use Resend's sandbox domain (`onboarding.resend.dev`). Preview deploys are not expected to deliver real recruiter mail.
    - The API SHALL use `siteConfig.links.email` as the `to` address.
    - The API SHALL set `reply_to` to the **submitter's bare email address only — no display-name wrapper**. This eliminates CRLF-header-injection risk from the `name` field (zod's `.trim()` strips only leading/trailing whitespace, not embedded CRLF, so `name: "Matt\r\nBcc: attacker@..."` would otherwise be a latent injection vector if wrapped into `reply_to: "\"${name}\" <${email}>"`).
    - **Subject contract**: The Resend `subject` field SHALL be constructed as the literal template `"Contact form submission from {source}"` where `{source}` is the validated `source` enum value (`'profile'` or `'contact'`) per Req 3.5(g), or the literal string `"unspecified"` when normalized to `undefined`. The handler SHALL NOT interpolate `name`, `email`, OR `message` into the subject. Rationale: subjects become RFC 5322 mail headers; if Resend's HTTP-to-SMTP layer ever fails to sanitize CRLF in subject (a class-of-vendor-trust assumption the spec rejected for `reply_to`), interpolating user input re-opens the same header-injection vector closed in the `reply_to` clause. Constants and the enum-bounded `source` are CRLF-impossible by construction.
    - User-submitted field values (`name`, `email`, `message`, `source`) SHALL be passed to Resend's `text` parameter only — never the `html` parameter. This prevents HTML/script injection in the inbox-webmail rendering of the email body.
7. IF Resend returns an explicit 4xx/5xx error THEN the API SHALL respond with HTTP 502 and a JSON body `{ error: "Unable to send message. Please try again or use an alternative method." }`. No vendor detail or stack traces SHALL leak to the client.
8. The Resend client timeout SHALL be set to **9 seconds**. This is strictly less than the Vercel Hobby plan's 10-second serverless function execution cap, leaving ~1s for the error-response code path to run after a Resend timeout. IF the Resend call times out THEN the API SHALL respond with HTTP 503 and a `Retry-After: 60` header with the same user-friendly JSON body as Req 3.7.
9. WHEN the server receives a form submission THEN it SHALL NOT persist the form data in any log, database, or external service beyond Resend itself.
10. The `/api/contact` handler SHALL NOT pass `name`, `email`, `message`, OR `source` field values to any `console.*` call, and SHALL NOT include those values in thrown `Error` messages or rejected-promise reasons. On Resend errors, the handler SHALL log only a sanitized code (e.g. the HTTP status and a generic class like `"resend_4xx"` or `"resend_timeout"`) — never the request body, never the Resend error response body. This is necessary because Vercel Function Logs capture `console.*` output and error stack traces, which would otherwise become a persistence channel in contradiction with Req 3.9. Additionally, the Resend SDK SHALL be instantiated without any debug/verbose logging options; if a future SDK version adds logging that cannot be disabled via construction options, the handler SHALL wrap the client to suppress SDK-emitted stdout/stderr.
11. WHEN the API route is deployed THEN the Resend API key SHALL be read from a Vercel environment variable. The Resend client base URL SHALL also be env-configurable via `RESEND_BASE_URL` (defaulting to `https://api.resend.com`), so that CI can point it at a local mock server (see Req 3.13). The `from` address and `to` address SHALL also be env-driven. **The Resend client SHALL be constructed inside the route handler (or via a getter that reads `process.env` at call time), NOT at module top-level.** Module-top construction (e.g. `const resend = new Resend(KEY, { baseUrl: process.env.RESEND_BASE_URL })` at the top of `lib/mail.ts`) freezes `RESEND_BASE_URL` at first import, after which any later env change (such as the test setup script exporting a mock URL after the Next.js server has booted) is silently ignored — defeating both CI mock interception and per-environment routing.

    **Vercel env-var scoping pattern** (configured in the Vercel dashboard under Project → Settings → Environment Variables; each variable SHALL be scoped to one specific environment, NEVER "All Environments"):
    - **Production**: `RESEND_API_KEY` (production key), `RESEND_FROM` (custom-domain alias e.g. `hello@matthew-field.ca`), `RESEND_TO` (production inbox), `RESEND_BASE_URL` left unset (defaults to `https://api.resend.com`).
    - **Preview**: `RESEND_API_KEY` (sandbox or scoped-down key), `RESEND_FROM=onboarding@resend.dev` (sandbox), `RESEND_TO` (Matthew's inbox or a preview-only alias), `RESEND_BASE_URL` left unset.
    - **Development**: documented in `.env.example`. `RESEND_BASE_URL=http://127.0.0.1:<port>` for the test mock; remaining vars sandboxed.

    Configuring any of these under "All Environments" leaks production credentials into preview deploys and lets QA traffic on shared preview URLs deliver mail into the production inbox indistinguishable from real submissions.
12. The `reply-to` header is attacker-controllable (the submitter can put any address there). This spec acknowledges the risk and does NOT add email verification. Matthew MUST treat inbound sender addresses as unverified until reply traffic confirms them.
13. WHEN CI runs THEN a Playwright smoke test SHALL exercise the form submission path from BOTH `/profile` AND `/contact`, filling and submitting on each page.

    **Sidecar mock Resend server**: A local HTTP server SHALL be spawned that the route handler talks to via `RESEND_BASE_URL=http://127.0.0.1:<port>`. The mock SHALL record each incoming request body and SHALL expose a `POST /__reset` endpoint that clears the recorded-request list and resets the call counter to zero.

    **Mock startup ordering — critical**: Playwright's `webServer` lifecycle starts the Next.js server BEFORE `globalSetup` runs and awaits the server's port reachability before invoking globalSetup. If `globalSetup` is what spawns the mock and exports `RESEND_BASE_URL`, the `pnpm start` child process has already forked from a parent whose env did not include `RESEND_BASE_URL` — and child-process env is captured at fork time, so later env-var assignment in the parent does not propagate. Therefore the mock spawn AND the `RESEND_BASE_URL` export SHALL happen in a wrapper script (e.g. `pnpm test:e2e` invokes a Node script that allocates a port, spawns the mock, exports `RESEND_BASE_URL` into the child shell, and only then forks `playwright test`) so the env var is in scope for both `webServer`'s child and any later `globalSetup`. Setting the var inside `globalSetup` and relying on `webServer` to see it is INVALID and SHALL NOT be done.

    **Per-test isolation**: `playwright.config.ts` runs `fullyParallel: true` with `retries: 2` in CI. A "total calls across the run" assertion against a single mock counter is brittle to parallel workers and retry inflation. Therefore: (a) each test SHALL `POST /__reset` to the mock in a `beforeEach` hook so its assertions start from a known zero state; (b) call-count assertions SHALL be scoped per-test (e.g. "after this single submission, the mock recorded exactly one call"), NOT cumulative across the run; (c) tests SHALL serialize within the same worker if cross-test mock state is unavoidable, via `test.describe.configure({ mode: 'serial' })`.

    **Per-page assertions**: For each of `/profile` and `/contact`:
    - The submission returns HTTP 200.
    - The mock received exactly one call for this submission.
    - The recorded payload shape matches `{ from, to, reply_to, subject, text }`.
    - The recorded `subject` exactly equals the literal `"Contact form submission from profile"` (or `"Contact form submission from contact"` for the `/contact` page) per Req 3.6's subject contract.
    - The recorded `text` body contains the expected `source` value (`'profile'` or `'contact'`) so prop-wiring regressions on either page are caught.

    Sandbox/live Resend testing is out of scope; deferred to future work if vendor contract drift bites.

### Requirement 4: Accessible, non-disruptive submission feedback

**User Story:** As any user — including assistive technology users — I want clear feedback after submitting the form, so that I know whether my message was sent and what to do next.

#### Acceptance Criteria

1. WHEN the form submits successfully THEN the system SHALL display an inline success message as an `<h2>` with `tabindex="-1"` inside a `role="status"` region. The `role="status"` region SHALL be mounted inside the `<main>` landmark (i.e. as a sibling or replacement of the form within the same page section, NOT as a global toast at the layout root outside any landmark) so axe-core's `region` rule (Req 4.10) does not flag it as content outside a landmark. The system SHALL move keyboard focus to the heading, scroll it into view if off-screen, render a visible focus ring on it, and clear the form fields.
2. WHEN the `scrollIntoView` behavior runs (Req 4.1) THEN it SHALL honor `prefers-reduced-motion`: smooth scrolling when the user has no motion preference; instant (default-behavior) scrolling when the user has `prefers-reduced-motion: reduce`.
3. WHEN the form fails server-side validation (HTTP 400) THEN the system SHALL: (a) for each invalid field, render an inline error hint with `aria-live="polite"` and associate it via `aria-describedby` on the input (cooperative, non-interrupting announcement per-field); (b) render a single top-level summary region with `role="alert"` ("Could not submit — please check the fields below") which is the one place interruption is appropriate; (c) PRESERVE the user's entered values; (d) move focus to the first invalid field.
4. WHEN the form fails due to a server error (HTTP 429 / 502 / 503 / 504 / network failure) THEN the system SHALL display a status message in a `role="status"` region (`aria-live="polite"`) with `tabindex="-1"`, mounted inside the `<main>` landmark (NOT as a global toast at the layout root, per the same rationale as Req 4.1). The system SHALL move focus to that region so keyboard users land adjacent to recovery affordances, PRESERVE the user's entered values, and render BOTH (a) a visible "Try again" button, and (b) an inline LinkedIn recovery CTA reading approximately "Or reach out on LinkedIn" with the LinkedIn URL rendered as a real `<a>` so it works irrespective of further JS state. The client SHALL NOT auto-retry; the user initiates any retry. The handled server-error set SHALL include:
    - **429**: Vercel platform throttling (e.g. function-invocation cap exceeded — see NFR Security note on the Hobby 100K/month invocation cap). The 429 may originate from the Vercel platform layer BEFORE the route handler runs, so the response body may be a Vercel-formatted page rather than the structured JSON of Req 3.7. The client SHALL treat any 429 status as a server error regardless of body shape and render the LinkedIn recovery CTA — this is the only user-visible signal during a platform-level throttle.
    - **502** (Resend vendor error per Req 3.7).
    - **503** (Resend timeout per Req 3.8, with `Retry-After: 60` header — the client MAY surface "try again in a minute" copy if the header is present, but is not required to).
    - **504** (Vercel function-cap kill, including cold-start tail-latency cases per the cold-start budget acknowledgement in NFR Reliability). The request body lacks the structured JSON of a Req-3.7-path response.
    - **Network failure / fetch rejection** (no response received).
5. WHEN the form is submitting THEN the submit button SHALL show a loading indicator and be disabled to prevent double-submission; all other controls remain operable.
6. WHEN the loading indicator is rendered (Req 4.5) THEN it SHALL honor `prefers-reduced-motion: reduce` — no rotating or spinning animation for users with that preference. A static text-only indicator (e.g. "Sending…") or an opacity-only pulse without rotation is acceptable.
7. WHEN any form control is rendered THEN it SHALL have a visible label, an accessible name matching the label, and native HTML5 `required` on required fields. `aria-required` SHALL NOT be added redundantly to native `required` inputs (it is noise for real HTML inputs; it is only useful on custom non-native controls). Invalid fields SHALL use `aria-describedby` to associate with their error hint.
8. WHEN the contact form is navigated by keyboard only THEN tab order SHALL be logical and focus indicators SHALL be visible on all interactive elements. Submission by pressing Enter from any focused `<input>` SHALL work. Enter from inside the `<textarea>` (message field) SHALL insert a newline per native browser behavior; users submit the textarea path via the submit button.
9. WHEN the contact form is rendered in either light or dark theme THEN all text, borders, focus rings, and error states SHALL meet WCAG 2.1 AA contrast (4.5:1 for normal text, 3:1 for large text and non-text UI).
10. CI verification: the Playwright smoke test SHALL run `axe-core/playwright` with the default WCAG 2.1 AA ruleset (which includes `color-contrast`, `heading-order`, `landmark-one-main`, `region`, and others — not limited to `color-contrast`). The assertion SHALL run against both the light theme AND the dark theme on `/profile` and `/contact`, toggling by setting the `next-themes` storage key between passes. Any axe violation fails the test.
11. WHEN any interactive target (button, link, form control) is rendered on a touch viewport THEN it SHALL have a minimum hit area of 44×44 CSS pixels.

### Requirement 5: Standalone `/contact` slash page

**User Story:** As a visitor who has been given the `/contact` URL directly (or who reaches it via the `/slashes` index), I want to land on a dedicated contact page with the same contact options as the profile page, so that I can reach out without scrolling through Matthew's resume.

#### Acceptance Criteria

1. WHEN a visitor navigates to `/contact` THEN the page SHALL render the same LinkedIn / GitHub links, obfuscated email, tagline copy, and contact form used on the profile page.
2. WHEN `/contact` is rendered THEN it SHALL use the standard content container width (the default used by other `(site)` routes), not the wider `max-w-5xl` profile container.
3. The three contact components — social links, obfuscated email, contact form — SHALL live in `src/components/shared/` and be consumed independently by `/profile/page.tsx` and `/contact/page.tsx`. Each page composes the three components directly; each page owns its own tagline copy and heading structure. There SHALL NOT be a `<ContactSection>` wrapper component, and the three shared components SHALL be layout-agnostic (no width concerns; the parent page imposes layout).
4. WHEN the contact form is submitted from either `/profile` or `/contact` THEN it SHALL use the same `/api/contact` handler and behave identically (same validation, same success/error UX).
5. The form SHALL additionally include a hidden `source` field (`source=profile` or `source=contact`) set by the page that renders it. The API handler SHALL server-side validate this value as `z.enum(['profile', 'contact']).optional().catch(undefined)` (see Req 3.5g) before using it in email construction. The API handler SHALL include the *normalized* value in the email body (never in a header) so Matthew can tell where a submission originated. This value SHALL NOT affect zod validation outcomes, routing, or any security check — invalid values are silently normalized to `undefined`, not surfaced to the client.

    **Enum lock-in note for future implementers**: Adding a new submission source (e.g. a future landing-page `<ContactForm source="landing">` callsite) SHALL require updating BOTH this `z.enum` literal AND the smoke test's per-source assertions in Req 3.13. Failure to update the enum results in silent normalization to `undefined` with no client-visible error and no test failure — emails arrive without source attribution, undetectable until manual QA. This coupling is accepted in trade for the closed-set security posture (CRLF-impossible, length-bounded, type-checked); the route handler is intentionally a chokepoint for source values.
6. `/contact` registration with the `/slashes` index is owned by a future spec (spec 7 per the decomposition) and is explicitly NOT this spec's scope. `/contact` inclusion in the XML sitemap is already handled by `src/app/sitemap.ts` from site-foundation (static route enumeration).

### Requirement 6: SEO disambiguation between `/profile` and `/about`

**User Story:** As a recruiter searching for Matthew, I want search engines to clearly distinguish his professional profile page from his personal `/about` page, so that I land on the page that fits my intent (resume vs. personal).

#### Acceptance Criteria

1. The `description` frontmatter on `/profile` SHALL be demonstrably distinct from whatever `/about` renders (copy focused on professional experience, skills, role fit). This is the minimum disambiguation the spec enforces; stronger structural content differentiation (heading content, body first paragraph, internal linking) is the author's responsibility when authoring `content/profile.mdx` — search rankers weight those signals above meta description, and the spec does not mandate body structure (Req 1.6).
2. `/profile` SHALL set its canonical URL via Next.js metadata: `metadata.alternates.canonical = '/profile'`. Next.js resolves this to an absolute URL via `metadataBase` (set to `https://matthew-field.ca` in `src/app/layout.tsx` by site-foundation).
3. The Playwright smoke test SHALL assert that the rendered `<link rel="canonical">` on `/profile` is an absolute URL starting with `https://matthew-field.ca/`. (Some search rankers treat relative canonical as a weak signal; asserting absoluteness prevents regressions if `metadataBase` is misconfigured.)
4. If the `/about` page is live at implementation time and includes Matthew's name or professional identity, the spec SHOULD note (not require) adding a link from `/about` to `/profile`. Full `/about` content is out of scope here (owned by the slash-pages spec).

## Non-Functional Requirements

### Code Architecture and Modularity

- **Contact component cohesion**: Three single-responsibility components in `src/components/shared/`:
    - `<ObfuscatedEmail />` — email display via `react-obfuscate`. Client component. Applies the tap-target sizing from Req 2.3.
    - `<SocialLinks />` — LinkedIn + GitHub links. Server component.
    - `<ContactForm />` — the form, owning its own state, validation, and submission logic. Client component. Accepts an optional `source` prop (Req 5.5).
  `<ContactForm />` renders with no required props for the happy path. Pages compose the three directly.
- **No wrapper component**: `/profile` and `/contact` compose the three shared components as siblings. There is no parent `<ContactSection>` component.
- **Layout ownership**: Layout width is imposed by the consuming page, not the shared components. The shared components render layout-agnostic markup.
- **Velite schema ownership**: This spec adds a new `profile` single-document collection to `velite.config.ts` (Req 1.2). No changes to the existing `pages` schema from site-foundation.
- **Site config extension**: `src/config/site.ts` is extended with a `links` field (`linkedin`, `github`, `email`). Contact components consume from `siteConfig.links`; LinkedIn/GitHub URLs and email SHALL NOT be hard-coded anywhere else.
- **No barrel files**: Components are imported from their own paths.
- **Server components by default**: `/profile` and `/contact` are server components; only `<ContactForm />` (stateful) and `<ObfuscatedEmail />` (react-obfuscate is client-side) are `"use client"`. `<SocialLinks />` is a server component.

### Performance

- **Lighthouse ≥ 90** on both `/profile` and `/contact` across performance, accessibility, best-practices, and SEO. Enforcement: `@lhci/cli` SHALL run as a non-blocking CI job that executes against the Vercel preview deploy for the PR and posts the four scores as a PR comment. Non-blocking because Lighthouse results in CI can be noisy; the scores become a persistent audit trail in PR comments. Falling below 90 on any category is a merge-review blocking issue, enforced by Matthew reading the PR comment.
- **No vertical layout shift** from obfuscation reveal or form state changes — the contact section reserves its vertical space up front. Horizontal layout shift on email reveal is **explicitly out of scope**: pre-click and post-click strings happen to be similar length for the current `hello@matthew-field.ca` alias, and Web Vitals excludes user-input shifts within 500ms from CLS scoring. If the alias is renamed in the future to a length that diverges significantly (e.g. a one-letter local part), reservation of horizontal space via `min-width` on the wrapper is a future-spec concern.
- **Client JS budget**: `<ContactForm />` and `<ObfuscatedEmail />` are the only client components on these pages. No additional client dependencies beyond `react-obfuscate`, `resend` (server-side), and `zod`.

### Security

- **Server-side validation**: All form data validated with zod on the server before any external call — client-side validation is UX only, never trusted.
- **Layered abuse defense** (composed, all evaluated server-side before Resend is invoked):
    - Request body size cap (32 KB → HTTP 413 with JSON body)
    - Origin/Referer header check with explicit absence policy (mismatch → HTTP 403; both absent → log + allow)
    - Honeypot field `url_secondary` (populated → silent 200, no email)
    - Zod schema validation (invalid → HTTP 400 with field errors)
- **Known latent risk — Resend 100/day quota DoS**: A headless-browser bot that parses the form, submits a legitimate Origin header, leaves the honeypot empty, and crafts zod-valid content will pass every check and consume the quota. Rate limiting via external state (Vercel KV / Upstash) is deferred per tech.md. If the funnel is exhausted, the error UI in Req 4.4 provides an inline LinkedIn CTA so recruiters have an explicit next step; the `<SocialLinks />` and `<ObfuscatedEmail />` components continue to work independently of Resend. Funnel outage is acceptable in principle; the LinkedIn recovery path is the mitigation.
- **Known latent risk — Vercel Hobby 100K-invocation/month DoS** (distinct from the Resend quota above): Vercel's Hobby tier caps function invocations at 100,000/month. This counter increments for EVERY invocation, including ones rejected at the size cap, origin check, JSON parse, plain-object check, honeypot, or zod validation — Resend's quota counts only successful sends, but Vercel's counts unconditionally. A 1-req/sec spray of invalid bodies (~86,400 invocations/day) consumes 26× the monthly cap in ~28 hours, after which Vercel platform-level 429s the project for the rest of the calendar month — the route handler does not run, no Req-3.7 structured response is emitted, and Matthew sees zero attempts in the Resend dashboard. Mitigation in this spec's scope: Req 4.4 includes 429 in the handled-error set so the LinkedIn recovery CTA renders even when the platform throttles before the handler executes. Edge-level rate limiting (Vercel firewall / edge middleware) is **deferred** as out-of-scope; if the function-invocation DoS becomes operational, it is a follow-up spec. The accepted residual is: a determined cheap-spray attacker can take the funnel dark for the rest of the calendar month, and the only user-visible signal is the Req-4.4 LinkedIn CTA.
- **No form-data persistence**: Submissions are relayed to Resend and not stored on the server or in logs. Enforced by Req 3.10 (no `console.*` of form fields; no error messages containing submitted content). Vercel Function Logs retain captured output for up to 1 day on Hobby tier; Req 3.10 is the mechanism that keeps submitted content out of those logs in the first place.
- **Secrets in env only**: Resend API key, Resend base URL, `from` address, and `to` address all live in Vercel environment variables.
- **Email alias in public source**: `siteConfig.links.email` is plaintext in the public repo (Req 2.7). `react-obfuscate` protects the rendered page HTML only; it does not protect git history or GitHub code search. The accepted defense is per-address filtering at the mail provider for the dedicated alias (e.g. `hello@matthew-field.ca` gets its own filter rules distinct from a personal address).
- **CSP hardening in this spec's scope**: This spec SHALL add a `form-action 'self'` directive to the production CSP in `next.config.ts`. CSP Level 3 does not inherit `form-action` from `default-src`, so without this directive the form submission destination is not CSP-restricted in modern browsers. The directive's value is **defense-in-depth against a future regression to native `<form>` submission**: today the form submits via JS (`fetch()` after `event.preventDefault()`), which goes through CSP `connect-src` rather than `form-action` — browsers only evaluate `form-action` for native form-navigation submissions where `preventDefault` is not called. If the JS handler is later removed or the form is changed to native submission, the directive ensures the destination remains restricted to same-origin without further code changes.
- **CSP compliance**: The contact form and obfuscation components SHALL NOT require further loosening the CSP. Verified by a Playwright test case that:
    - Registers a `securitypolicyviolation` event listener on `document` via `page.addInitScript(...)` BEFORE any page script runs (a listener attached via `page.evaluate` after navigation misses the inline-hydration-script phase).
    - Runs one pass against `/contact` under `Content-Security-Policy-Report-Only` matching production, clicking the obfuscated email to trigger the runtime decode AND submitting the form to the mock Resend server (Req 3.13's sidecar). Note: the JS-submit path exercises `connect-src 'self'`, NOT `form-action 'self'`. The smoke test does not actively exercise `form-action` in the JS-submit path; the directive is declared for the regression-protection rationale above.
    - Runs a second pass with the CSP injected as enforcing (via `page.setExtraHTTPHeaders`), re-running both the click-to-reveal and the form submission, asserting no errors are thrown and no resources blocked.
    - Asserts zero CSP violations across both passes.
- **`reply-to` is attacker-controlled**: Documented in Req 3.12. No verification; Matthew treats inbound senders as unverified.
- **IDN email not supported**: zod `.email()` rejects internationalized email addresses (Req 3.5d). This is an accepted limitation; IDN users reach out via LinkedIn or the obfuscated email.

### Reliability

- **Graceful Resend failure**: Resend outages show a clear, retryable error with form values intact AND an inline LinkedIn CTA (Req 4.4); the rest of the site continues to work.
- **CI smoke coverage**: The Playwright contact-form smoke test (Req 3.13) runs on every PR and blocks merge on failure. Resend is mocked via `RESEND_BASE_URL` pointing at a local sidecar server; real Resend contract drift is not covered (deferred).
- **Vercel function cap vs Resend timeout**: Resend client timeout is 9s (Req 3.8), strictly less than the Vercel Hobby 10s function cap, so the error-response path has a ~1s budget on warm invocations. **Cold-start caveat**: Vercel Hobby cold-start adds ~200–500ms before the handler executes, plus ~100–200ms of Node module-init for the Resend SDK + zod + route handler imports. On a cold-start invocation the Resend timeout fires at 9s relative to handler start, by which point wall-clock time may be ~9.3–9.7s; the error-response budget collapses to ~300ms or less. If the response cannot ship within the remaining budget, Vercel kills the function and emits 504 — already handled by Req 4.4's client error path. The "1s error budget" is therefore a warm-path approximation, not a guaranteed envelope; cold-path overruns surface as 504 rather than the structured 503 of Req 3.8.

### Usability

- **Mobile responsive**: Profile page, contact section, and `/contact` adapt gracefully from mobile to desktop. Name and email fields render side-by-side at `sm:` breakpoint (640px) and above; below `sm:` they stack vertically. Tap targets meet 44×44 CSS px (Req 4.11). Text scales with user settings.
- **Theme parity**: All pages and components render correctly in both light and dark themes with no contrast or styling regressions (Req 4.9, enforced by Req 4.10's two-theme axe pass).
- **Reduced-motion respect**: Scroll-into-view (Req 4.2) and loading indicator (Req 4.6) both honor `prefers-reduced-motion: reduce`.
- **No-JS fallback is explicit, not implied**: The LinkedIn link and GitHub link are server-rendered and work without JavaScript. The obfuscated email requires JS to reveal — this is deliberate (bot protection); no-JS users see a non-interactive label. The contact form itself requires JS. This is an accepted tradeoff for spam protection on the primary funnel.

### Observability (reserved, not wired)

- The contact form SHALL emit a named client-side event (a `CustomEvent` on `document` or an analytics-function call with a fixed identifier `contact_submit_success`) on successful submission, so a future analytics spec can subscribe without re-instrumenting the form. The specific analytics provider is out of scope for this spec. Server-side logging of successful submissions, Resend webhook handlers, and end-to-end delivery heartbeats are all out of scope (future work if/when they become warranted).
