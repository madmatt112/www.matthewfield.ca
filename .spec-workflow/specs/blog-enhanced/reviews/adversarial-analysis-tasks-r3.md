## Attack 1 — Task 17.5's "preview-route infrastructure" is a hidden multi-task lumped into a CSS-carve checkbox

v3 introduced Task 17.5 to (a) carve `globals.css` into nine per-component `@import` slice files AND (b) build the preview-route infrastructure at `src/app/(site)/blog/__component-preview/[name]/page.tsx` AND (c) build a `registry.ts` with nine placeholder entries AND (d) wire the `BLOG_INCLUDE_DRAFTS=1`-gated 404 behavior. This is the **same v1 antipattern v2 attacked**: one task with multiple distinct review surfaces under one checkbox.

- Challenge the claim that 17.5 is one task. The CSS-carve and the preview-route infrastructure are independent deliverables with independent failure modes. A CSS-carve regression looks like a blank page in dev; a preview-route regression looks like a 404 in CI. The reviewer cannot pre-declare what "done" looks like — there is no single Playwright smoke that exercises both. **Split into 17.5a (CSS slice carve + nine empty `@import`s) and 17.5b (preview-route + registry infrastructure).** **Novel.**
- Stress-test the "registry placeholder" mechanism. Each 18.x sub-task "swaps its registry entry from placeholder to its real component." Nine parallel sub-tasks editing the SAME `registry.ts` file in parallel is the **EXACT SAME merge-conflict factory** v3 attacked v2 for. v3 fixed the `globals.css` parallel-edit by carving into nine files; it then re-introduced the same antipattern in `registry.ts`. Either carve `registry.ts` into nine per-component re-exports OR re-declare 18.1–18.9 as strictly sequential. **Compounding** v2 attack 2.
- Challenge the `BLOG_INCLUDE_DRAFTS=1` gating. The task says preview-route "exits 404 otherwise via the existing draft-leak guard pattern from blog-core Req 7.12." But the per-component Playwright smokes in 18.1–18.8 must run against this route — meaning the Playwright test runner must set `BLOG_INCLUDE_DRAFTS=1`. Where? Task 35 extends the project glob but does NOT set the env var. The existing `pnpm test:e2e` step in ci.yml (inherited from blog-core) may or may not set `BLOG_INCLUDE_DRAFTS=1` — design didn't pin and Task 35 doesn't pin. **Per-component smokes will 404 in CI unless the env wiring is explicitly added.** **Novel.**
- Stress-test the "slice files start empty" claim. If 17.5 lands with nine empty `.css` slice files and a globals.css with nine `@import`s, then between 17.5 landing and 18.1–18.8 landing, the site has nine `@import` statements to empty files. PostCSS / Tailwind / the Next.js build will tolerate this, but the per-component theme tokens from blog-core (if any existed inline in globals.css) are now MISSING until 18.x lands. v3 admits "likely empty starting state — blog-core's globals.css has theme tokens at the top level, not per-component slices" — but "likely" is a hedge; if any blog-core inline component CSS exists, it disappears at 17.5-time and re-appears piecemeal at 18.x-time. **No mechanical verification that 17.5 is visually neutral.** **Novel.**
- Challenge the success criterion: "navigating to `/blog/__component-preview/series-badge` under `BLOG_INCLUDE_DRAFTS=1` shows the placeholder stub." Fine — but 18.1's success criterion ALSO depends on this route resolving. If 17.5 ships with the route returning a placeholder for `series-badge`, 18.1's Playwright smoke navigating to `/blog/__component-preview/series-badge` will see the placeholder (NOT the real component) until 18.1 swaps the registry entry. The order WITHIN 18.1 (component file first, then registry swap, then Playwright test) is the implementer's responsibility, undocumented. **Novel.**

## Attack 5 — Task 38's mechanical SHA gate has the wrong reference baseline

v3 replaced v2's "OR document the drift" escape hatch with a strict mechanical gate: `LIGHTHOUSE_BASELINE_SHA.txt` must equal `S_current = git merge-base main HEAD`. If they differ, the task FAILS and the implementer must either re-run Task 36 or rebase. Good — but the SHA being compared is wrong.

- Challenge the `git merge-base main HEAD` computation. The merge-base is the common ancestor of `main` and the current branch — i.e. the SHA where the spec branch diverged from main. This is NOT "the most recent commit on main reachable from this branch." If main has advanced 30 commits since the spec branch diverged, the merge-base remains the old SHA. The implementer's understanding may differ from the script's computation. v3 says "the most recent commit on `main` reachable from this branch — the SHA Task 38 is implicitly evaluating against" — that's an INCORRECT description of `git merge-base main HEAD`. Either the description is wrong (and `S_current` is older than expected) or the command is wrong (and should be `git rev-parse origin/main`). **Novel.**
- Stress-test the "rebase the spec branch onto S_baseline" remediation. If `S_baseline` is OLDER than the current main, rebasing onto S_baseline rewinds the spec branch — losing any main commits the spec branch has merged. This is data loss for the spec PR. The task offers this as one of two remediations alongside re-measuring; the re-measurement path is the only safe one. **The remediation menu includes a destructive option presented as equivalent.** **Novel.**
- Challenge the median-of-3 statistical methodology (re-examined). v3 confirms `lhci autorun --collect.numberOfRuns=3 --upload.numberOfRuns=3`. v2 review's per-URL retry concern remains: "all six URLs MUST pass ≥90 across performance/a11y/best-practices/SEO (median across 3 runs)" — if ONE URL's median dips to 89 on one category, the whole gate fails. The failure space is `4 categories × 6 URLs × 3 runs = 72 measurements`. There is no per-category retry, no per-URL relax. **Recurring** v2 attack 5 third bullet.
- Stress-test the `_Depends on:` correction. v3 now includes 23.1, 23.2, 23.3 in Task 38's `_Depends on:`. Verified — fixed. **Accepted (v3 closed v2 attack 5 first bullet).**
- Challenge the verifier-suite extension. v3 says Task 25 extends `scripts/verify-task-dependencies.mjs` for decimal IDs with regex `/^- \[[ x]\] (\d+(?:\.\d+[a-z]?)?)\. /`. Decimal-with-optional-letter-suffix captures `6.4`, `6.45`, `18.7` — but `6.45` is a TWO-digit decimal (`.45`), the regex `\.\d+` matches one OR MORE digits, so it captures fine. But `6.45` is semantically a NEW task ID created by v3 to slot AFTER 6.4 and BEFORE 6.5 — the convention "decimal-as-sub-ID" breaks down (6.45 > 6.5 numerically but < 6.5 textually only because `4 < 5`). The ID `6.45` is a string-sort hack that confuses readers and breaks downstream tooling that sorts numerically. **Use `6.4.1` or `6.4-impl` instead.** **Novel.**

## Top 5 risks / gaps

1. **Task 17.5's `registry.ts` is the new merge-conflict factory**. v3 fixed `globals.css` parallel edits by carving into nine slice files; it then introduced a SINGLE `registry.ts` that nine parallel sub-tasks edit. Concrete failure: two implementers branch off 18 in parallel, both edit `registry.ts` to swap their placeholder, the second merge conflicts; the resolver eyeballs the merge and silently loses a registry swap; one component never gets its preview-route binding; that 18.x's Playwright smoke returns the placeholder instead of the real component and the assertion silently passes (placeholder may match enough basic theme-parity checks). **(Attack 1 — Compounding v2 attack 2)**

2. **Task 23.1's `_Depends on:` does NOT include Task 35 despite v3's revision-history claim that it does**. Result: Task 35 (the Playwright-glob extension that wires the per-component smokes into CI) can land AFTER 23.1; in the interval, 23.1's draft-PR verification runs the existing `pnpm test:e2e` step WITHOUT picking up the nine new tests — the success criterion silently passes against an incomplete test surface. The v3 author SAID the fix landed but the artifact does NOT reflect it. **(Attack 6 — Novel)**

3. **Task 38's `git merge-base main HEAD` baseline-SHA description is wrong**. The merge-base is the divergence point, NOT "the most recent commit on main reachable from this branch." If the spec branch has merged in 30 main commits since divergence, the merge-base SHA is unchanged but the spec branch is effectively measuring 30 commits past the baseline. The mechanical gate THEN passes (SHA matches) — but the underlying assumption (Lighthouse measured against the same state) is violated. The v2 escape-hatch removal is a regression in disguise: the gate now passes silently where v2 documented the drift. **(Attack 5 — Novel; partial Recurring of v2 attack 5)**

4. **Task 6.45 retains the v2 implementer-cognitive-judgment problem**. v3 split 6.4 (log-only spike) and 6.45 (implementation), but 6.45 itself bifurcates into HOOK and SCRIPT review surfaces. There is no `verify-chosen-path.mjs` asserting 6.45's diff aligns with 6.4's logged `CHOSEN_PATH`. Concrete failure: 6.4 logs `CHOSEN_PATH: HOOK`; implementer of 6.45 reads ambiguous Velite docs, decides hook won't work, ships SCRIPT branch; reviewer reads PR diff (new mjs file + scripts.build edit) and sees a coherent SCRIPT-branch PR; mismatch with 6.4's log goes undetected; ci.yml + verifier expectations may diverge. **(Attack 2 — Compounding v2 attack 1, Recurring on error-surface timing)**

5. **Task 25's `BLOG_ENHANCED_CI_LITERALS_REQUIRED` flag has no meta-gate ensuring it stays on**. v3 says Task 23.3 sets it to `=1` in the verifier step's env; nothing prevents a future PR from removing the env line. The verifier itself doesn't enforce "I must be invoked with the flag on." Concrete failure: six months after blog-enhanced ships, a developer doing CI workflow refactor accidentally drops the env line; verifier reverts to default-off; the new literal checks are bypassed; a step removal regression passes CI silently. **(Attack 3 — Novel)**

## Top 3 conclusions to challenge or reverse

1. **Reverse: Task 17.5 must be split into 17.5a (CSS-slice carve) and 17.5b (preview-route + registry infrastructure), AND `registry.ts` must be carved into per-component re-exports.** The current shape repeats the v2 antipattern that v3 fixed for globals.css — single-file parallel edits across nine sub-tasks. The correct shape: each 18.x sub-task owns BOTH its slice file AND its registry entry file (e.g. `registry/series-badge.ts`), with a `registry/index.ts` aggregator that needs only ONE serialized edit during 17.5b.
   - Reasoning: v3's own logic for carving globals.css applies identically to registry.ts. The author noticed the file-coupling problem in CSS but not in the registry they introduced to solve it.

2. **Reverse: the `BLOG_ENHANCED_CI_LITERALS_REQUIRED` transitional flag must be replaced by atomic landing of 25 + 23.1 + 23.2 + 23.3 in a single PR**, OR the flag must default-ON with a one-line escape for the 23.x landing window (so future regressions can't silently re-disable the gate). The current shape defends against the v2 CI-red-line interval but introduces a new long-tail risk: silent gate-disabling. v2's atomic-PR alternative (sacrificing the split) is the simpler, more durable choice.
   - Reasoning: A transitional gate becomes a permanent gate once "transitional" no longer applies; there is no mechanism to retire it. Atomic landing of a four-piece PR is a one-time inconvenience; a forever-fragile flag is a perpetual risk.

3. **Reverse: rename Task 6.45 to 6.4.1 (or `6.4-impl`) AND split into 6.4.1-hook and 6.4.1-script as alternative entries selected by 6.4's `CHOSEN_PATH`.** v3's `6.45` ID is a string-sort hack (6.45 < 6.5 textually, but > 6.5 numerically). The split into one task with two branches retains the v2 antipattern — the reviewer can't pre-declare the diff shape. Two alternative tasks (only one of which is implemented) eliminate the ambiguity.
   - Reasoning: Decimal IDs are sorted lexically by most tooling; `6.4 < 6.45 < 6.5` only holds in string-sort with leading-zero padding (`6.4`, `6.45`, `6.50`), which the spec doesn't use. Use `6.4.1` to enforce hierarchy and avoid the sort-order bear trap.
