# Adversarial Analysis — blog-enhanced/requirements.md (v1)

Primary attack surface: **completeness, ambiguity, scope**. Sections targeted are real headings/clauses from the document. Each bullet is a directive grounded in the document's concrete content.

---

## Section A — Requirement 1 (Pagefind search) crawl topology & promotion path

This is the largest, riskiest requirement in the spec and it leans on assumptions that the document itself flags as Design-to-pin.

- Challenge the claim in Req 1.2 that the crawl target is `http://localhost:3013` matching `package.json`'s `start` script. The spec does not specify what happens when the configured Next.js port is changed (env var? hardcoded fallback?), nor does it forbid drift between the `start` script and the crawl script. Define the single source of truth for the port and require both consumers to read it from there, or this becomes a "works on the dev's laptop, fails in CI when someone touches package.json" trap.
- Stress-test Req 1.2's `next build → next start → wait → pagefind` sequence against the Vercel-hosted production deploy. The NFR section (lines 296–297) belatedly raises this as "Design pins (a) or (b)" but Req 1 itself assumes a `public/pagefind/` directory will be present at request time on Vercel. If Design picks option (b) — GitHub Actions builds & uploads — then Req 1.2's CI step is no longer "produces the index used in production"; the entire chain of integrity assertions (Req 1.12 draft-leak check, Req 10.9 manifest artifact) shifts meaning. Force this decision into Requirements before locking acceptance criteria that presume option (a).
- Attack the "promote to blocking" mechanism in Req 1.5 and Req 13.1. The acceptance criterion is "3+ consecutive green deploys" tracked in a followup-queue entry, with a deadline that can be extended "with a written reason." There is no upper bound on extensions, no escalation path, and no test that fails if the deadline lapses. This is the exact "deadline passes silently and the gap is never closed" failure that Req 13.1 itself names — and the proposed mitigation (write a reason) does not actually mitigate it. Either codify a hard cutoff (auto-promote, auto-fail CI, auto-open issue after N days) or admit `continue-on-error: true` is permanent.
- Challenge Req 1.6's claim that `<article>` carrying `data-pagefind-body` indexes "the post body, title, headings, and tags as a single searchable record." The `<TagChip />` `<ul>` on the post page is at `:91-99` and Req 1.6 explicitly says it carries `data-pagefind-ignore="all"` — which contradicts "tags ... as a single searchable record." Either tags are indexed via the ignored UL (impossible — ignore wins) or via the `data-pagefind-meta="tags"` attribute on `<article>` (Req 1.7), but the two clauses are written as if both happen. Pick one mechanism and remove the contradictory clause.
- Stress-test Req 1.12's draft-leak smoke check. The check parses `content/posts/*.mdx` filenames and derives slugs "either (a) by reading the post's `slug` frontmatter override if present, or (b) by stripping the `.mdx` extension." But the requirement is also explicit that it must NOT re-read Velite's output. So the smoke check now needs an MDX frontmatter parser that exactly mirrors Velite's slug derivation logic — which is itself a duplicated implementation that can drift. The "unit-tested helper" mitigation only catches drift within the helper, not between the helper and Velite. Require the slug-derivation helper to be the same module Velite imports, or accept that this check is permanently fragile.

## Section B — Requirement 4 (Related posts) algorithm assumptions

The algorithm is given as "simple is fine" — interrogate whether the simplicity is actually correct.

- Challenge Req 4.1's claim that tags and categories are "equally weighted at launch (simpler)." The site's categories are coarser than tags (typically 1 category per post, multiple tags), so weighting them equally means a single-category match scores the same as a single-tag match, despite carrying far less topical signal. With ~5 launch posts (per NFR Performance, line 303) that all share a small category set, the related rail will be dominated by category-only matches that are not actually related. Stress-test the algorithm on the actual fixture roster (which has every fixture in category `fixture`) and reconsider.
- Stress-test Req 4.2's "cross-series exclusion BEFORE scoring." This deliberately leaves the rail empty next to the navigator — but the navigator only renders when 2+ series members exist (Req 2.6). If a post is part of a series-of-1, the navigator does NOT render, so the cross-series exclusion suppresses sibling-series candidates without compensation. Re-derive the exclusion rule as "exclude only when navigator will render" or accept the dead-zone.
- Challenge the assumption embedded in Req 4.6 that "a reader doesn't need to know the absence" of related posts. This is a UX assertion, not a requirement — and it's untestable. Either remove the rationale or replace it with a falsifiable criterion (e.g., "the rail's empty-render is preferred over an explicit empty state per user-research finding X" — citing nothing).
- Stress-test Req 4.4's PostMeta extension. The requirement says "Design SHALL pin whether to add `description` to `PostMeta` or define a new `RelatedPostMeta` type to avoid breaking callers." This is the spec deferring a typed-API decision to Design — but the decision determines the public shape of `src/lib/blog.ts`. Either commit to the type contract now or admit that downstream consumers (blog-core helpers, anything importing `PostMeta`) may need updates.

## Section C — Requirement 7 (TOC) slug-parity claim

The Req 7.3 "slug-derivation parity with rehype-slug" is presented as bulletproof. Attack it.

- Challenge the assumption in Req 7.3 that importing `github-slugger` directly into `extractToc()` "replicates `rehype-slug`'s per-document scoping." `rehype-slug` may transform heading text (e.g., stripping certain HTML, normalizing whitespace, handling embedded MDX expressions in headings) BEFORE passing to the slugger. A heading like `## Setting up <Tool />` will produce different inputs to the slugger if extractToc walks MDAST nodes (text-only) vs. what rehype-slug sees post-HAST-stringification. The Req 7.4 fixture test catches this only for the headings the fixture contains — it does not establish a universal contract.
- Stress-test Req 7.2's "h2 and h3 only" decision against the existing posts. The spec contains no inventory of current heading depth usage. If existing posts use h4+ for substructure, the TOC will silently flatten that information. Either audit the corpus and document the rationale, or make depth configurable.
- Attack Req 7.6's "in-flow TOC vs. sticky rail — Design SHALL pin which is implemented for launch." This is a requirement that does not specify behavior. The acceptance criteria for scroll-spy (Req 7.7) ONLY apply if Design picks the sticky-rail variant. If Design picks in-flow, the entire scroll-spy requirement vanishes from the launch deliverable. A requirements doc that has acceptance criteria contingent on a Design choice is not a requirements doc — pick the launch variant now.
- Challenge Req 7.9's "TOC ignored by Pagefind." The rationale ("a reader searching for 'Installation' finds the post twice") is correct for the TOC, but the same logic applies to the heading text inside the body — `data-pagefind-body` indexes the headings AND the body text below them. The Pagefind result already contains both. The deduplication is not addressed; the requirement only handles the cosmetic case of the TOC list.

## Section D — Section "Non-Functional Requirements" — Vercel deployment ambiguity

The NFR section drops the largest architectural unknown of the spec into a passing aside.

- Challenge the placement of the Vercel deployment topology decision in NFR/Code Architecture (lines 296–297). This is a topology decision, not an architecture-modularity decision. It determines whether the Pagefind index is built on GitHub Actions or on Vercel, which in turn changes Req 1.2, Req 1.4 (continue-on-error semantics), Req 1.12 (smoke check location), and Req 12 (CI topology). Promote this to a top-level requirement and resolve it before any acceptance criterion that assumes option (a).
- Stress-test the NFR claim that "the default expectation absent a Design decision is (a) — extend Vercel's build command." Vercel's build environment may not have a working `next start` + crawl loop (build environments are typically not allowed to bind to ports for long-running processes). The default expectation is therefore likely to fail when Design implements it. Verify Vercel's build container behavior before defaulting to (a).
- Challenge the assumption that `public/pagefind/` being gitignored is compatible with Vercel deploys. Vercel deploys the `public/` directory as-is from the build output; if the directory is gitignored AND Vercel runs `next build` without running `pnpm build:search`, the deployed site has no index. The NFR mentions this as a Design question, but the Reliability NFR (line 323) already claims "the site deploys with a search box that fails to open (or opens an empty index) rather than blocking the deploy entirely" — which presumes the index exists. The two NFR clauses are mutually exclusive on the most-likely deployment failure mode.

## Section E — Section "Fixture Roster" — content reuse and risk

- Stress-test the table's row for `fixture-toc.mdx` which says "Body MAY share prose with `fixture-reading-time` to keep maintenance burden low." This is a content-coupling decision being made at the requirements layer. If `fixture-reading-time` is edited to change word count for blog-core reading-time tests, `fixture-toc`'s heading count and TOC structure may also change, breaking blog-enhanced tests. Forbid the sharing or pin the prose at a fixed snapshot.
- Challenge the assumption that all fixtures use `draft: true` (preamble to Fixture Roster, line 347). Req 1.12's draft-leak smoke check derives its expected-absent set from `content/posts/*.mdx` files with `draft: true`. The `fixture-search.mdx` post is meant to be searchable in the keyboard test (Req 10.3) — but if it is draft, it is excluded from CI Build 2's index. Either the search keyboard test runs against a non-production index (Build 1 with BLOG_INCLUDE_DRAFTS=1) — in which case Req 1.3's "index not generated on Build 1" contradicts it — or `fixture-search` is published, in which case the "all fixtures draft" preamble is wrong.
- Stress-test the related-posts fixture (Req 4 + fixture-related-a/b). The fixtures share tag `related-test` and category `fixture`. Under Req 4.1's algorithm: score = |tags ∩| + |categories ∩| = 2 (both fixture and related-test) + 1 (fixture) = 3. But ALL fixtures share category `fixture`, so EVERY fixture post will also score 1 against fixture-related-a. The related rail on fixture-related-a will surface fixture-toc, fixture-footnotes, fixture-series-1, fixture-series-2, and fixture-search — none of which are actually related. The fixture roster is not an isolated test bed; it pollutes itself.

## Top 5 risks/gaps

1. **Vercel deployment topology unresolved** (Section D). The single decision that controls whether the production search index actually exists is buried in NFR Architecture as a Design defer. Req 1, Req 12, and Reliability NFR all presume option (a) without verification that option (a) is feasible. **Failure mode: site deploys with empty/missing search index, Pagefind UI loads but returns zero results for every query, and CI does not catch it because CI builds the index on a different topology.**
2. **Draft-leak smoke check has duplicated slug logic** (Section A, Req 1.12). The check derives slugs from filenames separately from Velite. The proposed mitigation (unit tests on the helper) only checks the helper's internal consistency, not parity with Velite's `s.path()` transform. **Failure mode: a future Velite version changes slug derivation (e.g., supports `_index.mdx`), helper does not, smoke check passes a draft into production.**
3. **Fixture roster has cross-contamination via shared category** (Section E, Req 4). Every fixture has category `fixture`, so the related-posts algorithm pollutes every fixture's rail with every other fixture. The related-posts axe test (Req 10.1) may pass because axe doesn't check semantic relevance, but the rail will visibly contain unrelated content during local dev. **Failure mode: developer sees the rail showing 5 unrelated fixtures and concludes the algorithm is broken when it is in fact working as specified.**
4. **Promotion-to-blocking has no enforcement** (Section A, Req 1.5 + 13.1). The "extend the deadline with a written reason" escape hatch has no cap. **Failure mode: `continue-on-error: true` becomes permanent, draft-leak smoke check becomes the only blocking gate, and a future Pagefind regression silently ships a broken search to users for an unbounded period.**
5. **TOC slug-parity test scope is insufficient** (Section C, Req 7.3-7.4). The test covers fixture-code's duplicate headings but does not exercise headings with embedded MDX expressions, headings with HTML, or any non-trivial transformation that `rehype-slug` may apply after MDAST→HAST. **Failure mode: a post with `## Setting up <Tool />` produces a TOC link to `#setting-up-tool` while the rendered heading has id `#setting-up`, and the link is silently broken in production.**

## Top 3 conclusions to challenge or reverse

1. **Reverse: "the Vercel deployment mechanism is an NFR Architecture detail."** It is a topology requirement that controls the validity of Req 1, 10, 12, and the entire Reliability NFR. Promote it to Requirement 1.0 or Requirement 0, resolve before sign-off. Reasoning: every other acceptance criterion that references "the production index" is undefined until this is pinned, and the default option (a) is not verified feasible on Vercel's build container.
2. **Reverse: "all fixtures share `category: fixture`."** Either give each fixture its own category (fixture-toc-cat, fixture-related-cat, etc.) or accept that the related-posts rail is untestable on fixtures. Reasoning: the spec's own algorithm guarantees pollution; the fixture roster cannot serve as ground truth for a feature it is structurally incompatible with.
3. **Reverse: "promotion to blocking is a one-line follow-up after 3+ green deploys."** The mechanism has no enforcement. Either ship as blocking from day one (acceptable: blog-core already runs CI without Pagefind, so the failure mode is "CI fails because Pagefind is flaky" — recoverable by reverting), or accept that this requirement is informational, not actionable. Reasoning: a deadline that can be extended without cap is not a deadline; it is a polite suggestion.

## What's missing — work to do before acting

- **A Vercel build-environment investigation**: confirm whether `next start` + Pagefind crawl can run in Vercel's build container, or document the alternative (option b) with concrete CI deploy commands. Without this, Req 1 is implementation-impossible on option (a).
- **A fixture-category audit**: design fixtures so the related-posts algorithm produces predictable, isolated results. Today's roster guarantees cross-pollination.
- **A pinned `series` vs. `tags`/`categories` policy on series-name slugging**: Req 3.1 deliberately diverges from blog-core's kebab-case convention for series names. The spec does not address what happens if a future series-index route (Req 2.9 explicitly out of scope) needs a URL slug derived from the human-readable series name. Document the forward-compatibility cost of the divergence or unify the conventions.
- **An audit of the existing post corpus for heading depth, MDX-in-headings, and HTML-in-headings**: the TOC requirement (Req 7) asserts h2/h3-only and slug-parity without verifying the corpus matches. A 30-minute grep over `content/posts/` would falsify or confirm both assumptions.
- **A typed-API decision on `PostMeta` extension** (Req 4.4): commit to either extending `PostMeta` or adding `RelatedPostMeta` before Design. The choice affects every existing consumer of `PostMeta` in `src/lib/blog.ts` and any test that mocks the shape.
- **Resolution of the Req 1.6 contradiction** between "indexes ... tags as a single searchable record" and the explicit `data-pagefind-ignore="all"` on the tag UL. Pick one mechanism for tag indexing and remove the other clause.
- **A concrete promotion-enforcement mechanism** for Req 1.5 — either a scheduled workflow that auto-opens an issue at N days, or auto-promotion via a follow-up PR, or admission that the gate is permanent. The current text is aspirational and self-admittedly so.
