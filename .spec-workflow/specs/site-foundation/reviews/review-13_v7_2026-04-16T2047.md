### WARNING: Spike-discovered typography breakage means Button's font-family is silently broken — no test covers it
- **File:** e2e/tests/playground-isolation.test.ts:191
- **Issue:** spike-summary.txt:21-47 documents that the @layer playground re-declarations of font-family / font-size / line-height / color on .playground-container are shadowed by the unlayered `all: initial` on the same rule block, so the container (and shadcn Button by inheritance) renders with Chromium's initial 'Times New Roman' instead of the intended ui-sans-serif stack. Test 2 reads cs.fontSize=14px (which comes from the text-sm utility, not from inheritance), but never reads cs.fontFamily — so the actual fontFamily="Times New Roman" on the Button is invisible to the test suite. R11 AC3's plain-language reading ('shadcn components render correctly using re-established tokens') is therefore violated for typography, but the violation is hidden inside spike-summary's narrative rather than failing an assertion. At minimum add cs.fontFamily to Test 2's reads with a TODO/skipped expectation that surfaces the bug, so a future fix to playground.css unambiguously flips that test from observed-broken to passing.
- **Task Requirement:** R11 AC3
- **Classification:** novel

### WARNING: EXPECTED_INHERITED_FONT_FAMILY pins Test 6 to a Chromium-specific serif default
- **File:** e2e/tests/playground-isolation.test.ts:84
- **Issue:** Test 6 (e2e/tests/playground-isolation.test.ts:317-339) is the actual R11 AC2 anchor and asserts cs.fontFamily === '"Times New Roman"'. That literal is the value the bundled Playwright Chromium happens to return for the CSS initial font-family on this CI environment, but Chromium's per-platform font preferences (Linux distro, font packages installed in the test container, Chromium version bumps via Playwright updates) can shift the default serif to Liberation Serif / DejaVu Serif / etc. The assertion will then fail with a confusing diff that looks like a regression in the playground container instead of a font-availability change. Prefer asserting the *negation* — fontFamily must NOT include the host site's Geist variable name or any sans-serif family that could only have come from inheritance through the site cascade — or read the host's font-family from <html> first and assert the descendant differs from it. Either form makes the AC2 isolation claim without depending on a specific browser's initial-value serialization.
- **Task Requirement:** R11 AC2
- **Classification:** novel

### INFO: Dev-mode 'parity' run was scoped manually; reporter output is not direct evidence of suite parity

- **Issue:** spike-summary.txt:107-114 explains 'The dev run uses the single checked-in spike suite; smoke.test.ts is scoped to the production run because it asserts the default Next.js landing title.' The dev block lists 6 tests (no smoke), the production block lists 7 (with smoke). The 'No bundler divergence on this codebase' conclusion at line 327 is fair given that both runs PASS the same checked-in assertions, but the reporter outputs do not directly compare computed values across bundlers (R11 AC5's literal text). To make the parity claim auditable, also dump the actual computed values from one or two representative reads under each bundler so task 14 can diff the readouts rather than infer parity from twin green checks.

### INFO: Dark-mode harness pre-empts a ThemeProvider race that doesn't exist yet — assertion still future-dated
- **File:** e2e/tests/playground-isolation.test.ts:138
- **Issue:** applyDarkMode (e2e/tests/playground-isolation.test.ts:138-156) sets localStorage 'theme'='dark' AND adds .dark via init script, with the comment that this 'survives a future next-themes ThemeProvider integration'. There is no ThemeProvider in this build (task 16 has not landed), so the localStorage write is dead code today and the only mechanism that actually changes the theme is documentElement.classList.add. The defense against the hypothetical race is plausible but unverified — when task 16 lands, the next-themes hydration may still revert/race the manual class addition before the assertion runs. v6 already flagged the brittleness; this iteration adds defensive code but cannot demonstrate it survives the integration. Either add a follow-up task to re-audit Tests 4/5 immediately after task 16 ships, or replace the manual class manipulation with page.emulateMedia({ colorScheme: 'dark' }) plus a wait on the rendered class so the assertion is decoupled from the host's theme strategy entirely.
- **Task Requirement:** R11 AC5
- **Classification:** compounding
