# Implementation Log: Task 17.1

**Summary:** Added focus-management `useEffect` to `<ContactForm />` layered on top of task 17's state machine. Keyed on `[attemptId, state.kind]` so same-kind transitions (e.g. validation-error → validation-error on a second failed attempt) re-fire correctly via the always-changing attemptId. Three transitions implemented: on `success`, focus the success `<h2 ref={successHeadingRef} tabIndex={-1}>`; on `server-error`, focus the `role="status"` region via `serverErrorRegionRef`; on `validation-error`, query the form (`formRef`) for the first invalid input/textarea in field order (name → email → message) and call `.focus()`. The effect early-returns when `attemptId === 0` so the initial mount does not steal focus.

Refs added: `formRef: HTMLFormElement`, `successHeadingRef: HTMLHeadingElement`, `serverErrorRegionRef: HTMLDivElement`. The form element, the success `<h2>`, and the server-error `<div role="status">` container all received the corresponding `ref={...}` attribute. The placeholder `void attemptId;` from task 17 was removed.

The lint disable on the exhaustive-deps check is intentional: `state.errors` is read inside the effect via closure, but keying on the full `state` value would re-fire on every render due to the discriminated-union object identity churn. The design explicitly mandates `[attemptId, state.kind]`; attemptId's monotonic increment guarantees the effect re-runs on every submit, picking up the latest closure (including any new `state.errors`).

`pnpm typecheck` clean. `node_modules/.bin/eslint .` exits 0 (`pnpm lint` / `npx eslint` are filtered by the RTK proxy in this shell — direct-binary invocation is the workaround, not a code issue).

Tasks 17.2 (scrollIntoView) and 17.3 (CustomEvent dispatch) remain unimplemented per their separate task boundaries; they will layer onto this same effect.
