# Adversarial Analysis — blog-core/design (v1)

**Reviewer posture:** staff engineer, adversarial. Primary attack surface: feasibility, consistency, edge cases. Findings are framed as directives, grounded in the document's concrete claims.

---

## Attack 1 — The Velite `bodyHtml` pipeline (Components > Velite `posts` collection)

The design pins a dual-pipeline emit (`s.mdx()` body + `s.markdown()` bodyHtml) sharing one rehype array. It then defers most of the load-bearing details to "verified during implementation." That is exactly the spot to break.

- **Challenge the claim that `s.markdown()` exists and accepts the rehype/remark plugin array as designed.** The design cites `node_modules/velite/dist/index.d.ts` exposing `MarkdownOptions` with `remarkPlugins`/`rehypePlugins` and a top-level `markdown?` key on `defineConfig`. The current `velite.config.ts` (the only first-hand evidence in the repo) uses neither `s.markdown()` nor a top-level `markdown` block — it only uses `s.mdx()` and `mdx.rehypePlugins`. **Demand a 10-line proof-of-concept** that runs `s.markdown()` against a representative MDX-ish file in the installed Velite version and emits a string with the rehype plugins actually applied — before any further design weight is placed on this primitive.
- **Stress-test the assumption that the SAME shared plugin instance can be registered under both `mdx.rehypePlugins` and `markdown.rehypePlugins` without cross-pipeline state contamination.** The MDX rehype pipeline runs against a HAST tree that carries JSX-origin nodes and properties; the markdown rehype pipeline runs against a plain HAST tree from `remark-rehype`. `rehype-pretty-code` instantiates and (in some modes) caches a Shiki highlighter inside its plugin closure. The design's "stateless across files" claim is unverifiable from the documentation alone — the cache survives across files **by design** and is what makes Shiki tolerable. The risk is not "wrong output" — it is **non-determinism between builds** when the cache hashes differently on first cold run vs reuse. Demand the design either (a) pin two separate plugin instances (one per pipeline) and accept the cold-start cost twice, or (b) document explicitly what the contract with `rehype-pretty-code`'s internal state actually is.
- **Tear apart the `meta.content` claim in the reading-time transform.** Quote from design.md:113 — "The raw markdown body is available inside the transform via `meta.content` (Velite exposes the original file contents on `meta`)." The current `profile` collection at `velite.config.ts:40-54` uses only `meta.path` and reads file content via `execFileSync('git log …')` — there is zero in-repo precedent that `meta.content` is populated. If `meta` carries only `path`, the transform must `fs.readFileSync(meta.path)` and then re-strip the frontmatter delimiter, reintroducing IO and a frontmatter regex into the schema callback. **Verify against Velite source** before treating this as a free primitive; if absent, the reading-time transform shape changes materially.
- **Challenge the divergence between `mdx.rehypePlugins` and `markdown.rehypePlugins` on capitalized JSX tags.** Req 11.7 (cited by the design) explicitly acknowledges that a hypothetical `<Callout>` in a post body would fail the MDX page compile but **survive** the markdown bodyHtml compile as raw HTML. The Req 3.7 raw-HTML rejection visitor only walks the mdast tree for the reading-time / rejection step — it does NOT run against the `s.markdown()` compile path. The rejection lives inside the `posts` schema `.transform()` callback that fires once per file, **before** either pipeline emits. Verify that the visitor's throw genuinely blocks the bodyHtml emit; if the transform runs in parallel with the schema's primitive resolution, the bodyHtml may be computed and cached before the throw lands.

## Attack 2 — The CDATA-escape strategy (Components > feed.xml route + Req 11.10)

This is the single most dangerous claim in the document: that `]]>` → `]]]]><![CDATA[>` substitution inside the Velite `bodyHtml` transform produces a correct, parser-portable feed.

- **Challenge the claim that the `feed` package "wraps the already-escaped string in CDATA without further escape."** This is asserted at design.md:179 with no version pin, no API citation, and no test. The `feed` npm package's `addItem({ content })` behavior on CDATA wrapping has changed between major versions. Several common configurations XML-escape `<`, `>`, `&` inside `content` unless an explicit option is passed. If escaping fires, the entire `bodyHtml` — `<pre>`, `<code>`, Shiki spans, every inline style — renders in feed readers as literal `&lt;pre&gt;&lt;code&gt;...` text. **Pin the `feed` package version explicitly in this design, and add a concrete test asserting `feed.rss2()` output contains an unescaped `<![CDATA[<pre>` substring** before treating this path as solved.
- **Stress-test the visible-artifact case where `]]>` appears inside displayed code blocks.** A post legitimately demonstrating XML or CDATA contains `]]>` in its rendered `<pre><code>` text. The substitution mutates that text to `]]]]><![CDATA[>`. A conformant XML parser unwraps this back to `]]>` in the CDATA payload, so the reader sees the original. **A non-conformant feed reader that uses regex-grep instead of a real XML parser will display `]]]]><![CDATA[>` to the user inside the rendered code block.** The design hand-waves this as "semantically equivalent in any conformant XML parser" (design.md:360) — that is not the full reader universe. The downside is visible garbage in a small minority of readers; not a launch blocker, but the design should acknowledge it rather than assert correctness.
- **Tear apart the parity test (Req 11.11) interaction with CDATA escaping.** The parity test compares `bodyHtml` against page-rendered HTML for matching `<pre><code>` element presence and "matching Shiki token-class patterns." But `bodyHtml` has been CDATA-mutated; the page HTML has not. If the fixture-code post legitimately contains `]]>` (it should, to exercise this branch), the bodyHtml `<code>` text content diverges from the page `<code>` text content. The test's assertion that elements are "structurally equivalent" needs an explicit carve-out for CDATA-escape artifacts in text content — currently the assertion shape doesn't distinguish element identity from text-node equivalence.

## Attack 3 — The Shiki dual-theme CSS cascade (Components > globals.css additions)

The design pins a CSS cascade as the load-bearing safety mechanism for Req 9.2. Then it admits the selector is tentative.

- **Challenge the entire selector premise** at design.md:264: "Exact selector confirmed during implementation via inspecting a rendered fixture-code page; if the plugin uses different attribute names (`data-line` vs `data-rehype-pretty-code-fragment`) the selectors update accordingly." If `rehype-pretty-code`'s `defaultColor: false` emits inline `style="--shiki-light: …; --shiki-dark: …; color: var(--shiki-light)"` on every span — which is the documented variable-bridge mode — then **inline styles win over external CSS by specificity**. The design's external CSS rules at `html.dark [data-rehype-pretty-code-fragment] code { color: var(--shiki-dark) }` will lose to the per-span inline `color: var(--shiki-light)` set by the plugin. The cascade may need to either (a) override the CSS variable (`--shiki-light: var(--actually-dark)`) rather than the color property, or (b) use `!important`. Either changes the design materially. Demand a working POC before the cascade is treated as designed.
- **Stress-test the `:not(.light):not(.dark)` selector against `next-themes` hydration timing.** Even with `value={{ light: 'light', dark: 'dark' }}` configured, there is a brief window between page hydration and `next-themes` setting the class on `<html>`. During that window, neither class is present and the `@media (prefers-color-scheme: dark)` rule fires. If the user has system-dark + has-toggled-light, the first paint is dark, then re-flows to light when JS runs — a flash-of-wrong-theme. This is the exact class of bug `next-themes` is designed to eliminate via its inline blocking script, but the inline script writes the class before paint **only if** the symmetric-class config is honored end-to-end. Demand the design specify that the blocking script is verified to write the explicit `.light` class, not just `class="" `.
- **Challenge the ThemeProvider "one-line config change" framing.** The change is `attribute="class"` + `value={{ light: 'light', dark: 'dark' }}`. The existing ThemeProvider is shared with the entire site — every other page (profile, contact, home) currently runs without the symmetric `.light` class. A grep for `.dark` CSS selectors elsewhere in the codebase may surface rules that implicitly rely on "no class" meaning "light mode" rather than `.light` meaning "light mode." A symmetric-class config could shift other-page behavior in ways the design does not enumerate. **Audit every `.dark` selector in `src/styles/` and `tailwind.config`** for implicit-light-mode assumptions before treating this as a no-op tweak.

## Attack 4 — Draft-leak surface (Components > getPublishedPosts + scripts/verify-production-build.mjs)

The chokepoint-bypass story is the spec's stated structural guarantee. Several pieces of it don't hold up.

- **Challenge the location of the artifact `scripts/verify-production-build.mjs` reads.** The script "checks absence of the fixture-draft slug from `/blog/index.html`, every `/blog/tags/<tag>/index.html`, …" (design.md:228). For a `force-static` Next.js App-Router page, the rendered HTML lives at `.next/server/app/blog/index.html` (or `.next/server/app/(site)/blog/page.html` depending on route-group handling) — NOT at `public/blog/index.html` and NOT at a flat `/blog/index.html`. The script's described paths are pre-pages-router-era conventions and may not match App Router's emit structure. Similarly, `feed.xml` from a `force-static` route handler does not emit to `public/feed.xml` (Req 7.14b: "no `<item>` with `<link>` containing `/blog/fixture-draft` in the generated `feed.xml`" — design.md:228 then says `public/feed.xml`). **Pin the exact emit paths against an actual `next build` output** before the script is considered designed. If wrong, the script silently passes by globbing zero files.
- **Stress-test the Velite cache interaction across the two CI builds.** Build 1 runs with `BLOG_INCLUDE_DRAFTS=1` and produces `.velite/posts.json` containing every draft. Velite's content cache is keyed by file content hash, not env vars. If Build 2 runs without cleaning `.velite/`, it reads the cached posts array (drafts included) and only the `getPublishedPosts()` filter and the page render gate the output. That filter IS the chokepoint — but the design explicitly justifies the dual-build smoke check on the premise that "a future PR adding a consumer that imports `#site/content.posts` directly would bypass the helper" (requirements.md:197). If Build 2's `.velite/posts.json` contains drafts, that future-PR bypass-class IS present even in current code — any direct import of `#site/content.posts` returns drafts on Build 2 unless `.velite/` is cleaned first. **Pin an explicit `rm -rf .velite/ .next/` step between Build 1 and Build 2** in the design, or the smoke check protects nothing.
- **Tear apart the symmetric throw guards at the production-mode local-dev case.** Guard (b) — `VERCEL_ENV=preview && !BLOG_INCLUDE_DRAFTS` — throws. This fires during `generateStaticParams()`. But Build 2 of CI is invoked locally (or in GH Actions) with `VERCEL_ENV` unset, so neither guard fires; the script alone catches the leak. That is fine on its own, but the design at design.md:343 claims "CI Build 2 also independently fails via `verify-production-build.mjs`" — "independently" is misleading. The guard only fires on Vercel; the script is the only defense in CI. The design should state this honestly.
- **Challenge the assumption that `BLOG_INCLUDE_DRAFTS` is never read at module top-level by any of the four route files.** The design specifies the helper reads at call-time. But `generateStaticParams()` is a top-level function (per Next.js convention), and the route file's module-level imports run before it. If a future implementer adds `const ALL = posts` at the top of `[slug]/page.tsx` for "convenience" and then uses `ALL` in a metadata block while `getPostBySlug` correctly filters, the metadata leaks draft titles. The chokepoint is procedural, not structural. **Demand a lint rule** (or at minimum a CI grep) that fails on direct `#site/content.posts` imports outside `src/lib/blog.ts`.

## Attack 5 — The `rehypeAbsolutizeUrls` visitor and its file location

A small hand-rolled HAST visitor placed outside the structure.md tree, with an asserted statelessness contract.

- **Challenge the placement in `lib/rehype-absolutize-urls.mjs` "outside `src/`" (design.md:116).** structure.md, per the design's own framing, defines the `src/lib/` convention. A new top-level `lib/` directory is invented by this spec with no precedent in the repo. The justification given — "to avoid importing `siteConfig.url` from `src/config/site.ts` inside the velite config" — does not hold: `velite.config.ts` is itself a top-level file and the dependency direction (config → src/) is the actual concern, not the directory layout. Stress-test against the simpler alternative: place the visitor at `velite/rehype-absolutize-urls.mjs` (colocated with the velite config), or inline it in `velite.config.ts` at ~40 LOC. The new `lib/` directory creates a parallel convention that future contributors will have to discover.
- **Stress-test the `process.env.NEXT_PUBLIC_SITE_URL ?? siteConfig.url` fallback at design.md:116.** This runs inside the velite config at build time. `NEXT_PUBLIC_SITE_URL` is not declared anywhere in this design as a wired env var. If it's unset (the default), the fallback to `siteConfig.url` always wins — making the env var inert and the "launch fallback to avoid making the env var build-required" framing meaningless. Demand the design either (a) wire the env var and document its Vercel-scoping, or (b) drop the env-var branch entirely and use `siteConfig.url` directly. Carrying both is dead code that misleads readers.
- **Challenge the "stateless visitor" assertion** at design.md:111. The design promises a code-review verification at implementation time. But the visitor must absolutize URLs against a base URL passed in via factory parameter — that base URL IS closed-over state. The statelessness constraint is satisfied only because the base URL is invariant across files within a single build. If the base URL ever varies per-file (e.g., a future spec wants per-post canonical-domain overrides), the shared-instance pattern silently produces cross-contamination. Document this constraint explicitly rather than burying it in "verified by code review."

## Attack 6 — Reading-time minimum-cost fixtures + the test stub

The fixture roster and the `_neighbors` test design conflict.

- **Tear apart the `getPostNeighbors` test stub.** The design at design.md:142 offers: "a private `_neighbors(posts, slug)` is exported under a `__testing` namespace OR the test mutates env state to control the post array — the chosen approach is a private export for testability without env mutation." The public API `getPostNeighbors(slug)` takes only a slug and internally calls `getPublishedPosts()`. The "private export" is a parallel function with a different signature. This is fine for unit-testing pure logic, but it means **the unit tests do not exercise the actually-shipped path** — they exercise an internal sibling. A regression in the public wrapper (e.g., it forgets to apply the sort key before calling `_neighbors`) would pass the unit tests and ship broken prev/next. Demand at least one integration-style test that calls the public `getPostNeighbors` against env-controlled fixture state.
- **Stress-test the reading-time tolerance test against the three-fixture roster.** Req 6.5 (cited by the design) requires the fixture-reading-time post to contain ≥1000 prose words, both fence flavors, an image with alt text, AND a GFM construct. The design's unit-testing section at design.md:378 specifies `± max(20%, 1 minute)`. With 1000 prose words at 238 wpm, expected reading time is ~4.2 minutes, clamped to integer = 4 minutes. The ±20% bound is ±0.84 min ≈ ±1 min once integer-clamped. Any single sentence added or removed in the fixture (and there will be churn during the spec's iteration) shifts the count enough to fail the test. The "fixture is pinned" framing assumes the fixture never changes — but the same fixture is also the substrate for the bodyHtml-parity test, the no-JS theme test, and the explicit-override theme test. A change to satisfy one test risks failing another. Demand the design split responsibilities across fixtures or freeze fixture-reading-time's prose section under a code-review gate.
- **Challenge the `formatPostDate` decision-logic gap.** The helper returns `{ datetime, display }` but Req 8.2 requires the page to render an "Updated <date>" badge only when `updated > date`. The design lists no helper that returns the comparison decision — the page component must duplicate `new Date(updated) > new Date(date)` logic across the post page header AND the index card. The "single chokepoint" principle the design celebrates elsewhere is violated here. Demand a `shouldShowUpdatedBadge(post): boolean` (or richer) helper in `src/lib/blog.ts`.

## Top 5 Risks / Gaps

1. **The Shiki dual-theme CSS cascade is structurally unverified.** Inline-style precedence may invert the design's selector strategy; the actual `[data-rehype-pretty-code-fragment]` attribute is admitted to be a guess. Without a POC against the variable-bridge emit, Req 9.2's entire dual-theme correctness story is speculation. **Severity: high.** Catches in production as the user-visible regression "code blocks don't follow theme toggle."

2. **The `feed` package CDATA-wrapping behavior is asserted, not verified, with no version pin.** A wrong assumption here ships a feed full of XML-escaped HTML markup to subscribers. The CDATA-escape happens at the `bodyHtml` layer, so the route handler's only defense is the package's behavior matching the asserted contract. **Severity: high.** Catches in production as "every RSS reader displays HTML source instead of rendered content."

3. **`scripts/verify-production-build.mjs` reads paths that may not match Next.js App Router's actual static-emit structure.** A grep against the wrong directory silently passes on zero files, and the dual-build CI cost is paid for no protection. Compounded by the lack of an explicit `.velite/` clean between Build 1 and Build 2 — drafts can persist in the Velite cache into Build 2's environment. **Severity: high.** Catches in production as "draft fixture leaks but every assertion passed."

4. **`s.markdown()` API and `meta.content` are pinned to design weight without in-repo precedent.** The existing `velite.config.ts` does not use either primitive. If `s.markdown()` is not present in v0.3.1 or behaves differently than `s.mdx()`, the entire `bodyHtml` architecture needs redesign. **Severity: high.** Catches at first implementation attempt as "spec is unbuildable."

5. **Shared rehype plugin instances across MDX and markdown pipelines have no acknowledged contract about `rehype-pretty-code`'s internal Shiki highlighter cache.** Cross-pipeline state contamination would manifest as flaky build output (passing in CI cold-cache, failing on warm rebuild). **Severity: medium.** Catches as intermittent CI failures with no clear cause.

## Top 3 Conclusions to Challenge or Reverse

1. **"Emit bodyHtml from Velite via `s.markdown()`."** Reverse this to: render the page once at build time using the same MDX pipeline the page uses, capture the resulting HTML string via `renderToStaticMarkup`, and use that for both the page and the feed. This eliminates the dual-pipeline divergence surface, eliminates the shared-plugin-stateless contract, eliminates `s.markdown()` API risk, and eliminates the bodyHtml-vs-page parity test entirely (the parity is trivial because the string IS the same). The design rejected this at design.md:285 on the grounds that `<MDXContent />` uses `new Function(code)(runtime)` which "doesn't fit cleanly inside a route handler." That is true, but the rendering can happen at Velite-postprocess time, not route-handler time — emitting the rendered string into `.velite/posts.json` alongside `body`. **Reasoning:** the dual-pipeline approach saves one render per post and costs one entire class of subtle divergence bugs plus the entire Req 11.11 parity test apparatus. The trade is poor.

2. **"The Shiki CSS cascade with explicit-class precedence is the right safety mechanism for Req 9.2."** Reverse this to: ship the variable-bridge spans as-is, override the CSS variables themselves via `html.light { --shiki-light: <value>; }` / `html.dark { --shiki-light: <dark-value>; }` (note: same variable name, different value). This sidesteps the inline-style-specificity collision entirely because we're not fighting the `color: var(--shiki-light)` declaration, we're rewriting what `--shiki-light` resolves to. **Reasoning:** the proposed cascade fights the plugin's emit at the wrong layer; rewriting the variable wins by definition.

3. **"`scripts/verify-production-build.mjs` is a sufficient structural guard against the chokepoint-bypass class."** Reverse this to: add an ESLint rule (or simple CI grep) that fails on any `from "#site/content"` import outside `src/lib/blog.ts`. That fails fast at PR time on the actual bypass class, costs ~5 lines of config, and removes the entire dual-build CI step. The dual build defends against the same bypass class but at 30-60s per CI run, and it requires the smoke script to actually grep the right paths (see Risk 3). **Reasoning:** procedural enforcement at the import boundary is cheaper, faster, and more reliable than structural verification at the output boundary.

## What's Missing — Work Before Acting on This Document

- **Velite v0.3.1 API audit.** Read the actual `node_modules/velite/dist/index.d.ts` and confirm: (a) `s.markdown()` exists and emits a string; (b) `defineConfig` accepts a top-level `markdown` key; (c) `MarkdownOptions.rehypePlugins` is honored end-to-end; (d) `meta.content` is populated inside the schema `.transform()` callback. If any of (a)-(d) is false, the bodyHtml architecture needs redesign.
- **`rehype-pretty-code` variable-bridge POC.** Build the smallest possible fixture (one MDX file, one fenced code block, `defaultColor: false`) and inspect the emitted HTML. Confirm the actual attribute names on the wrapper element, confirm whether spans carry inline `style` attributes, and design the CSS cascade against the real output rather than the assumed output.
- **`feed` package CDATA behavior verification.** Pin a version, write a 5-line test: `new Feed(...).addItem({ content: '<pre><code>x</code></pre>' })` → assert the `rss2()` output contains the unescaped `<pre>` substring inside a `<![CDATA[` block. Iterate until correct; document the version pin in the design.
- **Next.js App-Router static-emit path audit.** Run `next build` against a minimal blog-shaped fixture and document where `/blog/index.html`, `/blog/[slug]/index.html`, and `/feed.xml` actually land in `.next/`. Rewrite `scripts/verify-production-build.mjs` against the verified paths.
- **CI build separation.** Add explicit `rm -rf .velite/ .next/` between Build 1 and Build 2 in the design; without this, Build 2's verification fires against a cache that contains drafts.
- **`ThemeProvider` blast-radius audit.** Grep every `.dark` selector in `src/styles/` and any `tailwind.config.*` for rules that assume "no class" = light mode. Catalog the changes needed when the symmetric `.light` class lands.
- **Lint/CI guard for `#site/content` direct imports.** Specify the rule and its scope. Without this, the chokepoint is procedural-only.
- **`shouldShowUpdatedBadge` helper.** Add to the `src/lib/blog.ts` interface list so the comparison is not duplicated across page and index card.
- **Reading-time fixture isolation.** Either freeze the fixture-reading-time prose under a code-review gate, or split the multi-purpose fixture into one-fixture-per-concern files so a tweak for the GFM test does not destabilize the ±20% reading-time tolerance.
