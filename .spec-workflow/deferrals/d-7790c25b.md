## Context
Task 15 review v1 flagged the missing token as a WARNING. Current upstream shadcn behaviour (verified by re-running shadcn init against a scratch create-next-app) does not declare --destructive-foreground in :root / .dark / @theme for the neutral base-color preset, and the installed destructive Button variant renders `text-white` + `bg-destructive` directly (src/components/ui/button.tsx:14 — dark mode applies `dark:bg-destructive/60`). components.json:3 (`"style": "new-york"`) pins the shadcn component style that governs the Button markup and its destructive variant; components.json:9 (`"baseColor": "neutral"`) pins the separate base-color preset that governs the oklch values in tokens.css. Re-introducing --destructive-foreground locally would require diverging from the upstream scaffold in two places: tokens.css (add the token) and src/components/ui/button.tsx (swap text-white for a token reference). Every subsequent `shadcn add` would then need a matching local patch to avoid regeneration drift. Declining to declare the token keeps the scaffold regenerable; this deferral records the deviation from the R5 AC5 prompt explicitly.

## Decision Deferred
Neither tokens.css nor the @theme inline block in globals.css declares --destructive-foreground / --color-destructive-foreground, even though R5 AC5's list of required pairs includes 'destructive / destructive-foreground'. Instead, shadcn's new-york destructive Button variant renders `text-white` + `bg-destructive` (with `dark:bg-destructive/60` in dark mode) — the foreground is a hardcoded white literal, not a token.

## Revisit Criteria
When (a) shadcn upstream re-introduces --destructive-foreground in the neutral preset, (b) a component other than Button needs a named foreground on a destructive surface (e.g., error panels rendering destructive text on --background), or (c) the R5 AC5 acceptance list is explicitly updated to drop destructive-foreground.
