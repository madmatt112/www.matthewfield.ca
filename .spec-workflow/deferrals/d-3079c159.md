## Context
Requirements v9 is approved and hard-capped (the convergence loop forbids a v10), so this cannot be fixed in the criterion itself. Req 10.2 states: "IF records exist for the SHA but none equal `Production` THEN the run SHALL fail immediately with a distinct cause naming the `environment` values it saw", gated by v7's amendment so it is evaluated only after at least one record has been observed. The design (Component 3) implements this faithfully. The residual hazard: if Vercel creates a Preview record for the sync SHA BEFORE the Production record, the first non-empty poll trips the fail-fast and the run goes red while the production build is still on its way — a false red on a healthy sync, after the data is already on `main`. Measured during design review r1 across all 156 deployment records in this repository: only two SHAs carry more than one record, and in the one that has a Production record at all, Production precedes Preview by 20 minutes. The last six first-parent commits on `main` each have exactly one record, `Production`. The Preview-first ordering has never occurred for a push to `main` here. Alternatives considered: (a) amend Req 10.2 to require the fail-fast only after a grace period or only at the timeout boundary - unavailable, requirements are capped and approved; (b) deviate in the design and document the deviation - rejected because a design that silently contradicts an approved criterion is worse than a recorded gap; (c) record and monitor - chosen, because the failure is loud (a red run naming the environments it saw), non-destructive (the data is already committed and Vercel deploys regardless), and self-diagnosing on the first occurrence.

## Decision Deferred
github-activity-sync will implement Req 10.2's fail-fast exactly as written, without a grace period or an ordering tolerance. The known consequence — a false red when a Preview record for the sync SHA arrives before the Production record — is accepted rather than designed around.

## Revisit Criteria
Revisit when a sync run fails with `deploy-environment-unrecognised` AND the production deployment for that same SHA is later confirmed successful — i.e. the fail-fast demonstrably fired early rather than correctly. Both halves are readable from the Actions log and the deployments API without instrumentation. Until then the measured base rate (0 occurrences in 156 deployment records) does not justify deviating from an approved criterion.
