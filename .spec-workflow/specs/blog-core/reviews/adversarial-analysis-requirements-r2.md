# Adversarial Analysis — blog-core/requirements.md (v2)

**Reviewer stance:** senior technical PM, directive, no validation. Primary attack surface: completeness, ambiguity, scope.

**Prior-review status (one-line summary):** v1's five headline findings (NODE_ENV/draft coupling, tag slug normalization, reading-time input contract, RSS HTML architecture, `updated ≤ date` rule) have all been substantively addressed. This review concentrates on **novel issues introduced by the fixes** and on **compounding gaps** that remain.

---

## Targeted attacks

### 1. Req 8.4 ↔ Req 3.10 — the `console.warn` rule contradicts itself

- **Challenge the direct contradiction.** Req 3.10 declares: "the build output SHALL emit zero `console.error` / zero `console.warn` lines attributable to blog-core code … CI SHALL fail if blog-core code emits build-time console noise." Req 8.4 specifies a `console.warn` that the Velite `posts` transform SHALL emit when `updated` is more than 30 days in the future. Either Req 3.10 is wrong (warnings are sometimes permitted) or Req 8.4 cannot fire without failing the build it was designed to allow through. Both clauses appear in the same document and they negate each other. This is not a soft tension — the spec gives implementers contradictory directives.
- **Stress-test the "fires only when typo is present" hedge in Req 8.4.** That hedge concedes the rule emits build-time noise whenever the typo exists. Combined with Req 3.10, the only states are (a) author has no typo, no warning, build green; (b) author has the typo, warning fires, build red. State (b) is *exactly* the state Req 8.4 was designed to make "non-blocking." The hedge does not resolve the contradiction; it surfaces it.
- **Challenge the rationale for putting the warning in Velite at all.** If the goal is to catch year-typos (`updated: 3026-…`) without blocking deploys, route the diagnostic somewhere that does not pass through Req 3.10's grep surface — e.g., write to a build artifact, fail with an error and require the author to set `updated: 3026-…` explicitly via a `confirmFutureDate: true` companion flag, or emit a structured warning to a separate channel. As written, the spec is internally inconsistent.
- **Stress-test "Build-noise tolerance".** Req 3.10 explicitly says no separate grep step is required because the happy path does not emit warnings. Req 8.4 introduces an unhappy path where a warning *is* emitted and the document expects it to survive CI. The two clauses were written by different concerns and not reconciled.

### 2. Req 7.3 — Vercel preview deploys expose drafts on the public internet

- **Challenge the privacy posture.** Req 7.3 sets `BLOG_INCLUDE_DRAFTS=1` on every Preview deploy. Vercel preview URLs (the `https://<branch>-<hash>-<scope>.vercel.app` form) are not authentication-gated by default on the Hobby tier; they are public. Anyone who learns the URL — by social leak, search-engine crawl of a forgotten link, or URL-pattern guess against a known PR number — can read every draft. The spec frames previews as "where collaborative review happens" but does not address that the preview URL is the public internet, not a private review channel.
- **Stress-test the implicit threat model.** Req 7.7's body banner and Req 7.8's `[DRAFT]` title prefix are anti-confusion safeguards (don't mistake a draft for a published post), not anti-disclosure safeguards. There is no mechanism in this spec preventing a draft from being indexed by a search engine that crawls a preview URL, leaked over Slack, or stored in a reviewer's browser history. If the implicit assumption is "preview URLs are private," state it and verify it; if not, draft confidentiality is not preserved by this design.
- **Attack the missing `robots` and `noindex` posture for preview deploys.** The site has site-wide `robots.txt` and meta-robots handling, but the spec does not require draft post pages to emit `<meta name="robots" content="noindex,nofollow">`. A search-engine crawler that reaches a preview deploy URL will index the draft body. Drafts on preview SHOULD carry per-page robots = noindex regardless of environment, but the spec does not require this.
- **Challenge the "fixture draft post" pattern implied by Req 7.10.** The Playwright test in Req 7.10 needs a draft post fixture committed to the repo. That fixture file ships in production builds too (the file exists in `content/posts/`) — it is just excluded by `getPublishedPosts()`. It WILL appear on every preview deploy at a stable, easily-guessable URL (e.g., `/blog/fixture-draft`). This is a permanent, public-internet draft fixture for the life of the project. State whether that is intended.
- **Stress-test the "NEVER All Environments" parenthetical in Req 7.3.** Vercel's env-var UI defaults the "Environment" multi-select to all three checkboxes checked. The spec gives prose guidance but no build-time guard. A future re-configuration mistake silently exposes drafts on production. Recommend a build-time assertion in `getPublishedPosts()` that throws when both `BLOG_INCLUDE_DRAFTS=1` and a production-only signal (e.g., `VERCEL_ENV === 'production'`) are present simultaneously — turning a configuration mistake into a deploy failure.

### 3. Req 9.2 + Req 13.7 — Shiki dual-theme code blocks render in the wrong theme for no-JS readers

- **Challenge the theme-attribute mechanism for no-JS.** Req 9.2 says Shiki emits CSS-variable-bridged markup that "responds to the site's `data-theme` (or class-based) theme attribute already set by `next-themes`." Req 13.7 says blog posts SHALL be readable with JavaScript disabled, and accepts that `next-themes` falls back to "system preference." But `next-themes` sets the `class="dark"` (or `data-theme`) attribute on `<html>` from JavaScript on first paint — with JS disabled, no attribute is ever set. The CSS-variable selectors that pick between Shiki's `light` and `dark` theme variants will not trigger; code blocks will render in the default-theme variant (typically `light`) regardless of the user's system theme.
- **Stress-test the "system theme is the no-JS fallback" claim in Req 13.7.** That claim is only true when the no-JS fallback path uses `prefers-color-scheme` media queries. The spec does not specify that the Shiki dual-theme CSS uses `@media (prefers-color-scheme: dark)` selectors as a fallback alongside the class/attribute selectors. With only attribute-driven selectors, no-JS users on a dark-system get light code blocks on a dark page — a contrast regression, not a parity result.
- **Attack the absence of an acceptance criterion for the no-JS code-block theme.** Req 13.2's axe pass runs with JavaScript enabled (Playwright launches a real browser). The no-JS path in Req 13.7 has no test — it is declarative, not verified. The compounding failure mode is: (a) light-theme prose with light-theme code blocks on a dark-mode system, (b) inverted-prose dark-mode body with light-theme code blocks if `dark:prose-invert` operates without a class on `<html>`, (c) Shiki tokens that pass contrast against light bg failing against dark bg. None of these are exercised by the spec's test plan.
- **Challenge the silence on which dual-theme strategy `rehype-pretty-code` will use.** The plugin supports both `theme: { light, dark }` (CSS-variable mode) and `theme: 'one'` (single-theme). The spec selects the dual form but does not say whether the consumer-side CSS will key off `[data-theme="dark"]`, `.dark`, or `@media`. These are not interchangeable; one of them needs to match what `next-themes` does in this repo. Pin it.

### 4. Req 11.7 — `s.markdown()` plugin alignment with `s.mdx()` is asserted, not specified

- **Challenge the "same plugin pipeline" claim.** Req 11.7 says the `bodyHtml` transform uses `remark-rehype` + `rehype-stringify` "with the same plugin pipeline that pages use, including `rehype-slug` and `rehype-pretty-code`." But the existing `velite.config.ts:79` registers those plugins under the `mdx.rehypePlugins` key — they apply to the MDX compile, not to a separate `s.markdown()` invocation. Velite's `s.markdown()` accepts its own plugin configuration (via `markdown.rehypePlugins` in `defineConfig`); the spec does not say plugin registration is duplicated, nor that a shared array is reused. Without that wiring, `bodyHtml` ships HTML with no slug anchors and no Shiki highlighting — silently divergent from the page. The parity fixture in Req 11.11 partially catches this, but only for code blocks; missing heading anchors would not be flagged.
- **Stress-test the parity fixture's scope.** Req 11.11 asserts "same fenced-code-block structure (same `<pre><code>` elements, same Shiki classes)." It does not assert heading anchors are present, nor that the inline-code styling matches, nor that link rendering matches. The fixture catches the regression it names and nothing else.
- **Attack the unstated build-time cost.** Compiling each post twice (`s.mdx()` for body + `s.markdown()` for bodyHtml) doubles MDX pipeline work. For the launch volume (single digits) this is irrelevant. For growth to "tens within a year" (Req 11.13) it is still fine. But the spec does not measure or bound build time, and `rehype-pretty-code` is the heaviest plugin in the stack — a future spec adding more rehype steps may notice the doubled cost. Worth a one-line note that bodyHtml compile shares plugin instances rather than constructing them per-post.
- **Challenge the silence on what happens when a post body contains capitalized JSX-like tags.** Req 3.7 says capitalized tags fail at MDX static-gen via `ReferenceError`. But `s.markdown()` does not run JSX — it treats `<Callout>` as raw HTML and passes it through `rehype-stringify`. So the MDX page path fails the build, and the markdown bodyHtml path silently produces a `<Callout>` element in the RSS feed (or strips it depending on `remark-rehype` config). These two pipelines disagree on what is an error. The spec asserts equivalence ("plain-markdown-equivalent") but does not verify it.

### 5. Req 6.4 — the prose-extraction contract is brittle for valid markdown variants

- **Stress-test the fenced-code regex against tilde fences.** Req 6.4(a) strips substrings matching `` /^```[\s\S]*?^```/gm ``. CommonMark and GitHub-flavored markdown both permit `~~~`-delimited fenced code blocks as an alternative to triple-backticks. A tilde-fenced code block is not stripped by this regex; its contents flow into the prose word count and double the reading-time estimate exactly the way v1 warned about. The spec acknowledges no author convention forbidding `~~~`. Pin it: either reject tilde fences in `.strict()`-equivalent prose linting, or extend the regex.
- **Attack the non-greedy lazy match for nested or multiple code blocks.** With `[\s\S]*?` and the `gm` flags, the regex matches the *first* opening triple-backtick fence to the *next* triple-backtick line, then continues. For a post with two adjacent fenced blocks separated by prose, the matcher correctly strips both. But for a meta-post that uses indented triple-backticks inside a fenced code block (a markdown post documenting markdown), the inner backticks terminate the outer match prematurely, leaving real prose stripped and code content surviving. The fix is fence-length-aware lexing (track exact backtick count on the open fence and require an equal-or-longer close fence at zero indent), not regex.
- **Challenge the JSX-tag-stripping regex against multi-line opening tags.** Req 6.4(b) uses `/<\/?[A-Za-z][^>]*>/g`. A multi-line JSX opening tag (`<Callout\n  title="foo"\n>`) contains a newline before `>`, and `[^>]*` matches non-`>` characters including newlines (yes, by default in JS regex). So it does match. But the regex matches greedily across `>` inside attribute values (e.g., `<a href="https://x.test/?q=a>b">`) — the matcher stops at the first `>`, leaving the rest of the attribute and the closing `">` as a prose fragment. This is a corner case but worth pinning.
- **Stress-test Req 6.5's tolerance bound.** "Within ±1 minute of the hand-counted prose-only word count divided by 238" — at 238 wpm, a one-minute tolerance is 238 words. For a 3-minute post (~714 prose words), 238 words is 33% of the total. The tolerance bound permits a 33% miscount before flagging a regression. That is wide enough to let a real regression (e.g., re-inclusion of one code block in a 5-block post) ship. A tighter bound — e.g., ±20% with a 1-minute floor — would actually exercise the contract.

### 6. Req 4.6 — the "excluded tag classes" enumeration is incomplete and the friction is undercounted

- **Challenge the enumeration's coverage.** Req 4.6 lists `C++`, `C#`, `.NET Core`, `Foo Bar`, `café` as excluded examples. Real technical-blog tag conventions also include `iOS`, `macOS`, `JavaScript`, `TypeScript`, `Node.js`, `npm`, `ESLint`, `GraphQL`, `OAuth2`, `JWT` — every one of which has community-established mixed casing. Each becomes the lowercase ASCII slug (`ios`, `macos`, `javascript`, `typescript`, `nodejs`, `npm`, `eslint`, `graphql`, `oauth2`, `jwt`). For some (`npm`, `eslint`, `jwt`) lowercase is correct. For others (`iOS`, `TypeScript`, `JavaScript`) the lowercase form is conventionally wrong and looks unprofessional. Req 4.7's "display = slug, by construction" trade-off was reasoned through with the C-family examples; expand it to the conventional-casing classes and confirm Matthew accepts the display fidelity loss for `iOS` → `ios`, `JavaScript` → `javascript`, etc.
- **Stress-test the "author has full control at authoring time" rationale.** That rationale assumes the author thinks about display casing at authoring time. The realistic flow is: author writes `tags: ['TypeScript']`, build fails, author changes to `tags: ['typescript']`, ships. Months later they notice the page heading "Posts tagged typescript" looks amateur, want it to say "TypeScript", and discover the spec offers no display-label override. The decomposition explicitly excluded a side-mapping (Req 4.7) as "incidental complexity." But the consequence — every technical conventional name gets lowercased forever — is not surfaced as a launch trade-off the user is consciously accepting.
- **Attack the inconsistency between Req 4.6's regex and Req 4.7's framing.** Req 4.7 says "Display casing for taxonomy slugs IS the kebab slug" by construction. But the regex permits `web3` (alphanumeric, no leading digit restriction). So `tags: ['web3']` becomes a tag chip reading "web3" — the chosen casing is preserved because the author wrote lowercase. So display=slug is true *given the regex constraint*, not by construction; it is by author discipline. Reframe to avoid the implication that the system enforces display-equality (it doesn't — the regex enforces ASCII-kebab; display follows because authors are forced to write what they want displayed).
- **Stress-test what happens when the author wants a tag spelled differently from the URL.** No mechanism. The spec actively forecloses this. State whether that is an intentional permanent constraint or a launch trade-off to revisit if friction emerges.

### 7. Req 7.10 — Playwright CI orchestration for the dual-build draft test is unspecified

- **Challenge the "run only against builds invoked with `BLOG_INCLUDE_DRAFTS=1`" clause.** The CI pipeline currently runs one production-style build (`pnpm build`). The spec adds a draft-aware build for one Playwright test. This is a new CI artifact, a new build step, a new test job — none of which are pinned. Does the existing CI build run twice (once with, once without)? Is there a separate job? Is the test gated by the `BLOG_INCLUDE_DRAFTS` env var via Playwright's test.skip? The spec defers all of this.
- **Stress-test the test fixture lifecycle.** The fixture draft must (a) exist in `content/posts/` to be committed to git, (b) appear in `generateStaticParams()` only when `BLOG_INCLUDE_DRAFTS=1`, (c) NOT appear in any production build, (d) survive across repo lifetime as a stable test target. Where does it live? A subdirectory like `content/posts/_fixtures/` would be excluded by the Velite pattern `posts/*.mdx` (flat, per Req 1.1). A real flat fixture (e.g., `content/posts/fixture-draft.mdx` with `draft: true`) IS included in `content/posts/` and IS evaluated by Velite — fine for the test, but it permanently occupies a top-level slug in the blog's namespace. Pin the convention.
- **Attack the absence of a test that the dual-build sequence works in CI from cold.** A new contributor running CI for the first time should see both the prod build and the draft-aware build succeed. Document the command sequence.

## Top 5 risks/gaps

1. **Req 8.4 emits a `console.warn` that Req 3.10 declares a build-failure condition.** Internal contradiction. The "warning, not failure" framing of 8.4 cannot coexist with 3.10's zero-warn CI gate. Pick one.
2. **Vercel preview deploys expose drafts on the public internet with no robots/auth posture.** Drafts can be crawled, leaked over Slack, or guessed by URL pattern. The spec confuses "preview-deployable" with "preview-private."
3. **Shiki dual-theme code blocks render in the wrong theme for no-JS readers.** Req 13.7 promises no-JS readability and Req 9.2 promises theme parity, but the `next-themes`-driven attribute is not set with JS disabled, and the spec does not require `prefers-color-scheme` media-query fallbacks.
4. **`s.markdown()` plugin pipeline alignment with `s.mdx()` is asserted, not configured.** The bodyHtml path will silently emit anchorless, unhighlighted HTML unless `rehype-slug` and `rehype-pretty-code` are explicitly registered on the markdown pipeline. The parity fixture (Req 11.11) catches code-block divergence but not heading-anchor divergence.
5. **Req 6.4 prose-extraction regex misses tilde-fenced code blocks and nested fences.** A `~~~`-fenced 200-line code listing inflates a 3-minute post to "11 min read," regressing the exact failure mode v1 raised.

## Top 3 conclusions to challenge or reverse

1. **Reverse: Req 8.4's `console.warn` mechanism.**
   Either drop the year-typo warning entirely (the asymmetric typo is rare; OpenGraph dates that project 1000 years forward are visually obvious to the author who looks at the rendered page), OR turn it into a build error with an explicit `confirmFutureDate: true` opt-out so the diagnostic does not run afoul of Req 3.10. The current "warn but build green" design is impossible under the spec's own CI contract.

2. **Reverse: implicit "Vercel preview URLs are private" assumption.**
   Add an explicit acceptance criterion that every draft post page emits `<meta name="robots" content="noindex,nofollow">` regardless of `BLOG_INCLUDE_DRAFTS` state. State the threat model: preview URLs are publicly reachable but unindexable; reviewers are trusted not to redistribute the URL; the body banner (7.7) is the anti-confusion safeguard, not anti-disclosure. If a stronger posture is required, add Vercel Password Protection (paid tier feature) as a configuration prerequisite.

3. **Reverse / harden: Req 9.2's theme-coupling claim.**
   Require the Shiki dual-theme CSS to include a `@media (prefers-color-scheme: dark)` fallback selector alongside the attribute-driven selector. Add a Playwright test that loads a post page with JS disabled and asserts the code block's background color matches the system theme. Without this, Req 13.7's "no-JS readability" is partially false on dark-system users.

## What's missing — work that should be done before acting on this document

- **Reconciliation of Req 3.10 and Req 8.4.** As written, the spec contradicts itself. Resolve in the requirements doc, not in design.
- **A pinned plugin-registration strategy for the `bodyHtml` Velite transform** — specifically whether `rehype-slug`, `rehype-pretty-code`, and the absolutization step (Req 11.8) are configured on `s.markdown()` or shared with `s.mdx()`. Pin the data flow.
- **A `<meta name="robots" content="noindex,nofollow">` requirement on draft post pages** independent of environment, so preview URLs cannot be crawled into search indexes.
- **A `prefers-color-scheme` fallback requirement in Req 9.2** so no-JS users get correctly-themed code blocks, with a Playwright test that confirms the fallback.
- **A fixture-post location and lifecycle convention** (Req 9.6 + Req 7.10): which slug, where in `content/posts/`, what happens when those slugs are also valid URLs on the production index. The cleanest convention is probably a fixture filename prefix that the index page filters out — but this contradicts Req 1.1's flat-pattern statement and Req 7.4's single-helper invariant.
- **Expand Req 4.6's "Excluded tag classes" enumeration** to cover the technical-blog conventional-casing names (`iOS`, `TypeScript`, `JavaScript`, `Node.js`, `ESLint`, `GraphQL`) and re-confirm the display=slug trade-off is acceptable with those names visible. The current C-family list understates the friction surface.
- **A fence-aware prose-extraction strategy in Req 6.4**, replacing the brittle regex with a markdown lexer (e.g., `remark-parse` + an AST visitor that drops `code` nodes), and broadening the tolerance test (Req 6.5) to bound the error at ±20% rather than ±1 min absolute.
- **A CI orchestration spec for the dual-build draft test** (Req 7.10): one job vs two, env-var handling, fixture file path. The current "Playwright test SHALL run … against builds invoked with `BLOG_INCLUDE_DRAFTS=1`" presupposes infrastructure the spec does not define.
- **A build-time guard against the "All Environments" misconfiguration in Req 7.3.** Throw at build-time when production-signal env vars (e.g., `VERCEL_ENV === 'production'`) coexist with `BLOG_INCLUDE_DRAFTS=1`, turning a configuration mistake into a deploy failure rather than a silent draft leak.
