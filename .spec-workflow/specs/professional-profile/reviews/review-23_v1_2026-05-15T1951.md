## Findings

### INFO: Console-error CSP filter is defensive redundancy
- **File:** e2e/tests/contact-csp.test.ts:85
- **Issue:** The `securitypolicyviolation` event listener registered via addInitScript is the authoritative signal; the additional `consoleErrors` filter on /blocked by csp|content security policy/i is belt-and-braces. This is fine and matches the design's intent, but the regex relies on Chromium's current 'Content Security Policy' phrasing — if the browser changes message wording the redundant guard silently degrades. The primary listener still catches everything, so this is informational only.

### INFO: form-action substring assertion assumes a single CSP header
- **File:** e2e/tests/contact-csp.test.ts:102
- **Issue:** expect(csp).toContain("form-action 'self'") reads response.headers()['content-security-policy'] which Playwright collapses into a single string. next.config.ts currently emits a single joined directive string so this matches reality. If a future refactor splits CSP across multiple headers (e.g., enforce + report-only) and the form-action directive lands in the second header, this assertion could pass or fail in surprising ways. Acceptable for now; flagging the implicit coupling.

### INFO [hygiene]: Repeated window-cast triple-narrowing reads verbosely
- **File:** e2e/tests/contact-csp.test.ts:34
- **Issue:** The cast `(window as unknown as { __cspViolations: SecurityPolicyViolationEvent[] })` is duplicated three times (lines 34, 37, 79). A single local `declare global { interface Window { __cspViolations: SecurityPolicyViolationEvent[]; __TEST_ID: string } }` in the test file (or a shared e2e types file) would tighten this. Cosmetic only — the test compiles and behaves correctly.
