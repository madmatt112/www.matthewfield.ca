# Adversarial Analysis — project-showcase/requirements (v3)

Role: senior technical product manager. v3 absorbed a substantial fraction of r2: `summary` is always required (the opportunistic split is gone), cover-and-OG are decoupled (no fallback), the aspect-ratio band is removed in favor of a width/height floor plus file-size caps, the chokepoint test enumerates four evasion patterns and adds a canary fixture, the container is narrowed from `max-w-7xl` to `max-w-5xl` with an auto-escape contract, the doc launch gate is now a section-by-section verification, and a `featured` user story is captured in the doc. That's real progress.

What follows is what v3 still gets wrong, where it overcorrected, and the new problems v3 introduced by adding constraints.

Findings tagged **[Novel]**, **[Compounding]** (deepens prior), **[Recurring]** (unresolved from v1/v2).

---

## Attack surfaces

### A. Req 1.2 / 1.3 — Length caps, the always-required `summary`, and the new pair-boundary

- **[Novel] Challenge the asymmetric caps `description ≤ 160` and `summary ≤ 140`.** v3 split them by 20 chars, but the rationale text says only that 160 is the SERP-clip heuristic and 140 targets the card range. The 140 number is now its own magic number: there is no doc anchor for "140 is the card-friendly upper bound." On a typical card width (~280–360px at the gallery breakpoint, ~16px line-height), 140 characters is roughly 2.5–3 lines of text — fine on desktop, but on mobile single-column cards (Req 2.10) 140 chars is ~5–6 lines and visually dominates the card body. Either lower the `summary` cap (~110 is the well-known card body sweet spot) or document the rationale that 140 is intentionally high to permit one-sentence summaries that span multiple breakpoints.
- **[Novel] Stress-test the "duplication is intentional and signals 'yes, you actually checked'" rationale.** Req 1.2 claims that requiring authors to paste the same string into both fields is a feature. That's a behavioral assertion: it presumes authors will *actually* check both surfaces rather than copy-paste once and move on. The dominant author behavior under "two required fields with the same content type" is to paste once — the field-pair existence is enforced, but the "checked it works on both" semantic is not enforced by anything. The schema gets you "two strings exist"; it does not get you "two strings have been thoughtfully tuned." Either accept this is a procedural hint (not a schema guarantee) and say so, or add a soft-warning when the two strings are byte-identical (suggesting the author hasn't tuned).
- **[Novel] Challenge the lack of a *lower* bound that differentiates the two surfaces.** Both fields are `1–N chars`. An author writing `description: "A"` and `summary: "A"` passes the schema. The minimum bound of 1 is technically valid but provides no protection against the "one-word description, one-word summary" failure where the author treats both as throwaway. Either raise the minimum (`description ≥ 50`, `summary ≥ 30` as crude heuristics) or document explicitly that the 1-char minimum is a deliberate "we trust authors" stance.
- **[Recurring] The 160 ceiling is still presented as a hard build error with no override.** r2 raised this; v3 retains the hard cap. An author writing a 161-char description that they've verified renders fine on every SERP they care about now has only one path: trim. There is still no documented escape hatch (warning, env-var override, etc.). The author doc (Req 11 §1) does not mention this friction, and the rationale paragraph in Req 1.2 still pins exactly at 160 with no acknowledgment that 160 is a heuristic, not a contract. Either acknowledge the boundary is heuristic and provide a soft-fail mode, or document the rationale concretely (e.g., "Google clips at 920px on desktop, ~158 chars in en-CA at typical font metrics").

### B. Req 1.3 / Req 3.1 / Req 6.4 — The cover/OG decoupling and what it does NOT enforce

- **[Novel] Challenge the silent-OG-loss when authors think the cover IS the share image.** v3's decoupling is correct in principle, but the author UX is now: drop a cover, ship a project, share the URL on LinkedIn — the share preview uses the *site's default OG image*, not the project. Most authors will be surprised. There is no build-time hint ("you haven't supplied `ogImage`, share previews will use the site default") and no doc warning. Req 11 §3 covers when to supply `ogImage` but the *default consequence* of omission is not surfaced in the build log or anywhere the author would encounter without reading the doc. Either log a build-time info message ("project <slug> has no ogImage; share previews will use site default") or accept that the default-quiet-failure pattern matches the v1/v2 "build teaches you" stance.
- **[Novel] Stress-test the `width ≥ 1200`, `height ≥ 800` floor in light of the gallery card target.** v3 removed the aspect-ratio band but kept a 1200×800 floor. The gallery card renders at ~280–600 px wide on desktop, with a `sizes` attribute appropriate for grid breakpoints (Req 3.4). A 1200×800 source serves a 600×400 display target at 2x retina — fine. But the detail page's outer container is now `max-w-5xl` (1024 px). A 1200×800 cover rendered at the full outer container width is downscaled to 1024×682 — wasting the height information, and authors who supply *exactly* 1200×800 will see the cover rendered nearly 1:1 on a 5xl-width viewport. The floor is now over-spec for the detail-page width but under-spec if anyone ever uses a wider outer in a future spec.
- **[Novel] Challenge the file-size cap of 1 MB as the only first-paint defense.** v3 added the 500 KB soft / 1 MB hard caps, addressing the "5 MB PNG" failure. But 1 MB on a gallery page with N cards is N MB of cover imagery — at N=8 published projects, that's 8 MB downloaded before any prose renders. Next.js's `<Image>` with lazy-loading mitigates this for below-the-fold cards, but the above-the-fold cards still load eagerly. The cap is per-image; the cumulative-page-weight failure mode is not addressed. Either add a "total cover weight" warning (sum of all cover bytes) or document that lazy-loading is the mitigation strategy.
- **[Novel] Stress-test what happens when `ogImage` is supplied but is *worse* than the cover.** The schema validates `ogImage` dimensions and aspect ratio. But there is no check that `ogImage` is a *different file* from `cover`. An author can supply `cover.png` (a 1200×900 screenshot) and `ogImage.png` (the same 1200×900 screenshot — which fails the 1.91:1 band, build fails) — or supply `ogImage` that is 1200×630 but lower quality / wrong content. The schema enforces shape, not appropriateness. Acceptable, but the doc (Req 11 §3) should explicitly say "`ogImage` is for share-card-shaped variants — don't supply the same file twice."

### C. Req 5 — Links rail, uniqueness, and the "omit kind to add a new type" escape hatch

- **[Novel] Challenge the "omit `kind` to add a new type" pattern as a usability footgun.** v3 says: to add a Figma link, omit `kind` and the entry renders label-only. This is correct for the "no React edits" goal, but the doc (Req 11) does not surface this clearly enough — authors who see `kind: demo`/`repo`/`docs`/etc. examples will assume they need a kind value. The natural author behavior is to invent a kind (`kind: figma`) and hit a build error. The error message is helpful, but the *first-encounter* UX is "I tried to follow the pattern and the build broke." Either reorder the doc to show the no-kind pattern FIRST, or include the kind enum's closed nature in the error message ("kind 'figma' is not in {demo,repo,docs,package,writeup}; omit kind for label-only rendering").
- **[Novel] Stress-test the uniqueness-per-kind constraint against the "two demos" scenario.** v3 says "at most one entry per `kind` value" and tells authors with two demos to "disambiguate by labels and omit `kind` on the duplicates." But the duplicate WITHOUT a kind loses its icon, while the kept ONE WITH a kind has an icon — visually asymmetric for two entries that are conceptually peers. An author with `staging demo` and `production demo` wants both to render with the demo icon and disambiguating labels. The current contract forces them into a "one icon-bearing, one icon-less" rendering. Either allow duplicate kinds with the icon repeated (the v2 approach) or document that paired entries of the same logical type render asymmetrically by design.
- **[Compounding] Stress-test the cap reduction from 10 to 6.** r2 argued 10 was too many; v3 lowered to 6. Six is closer to honest, but the math from r2 still applies: a 6-entry rail above a 200-word body (which Req 6.10 implies is acceptable) still pushes the body well below the fold on a laptop. The cap addresses the *upper* failure mode; the rail-above-body fold-eating failure is unresolved. v3 added container-width narrowing (5xl), which helps slightly, but the rail-position contract (Req 5.4) is still "ABOVE the MDX body" with no provision for short bodies. Either add a contract for "rail below body when body word count is short" or accept the failure mode and document it.
- **[Recurring] `kind` typo silent-accept.** v3 closes this by making the enum CLOSED — `kind: showhn` is now a build error. Resolved by escalation: the v2 behavior (silent iconless) is replaced with a build-time rejection. This is correct but introduces the footgun from finding 1 above (authors invent kinds and the build breaks). Net: the silent-typo failure is gone, replaced with a discoverable-error failure. That's the right tradeoff.

### D. Req 6.7 — Container contract and the wide-media auto-escape

- **[Novel] Challenge "auto-escape via CSS pattern targeting those elements within the prose container" as still under-specified.** v3 narrowed the outer to `max-w-5xl` and named the auto-escape contract: `<img>`, `<video>`, `<pre>`, `<figure>` inside the prose container escape to the outer container. The mechanism is "the design's responsibility." But CSS that lets a child element exceed its parent's `max-width` requires specific techniques: negative margins, `position: absolute` with computed offsets, CSS `width: 100vw` with calc-based margin offsets, or grid `subgrid`. Each has tradeoffs (negative margins break on RTL, `100vw` breaks with scrollbars, subgrid has limited browser support pre-2024). The contract is implementable but the spec does not commit to any specific technique — which means the design phase can ship a brittle implementation that breaks under scrollbar presence or RTL and the requirement still passes. State the technique (e.g., "use CSS calc + negative margin technique" or "use `width: 100%` with the wide elements rendered outside the prose container via a remark plugin"), or accept that this is a design-phase decision and that *any* working implementation passes the requirement.
- **[Novel] Stress-test the four-tag list (`<img>`, `<video>`, `<pre>`, `<figure>`) for completeness.** What about `<table>` (wide tables in MDX bodies — common for project specs)? `<iframe>` (embedded demos, CodePen, YouTube)? `<svg>` (inline diagrams)? `<canvas>`? The list is closed and excludes several elements that authors will reasonably want to render wide. Either expand the list, or document the rationale for choosing exactly these four.
- **[Novel] Challenge the "prose stays narrow" contract against MDX bodies that intentionally use full-width sections.** Some project writeups want a hero quote or a callout that breaks the prose column without being one of the four wide-media tags. With no custom components (Req 6.9.d), the author has no path to write "this paragraph is full-width." The auto-escape covers media; it does NOT cover prose elements that the author wants to be full-width. This is consistent with the "no components" stance but worth surfacing in the doc as a known constraint.
- **[Recurring] Wide-media escape contract is still mechanism-deferred.** r2 raised this; v3 names the contract more concretely but does not commit to a technique. The "design phase responsibility" hand-wave is reduced (four specific tags, automatic escape, no per-element opt-in) but the *how* is still open. Net: improved, not resolved.

### E. Req 6.9 — MDX body constraints (no h1, no h4+, no components) and the heading hygiene question

- **[Novel] Stress-test Req 6.9.c's "best-effort, not strict schema enforcement" stance against the lack of a TOC.** v3 says heading-sequence guidance (start with h2, no skip levels) is doc-only, not schema-enforced. With no TOC rendered (Req 6.6), the author has no visible feedback that their heading structure is poor. Screen-reader users get bad landmark navigation silently. The blog spec presumably enforces heading flow more strictly (or has the same gap); without a TOC OR a structural check, h2→h4 skips ship to production undetected. Either enforce heading-sequence in the schema (a remark check is cheap), or accept that bad heading flow is a documentation problem.
- **[Novel] Challenge the rationale for forbidding h4+ when the project body is potentially long.** v3 maintains the h1-only-page, h2/h3-in-body posture. For a project writeup with multiple major sections (architecture, deployment, lessons learned, future work), three heading levels (page-h1, body-h2, body-h3) may be insufficient — a "lessons learned" section with subsections wants h4 for nesting. The `PROJECTS_ALLOW_H4=1` env-var opt-in is a hidden mode that doesn't work in production (unless author sets it locally and commits the resulting deeper-nested body, which then renders fine because the build-time check is the gate, not runtime). The opt-in is a workaround for a constraint that is itself an editorial choice. Either accept h4 by default (with a doc note about discipline) or document why three levels is the right ceiling for project writeups specifically (as opposed to blog posts, where the same constraint applies).
- **[Compounding] The "no custom components" decision is doubled down without addressing r2's "MDX in name only" critique.** v3 documents that bodies are "plain-markdown-equivalent MDX with no custom component tags" and that a registry is a future spec. r2 argued this is a permanent ergonomic tax and that renaming the file extension to `.md` would be more honest. v3 does not engage with the rename suggestion or the broader "MDX vs. md user expectation" critique. The decision is now codified without acknowledging that authors conditioned on MDX elsewhere (Astro, Next.js docs sites, Docusaurus) will assume components work. Either rename `.mdx` to `.md` (which would also require updating the Velite glob pattern, the docs, and the file extension consistently) or accept that the format extension is misleading and document it.
- **[Novel] Stress-test the `<H1>` (capitalized JSX) edge case.** Req 6.9.a says the check rejects "(i) MDX-AST nodes of `type: "heading"` with `depth: 1`, AND (ii) literal `<h1>` or `<H1>` JSX/HTML tags in the source text." The literal-text check is a string scan, which is more brittle than the AST check — `<h1 className="foo">` in MDX source IS a JSX tag, but `<h1>` mentioned inside a code fence (e.g., a tutorial showing HTML examples) would also match a naive text scan and break the build. The spec doesn't define how the text scan disambiguates code-fenced content from real JSX/HTML. State the scan technique (regex with code-fence awareness, or AST-only with HTML-block walk) or accept the false-positive risk.

### F. Req 7 — Draft handling, env vars, and the chokepoint test (v3's biggest expansion)

- **[Novel] Challenge the `src/__fixtures__/chokepoint-canary.ts.txt` fixture path and extension.** v3 names the fixture path `chokepoint-canary.ts.txt` with the rationale "file extension `.txt` so the TS compiler doesn't try to type-check it." But Next.js/Velite's content globs include various file extensions, and a `.txt` file under `src/__fixtures__/` may or may not be picked up by other tools (eslint, prettier, the canary test's own scanner). If the chokepoint test's scanner is configured to scan `*.ts` and `*.tsx`, the canary file is OUTSIDE its scan path — the canary test then has to *explicitly* point the scanner at the canary file, which means the canary test is not exercising the real scan path. Verify the canary test invokes the same scanner code path that the production check uses, with the fixture file passed explicitly. State this explicitly in Req 7.6.h to avoid the test-of-the-test being a no-op.
- **[Novel] Stress-test the chokepoint test's allowlist.** Req 7.4 says `src/lib/projects.ts`, `src/lib/projects.test.ts`, and the canary fixture are excluded from the scan. But: what about `src/lib/projects.ts.bak` left from a refactor? What about a future `src/lib/projects-helpers.ts` that legitimately needs collection access? The allowlist is hard-coded by path, not by some pattern; any new file that needs the import gets blocked until the allowlist is updated. Document the allowlist-expansion contract (e.g., "to add a new chokepoint exception, edit `src/lib/projects.test.ts` and add the path") and the implications of forgetting (build fails on the new file).
- **[Novel] Challenge the "regex/AST scan" choice as still under-specified after r2.** v3 enumerates four evasion patterns to catch (named, namespace, barrel, dynamic) and says the implementation MAY use "(i) a regex/AST scan over source files OR (ii) a small TypeScript-compiler-API-based check; the regex/AST approach is the simpler default." The four patterns are the contract, but a regex-only approach struggles with TypeScript's import syntax variations (`import type`, conditional imports, re-exports with renames, default imports of a default-exported barrel, dynamic imports with template literals). The "AST" qualifier helps, but most TS-specific AST tooling is `@typescript/parser` or `ts-morph` — both are heavyweight dependencies for a single test. If the implementation lands as regex-only (the "simpler default"), the four-pattern contract has high false-negative risk. State which technique is the launch implementation, or accept that the test may be incomplete until iterated.
- **[Novel] Stress-test the `pnpm start` "deliberate consequence" admission (Req 7.2.c).** v3 explicitly admits that `PROJECTS_INCLUDE_DRAFTS=1 pnpm build && pnpm start` serves drafts, and that the author doc covers this. But the failure mode is: an author runs the include-drafts build locally to preview a draft, forgets to rebuild, deploys… wait, they can't deploy a local build to Vercel. The actual failure mode is the author thinking the local `pnpm start` reflects production behavior, missing a draft leak in production *because they assumed the env var was runtime-gated*. The doc note in Req 11 §8 helps, but the v3 admission of "deliberate consequence" doesn't engage with the user-model mismatch — authors expect runtime gates, not build-time gates, for environment-sensitive content. Either document this more prominently (in the build log when the env var is set?) or accept that the static-build model has this footgun.
- **[Compounding] The rollback window is now bounded by CI duration (3–5 minutes per Req 10.5).** r2 raised this as unbounded; v3 cites CI history. The bound is *empirical*, not contractual — if CI degrades to 15 minutes, the window grows silently. State the bound as a *contract* (e.g., "if CI deploys take > 10 minutes, this requirement no longer holds and rollback strategy must be revisited") or accept that the citation is descriptive, not prescriptive.

### G. Cross-cutting — Reqs 9, 11, 12, and the introduction

- **[Novel] Challenge Req 9.1's path pinning rationale.** v3 pins the path to `src/lib/format-date.ts` and explicitly closes the v2 "module overhead vs `utils.ts`" finding. But the rationale is "date formatting is a distinct concern with multiple consumers and is worth its own file." That's a defensible stance, but the *only* current and planned consumers are blog and projects — both content surfaces. If "shared content date formatter" is the concern, a path like `src/lib/content/format-date.ts` would scope it; the bare `src/lib/format-date.ts` invites any future surface to import it for dates that aren't content-related (e.g., a "last commit" timestamp on a dashboard). Minor concern, but the path commitment is now permanent.
- **[Novel] Stress-test Req 11.1's per-section content check as a "reviewer-eye check, not an automated test."** v3 says §1–§10 each have non-empty content addressing listed topics, and a separate task in tasks.md verifies this. But "reviewer-eye check" is the same kind of gate that r2 critiqued — it's a human, not a script. The reviewer in this case is Matthew (the author), who is also the implementer. Self-review of doc completeness has a known failure mode: the author who wrote the doc knows what's "obvious" and skips it. Either make the check a peer-review step (which doesn't exist in a solo project) or add automation: a small script that parses `docs/projects-authoring.md` and asserts the ten section headings exist (substantive content remains a judgment call but at least heading presence is mechanical).
- **[Novel] Challenge Req 11's 10-section ordering.** §1 Frontmatter, §2 Cover, §3 Sharing previews, §4 MDX body, §5 Container, §6 Updated, §7 Lifecycle, §8 Local dev env, §9 Featured, §10 Starter. The first-encounter author (writing their first project) will likely want §10 first (copy the starter), then §1 (what fields), then §2 (cover constraints). The current ordering is logical for a *reference* doc but not for a *tutorial* — and the spec frames it as both. Either reorder for tutorial-first (§10 starter, §1 frontmatter, etc.) or split into two docs (quick-start + reference). The current single-doc compromise may not serve either use case well.
- **[Novel] Stress-test the Lighthouse manual-verification contract (Req 12).** v3 acknowledges Lighthouse-CI is out of scope and the 90+ target is verified manually at launch. But "verified manually" with the result "documented in the spec's implementation log" is a one-time check. After launch, the gallery grows, more covers load, the page weight goes up — and there is no contract for re-verification. A project with 8 covers might score 92; a project with 16 covers scores 78. No re-verification path means the target degrades silently over time. Either commit to periodic re-verification (e.g., "re-run on every Nth project added") or accept the target is launch-only.
- **[Novel] Challenge the introduction's expanded "in scope" / "out of scope" lists for internal contradiction.** The "out of scope" list now includes "MDX image auto-optimization for in-body images (Req 3.7) and a custom MDX component registry (Req 6.9.d)." But Req 3.7 explicitly says "Plain `<img>` elements in the rendered output are wrapped in the CSS pattern of Req 6.7 that allows them to escape the prose column" — that IS a styling/processing step on in-body images. The line between "not auto-optimized" and "wrapped in escape-pattern CSS" is fuzzy. State explicitly what the in-body image pipeline does and does not do.
- **[Compounding] The "no `noindex` mechanism" finding from r2 is now acknowledged in the intro but not addressed.** v3 says "If a future need arises, the planned shape is a `meta: { noindex: true }` frontmatter field..." — this is the right "forward-aware deferral" pattern, but it's worded as "acknowledged for forward awareness only." For an author who wants to publish a project for direct linking without search indexing (e.g., a client project under NDA — though that probably belongs in a separate-host strategy), the current spec has no path. Net: r2's finding is now acknowledged; not resolved, but explicitly deferred with a planned shape. Reasonable.
- **[Recurring] The same-tab-default for outbound links remains unchallenged.** v1 raised it, r2 noted v2 "doubled down without research backing," v3 retains the same-tab posture with the same rationale ("Same-tab is the default; users who prefer a new tab use middle-click or Cmd/Ctrl-click. Authors are NOT given a per-link `target` override (uniform policy, no edge-case maintenance)."). This is the third version without engagement with the underlying critique. Either commit to the rigidity with a referenced rationale, or accept that the rigidity is a personal preference (which is fine for a solo portfolio) and document it as such.

## Top 5 risks/gaps

1. **The 1-character minimum on both `description` and `summary` permits "A"/"A" trivially passing the schema.** v3 made `summary` always required but the floor is `1`. The schema can be cheated trivially. The intent is "thoughtful tuning for two surfaces"; the schema enforces "two strings exist." This is a real gap — either raise the minimum (`description ≥ 50`, `summary ≥ 30` as starting heuristics) or admit the schema is a procedural hint, not a content guarantee.

2. **The wide-media auto-escape technique is still unspecified at the implementation level.** v3 narrowed the contract (four tags, automatic, no per-element opt-in) but did not commit to a CSS technique. The design phase can ship something brittle (negative margins that break under RTL, `100vw` that breaks with scrollbars) and the requirement still passes. State the technique or commit to manual review of the chosen implementation against known failure modes (scrollbar presence, RTL, narrow viewports below the prose width).

3. **The chokepoint canary fixture path (`.ts.txt`) may not exercise the production scanner.** Req 7.6.h says the fixture is excluded from type-checking via the `.txt` extension, but if the production scanner is configured for `*.ts`/`*.tsx`, the canary file is outside its normal scan path. The canary test must explicitly route the fixture through the same scanner code path the production check uses — and Req 7.6.h does not state this requirement.

4. **`pnpm start` after a draft-included build silently serves drafts.** v3 admits this is "deliberate consequence" but the user-model mismatch (authors expect runtime gates) remains a footgun. The fix-forward path is documentation in Req 11 §8, but the failure mode is "author runs locally, doesn't realize the local server reflects build-time decisions, and is surprised when they re-publish." Add a build-log notice when the env var is set, or accept the documented footgun.

5. **The h4-by-default-forbidden constraint plus no TOC plus no heading-sequence enforcement means bad heading flow ships silently.** v3 forbids h4+ unless opt-in, and skips/non-h2-start are "best-effort, not strict." With no TOC and no schema check, screen-reader users get bad landmark navigation and authors get no feedback. Either enforce h2-start and no-skip in the schema (a remark check is ~10 lines), or accept the gap.

## Top 3 conclusions to challenge or reverse

1. **Raise the minimum-length floor on `description` and `summary` to enforce "thoughtful tuning" mechanically, not procedurally.** v3 took the "always require both" stance correctly but kept a 1-char floor that defeats the rationale. `description ≥ 50` and `summary ≥ 30` give the schema teeth without being onerous (a project worth publishing has at least a sentence on each surface).

2. **Commit to a specific CSS technique for the wide-media auto-escape, OR move the technique-selection from "design phase responsibility" to "documented in the spec with known-failure-mode acknowledgments."** The current contract passes any implementation that compiles. Either pin the technique (e.g., "CSS-grid-based layout where the prose column lives in a named grid track and wide media spans the full track") or list the candidates with their tradeoffs and have the design phase pick from the list. The "design phase decides" hand-wave is now in its third version with no closure.

3. **Reverse the "reviewer-eye check" for doc completeness (Req 11.3) to a section-heading automated check.** v3's launch gate is "a reviewer-eye check, not an automated test." For a solo project where the reviewer and author are the same person, this is the weakest possible gate. A 20-line script that parses the markdown and asserts ten specific headings exist costs nothing and closes the self-review gap. The "substantive content" check remains human, but the structural completeness check should be mechanical.

## What's missing — pre-action work

- **A decision on minimum-length floors for `description` and `summary`.** Pick a number (or accept 1) with rationale documented in the same paragraph as the maximum.
- **A specific CSS technique commitment (or candidate list) for wide-media auto-escape.** The "design phase decides" hand-wave should be closed in requirements, not deferred to design.
- **Explicit text in Req 7.6.h confirming the canary fixture is processed by the same scanner code path as the production check.** Without this, the test-of-the-test risks being a no-op.
- **An automated section-heading check for `docs/projects-authoring.md`.** Parse the file, assert ten heading strings exist, fail the build if any are missing. Substantive-content review remains manual.
- **A build-log notice when `PROJECTS_INCLUDE_DRAFTS=1` is set during build.** Closes the `pnpm start` footgun by surfacing the env-var decision at build time, not just in the doc.
- **A heading-sequence enforcement (or explicit acceptance of the gap).** With no TOC and no custom components, heading discipline is the only structural authoring tool — and the schema currently does not enforce it.
- **A decision on whether `.mdx` is the right extension** given that the spec ships markdown-only behavior. Either rename to `.md` (and adjust the Velite glob) or document why the format extension is misleading.
- **A cumulative-page-weight contract for the gallery.** Per-image caps don't bound the total. Either cap N × max-image-size, or accept lazy-loading as the mitigation and document it.
- **A re-verification cadence for the Lighthouse target.** "Manual at launch" is one-time; the gallery grows. Pick a trigger (every N projects, every M months) or accept the target degrades silently.
