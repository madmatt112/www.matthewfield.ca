## Context
Surfaced by the profile-resume end-to-end verification, which broke `content/experience.yaml` five ways (invalid month `2026-13`, explicit `end: null`, unknown key, 260-char highlight, `end < start`) and found each correctly rejected — naming file, entry, and field — but only by `velite build`. Task 6's success criterion was worded as "a deliberately malformed seed entry fails the build", and tasks 6 and 8 both reason about build-time failure; that wording is true of a clean CI run but false of an incremental local `pnpm build`. The practical risk is a developer editing content locally, seeing a green `pnpm build`, and believing the schema validated. CI is not currently exposed, since `pnpm install` runs `postinstall` on every run — but that makes the guarantee incidental to install caching rather than explicit in the build graph.

## Decision Deferred
Left as-is. Content-schema validation is only enforced when Velite actually re-runs. `pnpm build` exits 0 against a stale `.velite/` directory, so a malformed `content/experience.yaml` passes it. The real gate is `pnpm exec velite build`, reached in practice via the `postinstall` script — i.e. CI's `pnpm install` step, not its build step.

## Revisit Criteria
Make the dependency explicit: have the `build` script run `velite build` itself (or depend on a task that does), so content validation is part of the build graph rather than a side effect of installing. Then re-test with a deliberately malformed entry and a warm `.velite/`.
