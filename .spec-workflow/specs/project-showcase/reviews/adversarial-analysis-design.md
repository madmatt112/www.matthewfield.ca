## Attack 1 — Chokepoint scanner (Component 11)

The scanner is the load-bearing CI gate enforcing Req 7.4. The algorithm sketched in the design has concrete holes that will either let violations through or fail spuriously.

- **Challenge the claim that the four-pattern visitor covers all import shapes.** The `visit` function inspects `ts.isImportDeclaration` and a `require`/`import()` call, but TypeScript `import` types (`type Foo = import("#site/content").Project`) and inline `typeof import("#site/content")` references are neither `ImportDeclaration` nor `CallExpression` — they are `ImportTypeNode`. The scanner will silently miss a maintainer who writes `type P = import("#site/content").projects[number]` and then references it. State explicitly whether type-only imports are in scope (they are also leaks of the `projects` symbol, because the chokepoint contract is about access, not about runtime).
- **Stress-test the `escapedText` comparison against renamed namespace imports done in a single statement.** `import { projects as p } from "#site/content"` is handled because both `propertyName` and `name` are checked. But `import * as content from "#site/content"; const { projects: p } = content;` is destructuring on a `VariableDeclaration`, not a `PropertyAccessExpression` — the second pass only checks `PropertyAccessExpression`. The scanner is bypassed by trivial destructuring.
- **Challenge the assumption that `ts.createSourceFile` over individual files is enough.** TypeScript path aliases (`#site/content` is one) require module resolution; a re-export chain through an intermediate barrel (`src/lib/intermediate.ts` re-exports `* from "#site/content"`, and `src/app/foo.tsx` imports from `src/lib/intermediate`) is invisible to a per-file scanner. The barrel case in the canary covers literal `export * from "#site/content"`, but it does NOT cover a maintainer who launders the import through a non-allowlisted module. Either make the allowlist exhaustive for ANY re-export of `projects`, or document the laundering loophole explicitly.
- **Stress-test the namespace second-pass scoping.** `recordNamespace(filePath, localName)` is keyed on `filePath`. If two files use the same local name (`content`), the predicate `isRecordedNamespace(filePath, identifier)` is per-file, so this is OK — but the design does not show the storage shape. More importantly, the second pass runs `ts.forEachChild(sf, visit2)` and an inner `visit2` recursively descends; the predicate fires on ANY `content.projects` property access regardless of whether `content` was actually the imported namespace or a shadowing local binding in a deeper scope. A function-scoped `const content = { projects: [] }` will produce a false positive.
- **Challenge the file-discovery layer.** The CI invocation says "walk all `.ts`/`.tsx` files under `src/`" — this happens at TEST time, inside Vitest. If the walk uses `fs.readdirSync` synchronously over `src/`, file count growth (10k+ component files in a hypothetical future) will balloon the test wall-clock time and there is no incremental mode. Spec out caching, or accept the cost. Also: the scanner reads files via `fs.readFileSync`, but the canary is excluded from `tsconfig` — confirm that excluded files are still on disk under `src/` (they are) and that the test-runner's own glob exclusion is not in play (Vitest's `exclude` defaults can hide `__fixtures__`).

## Attack 2 — Tailwind Typography wide-media claim (Components 1, 10)

The whole detail-page layout rests on a specific claim about Tailwind Typography v0.5's behavior. The claim is asserted twice (Overview, Steering §Technical Standards, Component 10) but it is wrong on the bare facts.

- **Challenge the claim that `prose` does not constrain `img`, `video`, `pre`, `figure`, `table`, `iframe`, `svg` widths.** Tailwind Typography v0.5 absolutely DOES style these elements — `prose img` sets margins, `prose pre` sets background/padding/overflow, `prose figure` sets margins and `prose figure > *` rules apply, `prose table` sets `width: 100%` and `table-layout: auto`. None of these are width-CONSTRAINED to ~65ch by `prose` itself (you are right that `max-width` is set on the container, not children), but the design's wording ("NOT width-constrained by `prose`") is technically true while practically misleading: the elements DO inherit the parent's `max-width` because they live inside the prose div. The design simultaneously claims (a) prose narrows text-flow elements to ~65ch via Typography defaults and (b) media fills the parent — but Tailwind Typography's `max-w-prose` (~65ch) lives on the `.prose` div itself, NOT on inner text-flow children. The narrowing is controlled by the OUTER `max-w-5xl`; the prose plugin does not have ch-based caps on children. Re-derive whether the desired effect (media wider than text) is actually achievable without additional CSS — likely it is NOT, contradicting the "no custom CSS" claim.
- **Stress-test the seven-tag list.** Why is `audio` not in the list? Why is `picture` excluded (it wraps responsive `<img>` and is what `next/image` ultimately emits)? Why are MDX-only block elements (`MDXContent`'s output for fenced code, which produces `pre > code` — already in the list — but ALSO `figure` for captioned code via remark plugins) not enumerated by their wrapper? If `next/image` generates a `<picture>` wrapper around `<img>`, the width constraint applies to `picture`, not `img` — the list is incomplete on this account alone.
- **Challenge the contradiction between "no custom CSS" and the layout goal.** The design says "no custom CSS, no `100vw`/negative-margin hacks." But Tailwind Typography does NOT, out of the box, produce a layout where prose paragraphs are narrower than the prose container while images fill the container. To achieve that, you need either (a) a narrower inner wrapper for text-flow elements, (b) per-tag CSS, OR (c) Typography's `prose-img:` modifiers. Pick one and commit; the current design wishes the layout into existence without committing to a mechanism.
- **Stress-test the RTL claim.** "RTL-safe (no negative margins, no `100vw`)" — true that the design avoids those, but the actual RTL story is unaddressed: the site is `lang="en"`, no RTL test is in the test plan, and the claim is unverifiable until someone authors RTL content. Either drop the RTL claim or write a test.
- **Challenge the `prose-lg` selection.** Component 10 uses `prose prose-lg dark:prose-invert`. `prose-lg` enlarges base font-size to 1.125rem and recalculates the ch-based widths. The "65ch" claim was for the default `prose` — under `prose-lg`, the constraint becomes ~75ch with larger font. State the actual target reading-width and the actual font scale, or pick `prose` (default) for parity with the blog.

## Attack 3 — Draft-leak guard and looks-like-prod (Component 5, Error Scenario 7)

The guard is the security-relevant code. The branches written in the design have a subtle inversion.

- **Challenge the "looks-like-prod" branch logic.** The pseudocode is:
  ```
  if (env !== "preview" && env !== "production" && drafts === "1") return { kind: "production" };
  ```
  This branch fires when `VERCEL=1` AND `VERCEL_ENV` is anything other than `preview`/`production` AND drafts is set. But Vercel's documented `VERCEL_ENV` values are `production`, `preview`, AND `development` (for `vercel dev`). The branch ALSO fires on `VERCEL=1 + VERCEL_ENV=development + drafts=1`, which is a legitimate local-dev configuration via `vercel dev`. Stress-test whether `vercel dev` sessions are supposed to be allowed to set drafts (Req 7.3 says "production" semantics; the design conflates "not preview, not production" with "looks like prod"). The fail-closed posture is defensible, but the design needs to say so explicitly and document the workaround for `vercel dev`.
- **Challenge the placement of the build-log warning (Component 12).** The design chooses the velite-transform path "because velite build runs first." But velite runs at `pnpm velite build` time, BEFORE `checkVercelDraftGuard()` runs in `getPublishedProjects()`. If `VERCEL=1 + VERCEL_ENV=production + drafts=1`, the velite step emits the per-draft warning lines AND THEN the next step (Next.js SSG) throws via the guard. The user gets a build log full of "including draft" lines followed by a fatal error — the warnings imply drafts were included when in fact the build aborts. Either skip the warnings when the guard would have thrown (requires reading `VERCEL`/`VERCEL_ENV` in the velite transform too — coupling velite to deploy environment), or accept misleading log output. The design does not address the ordering.
- **Stress-test the symmetry with `blog-errors.ts`.** Deferral 1 says the two `-errors.ts` files are kept separate for now. But the design also says `project-errors.ts` ADDS a looks-like-prod branch that `blog-errors.ts` does not have. So the two files are NOT actually parallel patterns anymore — blog has a different guard surface than projects. Either backport the looks-like-prod branch to blog (in scope of this spec? probably not), accept that the spec is making the blog less safe than projects, or front-load the unification now.
- **Challenge the "VERCEL=1" precondition.** The guard returns `null` when `VERCEL !== "1"`. This means a local `pnpm build` with `VERCEL_ENV=production` manually set in `.env.local` does NOT trip the guard. Documented? Intended? If a CI environment other than Vercel (a future migration to a different provider) runs the build, the guard does nothing and drafts leak silently. Add a non-Vercel fallback or document the Vercel-only scope.
- **Stress-test the `NODE_ENV === "production"` predicate in the build-log warning.** Component 3 step 3 emits the warning only when `NODE_ENV === "production"`. But `velite build` (Component 12's chosen location) is invoked from `pnpm build`, where Next.js sets `NODE_ENV=production`. Velite itself may run with `NODE_ENV=development` or unset, depending on how it is wired. Confirm the actual `NODE_ENV` value during `velite build` in this project; the design assumes it without stating the wiring.

## Attack 4 — Heading hygiene (Component 2)

- **Challenge the AST node-type list.** The visitor handles `mdxJsxFlowElement` and `mdxJsxTextElement` for capitalized `<h1>` (and `<H1>`) detection. But MDX expressions (`{props.heading}`) and dynamic JSX (`{condition ? <h1>X</h1> : <h2>X</h2>}`) are wrapped in `mdxFlowExpression`/`mdxTextExpression` nodes whose children include the JSX. The visitor traversal via `unist-util-visit` is "every node in document order" — visit's default traversal DOES descend into all children, so this is probably OK, but the design should state the traversal is unconditional. The design says "for each `heading` node" and "for each `mdxJsxFlowElement`" — that wording implies a type-filtered visit, which misses expression-wrapped JSX unless visit's filter is per-call and traversal continues.
- **Stress-test the `prev=0` exclusion.** The design says "there is no `prev=0` case because the first heading is already gated to h2." True only if the first-heading check happens BEFORE the pairwise walk. The pseudocode does check sequence[0] first, but the comment is misleading: the actual invariant is "after the first-heading check passes, every subsequent prev is ≥2." State the invariant, not the impossible case.
- **Challenge the `PROJECTS_ALLOW_H4=1` semantics.** "The env var unlocks the depth, NOT the sequence" — but the pairwise walk fails on `h2 → h4` because `4 > 2 + 1`. If `PROJECTS_ALLOW_H4=1`, the author who wrote `h2 → h4` probably did so intentionally (using h4 as a deliberate sub-sub-heading). Requiring them to insert a phantom h3 to satisfy the sequence check defeats the env-var's purpose. Either let the env var also unlock the skip OR document that authors using h4 must still avoid skipping through h3.
- **Stress-test fenced-code detection of `<H1>` (capitalized).** The design says capitalized `<H1>` is detected as `mdxJsxFlowElement`. But the MDX parser only treats capitalized JSX tags as JSX when they parse as such — inside a fenced code block, the entire content is a string `value` on a `code` node, regardless of capitalization. The design is consistent on this point. Confirm by testing the fixture `<H1>` outside a code block (real JSX) AND inside a code block (string content) — both cases are in the integration tests. OK.
- **Challenge the `meta.content` source.** "`content` is `meta.content` (frontmatter-stripped body, available on Velite's `VeliteFile`)." Verify the API: in Velite v0.3.x, the transform receives `(data, ctx)` where `ctx` exposes `meta` — but the property name for the frontmatter-stripped raw body is implementation-detail-dependent and may be `meta.content` OR `meta.body` OR require a separate read. Verify against `node_modules/velite/dist/index.d.ts` (the design already cites this file for the image shape; cite the relevant field here too).

## Attack 5 — Fixture project and contract tests (Overview, Req 1.8)

- **Challenge the "fixture project under `draft: true`" approach.** The fixture lives at `content/projects/fixture-placeholder.mdx` with `draft: true`. The build-time contract test (Velite output-shape, Req 1.11) needs to verify that `projects` is non-empty AND that an entry exists with the expected fields. If the fixture is the ONLY project AND it is a draft, then `getPublishedProjects()` returns `[]` in normal CI, and the gallery test asserts the empty state. Now the design has a contradiction:
  - Velite always emits the fixture (drafts are in the raw `projects` array, just filtered by `getPublishedProjects()`).
  - The "two-build" E2E (Build 1 with `PROJECTS_INCLUDE_DRAFTS=1`, Build 2 without) needs the fixture visible in Build 1.
  - The empty-state test asserts the empty state when zero published projects exist — which is Build 2's state.
  This is consistent but fragile: a future author adding a real (non-draft) project will break Build 2's empty-state assertion. The design does not describe how the empty-state test gets unsubscribed when the first real project ships. Either (a) make the empty-state test fixture-based with isolated content, (b) make the assertion conditional on `getPublishedProjects().length`, or (c) accept that the assertion will be deleted as part of the first real-project PR.
- **Stress-test the dual-build E2E.** "CI E2E in Build 1 (preview-like) asserts the placeholder project IS visible when `PROJECTS_INCLUDE_DRAFTS=1`. CI Build 2 (production-like) asserts the placeholder IS NOT in `/projects`." This requires running `pnpm build` twice in CI with different env vars. The blog-core spec presumably set up this dual-build topology already (commit `7b8d11f feat(blog): implement blog-core spec with CI dual-build topology`). Confirm the project-showcase plumbs into that existing topology rather than introducing a parallel one — the design does not name the integration point.
- **Challenge the silent fixture exclusion path.** Velite needs to scan `content/projects/` for files, and the fixture lives there. If a maintainer renames the fixture (or moves it under a subdirectory), the contract tests need to find it. The fixture path is hard-coded in tests; spec out the fixture-discovery contract or accept brittle tests.

## Attack 6 — Component reuse vs. duplication symmetry (multiple sections)

- **Challenge the `formatContentDate` re-export asymmetry.** `blog.ts` re-exports as `formatPostDate`; `projects.ts` does NOT re-export at all (Component 3 "Decision on re-export"). Page components consume `format-date.ts` directly. This means:
  - Blog page imports `formatPostDate` from `@/lib/blog` (legacy API).
  - Project page imports `formatContentDate` from `@/lib/format-date` (new API).
  - Two patterns coexist forever. A new content type added later will face an arbitrary precedent.
  Decide ONE pattern. The design's rationale ("blog had a legacy API; projects does not") is true but creates entrenched divergence. Either migrate blog to import from `format-date.ts` directly (delete the re-export), or commit to re-exporting from every content-type module.
- **Stress-test the `<UpdatedBadge />` being inline in the detail page.** Component 10 defines it as "a local component inside the page file — not extracted (single-use)." But the gallery card (Component 6, `<ProjectCard />`) does NOT render the updated badge — only the detail page does. Req 2.4 / Req 6.4 may require the badge on the card too (verify against requirements). If the badge appears on the card later, the inline-only definition becomes a refactor cost. Mirror the blog's badge structure or document the difference.
- **Challenge the absence of a `<ProjectMeta />` extraction.** The detail page renders date, updated badge, and status badge in the header. The card also renders date, updated state (?), and status badge. The design extracts `<StatusBadge />` but inlines the date and updated badge in two places. This is asymmetric and will be a refactor target on the third content type. State the rule.

## Attack 7 — Operational and ops-edge issues

- **Stress-test the `eager = i < 4` heuristic.** Comment in Component 6: "on mobile single-column that's 4 cards' worth of vertical scroll, all loading eagerly is acceptable for ≤4 covers at <500 KB each." But the file-size warning is at 500 KB and the hard cap is 1 MB. A gallery with four 1 MB covers eager-loaded over a slow connection is exactly the LCP regression the design is trying to avoid. Tighten the eager threshold to 1–2 OR enforce a stricter file-size cap on eager-loaded covers OR document the trade-off as accepted.
- **Challenge the sitemap `lastModified`.** "`lastModified: project.updated ?? project.date`" — but `date` is an ISO date (YYYY-MM-DD), and Next.js's sitemap `lastModified` expects a Date or ISO datetime. The date-only format may serialize to UTC midnight, which is then offset-relative in some sitemap consumers. State the format conversion or accept the ambiguity.
- **Stress-test the OG image fallback path.** "When `ogImage` is absent for a non-draft project, emit an INFO-level log line to `process.stdout` naming the slug and stating that share previews will use the site default." The "site default" is not defined in this design. Either name the default OG image asset path or note that the metadata simply omits `images` and lets Next.js / consumers fall back to platform defaults.
- **Challenge the `dynamicParams = false` interaction with deploys.** When a new project lands, the static-gen list changes. `dynamicParams = false` means any slug not in `generateStaticParams()` 404s. This is intended for production builds but causes friction in `vercel dev` if `PROJECTS_INCLUDE_DRAFTS` is toggled between sessions — the cache may serve a 404 for a slug that is now draft-visible. Either note that `vercel dev` always rebuilds or accept the dev friction.
- **Stress-test the doc test path picker.** Component 13 says: "if the project's Vitest config doesn't pick up `docs/**`, the alternative location is `tests/docs/projects-authoring.test.ts` — chosen during the tasks phase based on which path is already in the Vitest include glob." Deferring this to tasks defeats the design phase. CHECK the Vitest config now; do not punt.
- **Challenge the absence of a CSP-impact statement for `<iframe>` and `<svg>`.** Component 1 lists `iframe` and `svg` as wide-media tags. Embedding an iframe in MDX requires the site's CSP to allow `frame-src` for the embedded origin; the design says "CSP unchanged." If a project embeds a YouTube iframe, the existing CSP must already allow it (verify) OR the iframe support is theoretical and authors must coordinate per-project. State the policy.

## Top 5 Risks/Gaps (Long Doc — N=5)

1. **Tailwind Typography wide-media layout is asserted, not engineered.** The "no custom CSS" claim and the "media wider than prose text" goal are not jointly achievable with stock Tailwind Typography. The selective-element-width-constraint pattern referenced in Req 6.7 needs a concrete CSS sketch (likely involving an inner `max-w-prose` wrapper for text-flow children, or `prose-img:max-w-none` modifiers). Without it, the detail-page layout is undefined — and this is the SINGLE most visible feature of the spec.

2. **Chokepoint scanner has identified false-negative paths.** Type-only imports (`type P = import("#site/content").projects[number]`), destructured namespace imports (`const { projects } = content`), and re-exported barrels through non-allowlisted intermediates all evade the scanner as designed. The contract that "no file outside the allowlist references `projects`" is not enforced for these shapes. Either close the holes or document them as deliberate scope limits.

3. **Draft-leak guard ordering with build-log warnings is broken.** The velite-transform-emitted "including draft" warnings fire BEFORE `checkVercelDraftGuard()` runs in Next.js SSG. A production build with `PROJECTS_INCLUDE_DRAFTS=1` will log warnings as if drafts shipped, then abort the build. The log is misleading. The design either needs to gate the velite warnings on the same env-var checks the guard performs, or accept the misleading sequence.

4. **Velite output-shape assumption is single-point-of-failure.** The design cites `node_modules/velite/dist/index.d.ts` for `s.image()`'s `{ src, width, height, blurDataURL? }` shape and a `meta.content` field. Velite is v0.3.x — minor-version churn could rename fields. The "output-shape contract test (Req 1.11)" exists but it tests the EMITTED shape, not the consumed `meta.content` field name used by the heading-hygiene visitor. Add a `meta.content` shape test or pin the velite version with a code-comment lock.

5. **Empty-state and fixture coupling will break on first real project.** The fixture-as-draft strategy means the gallery test passes the empty-state assertion in normal CI. The first real (non-draft) project breaks that assertion. There is no transition plan — the assertion deletion must be remembered by the PR author six months from now. Either isolate the empty-state test to a synthetic fixture (e.g., a Vitest-only `__fixtures__/projects-empty/` directory) or change the assertion to be conditional on `projects.length === 0`.

## Top 3 Conclusions to Challenge or Reverse

1. **Reverse the decision NOT to re-export `formatContentDate` from `projects.ts`.** The asymmetry with `blog.ts` (which DOES re-export as `formatPostDate`) entrenches a "blog is special" precedent that will surface on every future content type. Either (a) re-export from every content-type module with a content-type-prefixed alias, OR (b) delete the blog re-export and have all page components import `formatContentDate` from `@/lib/format-date` directly. The current asymmetric choice is the worst of both worlds: the test-time `formatPostDate === formatContentDate` parity assertion proves the equivalence, but the runtime APIs diverge by name. Pick parity OR divergence — not both.

2. **Reverse the choice to emit per-draft build-log warnings from the velite transform.** Component 12 chooses the velite transform because "velite runs first." But the guard logic lives in `src/lib/projects.ts` and runs LATER. The right place to surface the env-var decision is the same place the decision has consequences — `getPublishedProjects()`. Yes, SSG log buffering varies, but the trade-off favors logging at the point of consequence over logging at the point of generation. Move the warning to `projects.ts`.

3. **Reverse the "no custom CSS" claim and own the per-tag styling.** The seven-tag wide-media list is essentially a tacit `prose-img:max-w-none prose-video:max-w-none prose-pre:max-w-none …` rule set. Acknowledge this. Write the actual Tailwind modifiers OR a small `globals.css` rule scoped to `.prose > img, .prose > video, …`. The current design hand-waves the mechanism and will fail the first time someone tests the layout. State the mechanism explicitly; "Tailwind Typography just does it" is wrong.
