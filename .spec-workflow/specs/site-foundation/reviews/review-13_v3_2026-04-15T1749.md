## Findings

### WARNING: Dark-mode test omits computed `color` property
- **File:** e2e/tests/playground-isolation.test.ts:130
- **Issue:** The task prompt explicitly says: "assert playground container computed styles for --background, --foreground, and color still match light-mode token values." The test at line 130-154 checks --background, --foreground, --primary, and --primary-foreground custom properties but never reads the computed `color` CSS property on the container. The playground.css @layer rule sets `color: oklch(0.145 0 0)` on .playground-container — the test should assert that this computed value persists after adding .dark to <html>. Without this assertion, a regression where the container's text color inherits the dark-mode foreground would go undetected.
- **Task Requirement:** R11 AC5 / task prompt dark-mode assertion list

### WARNING: R11 AC3 only partially verified — Button background/color not asserted
- **File:** e2e/tests/playground-isolation.test.ts:73
- **Issue:** AC3 requires that a shadcn/ui component 'SHALL render correctly using CSS custom properties re-established by the playground base stylesheet.' The test (lines 73-101) only verifies padding and font-size — not background-color or color, which are the properties that demonstrate token re-establishment. The deferral to task 15 is well-documented and the reason (missing @theme block) is sound, but as written AC3 is not fully met by this task's test suite. The spike-summary correctly records background-color as transparent, but the test itself makes no assertion about it, meaning a future regression (e.g., background resolving to an unexpected value) would not be caught. Consider adding a soft assertion (e.g., expect background-color to be rgba(0,0,0,0) with a comment explaining the task-15 dependency) so the test documents the current known state and fails if something changes unexpectedly.
- **Task Requirement:** R11 AC3
