## Naming Conventions

### Files

- **React components**: `kebab-case.tsx` (e.g., `hero-card.tsx`, `blog-post-card.tsx`). One exported component per file. Small, unexported helper components that serve only their parent may live in the same file. The component itself uses PascalCase as a named export.
- **Route files**: Next.js conventions — `page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `not-found.tsx`, `route.ts`.
- **Utilities/helpers**: `kebab-case.ts` (e.g., `content.ts`, `format-date.ts`).
- **Hooks**: `use-[name].ts` (e.g., `use-media-query.ts`).
- **Types**: `kebab-case.ts` (e.g., `content-types.ts`). Colocate types with the code that uses them when possible; only use `src/types/` for types shared across multiple directories.
- **Config files**: `kebab-case.ts` (e.g., `site.ts`).
- **Content files**: `kebab-case.mdx` (e.g., `my-first-post.mdx`). The filename becomes the URL slug via Velite's `s.path()`.
- **CSS Modules**: `[component-name].module.css` or `styles.module.css` when colocated.
- **Tests**: `[filename].test.ts` / `[filename].test.tsx`. Unit tests (Vitest) are colocated next to source files. E2E tests (Playwright) live in `e2e/tests/`.

### Code

- **Components**: `PascalCase` named exports (e.g., `export function HeroCard()`)
- **Functions/methods**: `camelCase` (e.g., `getPostsByTag()`, `formatDate()`)
- **Constants**: `UPPER_SNAKE_CASE` for primitive values and frozen enumerations (e.g., `MAX_POSTS_PER_PAGE`, `BREAKPOINTS`), `camelCase` for structured/config objects (e.g., `siteConfig`, `navItems`)
- **Variables**: `camelCase`
- **Types/interfaces**: `PascalCase` (e.g., `type BlogPost`, `interface SiteConfig`)
- **Enums**: `PascalCase` name, `PascalCase` members
- **URL slugs/routes**: `kebab-case` (enforced by content filenames and route folder names)

### Directories

- `kebab-case` for all directories (e.g., `hero-card/`, `blog-post/`)
- Exception: Next.js App Router conventions — `[slug]`, `(group-name)`, `_private`

## Import Patterns

### Preferred Import Order

1. React / Next.js imports (`react`, `next/...`)
2. External dependencies (`@radix-ui/...`, `clsx`, etc.)
3. Internal absolute imports (`@/components/...`, `@/lib/...`)
4. Content imports (`#site/content`)
5. Relative imports (`./`, `../`)
6. Style imports (CSS Modules)

Enforcement via `eslint-plugin-import` (or equivalent) should match this order when configured.

### Path Aliases

Defined in `tsconfig.json`:

- `@/*` → `./src/*` (application code)
- `#site/content` → `./.velite` (Velite-generated content data). Velite must run before type-checking or editor use — `.velite/` does not exist until the first build. A `postinstall` or `dev` script should ensure it exists.

### Module Rules

- Use absolute imports (`@/components/ui/button`) for cross-directory references.
- Use relative imports (`./hero-card`) only within the same directory or immediate children.
- Never use relative imports that go up more than one level (`../../` is a sign to use an absolute import).
- No barrel files (`index.ts` re-exports). Import modules directly by file path.

## Code Structure Patterns

### Component File Organization

```tsx
// 1. Imports
import { ... } from "react"
import { ... } from "@/lib/utils"

// 2. Types (if component-specific and not exported)
type Props = { ... }

// 3. Component
export function MyComponent({ ... }: Props) {
  return (...)
}
```

- Server components are the default. No directive needed.
- Client components add `"use client"` at the top of the file. Push `"use client"` as far down the component tree as possible — wrap only the interactive leaf, not the whole page.
- No default exports for components. Named exports only. Exception: Next.js route files (`page.tsx`, `layout.tsx`, etc.) use `export default` as required by the framework.

### Content File Organization

```mdx
---
title: "Post Title"
date: 2026-03-27
description: "Short description"
tags: ["tag-a", "tag-b"]
# ... other frontmatter per Velite schema
---

Content body in MDX.
```

- All content with prose bodies is MDX with frontmatter. Pure structured data collections (contributions, resources) may use YAML or JSON instead — see directory organization.
- Frontmatter schemas are defined in `velite.config.ts` — that is the single source of truth for what fields each content type has.
- Computed fields (slug, reading time, permalink) are derived via Velite schema transforms, not in components.
- Velite compiles MDX bodies into component code accessible via the content import. Page components render MDX bodies using Velite's provided component renderer.
- Single-entry content pages (about, now, colophon) import directly from Velite. Collection queries (blog posts, projects) use helpers in `src/lib/content.ts`.
- RSS feed includes blog posts only.
- `content/pages/` contains files for pages with authored markdown body content (about, now, colophon). Component-only pages (contact, sitemap, slashes) render entirely from code and have no content file.
- `content/blog/` is intentionally flat. Series/multi-part grouping uses frontmatter fields (`series`, `seriesOrder`), not subdirectories. This preserves stable URL slugs derived from filenames.
- **Content images**: Colocate images with the MDX file in `content/`. Velite copies them to `public/static/` at build time. Reference via relative paths in MDX (e.g., `![alt](./my-image.png)`).
- **Site images** (logo, OG, profile photo): Place directly in `public/images/`. Reference via absolute paths (e.g., `/images/logo.png`).

### Playground Item Organization

Each playground item lives in `playground/[item-name]/` at the project root:

```
playground/
└── pixel-art-editor/
    ├── index.tsx               # Entry component (must be a client component)
    ├── styles.module.css       # Scoped styles
    ├── canvas.tsx              # Sub-components
    └── palette.ts              # Item-specific helpers
```

The App Router route at `src/app/(playground)/playground/[slug]/page.tsx` dynamically imports the matching item from `playground/[slug]/index.tsx`. This keeps playground code separate from the main app while still being part of the same build.

`playground/manifest.ts` exports an array of item metadata (slug, title, description, tags, `iframeIsolated` flag) alongside lazy import functions (`() => import(...)`) for each item. This serves as the single source for `generateStaticParams`, the playground gallery page, and the dynamic import resolution in `[slug]/page.tsx`.

Playground items use `@/` aliases for `src/` imports and relative imports within their own directory.

Items needing full isolation (conflicting dependencies, `position: fixed`, viewport units) set `iframeIsolated: true` in the manifest and are loaded via the `embed/page.tsx` route inside an iframe.

## Module Boundaries

### Dependency Direction

```
content/ (MDX files)
    ↓ (processed by Velite at build time)
.velite/ (typed data + compiled MDX)
    ↓ (imported as data)
src/app/ (routes — orchestrate pages)
    ↓ (renders)
src/components/ (UI — receives data via props)
    ↓ (uses)
src/lib/ (non-React application logic)

playground/manifest.ts → imported by src/app/(playground)/ for generateStaticParams and gallery
playground/[item]/index.tsx → dynamically imported by src/app/(playground)/playground/[slug]/page.tsx
playground/[item]/ → may import from src/lib/ and src/components/ui/

src/config/ → imported by app/, components/, and lib/
src/hooks/ → imported by client components only
src/types/ → imported by anything in src/
next.config.ts → consumes route structure (CSP path patterns), content pipeline (Velite webpack plugin), and redirect rules
```

- **`src/lib/`** must not import from `src/components/` or `src/app/`.
- **`src/components/`** must not import from `src/app/`.
- **`src/components/ui/`** (shadcn) must not import from other `src/components/` subdirectories. Other components compose `ui/` primitives, not the other way around.

These boundaries are conventions. Enforcement via `eslint-plugin-boundaries` or `dependency-cruiser` may be added during implementation.
- **`playground/`** items may import from `src/lib/` and `src/components/ui/` but should not import from `src/components/shared/`, `src/components/layout/`, or `src/app/`. If a `src/components/shared/` component has no visual coupling to the site's design system, consider moving it to `src/lib/` so playground items can use it. Refactoring `src/lib/` or `src/components/ui/` may require updating playground items.

### Route Group Separation

- **`(site)/`**: Full site chrome (nav, footer). All main content pages.
- **`(playground)/`**: Minimal or no chrome. Playground index and items. Own layout with style reset (`all: initial`, `isolation: isolate`, `@layer playground`). Note: `all: initial` resets inherited typographic properties (`font-family`, `font-size`, `line-height`, `color`) and `box-sizing` to browser defaults. A playground base stylesheet must re-establish these properties for shared component (`src/components/ui/`) compatibility.
- **Embed routes** (`playground/[slug]/embed/page.tsx`) are complete standalone HTML pages with their own document, layout stack, and provider context — not fragments. They render inside an iframe's browsing context and do not share state with the parent page. Detailed embed architecture (parent-iframe communication, decision encoding) to be specified during implementation.
- Both groups share the root `layout.tsx` for `<html>`, `<body>`, and global providers (theme, fonts).

## Code Size Guidelines

- **File size**: Aim for under 300 lines. If a file exceeds 300 lines, consider whether it has multiple responsibilities that should be split. Config files serving a single purpose (e.g., `velite.config.ts`) may exceed 300 lines — extract computed field transforms into `src/lib/` if the file grows unwieldy.
- **Function/method size**: Aim for under 50 lines. Extract helpers when a function does multiple distinct things.
- **Component complexity**: A component that takes more than 8 props is a signal to reconsider the API or split into composed sub-components.
- **Nesting depth**: Maximum 3 levels of nesting in JSX per component file. Extract sub-components to flatten deeply nested markup.

## Documentation Standards

- Public utility functions in `src/lib/` get JSDoc describing purpose and parameters.
- Components generally do not need JSDoc — props types serve as documentation. Components with side effects, scroll listeners, or complex conditional logic should have a brief behavioral comment at the top of the file.
- Complex logic gets inline comments explaining *why*, not *what*.
- No README files per module. The structure.md (this document) is the project-level structural reference.
