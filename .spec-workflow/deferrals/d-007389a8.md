## Context
Confirmed live by the final task 24 reviewer against a clean Velite + `next build`, with the probes present verbatim in the rendered `profile.html`: `10.1073/7805550131`, `doi:10.1234/contact-780-555-0141`, and `doi:10.1073/pnas.1320040111,780-555-0151` all go unreported, while a plain-prose control on the same page is caught. The mask was introduced to close a worse hole: the previous round suppressed a DOI false positive with a lookbehind `(?<![\d./])`, which let URL-embedded numbers like `href="https://wa.me/17805550121"` escape entirely — a genuinely plausible "message me" link. The reviewer judged the replacement strictly better: reaching the new blind spot requires deliberately typing a number against a DOI prefix, whereas the `wa.me/` hole was reachable from natural prose. Alternatives not taken: bound the DOI mask's trailing run more tightly (e.g. stop at a comma or a digit boundary), or replace masking with an allowlist of the specific DOIs present in content.

## Decision Deferred
Accepted as a residual blind spot rather than fixed. `e2e/tests/profile-resume.test.ts`'s `maskNumericNoise` deletes DOI-shaped strings via `/\b(?:doi:\s*)?10\.\d{4,9}\/[^\s"'&lt;&gt;]+/gi` before the phone patterns run. Because `[^\s"'&lt;&gt;]+` swallows any whitespace-free run, a phone number typed hard against a `10.NNNN/` prefix is deleted and never reported.

## Revisit Criteria
Tighten the DOI mask's trailing character class so it cannot run through a comma or into a second number, then re-run the 20-probe evasion set and re-confirm zero false positives across all three build modes (56 / 68 / 69 documents, measured after `rm -rf .next`).
