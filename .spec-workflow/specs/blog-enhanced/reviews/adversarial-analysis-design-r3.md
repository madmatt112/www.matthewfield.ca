## Selected attack surfaces

### 1. `next.config.ts` reads `.velite/index.js` at config-load time (v3 Reversal #3, `X-Robots-Tag` headers)

The v3 fix for the meta-vs-header gap pushes a build-time read of `./.velite/index.js` into `next.config.ts`'s `headers()` callback:

```ts
import velite from "./.velite/index.js"; // built before next build (Velite postinstall hook)
const hiddenRoutes = velite.posts
  .filter((p) => p.hiddenFromLists === true && !p.draft)
  .map((p) => `/blog/${p.slug}`);
```

- **(Novel, P0) Challenge the claim that "Velite's postinstall hook produces `.velite/index.js` before `next build` runs."** Velite is not configured with a postinstall hook in this project. Check `package.json` — there is no `"postinstall": "velite"` script today. `velite` runs as part of `next.config.ts`'s existing `withContentCollections` wrapper (or via `velite build` in the build script), NOT during `pnpm install`. On a CLEAN clone — fresh `pnpm install`, NO prior build, run `next build` — `next.config.ts` is loaded by Next.js BEFORE the inner velite build fires. The `import velite from "./.velite/index.js"` will throw `Cannot find module './.velite/index.js'` on first build. The design has invented a postinstall hook that does not exist in the repo, has not been added by the design, and is not pinned in the `package.json` extensions list. **Action:** EITHER pin a `"postinstall": "velite build"` script in `package.json` (with the cost: velite runs on every `pnpm install`, including in CI cache-hits, ~5-10s overhead) OR move the hidden-route enumeration OUT of `next.config.ts` (e.g., generate a static `hidden-routes.json` as part of the velite transform output, with a fallback to empty array if absent), OR use `try/catch` around the import with empty-array fallback. As written, **first-time build is broken**.
- **(Novel, P0 compounding) Stress-test the `next build` topology dependency cycle.** Even IF the postinstall hook exists, the dependency chain becomes: `pnpm install → velite build → .velite/index.js created → next build → next.config.ts loads → imports .velite/index.js`. But velite's output depends on `content/posts/*.mdx`. On a PR that ADDS a new hidden post (`fixture-search`), the sequence on a clean CI worker is: checkout → `pnpm install --frozen-lockfile` (runs postinstall → velite build → reads content/posts/*.mdx including the new fixture-search → writes .velite/index.js with the new post). Fine on a happy path. **BUT:** if velite's transform FAILS (the new fixture violates the new audit), `pnpm install` ALSO fails. The `npm install` step in CI now has TWO failure surfaces it didn't have before: dependency resolution failures AND content schema failures. The error message for content-schema-fail-during-install will surface as `pnpm install` failure, not as a "content schema" failure. Operator diagnostic clarity degrades.
- **(Novel) Challenge the import path `"./.velite/index.js"` in a TypeScript config file.** `next.config.ts` is loaded by Next.js's config-loader, which uses `tsx`/`ts-node`-style loader. The literal `import velite from "./.velite/index.js"` resolves a `.js` file at runtime, but TypeScript needs a type declaration. There's no `.velite/index.d.ts` exposing the `posts` array's type — actually there IS one (250B per `ls`), but it's auto-generated by velite. Confirm `next.config.ts` typecheck under `tsc --noEmit` passes WITH the import. If `velite.posts` is typed `any`, the `.filter((p) => p.hiddenFromLists === true && !p.draft)` predicate compiles but loses type safety. Verify against the actual `.velite/index.d.ts` shape.
- **(Novel) Stress-test the `excludeFromSearch` interaction with the header rule.** The header rule fires for `hiddenFromLists === true && !p.draft`. The design adds `excludeFromSearch` as a second flag. A post with `excludeFromSearch: true && hiddenFromLists: false` is "visible in lists but excluded from search" (truth-table row 4). That post will NOT get `X-Robots-Tag` because `hiddenFromLists !== true`. But the rationale for `X-Robots-Tag` is "bots that parse only headers still get noindex." A post that's `excludeFromSearch: true` is exactly the post a search-bot SHOULD index (it's visible in lists, just not in site-internal Pagefind). So this is fine. **But** the design never explicitly states the header rule applies ONLY to `hiddenFromLists`-true posts and NOT `excludeFromSearch`-true posts. A future reader will assume both apply. Pin the rule explicitly: "the `X-Robots-Tag` header applies to `hiddenFromLists === true` posts only, regardless of `excludeFromSearch`."
- **(Novel) Challenge `next.config.ts`'s ability to filter by `!p.draft`.** Velite's posts collection in Build 2 mode excludes drafts before the JSON file is written. So `.velite/index.js`'s `posts` array DOES NOT CONTAIN drafts. The `!p.draft` filter is a redundant guard for Build 2 builds. **But** in Build 1 mode (drafts included), `.velite/index.js` DOES contain drafts. So the filter is correct for Build 1 and redundant for Build 2 — no harm. Fine. Move on.

### 2. The Task 0 pipeline spike (v3 Pre-implementation gate)

v3 pins a Task 0 spike that runs `next build → next start → wget → pagefind` against the CURRENT `main` branch and asserts wget produces `.html` files, Pagefind reads them, and a known-phrase query returns ≥1 result.

- **(Novel, P0) Challenge the claim that this spike VERIFIES the v3 pipeline.** The spike runs against the **current `main` branch**, which has NEITHER `fixture-search` NOR `hiddenFromLists: true` NOR the `--input-file=./urls-extra.txt` URL-list mechanism NOR `data-pagefind-body` attributes. The spike therefore verifies the **simple wget path** for the existing content, but verifies NOTHING about the **`--input-file` mechanism**, which is THE v3 P0 fix. Specifically: the spike does not run with `--input-file=./urls-extra.txt`; it does not test the "hidden post reachable only via input-file" case; it cannot confirm that wget actually fetches a URL from the input file AND that pagefind subsequently finds the resulting `.html`. The reviewer's v2 P0 #1 — "fixture-search is unreachable" — is NOT validated by this spike. **Action:** REWRITE Task 0 to specifically test the `--input-file` mechanism: create a temporary post (`/tmp/secret-page` or similar) that is reachable ONLY via the explicit URL list, run wget with `--input-file`, run pagefind, query for a known phrase from THAT page. As written, Task 0 is theater — it tests the parts of the pipeline that were already working in v2, not the parts v3 changed.
- **(Novel) Stress-test the spike's "blocks all other tasks" semantic against the tasks workflow.** The design says "if the spike fails, the design returns to revision (v4); the tasks document does NOT begin until the spike passes." But this gate is enforced by … what? It's a task in `tasks.md`. The tasks workflow's enforcement is "implementer reads the file and works through it." Nothing in CI, nothing in the spec-workflow tooling, prevents a contributor from skipping Task 0 and starting Task 1. The spike's outcome must be recorded somewhere observable — an `IMPLEMENTATION_LOG.md`, an implementation log entry, a checked checkbox in `tasks.md` — AND the design should pin that artifact. As written, the gate is a polite request.
- **(Novel) Stress-test the spike's `npx -y pagefind@latest` command against the pinned `package.json` version.** Step 5 of the spike runs `npx -y pagefind@latest --site ./out`. But the design pins `pagefind` as an EXACT version in `devDependencies`. The spike runs against `@latest`, which may be a DIFFERENT version than the pinned one. So the spike verifies "the latest pagefind works against current main's HTML" but the CI will run "the pinned pagefind version against new HTML." Pin the spike's pagefind invocation to use `node_modules/.bin/pagefind` (after `pnpm install`) or `npx -y pagefind@$(jq -r '.devDependencies.pagefind' package.json)`. As written, the spike validates the wrong version.
- **(Novel) Challenge "spike acceptance criteria" against the actual v3 pipeline.** The criteria are: (a) wget produces .html files, (b) pagefind reads them, (c) a query returns ≥1 result. The criteria do NOT include: (d) `--input-file` URL is fetched and indexed; (e) hidden posts with `noindex` meta tag are still indexed by Pagefind despite the meta tag; (f) `data-pagefind-body` (which doesn't exist in the current main) gates indexing correctly; (g) the master timeout fires as expected on a hung wget; (h) crashing wget mid-mirror produces a clean error rather than partial output. Without (d), the spike misses the v3 P0 fix entirely. Without (e), the noindex+pagefind contradiction is unvalidated. **Action:** expand criteria to include at MINIMUM (d).
- **(Compounding, recurring-pattern) The "pinned, no verification" pattern recurs at a meta level.** v1 had it for `pagefind --site URL`. v2 had it for `wget --mirror`. v3 has it for `next.config.ts` reading `.velite/index.js` (no postinstall hook actually configured), for the `--input-file` mechanism (no spike covers it), and for the `excludeFromSearch` flag (no Velite-transform test asserting it filters Pagefind crawl correctly). The reviewer's recommendation from v2 was "spike before approval." v3 added a spike — but the spike doesn't cover v3's actual novel mechanisms. The pattern is now: each revision pins a NEW mechanism without verifying it, and the next reviewer catches the gap.

### 3. The `excludeFromSearch` flag and its enforcement (v3 risk #4 fix)

v3 adds `excludeFromSearch?: boolean` to address the v2 "semantic overload" of `hiddenFromLists`. The Velite transform sets `data-pagefind-body` on the post page ONLY when `excludeFromSearch !== true`.

- **(Novel) Challenge whether `data-pagefind-body` is actually conditioned on `excludeFromSearch`.** The design SAYS the Velite transform sets `data-pagefind-body` only when `excludeFromSearch !== true`. But the Integration Point for `src/app/(site)/blog/[slug]/page.tsx` (line 103) says: `data-pagefind-body` attribute on `<article>` (gated by `!post.excludeFromSearch` — v3). That's the page-render layer, NOT the Velite transform layer. So who actually gates it? The page renders `<article data-pagefind-body={post.excludeFromSearch ? undefined : ""}>`? Pin the EXACT JSX. Without that pin, the implementer will set `data-pagefind-body=""` (empty string) which Pagefind treats as present-and-true OR `data-pagefind-body={false}` which renders as the attribute being absent. The condition is ambiguous.
- **(Novel) Stress-test the wget URL list against `excludeFromSearch: true` posts.** The v3 URL-list generator at script line 843-847:
  ```js
  const extraSlugs = [
    ...velite.posts
      .filter((p) => p.hiddenFromLists === true)
      .map((p) => p.slug),
  ];
  ```
  This filter does NOT exclude `excludeFromSearch: true` posts. So a post with BOTH `hiddenFromLists: true` AND `excludeFromSearch: true` (truth-table row 3: "hidden everywhere") will be in `urls-extra.txt` and wget WILL fetch it. The resulting HTML will go into `./out/`. Pagefind will then crawl it. The `<article>` element will NOT have `data-pagefind-body`, so Pagefind's body-indexing skips it — BUT Pagefind's default behavior when `data-pagefind-body` is ABSENT depends on configuration. Per Pagefind docs, when `data-pagefind-body` is absent on ALL pages, Pagefind indexes the full `<body>`. When SOME pages have it and OTHERS don't, Pagefind's behavior is "pages with the attribute are indexed via that scope, pages without are skipped IF the bundle is configured to require it." This is not pinned anywhere in the design. The design assumes "absent attribute = skip" but Pagefind's actual default is "absent attribute = use root scope." So `excludeFromSearch: true` posts may STILL be indexed. **Action:** EITHER add an exclude filter to `extraSlugs` (`.filter((p) => p.hiddenFromLists === true && p.excludeFromSearch !== true)`) OR pin Pagefind's `--root-selector` to a selector that doesn't match `excludeFromSearch:true` pages.
- **(Novel) Challenge the absence of a test for the truth table.** The design pins a four-row truth table for `(hiddenFromLists, excludeFromSearch)`. There is no Vitest, no Playwright test that asserts each row's behavior. Without a test, the implementer ships row 1 and row 2 (the common cases), and rows 3 and 4 (the operational cases — "thanks for subscribing," "ToC landing page") drift into undefined behavior. Pin a test matrix.

### 4. The `src/lib/blog-taxonomy.ts` module split (v3 risk #3 fix)

v3 moves `getAllTags`, `getAllCategories`, `getPostsByTag`, `getPostsByCategory` from `src/lib/blog.ts` to a new `src/lib/blog-taxonomy.ts` so the file-level allow-list in the verifier doesn't accidentally allow taxonomy code to use the unfiltered function.

- **(Novel, P0) Challenge the migration scope.** The design says `src/app/(site)/blog/tags/[tag]/page.tsx`, `src/app/(site)/blog/categories/[category]/page.tsx`, and `src/app/sitemap.ts` update their import paths. **But:** the existing `src/app/sitemap.ts` calls `getAllTags()` AND `getAllCategories()` at the very least. Per the design's own Integration Points: `getAllTags`, `getAllCategories` are updated to source from `getVisiblePublishedPosts()` so `fixture-search`'s `search-test` tag doesn't generate a `/blog/tags/search-test` static page. So the import in `sitemap.ts` flips to `@/lib/blog-taxonomy`. Good. **But** the migration ALSO requires updating any TEST that imports these helpers. The existing `src/lib/blog.test.ts` (which the design extends) likely has tests for `getAllTags`, `getAllCategories`. Those tests need to move to `src/lib/blog-taxonomy.test.ts`. The design mentions "Vitest tests follow: `src/lib/blog-taxonomy.test.ts` (new) replaces the taxonomy section of `blog.test.ts`" — fine. **But the existing test file path needs to be VERIFIED** because `src/lib/blog.test.ts` may have intermixed test cases that depend on shared setup. Pin which tests move and which stay.
- **(Novel) Stress-test the verifier's behavior on the new file's `getVisiblePublishedPosts()` calls.** `src/lib/blog-taxonomy.ts` will call `getVisiblePublishedPosts()` (not `getPublishedPosts()`). The verifier's regex matches `\bgetPublishedPosts\(\)` (word boundary). Does it match `getVisiblePublishedPosts()` as a partial? The `\b` (word boundary) is between non-word and word characters. `getVisible` ends with `e` (word char); `Published` starts with `P` (word char) — there's NO word boundary between them, so `\bgetPublishedPosts\(\)` does NOT match inside `getVisiblePublishedPosts()`. Good — the verifier is correctly narrow. **But:** if a future contributor types `getPublishedPosts()` in a JSDoc above `getVisiblePublishedPosts` in `blog-taxonomy.ts` (e.g., "this function calls `getPublishedPosts()` internally via `getVisiblePublishedPosts`"), the verifier flags it. The v3 line-comment-skip logic catches `// ...` and `/* ... */` opener lines but only at the LINE level. A JSDoc body line that has `* @see getPublishedPosts()` as its content (no leading `/*`) is matched by the regex `/^\s*(\*|\/\/|\/\*)/` because the leading `*` indicates a JSDoc continuation line — so it's skipped. Good. **But** a single-line JSDoc like `/** Uses {@link getPublishedPosts()} internally */` starts with `/**`, which `/^\s*(\*|\/\/|\/\*)/` matches via `\/\*`. Good. The regex covers the common JSDoc cases. **However:** a regular line containing `// uses getPublishedPosts() per requirements` (an INLINE `//` after code on the same line) is NOT skipped — `/^\s*(\*|\/\/|\/\*)/` requires the line to START with the comment marker. An inline trailing comment on a non-call line still trips the verifier. Tighten: split each grep match into (code part before `//`) + (comment part) and only match the code part.
- **(Novel) Challenge the verifier's "blog-taxonomy.ts is INTENTIONALLY NOT here" comment as fragile.** The verifier is a 25-line script with a hard-coded allow-list. The comment "NOTE: src/lib/blog-taxonomy.ts is INTENTIONALLY NOT here" is a polite reminder but doesn't enforce anything. A future contributor doing a global rename ("split the helpers further") may move taxonomy code BACK to `blog.ts` (which is allow-listed) or to another file and forget to update the verifier. The contract is "any file not in the allow-list cannot call `getPublishedPosts()`" — that's enforced. The fragility is that the allow-list itself is a single point of failure. Pin: add a Vitest test that runs the verifier against the current codebase and asserts pass. That test will FAIL on any new violation, providing a second enforcement layer beyond CI.
- **(Compounding) Challenge the "taxonomy helpers MUST use `getVisiblePublishedPosts()`" without testing what happens for `getPostBySlug`.** `getPostBySlug` is the direct-URL contract; it currently uses the unfiltered `getPublishedPosts()` so a direct visit to `/blog/fixture-search` still resolves. But `getPostsByTag` and `getPostsByCategory` (in the new taxonomy module) are list-context — they filter visibility. A scenario: an operator sets `hiddenFromLists: true` on a post WITHOUT setting `draft: true`. Direct URL works (good). Tag pages no longer list the post (good). Sitemap excludes it (good). RSS excludes it (good). Now Pagefind: it's in the URL list (per the v3 wget extra-URLs logic), so Pagefind indexes it. Search returns it (good if `excludeFromSearch: false`). A user clicks the search result → arrives at `/blog/{slug}`. The page renders with `data-pagefind-body` set (assuming `excludeFromSearch: false`). All good. **But:** the post's `<meta robots>` says `noindex, nofollow`. Google's bot, ALSO finding the URL via the sitemap (no — sitemap excludes it) … via what? Google can find it ONLY via (a) external backlink, (b) the search bot brute-discovering it. Path (b) is mitigated by `noindex`. Path (a) is the open surface — if any external site links to `fixture-search`, Google may crawl it. The `noindex` meta + the new `X-Robots-Tag` header should both prevent indexing. Good. The chain holds. Move on.

### 5. The single shared `<output aria-live="polite" aria-atomic="true">` region (v3 ARIA reverse-reverse)

v3 reverts v2's per-button regions in favor of a single shared `<output>` with `aria-atomic="true"`, rendered once per post page in `[slug]/page.tsx`'s root, owned by a `<CopyStatusProvider>` React context.

- **(Novel) Stress-test the context provider's mount point.** The design says "rendered once per post page in `[slug]/page.tsx`'s root." But `[slug]/page.tsx` is a Server Component (per the Steering Doc). `CopyStatusProvider` uses `useState` and is marked `"use client"`. Mounting a client provider as the ROOT of a server component means EVERYTHING inside is rendered as a client child of the provider. That's fine for React (client component can have server children via composition), but it means the provider's children include `<MDXContent />`, `<ShareBar />`, `<TableOfContents />`, etc. — most of which are server components. They still server-render, but the provider's `useState` re-renders cascade through all of them on each `setStatus()` call. Performance: each click re-renders the entire post page tree client-side. The page is small enough that this isn't a real-world problem, but it's a re-render budget the design hasn't quantified.
- **(Novel) Challenge "all copy buttons consume the context."** The `<CopyButton />` is hydrated via the DOM-marker pattern — the `rehypeCopyButton` plugin emits a static `<button data-copy-button data-copy-source="...">` element in the SERVER-RENDERED HTML, then a thin hydrator (`document.querySelectorAll('[data-copy-button]')`) progressively enhances each. **But:** "progressive enhancement via DOM hydration" is NOT React component rendering. The hydrated DOM nodes are NOT inside any React tree — they're sibling DOM nodes. They cannot consume a React context. The design contradicts itself: it says `<CopyButton />` consumes `useCopyStatus()` via context, but the actual hydration mechanism is `querySelectorAll`-based progressive enhancement, NOT React mounting. Either (a) the hydration mechanism changes to "create React roots at each marker via `createRoot()` and render `<CopyButton />` inside the Provider's context," which requires the Provider's context value to be propagated to those roots (and `createRoot()` doesn't share context — each root has its own), OR (b) the shared `<output>` is updated via direct DOM manipulation, not React state, in which case the provider's `useState` is dead code. **This is a P0 architectural contradiction.** Action: pick one mechanism. If React context: rewrite hydration to use `createRoot` AND inject the status setter via a global window function or imperative API. If DOM-only: drop the context provider, render a static `<output>` once, and have the hydrator find it via `querySelector` and update `textContent` directly.
- **(Novel) Challenge `aria-atomic="true"` for a region that's expected to clear to `""` after 1s.** The design says "A brief idle timeout (1s) clears the status to `""` so the region doesn't permanently announce stale text." Setting `aria-atomic="true"` causes a re-announcement on every text change — INCLUDING the clear to `""`. So screen readers will announce the success message, then announce silence (the empty string). NVDA, JAWS, and VoiceOver handle this differently — some announce "blank" or nothing; others say the entire text including empty content. The clear-to-empty pattern is non-standard. Better: don't clear; leave the region populated with the last status. Subsequent clicks re-announce. The 1s clear is fighting `aria-atomic` semantics.
- **(Novel) Stress-test the `<output>` element choice.** `<output>` has implicit `role="status"` per the HTML spec. `role="status"` is roughly equivalent to `aria-live="polite"`. So the explicit `aria-live="polite"` is redundant (harmless). But: `<output>` is intended for "the result of a calculation or user action" — it's the semantically correct element here. Fine. **However:** `<output>` outside a `<form>` element is unusual, and some screen readers handle it inconsistently. The Material Web docs warn against using `<output>` for arbitrary live regions; the standard pattern is `<div role="status" aria-live="polite">`. Verify against actual SR behavior, or use the standard `<div>` form.

### 6. `--input-file=./urls-extra.txt` mechanism in `run-pagefind-crawl.mjs` (v3 P0 #1 fix)

The script writes `./urls-extra.txt` then invokes wget with `--input-file=./urls-extra.txt http://localhost:${PORT}/` as the entry point.

- **(Novel, P0) Challenge wget's handling of `--input-file` PLUS a positional URL argument.** Per wget docs, when BOTH `--input-file` AND positional URLs are provided, wget reads URLs from BOTH and processes them all. **But:** the script writes URLs to `urls-extra.txt` AS ABSOLUTE URLs (`http://localhost:3013/blog/...`). And the positional argument is `http://localhost:${PORT}/` (root). Wget with `--mirror` will start at the root, walk links, AND ALSO fetch the input-file URLs. So `fixture-search` gets fetched via the input-file. **But:** wget treats the input-file URLs as separate entry points — links from `fixture-search` (back to other blog posts) MAY be re-fetched. With `--mirror`, wget de-duplicates by URL, so re-fetches are no-ops. Fine. **However:** the `--no-parent` flag is in the wget invocation (line 888). `--no-parent` means "don't ascend to the parent directory when following links." With `--no-parent` and a starting URL of `http://localhost:3013/`, the "parent" is the root — so nothing is "ascended." But for `http://localhost:3013/blog/fixture-search`, the parent is `http://localhost:3013/blog/`. `--no-parent` will prevent wget from following ANY link that goes UP the tree from `fixture-search` — including the navbar's `/`! So wget fetches `fixture-search`, sees a `<a href="/">` in the navbar, decides "/ is a parent of /blog/fixture-search" (debatable but wget's behavior is "any URL outside the starting URL's directory tree is a parent"), and skips it. The result: wget mirrors fixture-search BUT NOT any pages linked FROM fixture-search (which is fine for indexing). The bigger risk: `--no-parent` with `http://localhost:3013/` as start AND `http://localhost:3013/blog/fixture-search` as input-file entry creates AMBIGUITY about what "parent" means relative to TWO different entry points. Per wget source, `--no-parent` is enforced per-URL relative to that URL's directory. So fetching from `http://localhost:3013/` walks all of `localhost:3013`, fetching from input-file URLs may walk only their subtrees. **Action:** REMOVE `--no-parent` from the wget invocation. The `--exclude-directories=/_next,/static` and `--reject` flags already handle the "don't fetch assets" case. `--no-parent` is over-restrictive for a mixed-entry-point crawl.
- **(Novel) Stress-test the `extraSlugs` filter for draft handling.** The filter at line 843-847 reads from `velite.posts` (the post-build velite output) and filters by `hiddenFromLists === true`. The design's comment says: "Any slug in the roster that is also present in velite.posts but draft:true is automatically excluded (Build 2 doesn't include drafts)." **But:** the v3 `pnpm build:search` is called from `Pagefind crawl (Build 2)`. Build 2 produces a velite output WITHOUT drafts. So drafts are excluded. Good. **But:** if the operator runs `pnpm build:search` LOCALLY in dev mode (drafts included), `velite.posts` INCLUDES drafts. Hidden draft posts will then be in `urls-extra.txt`. wget will try to fetch `http://localhost:3013/blog/{draft-slug}`. Next.js in dev mode serves drafts (per blog-core). So wget mirrors them. Pagefind indexes them. The LOCAL pagefind index contains drafts. The `verify-pagefind-no-drafts.mjs` script (which is a CI check, NOT a local check) doesn't catch this because it doesn't run locally. **Action:** the script SHOULD assert it's running against a draft-excluded velite output, OR explicitly filter draft posts from `extraSlugs`: `.filter((p) => p.hiddenFromLists === true && !p.draft)`.
- **(Novel) Challenge `urls-extra.txt`'s lifecycle.** The script writes `./urls-extra.txt` (line 855: `await fs.writeFile("./urls-extra.txt", ...)`). The script's cleanup at step 7 removes `./out` but does NOT remove `./urls-extra.txt`. So `urls-extra.txt` persists in the repo root after each crawl. It needs to be `.gitignore`'d OR cleaned up. The design's `.gitignore` extension adds `public/pagefind/` but NOT `urls-extra.txt` (and not `./out` either — line 947 says "`./out` is a transient build directory added to `.gitignore`" but no mention of `urls-extra.txt`). **Action:** add `urls-extra.txt` and `./out` to the `.gitignore` extension list. Better: write the file to a temp path like `node:os.tmpdir() + '/pagefind-urls.txt'` so it never touches the repo tree.
- **(Compounding) Challenge the script's TypeScript import `await import("./src/lib/build/derive-post-slug.js")` at line 841.** This imports from a `.js` path, but the source is `.ts`. The script is `.mjs` — pure Node ESM. It cannot resolve `./src/lib/build/derive-post-slug.ts` unless the build has produced a `.js` output. Velite doesn't compile `src/lib/build/*.ts` files. Next.js's build does, but the output goes to `.next/` not to a sibling `.js` next to the source. **The import is broken as written.** Action: EITHER use a `.mts` script with a TypeScript loader (`tsx` or `ts-node`), OR move `derive-post-slug.ts` to `.mjs`, OR duplicate `KNOWN_FIXTURE_SLUGS` in the script (small enough to inline). Note: the `verify-pagefind-no-drafts.mjs` script also calls `derivePostSlug` per the design — same broken import.

## Top 5 risks/gaps

First-time `next build` cannot resolve `./.velite/index.js`. **Action:** pin a `"postinstall": "velite build"` script in `package.json` extensions OR wrap the import in try/catch with empty-array fallback OR generate a separate `hidden-routes.json` file as part of the velite transform output.

## Top 3 conclusions to challenge or reverse

1. **REVERSE: `next.config.ts` reading `.velite/index.js` directly.** This creates a topology that's broken on first clone, requires a postinstall hook that doesn't exist, and reads a build artifact at config-load time (a fragile pattern). **Better:** the Velite transform writes a separate `hidden-routes.json` (or appends a `__meta` block to velite output) at content-build time. `next.config.ts` reads that JSON file with a `try/catch` and empty-array fallback. The header rules are computed at config-load time but the data source is decoupled from velite's output structure. Even better: pre-compute the routes in a script and write them to a static `headers.json` consumed by `next.config.ts`, removing the dynamic dependency entirely.

2. **REVERSE: the React-context shared aria-live region.** The DOM-marker hydration pattern for `<CopyButton />` cannot consume React context across `createRoot()` boundaries; the provider is dead code. **Better:** drop the React context. Render ONE static `<output aria-live="polite" aria-atomic="true" id="copy-status" class="sr-only">` in `[slug]/page.tsx`. The progressively-enhanced copy-button hydrator calls `document.getElementById("copy-status").textContent = "Copied!"` directly. No context, no provider, no re-render cascade. The v3 architecture is over-engineered for a 1-line DOM update.

3. **REVERSE: the Task 0 spike's coverage scope.** As written, it tests what already worked. **Better:** the spike must test the SPECIFIC v3 mechanisms — `--input-file` with an unlinked URL, `--adjust-extension` producing `.html` for extensionless responses, AND the master timeout firing on a deliberately-hung wget request. If the spike doesn't validate what v3 changed, it provides no signal.
