## Findings

### WARNING: FIXTURE-NOTE leaks into bodyHtml as visible text
- **File:** /home/mcf/repo/matthew-field.ca/content/posts/fixture-code.mdx:10
- **Issue:** Because `s.markdown()` does not understand MDX expression syntax, the `{/* FIXTURE-NOTE: ... */}` token is parsed as literal markdown text and emitted in `bodyHtml` as `<p>{/* FIXTURE-NOTE: this fixture is referenced by the spec tests; coordinate edits accordingly. */}</p>`. Verified in `.velite/posts.json` for all three fixtures. Consequences: (a) the RSS/Atom feed would surface this paragraph in any environment with `BLOG_INCLUDE_DRAFTS=1`; (b) the Pagefind index will include the FIXTURE-NOTE text as searchable content; (c) the Req 11.7-11 RSS body-parity assertions (a-d) still pass because they are structural (no exact-string equality), but the page-rendered MDX body has NO equivalent paragraph (s.mdx() correctly strips comment expressions). The spec's original `<!-- -->` design relied on `remark-parse` treating HTML comments as `type:'html'` nodes that `remark-rehype` then passes through as raw HTML that browsers strip. The `{/* */}` switch achieves visitor-bypass but breaks the bodyHtml-stripping behavior. Remediations: (i) strip `mdxFlowExpression`/`mdxTextExpression` nodes from the markdown-parse tree before `s.markdown()` serializes, (ii) post-process `bodyHtml` to remove `<p>{/* ... */}</p>` paragraphs, or (iii) move the FIXTURE-NOTE into frontmatter as a non-rendered key (would require schema relaxation).
- **Task Requirement:** 11.9, 11.11

### WARNING: MDX-comment carve-out is overly permissive (same shape as the Task 4 r1 finding)
- **File:** /home/mcf/repo/matthew-field.ca/velite.config.ts:152
- **Issue:** velite.config.ts:152 uses `v.startsWith('/*') && v.endsWith('*/')` after trim. This is the structural twin of the Task 4 review finding for `<!-- -->`. A constructed value like `/* a */ + maliciousIdentifier /* b */` would satisfy both predicate halves and slip through, even though the middle is non-comment JS. Whether such a node is reachable depends on how `remark-mdx` chunks expressions, but the predicate is not a strict comment-only matcher. Tighten by matching the entire trimmed value against `/^\/\*[\s\S]*?\*\/$/` (single comment, with the inner `*/` being the FIRST `*/`) — i.e., require that no `*/` appears mid-value. Same remediation pattern as the v1 review recommended for the HTML-comment predicate.
- **Task Requirement:** 3.7, 11.7a
