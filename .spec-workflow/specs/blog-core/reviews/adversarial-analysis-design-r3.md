# Adversarial Analysis — blog-core/design (v3)

**Reviewer posture:** staff engineer, adversarial. Primary attack surface: feasibility, consistency, edge cases.

**Prior-review status (read from `adversarial-memory-design.md` and `adversarial-analysis-design-r2.md`):**
The v3 design absorbed nearly every v2 conclusion at the structural level:

- Reading-time AST walk now declares "markdown + GFM only," drops MDX-node recursion, and the rejection visitor is extended to cover MDX expressions. **v2 Unresolved #1 + #2 addressed.**
- Two-visitor ordering pinned (rejection → reading-time → bodyHtml) inside `.transform()`. **v2 Attack 1 bullet 2 addressed.**
- `feed` exact-pinned at `4.2.2` (no caret). **v2 Compounding #6 addressed.**
- Launch-gate test upgraded to strict-parse via `fast-xml-parser`. **v2 Attack 5 bullet 2 addressed.**
- CI job-topology pin written into the design ("two sequential steps inside a single CI job, MUST NOT split"). **v2 Compounding #5 addressed at the prose level — see Recurring #2 below for the gap that remains.**
- `verify-production-build.mjs` shapes enumerated literally (no more "or equivalent"). **v2 Attack 4 bullet 3 addressed — but see Novel #4 below for the launch-state failure mode the enumeration introduces.**
- `validate-feed.mjs` separated from the production-build glob filter (route-handler emit shapes). **v2 Attack 6 bullet 3 addressed.**
- `VERCEL === '1'` gate added to build-time guards — local-dev footgun eliminated. **v2 Unresolved #4 addressed.**
- `THEME_STORAGE_KEY` import path pinned to `@/components/layout/theme-provider` with cross-spec compile-time defense. **v2 Unresolved #5 addressed (verified: `src/components/layout/theme-provider.tsx:6` exports `THEME_STORAGE_KEY = "theme"`).**
- Build-ordering pin recast as a structural argument: the rejection visitor prevents `bodyHtml` from existing without a valid `body` for the same input. **v2 Unresolved #8 / Reversal #2 addressed.**
- Reading-time test decoupled into word-count + conversion + end-to-end assertions. **v2 Compounding #3 addressed — but the breakpoint has moved, not vanished. See Compounding #3 below.**

The v3 design is responsive. What remains is a smaller set of issues that v2 did not surface: gaps the v3 changes themselves introduced (the enumerated globs, the manual Vercel-UX verification), procedural pins that masquerade as structural ones, and a class of dependency-pin and runtime-version hygiene v2 did not cover.

## Attack 1 — Rejection-visitor parse-failure path and error-scenario self-contradiction

The v3 rejection visitor uses a locally-instantiated `remark-mdx` parser stack so MDX-only node types appear in the tree it traverses (design.md:117–121). This closes the divergence surface — but introduces two unaddressed problems.

- **Challenge the claim that the rejection visitor's parser tolerates the same input surface the `s.mdx()` compiler tolerates.** `remark-mdx`'s micromark extension is strict about constructs the design assumes will produce mdast nodes for the visitor to reject — e.g., a half-formed JSX tag `<div foo=>` produces a *parse error*, not a `mdxJsxFlowElement`. **Pin what happens when the rejection-visitor parser throws before any visit walks the tree.** The design says "throws a named error from inside the schema `.transform()` callback before either `body` or `bodyHtml` is emitted" — but that contract only covers the "successful parse, forbidden node found" path. A raw parser exception either (a) propagates out of `.transform()` as an unnamed error, surfacing in Velite output as a stack trace with no file/snippet context, or (b) gets caught by some implicit try/catch and turns into a different error path. Neither is specified. Demand explicit `try { parse } catch (err) { throw new NamedRejectionError(file, ...) }` wrapping so parse failures and node-rejections produce the same operator-facing UX.
- **Stress-test the self-contradiction between Error Scenarios #3 and #4.** Scenario #3 (design.md:394–396) says the mdast `type: 'html'` visitor rejects raw HTML at the Velite transform layer. Scenario #4 (design.md:398–400) says "Capitalized JSX tag reference in post body without an MDX component registry … Velite's MDX compile via `s.mdx()` fails with a `ReferenceError`-style message." This was true in v2; in v3 the rejection visitor has been extended to reject `mdxJsxFlowElement` *and* `mdxJsxTextElement` (design.md:117–119). A `<Callout>` in a post body now triggers Scenario #3's named rejection error, **not** Scenario #4's `ReferenceError` from `s.mdx()` — because the transform throws before `s.mdx()` runs. Scenario #4 is dead. Either delete Scenario #4 and document the unified rejection-visitor message under #3, or document that the v3-extended rejection visitor preserves Scenario #4 as a fallback for cases the visitor misses (and pin which cases those are). As written, the design contradicts itself about which error the author sees.
- **Tear apart the "negligible at launch volume" cost claim.** Design.md:120: "two parser instantiations per post — accepted; the cost is negligible at launch volume." But the per-post cost is now significantly larger than this hedge implies: (a) reading-time parser (`remark-parse` + `remark-gfm`); (b) rejection-visitor parser (`remark-parse` + `remark-gfm` + `remark-mdx`); (c) Velite's `s.mdx()` page compile; (d) Velite's `s.markdown()` `bodyHtml` compile. That is **four parser instantiations per post per Velite build cycle**, plus `pnpm dev`'s watcher re-runs these on every changed-file event. The design pins no quantitative target (e.g., "< 500ms per post on the fixture set") and provides no profiling result. Demand either a measured baseline against the three fixtures or an explicit deferral ("will profile post-launch; no per-post budget pinned now"). "Negligible at launch volume" without a number is the same hedge category as v2's "or equivalent."

## Attack 2 — CI job-topology pin: procedural-as-design pattern recurring (escalated)

v2 Unresolved #5 flagged the cache-topology gap. v3 added prose (design.md:260): "Build 1 and Build 2 run as two sequential steps inside a single CI job. They MUST NOT be split into separate jobs … If a future CI refactor needs to split the builds across jobs, the draft-isolation guarantee MUST be moved out of the cache layer first." This is improvement at the documentation level — but it is procedural enforcement, not structural.

- **Recurring (escalated): Challenge the structural-vs-procedural classification of the job-topology pin.** The pin lives in markdown prose; the CI workflow YAML does not enforce it. A future maintainer opening `.github/workflows/ci.yml` sees two `pnpm build` invocations in a single job and has no signal that splitting them would break a draft-isolation guarantee — no comment in the YAML, no schema check, no CI lint rule. The pattern matches v1/v2's repeated finding: when a guarantee depends on a configuration that lives in a different file from the design doc, the guarantee is one careless edit away from breaking. **Demand at minimum**: (a) a comment block in `ci.yml` referencing this design section by URL/heading, (b) a structural defense — e.g., generate a `BUILD_ID` env var in Build 1 and assert in Build 2's `verify-production-build.mjs` that the Velite output's content-hash is different from Build 1's expected hash, so a cache-bleed produces a script failure rather than a silent draft leak.
- **Stress-test the `rm -rf .velite .next` step against `pnpm install` cache state.** The clean step targets the build-output directories. It does NOT clean `node_modules/.cache/` or any tool-specific cache (Next.js's webpack cache lives partially under `.next/cache/` and is targeted; but Velite's own internal caches — including any cached parsed-AST behind `meta.mdast` — may live elsewhere depending on the version). The design treats `.velite/posts.json` as the cache surface, but Velite v0.3.1's full cache topology is not audited in the design the way the type definitions were. **Demand a Velite cache-surface audit equivalent to the `.d.ts` audit** the v2 review already accepted, or pin that the clean covers every Velite-side caching directory by literal path.
- **Tear apart the orchestration if Build 1 fails partway through.** The design assumes Build 1 completes, then the clean step runs, then Build 2 runs. If Build 1's `pnpm test:e2e` step fails (axe regression, draft-visibility test flake), does the CI job halt? If yes (`set -e`-style), Build 2 never runs and the production-build verification never executes for that PR — meaning a draft-leak class regression introduced in the same PR as an axe regression can ride the axe fix to merge without ever being caught by Build 2. The design does not pin "Build 2 runs unconditionally even when Build 1's test steps fail." Demand the workflow declare each `build` step with `if: always()` semantics, or explicitly accept the gap.

## Attack 3 — Reading-time word-count band: the v3 decoupling moved the breakpoint, did not remove it

v2 flagged integer-clamp fragility at the 4.5-minute rounding boundary. v3 decoupled into (1) word-count ±10% assertion, (2) pure-function `wordsToReadingTime` correctness, (3) end-to-end identity check against the observed count (design.md:440–443). This is structurally better — but the ±10% band is its own breakpoint.

- **Compounding finding: Challenge the ±10% bound on the word-count assertion.** The fixture is pinned at ≥1000 prose words. A ±10% band over 1000 = ±100 words. If a future accessibility-driven alt-text edit adds 110 words (a long alt for a complex diagram — entirely plausible per WCAG 2.1 1.1.1 for data visualizations or detailed code-output screenshots), the assertion fails. The decoupling defends against the *rounding-boundary* breakpoint but trades it for a *band-edge* breakpoint farther out. The design claims "an alt-text change shifts the word count within the ±10% bound and re-pins the end-to-end assertion through the conversion function" — true for small alt-text changes, untrue for large ones. **Demand either** a wider band justified by a worst-case alt-text growth estimate, **or** drop the word-count assertion entirely and rely on the end-to-end identity check alone (the conversion-fidelity assertion already covers the conversion logic; the word-count band is the only fixture-coupled assertion left and is the only one that breaks on legitimate edits).
- **Stress-test the assertion #1 walk's agreement with the Velite transform's walk.** Assertion #1 says "compute the prose word count from the fixture body using the same AST walk the Velite transform uses (drop `code` nodes, flatten with `includeImageAlt: true`, split on whitespace)." But the test imports its own parser (`remark-parse` + `remark-gfm`) and runs the walk in test code — separate from the Velite transform's instance. Any drift between the two implementations (a future change to one and not the other) makes assertion #3 fail because they disagree on `observedWordCount`. **Demand the walk be exported as a named function from `velite.config.ts` (or extracted to a shared module) and imported by both the transform and the test**, so a single source of truth governs both word counts.
- **Tear apart the "split on whitespace" word-count definition under GFM.** `mdast-util-to-string({ includeImageAlt: true })` flattens nodes to a string with default separators. The test's word-count definition is "split on whitespace" — but the flattened string from a markdown table or task list may produce runs of internal whitespace, punctuation-only tokens (`---`, `|`), or empty strings between cells. A naive `.split(/\s+/).filter(Boolean).length` counts table-cell content reasonably; a `.split(' ').length` is wrong; the design doesn't pin which. **Demand the exact splitter regex** so the test can be replicated and the `reading-time` package's internal definition (which may also differ) is reconciled.

## Attack 4 — `verify-production-build.mjs` launch-state failure: the enumerated globs assume taxonomy emits exist

v3 replaced "or equivalent" with literal expected-file shapes (design.md:246–252). The taxonomy shapes are:

- `**/server/app/**/blog/tags/**/*.{html,rsc}` AND
- `**/server/app/**/blog/categories/**/*.{html,rsc}`

The hit-count gate fails on zero matches.

- **Novel finding: Challenge the gate behavior on a launch-state production build.** Per Error Scenario #7 (design.md:411), the launch state is "Empty `content/posts/` directory, before any post is authored." In that state, `getAllTags()` and `getAllCategories()` return `[]`, `generateStaticParams()` on the tag/category routes returns `[]`, and **Next.js emits zero files under `blog/tags/` and `blog/categories/`**. The taxonomy globs match nothing. The hit-count gate fires, the script exits non-zero, **the production-mode CI build fails on a green-state launch**. The script is structurally incompatible with the launch state the design explicitly carved out as supported. **Demand either**: (a) gate the taxonomy hit-count checks behind a "if there are any non-draft posts" check the script reads from the build manifest, (b) make the gates conditional on `getAllTags().length > 0` (read from `#site/content` or from the Velite output JSON), or (c) document that the script is intended to run only after real content exists and add a launch-bootstrap shim. As written, the launch-day deploy fails CI.
- **Stress-test the script against `fixture-draft` substring collision.** The script (design.md:245) "globs for any file referencing the literal substring `fixture-draft` (the slug) OR the fixture-draft post `title` frontmatter value." In Build 2, `getPublishedPosts()` excludes `fixture-draft` (draft), so no `blog/fixture-draft/` page emits. But the `fixture-draft` slug also appears in the **sitemap source** for Build 1 — and the Build 2 sitemap is regenerated independently. If a developer's `siteConfig.description` or a navigation component ever embeds the literal string "fixture-draft" for some unrelated reason (a comment, a placeholder), the script reports a false positive. **Demand the slug be made deliberately exotic** (e.g., `__fixture-draft-do-not-match-on-this__`) or document that the substring match relies on the slug being globally unique to draft-leak detection — and add a test that asserts the live codebase contains zero non-draft references to the literal string.
- **Tear apart the unconditional title-frontmatter substring match.** Design.md:245: the script also greps for "the fixture-draft post `title` frontmatter value." This is presumably a literal like `"Fixture: Draft Post"`. If the title contains a common phrase ("Draft"), the substring "Draft" appears in countless legitimate places (Next.js error-page boilerplate, sitemap last-modified strings, OG meta). Either the title is pinned to a unique-enough string explicitly in the design (it isn't), or the script's title-match logic is a high false-positive surface. **Demand the fixture title be pinned to a substring not present anywhere else in the build output** (e.g., include the slug verbatim in the title, so the title match collapses to the slug match).

## Attack 5 — Dependency-pin discipline gap: v3 pinned `feed` exactly but the same discipline is not applied to dev tooling

v2's Compounding #6 demanded exact pinning of `feed`. v3 delivered. But the design has accumulated other version-sensitive dependencies and runtime requirements without applying the same discipline.

- **Novel finding: Challenge the absence of an exact pin on `fast-xml-parser`.** The launch-gate test (design.md:195) parses the feed XML using `fast-xml-parser` and locates `<item><content:encoded>` to assert CDATA wrapping. This is now load-bearing for the launch decision. `fast-xml-parser` v3 → v4 changed default attribute parsing (`attributeNamePrefix`, `ignoreAttributes` defaults), namespace handling for `<content:encoded>` (the `xmlns` prefix may parse differently), and the structure of the returned tree. A silent minor bump can change the path the test traverses (`parsed.rss.channel.item['content:encoded']` vs `parsed.rss.channel.item.content_encoded`). The design accepted exact pinning for `feed` but does not extend the discipline to `fast-xml-parser`. **Demand `fast-xml-parser` be exact-pinned too**, with the same dependabot-PR + launch-gate-as-merge-gate flow.
- **Novel finding: Challenge the implicit dependency on `fs.glob` (Node 22+).** Design.md:242 lists "`fs/promises` glob via `fs.glob` available in Node 22+" as a dependency of `verify-production-build.mjs`. `fs.glob` is **still marked experimental in Node 22.x** as of writing and emits `ExperimentalWarning` to stderr. Vercel's runtime Node version is pinned via `package.json` `engines` or `.nvmrc` — but the design does not pin either. If CI runs Node 20 (the previous LTS), `fs.glob` is undefined and both scripts fail to start with `TypeError: fs.glob is not a function`. **Demand**: (a) explicit `engines.node: ">=22"` in `package.json` pinned by the design, (b) an `.nvmrc` value pinned, (c) explicit handling of the `ExperimentalWarning` (either `--no-warnings=ExperimentalWarning` or a fallback to a userland glob like `tinyglobby`). The design treats `fs.glob` as a stable API; it is not.
- **Tear apart the "added to devDependencies" hedge for `fast-xml-parser`.** Design.md:269: `fast-xml-parser` is "added to devDependencies." But the launch-gate test (design.md:195) runs in Vitest as part of the test suite that gates merges. `pnpm install` in CI installs devDependencies; in production deploys it may not (depending on `NODE_ENV` and the Vercel install command). The test never runs in production — fine. But if `fast-xml-parser` is ever pulled into `validate-feed.mjs`'s actual production-build-validation path (design.md:451 says "Parses the generated feed XML"), the script must run with devDependencies available. Vercel's build environment installs devDependencies by default — fine for now — but the design does not pin this. A future "production install" optimization breaks the script. **Demand the design state explicitly that CI build environments must install devDependencies**, or move `fast-xml-parser` to dependencies if it runs in any build-side script.

## Attack 6 — Operator-facing error UX: the manual verification is a one-shot that stales over time

v3 introduced (design.md:152) "Launch-time verification step (not automated, called out): before public launch, deliberately misconfigure one Vercel environment-variable scope … confirm the build log surfaces the named error legibly." This is responsive to v2's Attack 4 bullet 1 — but the verification is a one-time human action against a third-party (Vercel) log format that changes without notice.

- **Compounding finding: Challenge the durability of a one-shot manual verification against Vercel's log UX.** Vercel ships incremental UI/log changes monthly. The manual verification confirms the named error is legible on launch day; six months later, Vercel may re-format build logs, add a "Show more" collapsing affordance, or truncate stack traces to a new character limit. The named error becomes silently illegible — operator's only signal that env-var scoping is wrong is now a generic build failure. **Demand**: (a) a scheduled (e.g., quarterly) re-verification cadence written into the design, **or** (b) an alternative structural defense — for example, an additional output-surface check at the top of `next.config.ts`'s `headers()` callback that throws with `process.stderr.write` BEFORE Next.js's prerender wrapper kicks in, so the message appears at a log layer Vercel is less likely to re-format. The design rejected the `headers()` approach in v3 ("`headers()` runs without access to the post-list query layer and is the wrong abstraction") — but the env-var check is just two `process.env` reads; the post-list access is not required for the throw. The rejection is too quick.
- **Stress-test the "verification before launch" against the actual signal path.** The verification step has the operator misconfigure one env-var scope and check the log. But the failure mode this is supposed to defend against is "env-var scoping mistake on a future deploy" — six months from now, on a deploy the operator did not anticipate, the operator is reading a build log under time pressure. The launch-day verification confirms the message was legible *once*, not that the message is legible *under conditions the actual failure occurs in*. **Demand a runbook entry** that points operators at the named error message (by exact substring) so a future on-call grep can find guidance even if the rendered log truncates the surrounding context.
- **Tear apart the symmetric-case test coverage for the `VERCEL === '1'` gate.** Design.md:151 adds the `VERCEL === '1'` gate to eliminate the local-dev footgun. The unit tests (design.md:432–433) cover `VERCEL_ENV=production`/`preview` paths but do not include a test asserting that `VERCEL` unset → no throw. So a regression that drops the `VERCEL` gate (a future "simplification") makes `pnpm dev` brittle again, and the test suite does not catch it. **Demand a positive test**: `getPublishedPosts()` with `BLOG_INCLUDE_DRAFTS=1` and `VERCEL_ENV=production` BUT `VERCEL` unset → does NOT throw. This is the v2-flagged local-dev case, and its absence from the test suite means the structural defense is unguarded.

## Top 5 Risks / Gaps

1. **`verify-production-build.mjs` fails CI on the launch state (zero posts).** The enumerated taxonomy globs assert at least one match for `blog/tags/**` and `blog/categories/**`. With no real posts and all fixtures `draft: true`, Build 2's `getAllTags()` returns `[]`, no tag pages emit, the hit-count gate fires. **Severity: high.** Catches as "launch-day deploy blocked by the very script written to defend it." Novel.

2. **Error Scenarios #3 and #4 contradict each other after the v3 rejection-visitor extension.** v2's design had #4 surface as `s.mdx()`'s `ReferenceError`. v3's rejection visitor catches `mdxJsxFlowElement` first, so a `<Callout>` now hits #3's named error. The design tells the author one story and produces another. **Severity: medium.** Catches as documentation inconsistency; operator sees one error, design predicts another. Novel.

3. **CI job-topology pin remains procedural — markdown prose, not CI-enforced.** v2 flagged this; v3 added prose to design.md:260 and an admonition that future splits must move the guarantee out of the cache layer first. There is no CI lint, no comment in the workflow YAML, no structural BUILD_ID/hash check. A casual `ci.yml` refactor still breaks draft isolation silently. **Severity: medium.** Recurring (escalated): same procedural-vs-structural pattern as v1's chokepoint-bypass (which v2 closed with a lint rule) and v2's build-ordering (which v3 closed with the rejection visitor). Topology is the last procedural pin standing.

4. **`fs.glob` (Node 22 experimental) and `fast-xml-parser` (unpinned version) introduce silent failure modes the v3 design did not anticipate.** Node 20 → `fs.glob is not a function`; `fast-xml-parser` minor bump → CDATA-locating test traverses wrong tree path and silently passes. The v3 design exact-pinned `feed` but did not extend the discipline. **Severity: medium.** Catches as either CI failure on a Node version mismatch (loud, recoverable) or as a launch-gate test passing on a broken feed (silent, unrecoverable). Novel.

5. **Reading-time word-count assertion has a ±10% band breakpoint at ~100 words.** v3 decoupled the rounding boundary but introduced a band that fails on legitimate large alt-text additions (≥110 words). The fixture's accessibility load is the design's load-bearing case for `includeImageAlt: true`; large alt is exactly the use case the design wants to support. **Severity: low–medium.** Catches as intermittent CI failure on accessibility-driven edits. Compounding (builds on v2's Compounding #3 — the breakpoint has moved, not vanished).

## Top 3 Conclusions to Challenge or Reverse

1. **"The rejection visitor's transform-time throw is a structural guarantee that `bodyHtml` only exists for posts that also produce a valid `body`."** This is design.md:194's reframing of v2's build-ordering pin (Reversal #2). It holds for the *successful parse + forbidden node found* path. It does NOT hold for the *parse failure* path, because the design does not specify what happens when the rejection visitor's `remark-mdx` parser throws before the visit walk runs. Either pin a `try/catch` wrapper that produces the same named-error UX as a successful rejection, or accept that the structural guarantee has a hole where a parse-failing post can emit nothing (both pipelines fail with stack traces, no operator-friendly file/snippet message). **Reasoning:** the structural argument is strong but the design only covers half its surface; the other half is silently delegated to whatever Velite does with uncaught exceptions in `.transform()`.

2. **"The launch-time verification of the operator-facing Vercel error message is sufficient defense."** Reverse to: the verification confirms legibility *on launch day*, against a log format Vercel can change at any time, on a code path operators read under time pressure six months later. Add either a scheduled re-verification or a structural fallback (a `process.stderr.write` from `next.config.ts`'s `headers()` callback that fires before Next.js's prerender wrapper can format the error). The v3 design rejected the `headers()` approach because "headers() runs without access to the post-list query layer" — but the env-var check is two `process.env` reads and a `throw`; the post-list access is not required for the check, only for the filtering. The rejection conflates the check (cheap, top-level) with the filter (which legitimately needs the query layer). **Reasoning:** operator UX defense should not depend on a third-party UI's invariance over time.

3. **"The taxonomy hit-count assertions in `verify-production-build.mjs` are an unambiguous safety net."** Reverse to: they are a launch-day liability. The assertions assume tag-page and category-page emits exist, which is true after the first real post, false at launch state, false after a future content audit that removes all taxonomy use. Gate the taxonomy assertions on `getAllTags().length > 0` (read from the build manifest or `#site/content`) so the script defends against draft leaks **without** failing on legitimate empty-taxonomy states. **Reasoning:** a safety net that fires on the intended green-state launch path is mis-calibrated. The hit-count strategy is sound; the gating predicate is wrong.

## What's Missing — Work Before Acting on This Document

- **Launch-state gating for `verify-production-build.mjs` taxonomy assertions.** Either gate on `getAllTags().length > 0` read from build manifest, or document a launch-bootstrap shim that disables the taxonomy checks until the first real post lands.
- **Rejection-visitor parse-failure UX pin.** Wrap the local `remark-mdx` parser invocation in try/catch and rethrow as the same named-error class the node-rejection path throws. Pin the wrapping in the design, not at implementation time.
- **Error Scenario #4 reconciliation.** Delete or rewrite to reflect that the rejection visitor now catches `mdxJsxFlowElement` before `s.mdx()` runs. The two scenarios cannot both be the path a `<Callout>` takes.
- **Structural enforcement of the CI job-topology pin.** Either (a) a comment block in `ci.yml` referencing design.md:260, (b) a script in `verify-production-build.mjs` that reads a Build-1-written sentinel and fails if found (asserting the previous job's state did not leak), or (c) a CODEOWNERS gate on `.github/workflows/ci.yml` requiring spec-author review.
- **Exact-pin discipline extended to `fast-xml-parser` and a Node-version pin.** Add `engines.node: ">=22"` to `package.json`, add `.nvmrc`, exact-pin `fast-xml-parser` with launch-gate test as the merge gate. Suppress or handle the `ExperimentalWarning` for `fs.glob`.
- **Word-count walk extracted to a single source.** Export the reading-time AST walk from `velite.config.ts` (or extract to a shared helper) and have both the Velite transform and the Vitest test import it. Today the test duplicates the walk inline.
- **Positive test for the `VERCEL === '1'` gate.** Unit test: `BLOG_INCLUDE_DRAFTS=1` + `VERCEL_ENV=production` + `VERCEL` unset → `getPublishedPosts()` does NOT throw. Without this test, a regression that drops the `VERCEL` gate revives the local-dev footgun and the test suite stays green.
- **Velite cache-surface audit.** The `rm -rf .velite .next` step protects against the surfaces the design names. A Velite v0.3.1 cache-directory enumeration equivalent to the v2 `.d.ts` audit would close the residual ambiguity.
- **Decision on the word-count ±10% band.** Either widen with a justified worst-case alt-growth estimate, or drop the band entirely and rely on the end-to-end identity check (assertion #3) + the conversion-fidelity check (assertion #2). The band as written is fragile against legitimate accessibility edits.
