## Findings

### WARNING: Theme-parity assertion depends on next-themes hydration timing after emulateMedia
- **File:** /home/mcf/repo/matthew-field.ca/e2e/tests/component-preview/footnotes.test.ts:56
- **Issue:** tokens.css switches `--muted-foreground` only via the `.dark` class on <html>; it has no `prefers-color-scheme` media-query fallback. `page.emulateMedia({colorScheme: 'dark'})` only flips the OS-preference media query — next-themes must hydrate, read `window.matchMedia`, and add `.dark` before the back-ref color reflects the dark token. The test reads computed `color` right after `expect(section).toBeVisible()`; if hydration hasn't applied `.dark` yet, lightColor === darkColor and `expect(lightColor).not.toBe(darkColor)` flakes. Safer: explicitly wait for `html.dark` (e.g. `await expect(page.locator('html.dark')).toBeAttached()`) after the dark `goto`, or toggle the theme via the app's theme switcher / localStorage rather than relying on `emulateMedia`+hydration.
- **Task Requirement:** 9.8 (both themes / theme-parity proof)

### INFO [hygiene]: `li:target` highlight has no horizontal padding
- **File:** /home/mcf/repo/matthew-field.ca/src/styles/blog/footnotes.css:42
- **Issue:** `[data-footnotes] li:target` sets `background-color: var(--muted)` and `border-radius: 0.25rem` but no `padding` or negative `margin`, so the highlight box ends flush with the text edges and bleeds into the list-marker gutter. Cosmetic — does not violate the spec, but the affordance is weaker than typical GFM footnote target styling.
