## Analysis Dimensions

### 1. The Velite `profile` collection and the `git log` transform

The design pins `updatedAt` to a synchronous `execSync('git log -1 --format=%cI -- "${filePath}"')` call inside the Velite transform, with a `vercel.json` `buildCommand` doing `git fetch --deepen=1000 || git fetch --unshallow || true && pnpm build`. Stress-test this:

- The design line "the implementation verifies against the installed version and uses the documented field" (re: `meta.path` vs `data._meta.filePath` etc.) is a punt: the design itself doesn't know the API surface. Identify the concrete failure cases — what happens when `meta.path` is a relative path, undefined, or differs across Velite minor versions? Will the `--` flag-separator argument actually reach `git`, given how `execSync`'s shell expansion handles the embedded path?
- The fallback chain `git fetch --deepen=1000 || git fetch --unshallow || true` swallows network failures with `|| true`. Walk through what happens on a clean Vercel build cache where the deepen step partially completes, leaving an inconsistent state, vs. the second case where `--unshallow` errors on an already-complete clone vs. the third (`|| true`) case where everything failed. Does the downstream "transform throws on empty output" actually catch the wrong-history-but-non-empty case (e.g. file was renamed and the deepen window doesn't reach the rename)?
- File rename / move scenarios. The design assumes `content/profile.mdx` is the source forever. What happens when Matthew renames it, or splits it, or moves it? `git log -1 -- path` returns the most recent commit touching that exact path, which goes empty on the post-rename history without `--follow`. Identify whether the design's named-error contract is tripped on a rename and whether that matches the author's intent.
- Build performance and correctness implications of running `execSync` synchronously inside a Velite transform. Is this re-run on every dev-server hot reload? Does Velite's incremental build cache invalidate when the git repo state changes but the file content does not? What's the dev-loop cost of stat-ing git on every save?
- The "local-build quirk (acknowledged, not fixed)" punt from Req 1.4 — the design accepts a shipped behavior where local builds show stale dates. Is there a cheaper alternative the design did not consider (e.g. fall back to mtime when `git log` returns the same SHA as `HEAD` and the file is dirty)? Or a way to inject the date at preview-deploy time from the commit SHA Vercel already knows? Argue whether the design's punt is the right tradeoff.
- The "same-commit constraint" (Req 1.14, design line ~307 and ~537) is enforced by human discipline, not by code. What concrete CI gate would prevent the schema-only or content-only commit from ever landing? The design declines to add one — challenge that decision.

### 2. The Origin/Referer check, preview deploys, and `NEXT_PUBLIC_SITE_URL`

The route handler accepts the origin from `process.env.NEXT_PUBLIC_SITE_URL`. Walk this through every Vercel deploy environment:

- Vercel preview deploys get `*.vercel.app` URLs that do NOT match production `NEXT_PUBLIC_SITE_URL`. Will the contact form work at all on preview deploys, given the design's "mismatched origin → 403" rule? The design appears to silently break preview submission unless `NEXT_PUBLIC_SITE_URL` is per-environment scoped. Cross-reference with Req 3.11's env-scoping table — does it actually list `NEXT_PUBLIC_SITE_URL` per environment? If it doesn't, this is a hidden production-only assumption that breaks the smoke-test promise of `/profile` and `/contact` parity on previews.
- `Origin` is a single string, but the configured site origin is a single string. There is no list of accepted origins (production + preview + localhost). Walk through how Playwright's `webServer` (running on `http://localhost:3013`) is supposed to satisfy the origin check — the wrapper script sets `NEXT_PUBLIC_SITE_URL=http://localhost:3013` per the design, but that means tests CANNOT also exercise the production-origin code path in the same run. Identify whether the smoke test verifies the *production* CSRF defense or just that the form works in localhost.
- The "both absent → allow" fallback is a real attacker affordance against any client that strips both headers. Curl-style attacks set neither. Walk through what the rest of the layered defense (honeypot, zod) actually buys against an attacker that can craft both a curl request *and* zod-valid content. The design dismisses this as "near-impossible from a real browser" (line 504) but a determined script is the threat, not a real browser.
- The decision to NOT log fallback firings (Req 3.5b, design line 258) means there is zero observability into how often this code path runs in production. Without that signal, how does Matthew ever discover the fallback is being abused? The design treats this as resolved-by-requirement but it bakes an undetectable gap into production.

### 3. The Resend client, timeout, and lazy construction

The design's `lib/mail.ts` contract is "lazy `getResendClient()` per call, 9s timeout via SDK option *if available*, otherwise `Promise.race` against `setTimeout`." Attack this:

- "If available" is a bet. Identify what the *actual* timeout option is in the current Resend SDK (`resend@npm`) and whether it honors a per-call timeout that aborts the underlying fetch. If the SDK does not actually abort the in-flight HTTPS connection at the timeout, `Promise.race` only abandons the *promise* — the underlying socket may keep the function alive until Vercel's 10s cap. Walk through whether a `Promise.race`-only timeout actually saves the ~1s error-response budget in Req-NFR-Reliability.
- Cold-start path: the requirements call out (Req-NFR-Reliability) that cold start collapses the error-response budget to ~300ms. The design's response is "this surfaces as 504 — already handled." But what if the 504 response itself loses the form values because the user's browser navigated away during the cold start? The design says values are preserved (Req 4.4) — but values live in client state, which survives only if the page didn't reload. Does a 504 from Vercel kill the in-flight `fetch()` cleanly back to the client, or does the user see a Vercel error page that replaces the form?
- "Per-call client construction" reads `process.env` on each invocation. Identify the cost: in serverless, env reads are cheap, but constructing a new SDK client *per request* may cost more than a cached client. Argue whether the lazy-construction pattern is justified by the env-mutation case described in Req 3.11, or whether a "construct once per env-revision" cache would be both correct and cheaper.
- The `text` body composition: `From: ${name} <${email}>\nSource: ${source ?? 'unspecified'}\n\n${message}`. The design proudly notes user fields go into `text` only (no HTML). But this same `text` body is what Matthew reads in his inbox. If `name` contains `\r\n` (zod's `.trim()` doesn't strip embedded CRLF, per the design's own Req 3.5e note), the rendered text in webmail is fine — but is there a downstream concern about CRLF in Resend's *plain-text MIME body*? Argue whether the design's "CRLF risk is closed at `reply_to`, not at `text`" claim is actually sufficient.

### 4. The Playwright wrapper script and mock-Resend ordering

The design splits the E2E harness into `scripts/run-e2e.mjs`, `e2e/fixtures/mock-resend.mjs`, and `e2e/playwright.config.ts`. Attack the orchestration:

- The wrapper script "allocates an ephemeral port, spawns the mock, exports `RESEND_BASE_URL`, then spawns Playwright." But Playwright's `webServer.command` (in `playwright.config.ts`) is what spawns `pnpm start`. Does the wrapper's exported env actually reach the `pnpm start` child fork? Walk through Node's `process.env` semantics — modifying `process.env` after fork does NOT propagate to children, so the wrapper must export *before* spawning Playwright, AND Playwright must inherit env into `webServer.command`'s spawn call. Identify the precise fork-time env capture point and whether the design's described ordering is actually correct.
- The mock ready-signal: "the mock writes `READY` to stdout once listening." How does the wrapper script know to wait? The design says "wait for ready signal" without specifying the mechanism — is it a stdout pipe-read with `data` events, a poll loop on the port, or something else? Identify the race window between mock-spawn and Playwright-spawn.
- `test.describe.configure({ mode: 'serial' })` is described as the parallel-worker mock-state hazard mitigation. But Playwright's `serial` mode only serializes within a single file; cross-file isolation requires `fullyParallel: false` at the project level. Is the design's `serial` mode sufficient given the existing `e2e/playwright.config.ts` runs `fullyParallel: true` with retries (per Req 3.13)? Identify whether retries within a serial-block correctly hit `__reset` again.
- The mock `POST /__reset` is hit in `beforeEach`, but the mock's port is shared across all workers in the same Playwright run. If a different test file (e.g. CSP test) submits a form during the Resend-mock test's `beforeEach` window, that submission gets recorded against the about-to-be-reset state. Identify whether the design's per-test isolation is actually achievable given a single shared mock instance.
- The wrapper kills the mock with `process.kill` on Playwright exit. What happens if Playwright crashes (segfault, OOM)? Does the wrapper actually clean up? Is there a port leak across runs?

### 5. The form-state machine and accessibility correctness

The design defines a discriminated union state machine and a `useEffect` keyed on `state.kind` for side effects. Attack the a11y claims:

- Side effects in `useEffect` keyed on `state.kind` will fire on transitions to *and from* a state. The design says "run exactly once per transition" — but a re-render with the same `state.kind` does not retrigger. What happens when `validation-error` fires twice in a row (user submits, fixes one field, submits again, fails on a different field)? The state object is a new reference both times but `state.kind` is the same — does focus move to the new first-invalid field, or stay on the old one? Walk through the React semantics.
- Focus management: "focus moves to the first invalid input" on validation-error. But if the user is *already* in an input (typing) when they submit via Enter, the submit handler runs synchronously, the state transitions to `validation-error`, and the effect fires after re-render. In which event tick does the browser dispatch the synthetic blur from focus-stealing? Identify whether the user's keypress can race with focus restoration.
- The `<button disabled>` pattern in the submitting state. Disabled buttons are not focusable; if the user was on the submit button when they clicked, focus is lost on disable. The design does not address where focus goes during the `submitting` state. Identify whether the screen-reader experience during submit is correct.
- The design uses `role="status"` for *both* success and server-error regions, with `tabIndex={-1}` and focus-move. `role="status"` implies `aria-live="polite"` — but the design also has a top-level `role="alert"` for validation summary. Walk through what a screen reader does when both regions exist on the page simultaneously across a state transition (e.g. validation-error → submitting → success). Is there a stale-region cleanup concern?
- The honeypot uses `display: none`. The design rejects sr-only / off-screen positioning, citing Req 3.2. But `display: none` removes the field from the form's submission entirely in some browsers' behavior — wait, that's wrong, hidden inputs still submit. Verify: does `display: none` on the *container* (a `<div>` wrapping the input) actually remove the input from the form submission? If the input itself is not `display: none` but its parent is, the input is still in the form. Walk through the actual browser semantics.
- "Inputs cleared" on success and "values preserved" on error — the design calls this out, but `<ContactForm />` holds field values in a sibling `useState`. Identify whether the focus restoration races the value-clearing in the success effect.

### 6. The CSP claim, `form-action`, and the test that "doesn't actively exercise" it

The design adds `form-action 'self'` to `next.config.ts` and admits (line 208 of requirements, design CSP test description) that the smoke test does NOT actively exercise `form-action` in the JS-submit path. Tear into this:

- The directive is described as "defense-in-depth against a future regression to native `<form>` submission." Identify what regression scenario actually triggers `form-action` enforcement, and whether the design's CSP test would detect a regression that *added* a native fallback. The current test asserts no violations — but a future regression to a native `<form>` would also produce no violations because `form-action 'self'` permits same-origin. So the CSP directive prevents *cross-origin* exfiltration, not *any* regression. Recharacterize what the directive actually buys.
- The CSP test's pass-1 (Report-Only) listener attaches via `page.addInitScript`. Walk through whether `addInitScript` runs *before* the inline hydration script tag — the design claims it does. If it actually runs *after* the very first inline script, hydration violations are missed. Identify whether the design's claim is verifiable.
- The two-pass test pattern: pass-1 with Report-Only headers, pass-2 with `setExtraHTTPHeaders` injecting enforcing CSP. The `setExtraHTTPHeaders` call sets the header on *every* request from the page including subresources — does this differ from how Vercel serves the production CSP (path-scoped via `next.config.ts`)? Identify whether the test's enforcing pass actually mirrors production semantics or constructs a different enforcement context.
- axe-core in light AND dark theme by toggling `next-themes`'s localStorage key. The design's `addInitScript(...localStorage.setItem('theme', theme))` runs before navigation — but `next-themes` reads from `localStorage.getItem('theme')` (or `'next-themes'`?). Verify the storage key against the actual `next-themes` library, and identify whether the toggling actually changes theme before paint.

### 7. Deferred risks promoted to deferred-still

The design's "Implementation Sequencing & Risk Notes" closes by re-stating four "acknowledged latent risks" from requirements: Resend 100/day quota DoS, Vercel 100K-invocation/month DoS, IDN email rejection, attacker-controlled `reply-to`. Tear into whether the design itself adds any new mitigation or simply forwards the requirements' acceptance:

- The requirements' Vercel 100K/month DoS analysis (Req-NFR-Security) calls out that ANY invocation increments the counter, *including* size-cap rejections, origin rejections, JSON parse failures, etc. The design's pipeline puts the size cap first (good — short-circuits early), but the route handler still runs to do that check. Argue whether the design buys anything beyond what the requirements already describe, or whether edge-middleware-based rejection (rejecting at the edge before invocation) was a design-level option that should have been considered and either adopted or explicitly rejected here.
- IDN email rejection: zod `.email()` rejects non-ASCII local parts. The design's `lib/mail.ts` and route handler both use the same zod regex. Is there an alternate validator the design could have selected (e.g. `email-validator` or a regex-free `URL`-based check) that closes this gap with no additional dependency cost? The design accepts the limitation by inheritance — challenge whether that inheritance was load-bearing.
- The design's `<ContactForm />` uses a 30s client `AbortController` ceiling "for the no-response case" — but this contradicts Req 4.4's "client SHALL NOT auto-retry; the user initiates any retry." A 30s abort is not an auto-retry, but it IS a silent abandonment that drops the user into the `server-error` state with no clear cause. Walk through the UX of a 30s abort vs. the user pressing the back button at 8s — and identify whether the 30s ceiling is documented anywhere a user-facing copy-writer could find it.

The design self-acknowledges this — but is the structure.md gap *itself* a gap to flag? structure.md is supposed to be the SSOT for project structure; the design adding new top-level directories without updating it is a documentation drift the design propagates.
- structure.md line 71 already lists `src/lib/mail.ts` as the Resend helper. Confirm the design's path matches; identify whether the design adds anything in `src/lib/` not yet declared in structure.md (e.g. a TimeoutError class — should it have its own file?).
- structure.md line 188 says "Push `'use client'` as far down the component tree as possible — wrap only the interactive leaf, not the whole page." The design has `<ContactForm />` and `<ObfuscatedEmail />` as `"use client"` — fine. But identify whether the form's per-field error spans, the LinkedIn CTA `<a>`, or the success heading need to be hoisted/lowered to comply more strictly.
- The design's component file paths use `kebab-case.tsx` (✓). Verify the actual filenames against structure.md's "social-links.tsx → SocialLinks" mapping. Are there capitalization edge cases (e.g. `ObfuscatedEmail` → `obfuscated-email.tsx` vs. `obfuscatedemail.tsx`)?
- tech.md line 113 says "Honeypot field (hidden input that bots fill but humans don't)." The design uses `display: none` for the honeypot container. But tech.md doesn't specify the exact hiding mechanism. Identify whether the design's choice is consistent with tech.md or extends it.
- Velite is described as the second collection added. tech.md's content-pipeline section establishes Velite as the SSOT for content schemas. Verify the design's `single: true, pattern: "profile.mdx"` collection actually compiles against Velite's API surface for *single-document* collections — does Velite v0.3.x emit a singular object via `import { profile } from '#site/content'`, or does it emit an array of length 1?

### 9. The site config extension

The design extends `siteConfig` with a `links` object containing `linkedin`, `github`, `email`. structure.md line 130 says "`UPPER_SNAKE_CASE` for primitive values and frozen enumerations, `camelCase` for structured/config objects." The design's URL fields ARE camelCase — but the email value committed to the public repo is plaintext (Req 2.7 / 2.8). Tear into:

- The design says "actual URL/email values are filled in during the implementation task; design only fixes the shape." But the *shape* alone doesn't address that putting the email plaintext in the repo means GitHub Code Search exposes it instantly, before any production deploy. The acknowledged defense is "per-address filtering at the mail provider" — but the design does not call out that this filter must be in place *before* the first commit lands. Identify the launch-prerequisite gap.
- If Matthew rotates the alias later (e.g. `hello@matthewfield.ca` → `matthew@matthewfield.ca` due to spam exhaustion), the previous alias is in git history forever. The design doesn't address rotation. Identify whether this should be a design-time mitigation (e.g. read the email from `siteConfig` constant + a short prefix that's env-driven, or split it across two strings) or whether the residual is correctly accepted.

### 10. Test coverage gaps

The design declines to write jsdom unit tests for `<ContactForm />` ("its surface is screen-reader behavior, focus management, and reduced-motion handling, all of which are fragile to assert in jsdom"). Walk through what is *not* covered:

- Reduced-motion: the design says the loading indicator and scroll honor `prefers-reduced-motion: reduce`. Is this actually tested anywhere? Playwright supports emulating `prefers-reduced-motion` via `page.emulateMedia({ reducedMotion: 'reduce' })`. The design's test files don't mention this — argue whether the reduced-motion claim is verified or only declared.
- The state machine: each of the 5 `FormState` kinds has a corresponding UI surface. Each transition is described. Identify which transitions are exercised by the smoke tests vs. which are described-only. E.g. the validation-error → server-error transition (user fixes fields, server returns 502 on retry) — is this in any test plan?
- The honeypot path: the smoke test only exercises happy-path submissions. Identify whether the design's silent-200 honeypot path is asserted-as-not-emitted-to-Resend by *any* test (Playwright OR Vitest), and walk through what regression class this allows.
- The 413 / 403 / 502 / 503 paths: the Vitest unit tests cover them at the route-handler level, but only in isolation with the mail helper mocked. The design's "Resend timeout fires 503 + Retry-After: 60" behavior: is the *header* asserted, or just the status code?
