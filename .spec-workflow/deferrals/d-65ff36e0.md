## Context
Adversarial rounds r2 and r3 each produced a MUST_FIX rooted in these three criteria, and each fix exposed another layer: the escalation needs an issue label (repository state, outside the spec's declared file surface); the repo default workflow permission is `read` so it needs an explicit `issues: write`; "the label exists" has no checker, no invocation point, and no permitted home (Req 8.1 allows one ci.yml step, already spent on Req 4.8, and ci.yml declares no permissions block so it has no issues scope); and nothing closes the issue on recovery, so the channel's signal dies after first use. r3 also established the escalation has NO roadmap support - decomposition.md:212-229 names no escalation channel, and its only mention of detection (:228) is the thesis this spec explicitly withdraws. A create-reuse-distinguish-resolve-verify channel is a feature wearing three acceptance criteria. Deferring removes the only non-file prerequisite, removes issues:write from Req 7.3, and brings the spec back to a size shippable in one pass (it had reached 13 requirements / ~70 criteria). Alternatives considered: (a) keep and fully specify it - rejected as scope creep against a decomposition entry describing only "a scheduled workflow that refreshes the file"; (b) drop failure visibility entirely - rejected, Req 9.1-9.3 retain a real channel.

## Decision Deferred
github-activity-sync will NOT file/update/close a GitHub issue when the scheduled sync fails. Requirements v3's Reqs 9.7-9.9 (escalate via issue, idempotent reuse, verified label prerequisite) are withdrawn in v4. The delivery channel for a failed sync is Req 9.1's red run plus GitHub's own workflow-failure notification.

## Revisit Criteria
Revisit when EITHER of these observable events occurs: (1) `verify-vercel-token.yml` is repaired — the labels and the `issues: write` pattern then already exist, so the marginal cost of adding escalation here is small; or (2) the sync workflow's own run history shows two or more consecutive failed scheduled runs (visible in the Actions tab and countable by anyone looking, including a future agent). Criterion (2) replaces an earlier wording — "a failure persists without Matthew noticing" — which r4 correctly flagged as having no actor who could ever evaluate it: by construction, nobody who has not noticed can report not noticing. Honest caveat retained: this repository has direct evidence that the red-run notification channel can go unread for eleven consecutive weeks, so neither criterion should be treated as self-firing.
