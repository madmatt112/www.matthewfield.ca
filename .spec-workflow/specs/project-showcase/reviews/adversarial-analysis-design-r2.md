## Attack 1 — `proseClasses` ch-narrowing mechanism (Component 10)

The v2 design committed to a concrete CSS mechanism in response to v1 Risk 1 / Reversal 3. Good. The mechanism it committed to is internally inconsistent.

- **[Novel] Challenge the claim that `prose-p:max-w-prose prose-p:mx-auto` produces the desired narrow-text-wide-media effect.** `max-w-prose` is `65ch`. Tailwind Typography's `prose` already sets `max-width: 65ch` ON THE `.prose` DIV — the design then overrides with `max-w-none` to widen the container, then RE-narrows text children with `prose-p:max-w-prose`. This re-narrowing applies to `<p>`, `prose-headings:` covers headings, `prose-ul:`/`prose-ol:`/`prose-blockquote:` cover those four. **The list is incomplete.** Missing text-flow children that will render at the full `max-w-5xl` width and look broken next to narrowed siblings: `<dl>` / `<dt>` / `<dd>` (description lists, rendered by GFM), `<hr>` (horizontal rule — purely visual, but stretching it 1024px wide is the layout regression), inline `<code>` wrappers within `<p>` (covered transitively, OK), `<details>`/`<summary>` (HTML5 disclosure, valid in MDX). Either enumerate every text-flow tag Tailwind Typography styles, or invert the model and narrow at the container level with a media-escape mechanism instead.
- **[Novel] Stress-test the `prose-headings:max-w-prose prose-headings:mx-auto` directive against the gallery anchor structure on the DETAIL PAGE.** The detail page header `<h1>` lives OUTSIDE the `.prose` div (see Component 10 structure: `<header>` precedes `<div className={proseClasses}>`). So `prose-headings:max-w-prose` does NOT apply to the page title — only to MDX-body headings. The h1 page-title is governed by the outer `max-w-5xl` container and will render full-width. Whether this is the intended visual is unstated. Either explicitly state "h1 page title spans the container, body headings narrow to 65ch and center," or the design forgets that authors will see an h1 that visually disagrees with the body-heading width.
- **[Novel] Challenge the centering decision (`mx-auto`).** The narrowed text-flow children center themselves (`mx-auto`) inside a 1024px outer container. With `max-w-prose = 65ch ≈ 700px` (depends on font size), text-flow children sit in the middle of a 1024px column with ~160px of empty space on each side. **A wide media child (`<img>`, `<table>`) then spans the full 1024px and visually pushes the centered text-flow back toward the left/right edges in a vertical sequence that LOOKS like alternating indent.** Open question: is this the intended visual or is the design unaware that centered narrow text + flush-edge wide media creates a "stair-step" rhythm? The design does not show a wireframe or screenshot. State the visual intent.
- **[Novel] Stress-test the `.prose-projects > :where(table, iframe, svg)` selector specificity.** The CSS rule uses `:where()` (zero specificity) on a direct child combinator (`>`). But `<table>` inside an MDX body is typically wrapped — `remark-gfm` produces `<table>` as a direct child of the MDX root, which then becomes a child of `.prose`. The `.prose-projects` class is added to the same div as `.prose`, so the direct-child selector finds the table. **BUT**: `<figure>` wraps `<img>` in some remark plugin configurations; an `<iframe>` inside a `<figure>` is NOT a direct child. The `> ` combinator misses nested wide-media. Either drop the direct-child combinator (`.prose-projects :where(table, iframe, svg)`) or document that nested wide-media is not supported and authors must avoid figure-wrapping iframes.
- **[Compounding] Challenge the picture/img interaction.** `next/image` emits `<img>` directly in many modes, but can also wrap in `<picture>` when `<source>` elements are present. v2 added `picture` to the wide-media list. **The Tailwind Typography prose-modifier namespace does NOT include `prose-picture:`** (Tailwind Typography v0.5 only defines modifiers for the elements it styles; `picture` is not in that list — the modifier compiles to a no-op class). Verify by reading `node_modules/@tailwindcss/typography/src/styles.js` or the package's exported modifier map. If `prose-picture:max-w-none` is a no-op, the `<picture>` wrapper widens via its default `display: inline`, and the inner `<img>` widens via `prose-img:max-w-none`. Outcome may be correct by accident. **Verify or remove the `prose-picture:` modifier and rely on `prose-img:` alone.**

## Attack 2 — Guard re-entrance and import-time side effects (Components 3, 5)

v2 moved the build-log warning to `getPublishedProjects()` and gates it on the guard returning `null`. This closes Risk 3's ordering issue but introduces new ones.

- **[Novel] Stress-test the assumption that `getPublishedProjects()` is called once per build.** The function is called from (1) the gallery page, (2) the detail page's `generateStaticParams`, (3) the detail page's `generateMetadata`/default export (transitively via `getProjectBySlug`), (4) `sitemap.ts`. Each call site runs the guard AND emits per-draft `process.stderr.write` lines. **With `PROJECTS_INCLUDE_DRAFTS=1`, a build with N drafts and M call sites prints N×M warning lines.** The test in §"Unit Testing" spies on `process.stderr.write` and asserts "once per draft slug" — this assertion is only correct if the test calls `getPublishedProjects()` once. The real build will emit duplicates. Either (a) memoize the warning emit at module-scope (`const warned = new Set<string>(); … if (!warned.has(slug)) { warned.add(slug); process.stderr.write(...); }`), (b) move the warning to module-top-level so it fires once at module-load, or (c) accept the noisy log.
- **[Novel] Challenge the `getProjectBySlug` guard path.** Component 3's public surface lists `getProjectBySlug(slug)` separately from `getPublishedProjects()`. Does `getProjectBySlug` also call `checkVercelDraftGuard()`? If yes, every detail-page render re-runs the guard (probably fine — guard is pure env-var read). If no, a draft project can be reached by direct slug URL during a misconfigured build. The design does not specify the implementation of `getProjectBySlug`. Spec the body: does it call `getPublishedProjects()` and `.find(...)`, or does it scan the raw `projects` array? The answer determines whether draft slugs are 404 in production or accessible.
- **[Novel] Stress-test the early-stderr guard at `next.config.ts` top-level against `pnpm test`.** The v2 extension imports `checkVercelDraftGuard` from `./src/lib/project-errors` at `next.config.ts` top level. `next.config.ts` is loaded by Next.js, but it is ALSO loaded by Vitest when tests transitively touch `next/...` config inspection or when E2E setup invokes the Next.js build. **`process.exit(1)` at config-load time will kill the test runner mid-suite** if any test environment happens to set `VERCEL=1` and a draft env var. Probably won't happen, but the symmetric concern for blog already exists. Confirm `next.config.ts` is not imported by Vitest (check existing blog setup); if it is, the `process.exit(1)` is a test-killer waiting for an unrelated CI env config drift.
- **[Compounding] Challenge the `VERCEL=1` precondition unchanged from v1.** v1 raised it; the v2 response is silent. The guard still returns `null` when `VERCEL !== "1"`, meaning a non-Vercel deploy (a future migration to Cloudflare Pages, Netlify, a self-hosted Node server) skips the guard entirely. With `PROJECTS_INCLUDE_DRAFTS=1` set in a non-Vercel CI env, drafts ship silently. This is a **recurring** finding. Either add a non-Vercel sibling check (CI env vars: `CI=true && NODE_ENV=production` AND drafts=1 → fail), or document the Vercel-only scope as deliberate.

## Attack 3 — Scanner coverage matrix gaps (Component 11)

v2 added type-only and destructure coverage. The matrix is more thorough but still has holes.

- **[Novel] Stress-test the destructure visitor against renamed destructures bound to non-identifier initializers.** The v2 algorithm checks `ts.isVariableDeclaration(node) && ts.isIdentifier(node.initializer) && namespaceLocals.has(...)`. But destructure can chain: `const inner = content; const { projects } = inner;` — `inner` is a new identifier, NOT in `namespaceLocals`. The destructure on `inner` is missed. To close: either follow identifier aliases (TypeScript symbol table — heavyweight) or accept that aliasing-through-a-local-variable bypasses the scanner. Document either way.
- **[Novel] Challenge the `ts.isIdentifier(el.propertyName) ? el.propertyName : ts.isIdentifier(el.name) ? el.name : null` fallback for binding-element propertyName.** Object destructure can use a computed property (`const { ["projects"]: p } = content;`) — `propertyName` is a `ComputedPropertyName` containing a `StringLiteral`. The current visitor skips this case (`ts.isIdentifier(el.propertyName)` returns `false`). String-literal computed access bypasses the scanner. The fix is small (handle `ComputedPropertyName` with string-literal expressions), but the v2 design does not include it.
- **[Novel] Stress-test `isContentSpecifier`.** Not shown in the design — what string match does it perform? Exact equality `=== "#site/content"`? Trailing-slash tolerance (`"#site/content/"`)? Sub-path imports (`#site/content/projects` if Velite's barrel ever exposes that)? Specify exactly. A future Velite version that exposes per-collection sub-paths bypasses the scanner.
- **[Novel] Challenge the canary fixture's reliance on `void` to suppress unused-variable lint.** The fixture uses `void projects; void renamed; void _ns; ...` to mark imports as used. But the fixture is marked `// eslint-disable` AND is in the `tsconfig` `exclude` list. **If it's excluded from tsconfig, the scanner runs on it at file-walk time, but TypeScript's own checks do not.** Fine. But: the scanner test imports `runChokepointScan` and runs it on the canary file path. The canary file IS read from disk. If a maintainer edits the canary and breaks a shape (e.g., removes the `export * from "#site/content"` line), the canary test silently passes a subset. Add an assertion that the FILE on disk contains the expected literal patterns (e.g., regex-match each line) before running the scanner — the test must fail if the fixture is mutated, not just if the scanner regresses.
- **[Compounding] Challenge the namespace-shadow false-positive mitigation.** v2 documents the false positive but offers "rename the inner local" as the only mitigation. **Recurring concern.** A real-world scenario: a contributor adds `function f() { const content = useContent(); return content.projects; }` where the outer file ALSO imports `import * as content from "#site/content"`. The scanner fires on the inner `content.projects`. The contributor's only recourse is to rename. Document this in `docs/projects-authoring.md` §9 — the v2 design says it's documented in the scanner header comment, but Author Doc §9 doesn't mention it. Mirror.

## Attack 4 — Symmetric divergence: blog vs. projects (Components 5, 4)

v2 made `projects.ts` re-export `formatProjectDate` for parity with blog (good). But it ALSO narrowed the looks-like-prod branch in `project-errors.ts` and explicitly did NOT backport to `blog-errors.ts`. This creates a new asymmetry while resolving the old one.

- **[Novel] Challenge the deferred `content-errors.ts` unification.** Deferral 1 trigger conditions: "third content type, OR an explicit `blog dev` `VERCEL_ENV=development` issue." But the asymmetry NOW means `blog-errors.ts` will fire on `vercel dev` with `BLOG_INCLUDE_DRAFTS=1`, while `project-errors.ts` correctly allows it. **The fail-closed posture for blog under `vercel dev` is broken work that v2 chose not to fix.** Either (a) backport the narrowing to blog NOW (cheap edit, in the v2 spirit), (b) name the asymmetry in the design as a known regression of blog UX, or (c) raise this as a separate change in this PR rather than deferring. The current "wait for a complaint" trigger leaves an actively broken developer workflow.
- **[Novel] Stress-test the parity-test triangle.** v2's parity tests assert `formatPostDate === formatContentDate` AND `formatProjectDate === formatContentDate`. By transitivity `formatPostDate === formatProjectDate`. But the design does NOT assert this third relation directly. A bug where one re-export is replaced by a wrapper function still satisfies the two binary assertions if `wrapper === wrapper`. Verify the literal `const = formatContentDate` pattern (identity assignment) survives — and add a single transitive assertion to lock down the pattern.
- **[Compounding] Challenge the asymmetric guard semantics propagating to error messages.** `PROJECTS_DRAFT_LEAK_GUARD_MSG_PRODUCTION` says "production build" but the looks-like-prod branch fires on `VERCEL_ENV=undefined/empty/unrecognized` and returns `{ kind: "production" }`. **The message is wrong for non-production cases** — it tells a developer their `vercel build` with a missing `VERCEL_ENV` is a "production" build, when really it's "unrecognized environment, fail-closed." Either parameterize the message ("production-or-unknown") or add a third `kind: "unknown"` with its own message.

## Attack 5 — `proseClasses` and CSS module wiring (Component 10)

The `src/styles/projects.css` import is mentioned but the wiring is hand-waved.

- **[Novel] Challenge the import location ambiguity.** "imported once from the detail page's parent layout or `src/app/layout.tsx`." Pick one. The detail page's parent layout is `src/app/(site)/layout.tsx` (or a per-route layout). If the CSS is imported into the site-wide `layout.tsx`, the `.prose-projects` class lives globally — fine, but every page parses it. If imported into the detail page's layout, the CSS module's loading is per-route — fine but introduces a new layout file. **The design must pick one.** As written, this is a tasks-phase decision smuggled into design.
- **[Novel] Stress-test the CSS rule's interaction with Tailwind's preflight.** Tailwind preflight resets `iframe { border: 0; }` and other normalizations. The added `max-width: 100%; width: 100%; height: auto;` for iframes is unconditional — but iframes typically need a height set (intrinsic dimensions don't apply to iframes the way they do to `<img>`). `height: auto` on an iframe collapses to `0px` in most browsers (iframes have no intrinsic content height). **Authors embedding a first-party iframe will see a zero-height iframe.** Either set a default `aspect-ratio: 16/9` on the rule, document that authors must set inline `height` attribute, or remove iframes from the wide-media rule entirely.
- **[Novel] Challenge the `svg` height handling.** The same `height: auto` applies to inline `<svg>` from MDX. Inline SVG without `viewBox` and explicit dimensions will collapse. With `viewBox`, `height: auto; width: 100%` gives a proportional render — usually desired. But the rule does not check for `viewBox` presence; an author who pastes a fixed-pixel SVG sees it scaled in unexpected ways. Document that inline SVG MUST have a `viewBox`.

## Attack 6 — `dynamicParams = false` + draft toggling (Component 10)

- **[Novel] Stress-test `dynamicParams = false` against draft promotion.** When a draft project (slug `foo`) is promoted to `draft: false` in the same PR that re-runs the build, the build's `generateStaticParams()` now includes `foo`, so the route works. **But for `vercel dev` sessions toggling `PROJECTS_INCLUDE_DRAFTS=1`**: `dynamicParams = false` is honored by Next.js's static generation at build time. In dev mode, Next.js typically renders on demand and ignores `dynamicParams = false` for build-time-only enforcement — but v15+ behavior here is non-obvious. Verify the actual dev-server semantics, OR document that the dev story is "rebuild between draft toggles."
- **[Novel] Challenge the empty-state fixture path resolution.** v2 introduced `src/__fixtures__/projects-empty/` — a synthetic Velite output JSON. **But the empty-state test mocks `getPublishedProjects()` to return `[]`**, per Component 9. So the synthetic fixture directory is unused by the unit test. Either (a) the fixture directory holds something else (synthetic raw Velite output that flows through `projects.ts`'s draft filter and yields `[]`), or (b) the fixture directory is unused dead-code. Clarify what `src/__fixtures__/projects-empty/` actually contains and why a directory is needed if the test mocks the function.
- **[Novel] Stress-test the page-level E2E assertion "if `getPublishedProjects()` returns N items, exactly N cards render."** This decouples from real content state, good. But the E2E runs against a built `vercel preview`-equivalent — it cannot intercept the function to verify N. The E2E will count cards rendered and assert the count matches `content/projects/*.mdx` files filtered by draft state. The implementation of "count expected N" in the E2E test is unstated. Either inline the test-time content discovery, or accept that the E2E is environment-coupled to the fixture set at build time.

## Attack 7 — Velite version pin + meta.content (Steering, Component 2)

v2 cites line numbers in `node_modules/velite/dist/index.d.ts` and added a `meta.content` shape test (good). New concerns.

- **[Novel] Challenge the pinning policy enforcement.** `docs/projects-authoring.md §9` says "Velite is pinned to the current minor version." But `package.json`'s default semver behavior is caret (`^0.3.x`), which permits minor-version updates. **Specify the exact pin operator** — `~0.3.x` (patch only), `=0.3.x` (exact), or a `velite` line in a `pnpm-overrides`. The doc-only policy without an enforced lockfile constraint relies on human discipline. Add a CI check or a `package.json` resolution pin.
- **[Novel] Stress-test the `velite-output-shape.test.ts` against `node_modules` rebuilds.** The new test asserts the `Image` shape and `meta.content` shape. **But the test reads from compiled Velite output, not from the `.d.ts` file directly.** A Velite update that changes the runtime shape but keeps the TypeScript types compatible (or vice versa) is detected. A Velite update that changes BOTH consistently still passes — and the test does not detect that the *contract* has changed. The "contract test" is really a "doesn't-regress-current-output" test. Acceptable, but state the limitation.
- **[Compounding] Challenge the `s.path()` strip claim.** Steering says "`s.path()` is the standard slug-derivation primitive used by all existing collections — its return value is the velite-root-relative path (e.g. `projects/my-slug`), so the `.transform()` strips the `projects/` prefix." **Cite the file/line in `node_modules/velite/dist/index.d.ts`** for `s.path()`'s return value (other Velite primitives were cited; this one is not). If the assumption is wrong, the slug strip fails silently or generates double-prefixed routes.

## Top 5 Risks/Gaps

1. **`proseClasses` text-flow narrowing is incomplete and the visual is unspecified.** The per-tag list of narrowed text-flow elements (`p`, `headings`, `ul`, `ol`, `blockquote`) misses `dl`/`dt`/`dd`, `hr`, `details`/`summary`. The detail-page h1 lives OUTSIDE the prose div, so it renders at container width while body h2/h3 narrow to 65ch — a likely-unintended visual disagreement. The centering pattern produces a "stair-step" rhythm with alternating wide-media and centered-narrow text-flow. **No wireframe or screenshot is in the design.** Build the prototype and visually verify before coding the production page.

2. **Stderr warning emit is per-call, not per-build.** `getPublishedProjects()` is called from at least four entry points per build (gallery, sitemap, detail's `generateStaticParams`, detail's `generateMetadata`). With N drafts and four call sites, the build log shows 4N "including draft" lines, not N. The unit test that "spies on `process.stderr.write`" passes because it calls the function once; the real build is noisy. Memoize at module scope or move to module-top-level emit.

3. **Blog vs. projects guard asymmetry is an unfixed regression.** v2 narrowed the looks-like-prod branch in `project-errors.ts` to allow `VERCEL_ENV=development`. `blog-errors.ts` did NOT get the same narrowing. `vercel dev` with `BLOG_INCLUDE_DRAFTS=1` now incorrectly fail-closes for blog while projects works. The deferral trigger ("explicit `blog dev` issue") waits for a complaint; the regression is shippable today. Either backport the narrowing to blog in the same PR or explicitly call out the broken state.

4. **Iframe wide-media rule produces zero-height iframes.** The CSS rule `.prose-projects > :where(table, iframe, svg) { max-width: 100%; width: 100%; height: auto; }` collapses iframes to zero height because iframes have no intrinsic height. The CSP-permitted first-party iframe surface (e.g., `/playground/*`) will render invisibly. Either add `aspect-ratio: 16/9` to the rule, mandate inline `height` attributes in author doc §6, or drop iframes from the wide-media rule.

5. **Scanner destructure-through-local-alias bypass.** v2 added destructure coverage for `const { projects } = content`, but `const inner = content; const { projects } = inner;` bypasses because `inner` is not in `namespaceLocals`. A motivated maintainer (or accidental refactor) can launder around the scanner. Either follow identifier aliases via the TypeScript symbol table or document the bypass as a known limit and trust code review.

## Top 3 Conclusions to Challenge or Reverse

1. **Reverse the "narrow text via per-tag prose modifiers" pattern in favor of a two-div structure.** The current pattern (override prose's `max-w-prose`, then re-apply via `prose-p:max-w-prose prose-headings:max-w-prose ...`) is fighting Tailwind Typography. The simpler pattern: outer `max-w-5xl` container, INNER `max-w-prose mx-auto` for text-flow, wide-media uses an "escape" CSS rule that breaks out of the inner container (`margin-inline: calc(-1 * var(--container-padding))` or a CSS subgrid). The inverted model is closer to how real article layouts are built (e.g., the New York Times pattern). The current design picked the wrong primitive to fight. Build a prototype both ways and pick the readable one.

2. **Reverse the "wait for a `blog dev` complaint" deferral.** Backport the looks-like-prod narrowing to `blog-errors.ts` in this PR. The change is ~5 lines, surfaces immediately, and prevents shipping a regression to blog. The deferral logic ("third content type") makes sense for the larger `content-errors.ts` unification — but the looks-like-prod narrowing is a bug fix, not a refactor, and should not wait on the refactor's trigger.

3. **Reverse `dynamicParams = false` for the projects detail route.** The combination of `dynamicParams = false`, dual-build draft topology, and `vercel dev` toggling produces confusing 404s. Use `dynamicParams = true` and let unknown slugs hit `notFound()` from `getProjectBySlug` — same end-state for end users, less Next.js-version-specific dev surface. The "static-only enforcement" benefit of `dynamicParams = false` is minor; the dev-mode surprise is real.
