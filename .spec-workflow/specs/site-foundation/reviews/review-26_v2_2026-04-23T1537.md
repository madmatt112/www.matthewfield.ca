## Summary

Navigation E2E suite covers R4 AC2/AC3, R7 AC1, and R8 AC1 across desktop nav, placeholder pages, 404, and mobile hamburger interactions. Three prior info findings persist unchanged; one novel info finding noted about the 'mobile' viewport being tablet-sized (768x1024) rather than a phone-sized viewport.

## Findings

### INFO: Desktop nav click test does not verify heading text matches the target section
- **File:** e2e/tests/navigation.test.ts:19
- **Issue:** The desktop nav parametric test asserts only `page.getByRole('heading', { level: 1 }).toBeVisible()` after clicking a nav link — it does not check the heading text corresponds to the expected section. Because `toHaveURL(item.href)` does not distinguish a placeholder render from a 404 body (Next.js leaves the URL intact on 404), the click test alone could pass even if a route silently rendered the 'Page not found' h1. Coverage is compensated by the separate placeholder tests (which assert heading name = item.label), so this is a weakness in test precision rather than a gap, but worth tightening by asserting `{ level: 1, name: item.label }` in the click tests.
- **Task Requirement:** R4 AC2
- **Classification:** recurring

### INFO: Placeholder verification bypasses nav clicks and uses page.goto
- **File:** e2e/tests/navigation.test.ts:29
- **Issue:** The placeholder tests navigate via `page.goto(item.href)` rather than clicking the nav link. The task prompt specifies 'Navigate to each section via nav links, assert placeholder page renders with correct title (not 404)' — the current split has one test that clicks-but-doesn't-verify-title and another test that verifies-title-but-doesn't-click. Neither test alone fully demonstrates the flow the task describes. Consolidating into a single per-section test that clicks the nav link and then asserts heading name + 'under construction' body text would match the prompt more literally.
- **Task Requirement:** R4 AC2, R7 AC1
- **Classification:** recurring

### INFO: Mobile 'closes after selection' test exercises only one nav link
- **File:** e2e/tests/navigation.test.ts:73
- **Issue:** The 'selecting a link navigates and closes the menu' test clicks only the Projects link to verify the Sheet closes on selection. If `onClick={() => setOpen(false)}` regressed for a subset of items (e.g. via conditional rendering), this test would not catch it. Iterating `siteConfig.navItems` inside this test (or a second parametric test) would give equivalent coverage to the desktop-nav click loop.
- **Task Requirement:** R4 AC3
- **Classification:** recurring

### INFO: 'Mobile' viewport is tablet-sized (768x1024) rather than phone-sized
- **File:** e2e/tests/navigation.test.ts:8
- **Issue:** `MOBILE_VIEWPORT = { width: 768, height: 1024 }` is iPad portrait — it sits exactly at Tailwind's `md` breakpoint and well above typical phone widths (320-414px). The task restriction ('below lg breakpoint `< 1024px`') is satisfied because `lg` fires at >=1024 so the DesktopNav is correctly hidden at 768. However, R4 AC3 is framed around 'mobile device' users and the task title says 'mobile nav menu open/close at small viewport'. A phone-sized viewport (e.g. 375x667 iPhone SE) would better represent the target audience and also catch any `md:`-specific regressions. Current selection is compliant with the written restriction but weaker than intent.
- **Task Requirement:** R4 AC3
- **Classification:** novel
