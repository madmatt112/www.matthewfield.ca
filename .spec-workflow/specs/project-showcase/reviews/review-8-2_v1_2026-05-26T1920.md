## Findings

### INFO: assets key derivation does not strip query/hash suffix from cover.src
- **File:** /home/mcf/repo/matthew-field.ca/velite.config.ts:330
- **Issue:** velite's processAsset builds src as `baseUrl + name2 + suffix`, where suffix is the trailing `?query`/`#hash` portion of the original asset reference. The transform recovers the key by stripping only `^/static/` from data.cover.src (line 330). For typical MDX-frontmatter `cover: ./foo.png` references resolved by `s.image()` there is no suffix, so resolution succeeds. If a frontmatter author ever writes `cover: ./foo.png?v=2` (or velite ever attaches a query for cache-busting), the resulting key would include the suffix and `assets.get()` would return undefined, fast-failing via the cover-asset-unresolved branch. Not a defect today; flag for awareness if cover asset references gain query params in future.

### INFO [hygiene]: Cover error code prefixes diverge from posts collection convention
- **File:** /home/mcf/repo/matthew-field.ca/velite.config.ts:334
- **Issue:** posts collection uses bare reason words (e.g. `mdx-parse-failure`, `html rejected`) in its diagnostic shape. projects uses dashed `<code>` tokens (`cover-too-large`, `cover-too-small`, `ogImage-too-narrow`, `ogImage-bad-aspect`, `cover-asset-unresolved`, `links-duplicate-kind`). The dashed tokens are crisper and grep-friendly, but the two collections now disagree on diagnostic shape. Non-blocking; raise iff requirements 1.6 / observability docs end up referencing a single shape.
