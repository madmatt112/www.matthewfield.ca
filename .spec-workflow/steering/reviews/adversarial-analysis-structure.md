# Adversarial Analysis: Project Structure Document

## 1. Directory Organization: Completeness and Coherence

### Playground at project root: awkward but defensible

The `playground/` directory at the project root importing from `src/lib/` and `src/components/ui/` does violate the intuitive dependency direction — source code outside `src/` reaches into `src/` internals. However, the alternative (putting playground items inside `src/`) would tangle playground experiments with the application codebase and make it harder to treat them as self-contained. The real problem isn't the directory location — it's that the `@/*` path alias maps to `./src/*`, which means playground items can use `@/lib/utils` and it will resolve correctly from the project root because TypeScript path aliases resolve relative to `tsconfig.json`, not the importing file. This works. But it means playground items look like they're part of `src/` in their import statements while physically living outside it. A dedicated alias (e.g., `#playground/*` → `./playground/*`) for playground-to-playground imports would make the boundary clearer, but isn't strictly necessary. **Verdict: awkward import semantics, not a structural failure.**

### `public/static/` gitignored: deployment hazard is real but small

Vercel runs the full build pipeline on every deploy, which includes Velite processing. Velite copies content images to `public/static/` during build, and since Vercel builds from a clean checkout, there are no stale images — the directory is rebuilt fresh each time. The gitignore just keeps binary files out of the repo. **This is fine.** The only hazard is local development after a `git clean -fdx` — a developer must run the Velite build before images appear. The structure document doesn't mention this bootstrapping step, but it's a minor DX annoyance, not a deployment risk.

### Missing generated artifact locations

The product doc describes:
- **RSS/Atom feed**: Tech doc says "generated at build time as static XML files" but the structure doc doesn't show where they live. Likely `public/feed.xml` or generated via a Next.js route handler at `src/app/feed.xml/route.ts` — but the structure is silent.
- **Sitemap XML**: Next.js can generate this via `src/app/sitemap.ts`, but the structure doesn't show this file. The structure shows `src/app/(site)/sitemap/page.tsx` for the HTML sitemap but says nothing about the XML sitemap that search engines consume.
- **Pagefind search index**: Generated by crawling the built site, output presumably goes into `public/` or a build artifact directory. Not shown anywhere in the structure.

**This is a gap.** Three build-generated artifacts with no defined home. During implementation, someone will have to decide where these go and whether they're gitignored. The RSS feed and XML sitemap are especially important — they're referenced in the tech doc's CI link checker configuration, so their paths matter for validation.

### `content/pages/` vs App Router pages: clear enough

The separation is actually fine. `content/pages/about.mdx` provides the markdown body content; `src/app/(site)/about/page.tsx` is the route that renders it. The route file imports the content from Velite and wraps it in layout/components. This is the same pattern used for blog posts. **No conflict here** — the naming is slightly confusing ("pages" in two places), but the roles are distinct.

### Missing test directory conventions

The document says test files are named `[filename].test.ts` but says nothing about:
- Where Playwright E2E tests live (the tech doc mentions Playwright for "interactive flows: contact form, theme toggle, search, playground loading")
- Where test fixtures, helpers, and setup files go
- Whether tests are colocated with source files or in a separate directory

This matters because Playwright tests need a config file (`playwright.config.ts`), a test directory (commonly `e2e/` or `tests/`), and potentially fixture files. Vitest unit tests could be colocated or in `__tests__/` directories. The structure document doesn't show any of this. **Gap: test infrastructure has no structural home.**

## 2. Naming Conventions: Enforceability and Edge Cases

### No enforcement tooling for filename conventions

The structure document prescribes kebab-case files, one component per file, and specific naming patterns for hooks, tests, and CSS modules. The tech doc mentions ESLint and Prettier but neither of these enforce filename conventions out of the box. Without `eslint-plugin-check-file` or similar, these rules will drift. Specifically:
- A developer might create `BlogPostCard.tsx` instead of `blog-post-card.tsx`
- Hooks might be named `mediaQuery.ts` instead of `use-media-query.ts`
- Nothing stops two components from being defined in one file

**Risk level: low for a solo developer, but the rules are unenforceable and the document doesn't acknowledge this.** If Matthew steps away for months and returns, or if he ever brings in a contributor, there's no guardrail.

### One component per file vs. small helper components

The document says "one component per file" but real-world React development frequently produces small helper components that exist solely to serve their parent. A `BlogPostCard` might need an internal `TagList` that's five lines of JSX and used nowhere else. Creating a separate file for this is bureaucratic overhead.

**The document should either explicitly permit small, unexported helper components in the same file (the pragmatic choice), or acknowledge that the one-component rule applies only to exported components.** As written, it's ambiguous.

### UPPER_SNAKE_CASE vs. camelCase constant ambiguity

The rule — `UPPER_SNAKE_CASE` for "true constants", `camelCase` for "config objects" — relies on a subjective distinction:

- `siteConfig` is a config object → camelCase. Clear enough.
- `MAX_POSTS_PER_PAGE = 10` is a true constant → UPPER_SNAKE_CASE. Clear.
- `NAV_ITEMS = [{ label: "Blog", href: "/blog" }]` — is this a "true constant" or a "config object"? It's a constant array of objects.
- `DEFAULT_THEME = "system"` — true constant or config value?

**This will produce inconsistency.** The distinction should be: primitive values and frozen enumerations get UPPER_SNAKE_CASE; structured objects get camelCase. But the document doesn't say that.

### CSS Module naming ambiguity

When a directory contains multiple components (e.g., `src/components/layout/` with `header.tsx`, `footer.tsx`, `nav.tsx`), the convention allows both `[component-name].module.css` and `styles.module.css`. If someone uses `styles.module.css` in a directory with multiple components, it's unclear which component it belongs to. **In practice this won't be a problem** because CSS Modules are explicitly imported by the component that uses them — the import path makes ownership clear. The naming is slightly loose but functionally harmless.

## 3. Import Patterns: Practical Conflicts and Missing Rules

### `#site/content` alias and cold start bootstrapping

The `#site/content` alias points to `./.velite`, which doesn't exist until Velite runs. This means:
- `tsc --noEmit` (type checking) will fail before a Velite build
- Editor intellisense for content imports won't work until Velite has run
- CI must run Velite before type checking

The tech doc mentions "TypeScript strict mode, checked in CI" but doesn't specify the build order. The structure document is silent on this dependency.

**This is a real implementation concern.** The fix is documented in Velite's own docs (generate a `.velite/index.d.ts` stub or run Velite first), but the structure document should acknowledge the bootstrapping dependency since it defines this alias as a core import pattern.

### Playground imports and the `@/*` alias

The `@/*` alias maps to `./src/*` in `tsconfig.json`. Playground items at `playground/[item-name]/` importing `@/lib/utils` will resolve correctly because TypeScript resolves path aliases relative to the `baseUrl`/`tsconfig.json` location, not the importing file's location. **This works without a separate tsconfig.**

However, the "never use relative imports that go up more than one level" rule is awkward for playground items. A playground item at `playground/pixel-art-editor/canvas.tsx` importing from `playground/pixel-art-editor/palette.ts` uses `./palette` (fine). But if two playground items ever needed to share a utility, there's no `playground/shared/` convention and relative imports would require `../../other-item/util.ts`. The document says playground items should be "self-contained" so this theoretically shouldn't happen — but it's an unaddressed edge case.

### Import order vs. auto-formatters: will be destroyed

The prescribed import order (React → external → internal → content → relative → styles) is a convention that will last exactly until someone configures `eslint-plugin-import` or `@trivago/prettier-plugin-sort-imports`. These tools have their own ordering logic. Unless the ESLint/Prettier configuration explicitly encodes this exact 6-group ordering, the first auto-format will rearrange imports.

**The structure document prescribes an import order without specifying the tooling that enforces it.** This is a convention waiting to be violated by the tools meant to help.

### Barrel files: silent omission

The document says nothing about barrel files (`index.ts` re-exports). `shadcn/ui` components don't use barrel files — each component is imported directly (`@/components/ui/button`). But the document doesn't state whether other directories should follow this pattern.

Without guidance:
- Should `src/components/shared/` have an `index.ts`?
- Should `src/lib/` have one?
- Should `src/hooks/` have one?

**For a small codebase with a solo developer, this is low-risk.** But the document should either say "no barrel files" (simpler, matches shadcn convention) or define when they're appropriate.

## 4. Module Boundaries: Enforcement and Playground Coupling

### Module boundaries are honor-system only

The rules are clear:
- `src/lib/` must not import from `src/components/` or `src/app/`
- `src/components/` must not import from `src/app/`
- `src/components/ui/` must not import from other `src/components/` subdirectories

Without `eslint-plugin-boundaries`, `dependency-cruiser`, or similar tooling, these are aspirational. A solo developer will likely maintain discipline initially, but boundary violations accumulate silently. A utility in `src/lib/content.ts` that needs to render a preview might import a component. A shared component might import a config that imports a component.

**The tech doc's CI pipeline doesn't include boundary checking.** Lint, type-check, test, build — none of these catch import direction violations. The boundaries exist only in this document and in the developer's memory.

### Playground "self-contained" is misleading

The document says playground items "should be self-contained — minimize coupling to the main site" but then permits imports from `src/lib/` and `src/components/ui/`. If a shadcn `Button` component changes its props API, playground items that import it break. If `src/lib/utils.ts` changes the `cn()` signature, playground items break.

"Self-contained" in this context means "no app-level imports" — not "independently deployable" or "isolated from changes." The document should be more precise about what self-containment means and doesn't mean. As written, a developer could reasonably expect that refactoring `src/components/ui/` won't break the playground — but it will.

### `src/config/` import permissions are underspecified

The dependency diagram shows `src/config/ → imported by app/ and components/`. But what about `src/lib/`? The likely scenario:

- `src/lib/content.ts` needs `siteConfig.url` to construct absolute URLs for RSS feeds
- The rule says `src/lib/` is "pure utilities — no React, no side effects"
- Is importing a config object a side effect? No. Is it allowed by the diagram? The diagram doesn't say.

**The document should explicitly state whether `src/lib/` can import from `src/config/`.** The pragmatic answer is yes — config values are static data, not React components. But the diagram omits this edge.

### Playground layout reset: ownership unclear

The structure document says `(playground)/` has "minimal or no chrome" with its own layout and style reset. The tech doc specifies the reset: `all: initial` (with overrides), `isolation: isolate`, `@layer playground`. But the structure document doesn't clarify:

- Does the reset live in `src/app/(playground)/layout.tsx` as inline styles, a CSS Module, or Tailwind classes?
- How does the playground layout compose with the root `layout.tsx`'s global providers? The root layout wraps everything in `<html>`, `<body>`, and providers (theme, fonts). The playground layout needs to reset styles while preserving the React context from the root layout.
- If the root layout loads fonts via `next/font`, does `all: initial` on the playground container undo the font assignment?

**The `all: initial` reset will reset `font-family` to the browser default.** The playground container must explicitly re-declare `font-family` if playground items should use a specific font (even a system font stack). The tech doc doesn't mention this. This will surface as a visual bug on first implementation.

## 5. Code Size Guidelines and Documentation Standards: Realism

### 300-line limit vs. `velite.config.ts`

`velite.config.ts` defines typed schemas for five content types: blog posts, projects, contributions, resources, and pages. Each type needs:
- Frontmatter field definitions with zod-based types
- Computed fields (slug, reading time, permalink, excerpt)
- Transform functions (for series grouping, related posts, tag normalization)

The blog post schema alone — with title, date, description, tags, categories, series, draft status, last-updated, computed reading time, computed slug, computed TOC — will consume 40-60 lines. Five content types plus shared configuration and any custom zod schemas will likely land at 200-350 lines.

**300 lines is tight but possible if the schemas are concise.** The real risk is that computed fields for the blog type (series grouping, related posts) will push the file over. The document should acknowledge that `velite.config.ts` is a likely exception to the 300-line guideline, or pre-plan extraction of complex transforms into `src/lib/` helpers imported by the config.

### "Components do not need JSDoc" vs. complex components

The product doc describes components with significant behavioral complexity:
- Reading progress bar (scroll position tracking, visibility logic)
- Series/multi-part post grouping (conditional rendering based on series membership, current position)
- Related posts (algorithmic selection, fallback behavior)
- Table of contents (heading extraction, scroll-spy, active heading highlighting)

For these, "props types serve as documentation" is inadequate. A `TableOfContents` component's props might be `{ headings: Heading[] }` — but the behavioral questions are: Does it track scroll position? Does it highlight the active heading? Does it collapse on mobile? Props types don't answer these.

**The blanket "no JSDoc for components" rule is too rigid for complex interactive components.** A middle ground: components with side effects, scroll listeners, or complex conditional logic should have a brief behavioral comment at the top. Simple presentational components don't need it.

### No per-module READMEs: scales for now

For a solo developer building a site with this level of documentation (three steering documents, a structure document), inline READMEs are unnecessary overhead. The structure document is the single reference. **This is fine for the current scope.** If Matthew returns after months, re-reading this document (~250 lines) takes 10 minutes. The real documentation risk isn't missing READMEs — it's that this structure document might not be updated as the code evolves.

### 8-prop limit vs. blog post page

The blog post page needs: title, date, content (MDX body), description, tags, reading time, series info, previous/next post, table of contents, last-updated date, categories. That's 11+ distinct data points.

But this is a false conflict. The blog post page component at `src/app/(site)/blog/[slug]/page.tsx` will receive a single `BlogPost` object from Velite that contains all these fields. The component destructures the fields internally — it doesn't receive them as 11 separate props. Sub-components like `PostHeader`, `PostNavigation`, or `TableOfContents` each receive a focused subset. **The 8-prop limit applies to individual component APIs, not to the total data a page needs.** This is actually fine as long as the page component passes focused slices to its children.

## 6. Content Pipeline: Structural Gaps

### Draft handling: unspecified mechanism

The product doc requires "Draft/unpublished status (local only, not rendered in production)." The structure doc shows `content/blog/my-post.mdx` but says nothing about how drafts work. The likely implementation is a `draft: true` frontmatter field filtered out by the Velite schema or the content query layer. But:

- Is it a frontmatter field? A filename prefix (`_draft-my-post.mdx`)? A separate directory (`content/blog/_drafts/`)?
- Does the Velite schema exclude drafts from the generated collection, or do consuming components filter them?
- Are drafts visible in `next dev` but hidden in production builds, or always hidden?

**The mechanism matters for implementation.** A frontmatter field is the simplest approach (and the most common in static site generators), but the structure document should state this explicitly since it defines frontmatter as the content organization pattern.

### `content/pages/` inconsistent with product spec

The structure doc says `content/pages/` contains "about, now, colophon." The product doc lists six slash pages: about, contact, now, colophon, sitemap, slashes.

- **Contact**: The structure shows `src/app/(site)/contact/page.tsx` but no `content/pages/contact.mdx`. The product doc says contact reuses components from the Professional Profile — it's likely a pure-component page with no markdown content. This is consistent but the structure doc's description of `content/pages/` as the home for "standalone page content" is misleading if some standalone pages don't have content files.
- **Sitemap**: Described as "auto-generated" — no content file needed. Fine.
- **Slashes**: An index page listing all slash pages. Could be auto-generated or have a content file. Not shown.

**The inconsistency is minor but will cause a moment of confusion during implementation.** Which pages get content files and which don't? The answer is "pages with authored markdown body content get files; component-only pages don't." The document should state this rule.

### Playground item metadata: nowhere to be found

The product doc describes "a listing/gallery of available items" for the playground. This gallery needs metadata per item: title, description, thumbnail/preview, tags, date added. Where does this metadata live?

Options:
1. A frontmatter-style metadata file in each `playground/[item-name]/` directory (e.g., `meta.json` or `meta.ts`)
2. A centralized registry (e.g., `src/config/playground.ts`)
3. Derived from the component itself (exported constants)

The structure document shows `playground/[item-name]/` containing `index.tsx`, `styles.module.css`, and `[other files]` but doesn't address metadata at all. **This is a real gap** — the playground gallery page can't be built without knowing where item metadata comes from.

### Image management: workflow undefined

Blog posts and project writeups will have images. The structure shows:
- `public/images/` — "site images (logo, profile photos, OG images)"
- `public/static/` — "Velite-copied content images (gitignored)"

But the workflow is unclear:
- If a blog post has images, does the author put them next to the MDX file in `content/blog/`? Then Velite copies them to `public/static/`?
- Or does the author put images directly in `public/images/` and reference them with absolute paths?
- How are images referenced in MDX? `![alt](./my-image.png)` (relative, Velite resolves) or `![alt](/images/blog/my-image.png)` (absolute)?

**The Velite-copied approach (colocate images with content, Velite copies to public) is the better DX** — authors don't have to think about public paths. But the structure document doesn't explain the workflow, and the split between `public/images/` and `public/static/` suggests two different image management strategies without clarifying when to use which.

## Deliverables

### Top 5 Risks or Gaps (ranked by implementation pain)

1. **Playground item metadata has no defined home.** The playground gallery page is a product requirement, but the structure document doesn't specify where item titles, descriptions, and thumbnails live. This will block implementation of the `/playground` index page. Someone will have to make an architectural decision on the spot — centralized registry vs. per-item metadata file vs. exported constants — and that decision affects the dynamic import pattern, the Velite pipeline (or lack thereof), and the gallery page component.

2. **`#site/content` alias breaks before first Velite build.** Type checking, editor intellisense, and `import` resolution all fail when `.velite/` doesn't exist. The CI pipeline ("lint, type-check, test, build") must run Velite before `tsc` — but the structure and tech docs don't specify this ordering. First CI run will fail, and every developer clone requires a Velite build before the editor works. Needs an explicit bootstrapping step or a stub generation approach.

3. **Import order convention has no tooling enforcement.** The 6-group import order will be rearranged the moment an import sorting plugin is configured (or when one isn't configured and a developer manually reorders). The same applies to module boundary rules — no `eslint-plugin-boundaries` or `dependency-cruiser` in the tooling list means import direction violations accumulate silently. These conventions need either tooling backing or an explicit acknowledgment that they're guidelines, not rules.

4. **Draft content handling is unspecified.** "Draft/unpublished status" is a product requirement with no structural definition. Frontmatter field? Separate directory? Filtered at build time or query time? The Velite schema is the "single source of truth" for content types — but if draft handling isn't defined in the schema specification, the first blog post draft will require an ad-hoc decision that affects the content pipeline.

5. **RSS/Atom feed, XML sitemap, and Pagefind index have no defined output locations.** Three build artifacts referenced across the product and tech docs with no structural home. The RSS feed path matters for the link checker CI step. The XML sitemap path matters for `robots.txt` and search engine submission. The Pagefind index path matters for the search component's configuration. All three will require decisions during implementation.

### Top 3 Conclusions to Challenge or Reverse

1. **"Components do not need JSDoc" should be relaxed for behavioral components.** The product spec describes components with scroll tracking, series navigation, and algorithmic content selection. Props types document the interface but not the behavior. Components with side effects, event listeners, or complex conditional rendering should have a 1-2 line behavioral comment. This costs nothing and prevents "what does this component actually do?" confusion during maintenance. Not a full JSDoc requirement — just a brief behavioral note for non-obvious components.

2. **"No README files per module" assumes this structure document stays current.** The structure document is the single source of truth for project organization, but it's not checked by CI and has no mechanism for staying in sync with the codebase. If the playground architecture evolves (new metadata approach, new isolation patterns), the structure document may not be updated. A lightweight `playground/README.md` explaining the item creation workflow (metadata, entry component, dynamic import pattern) would survive codebase changes better than a steering document. Consider allowing READMEs for architecturally complex subsystems — playground and the content pipeline are the two candidates.

3. **The `all: initial` style reset for playground items will have unintended side effects.** `all: initial` resets every CSS property to its initial value, including `font-family` (to browser default serif), `color` (to black, ignoring dark mode), `line-height` (to `normal`), `box-sizing` (to `content-box`), and `-webkit-font-smoothing`. The tech doc mentions overrides for `display`, `box-sizing`, and `unicode-bidi` but not for `font-family`, `color`, `line-height`, or font smoothing. Every playground item will need to re-declare these basics, creating boilerplate. Consider using `all: revert-layer` with the `@layer playground` approach instead, or define a baseline playground CSS Module that items extend, so the reset doesn't push boilerplate into every item.

### What's Missing

1. **Playground item metadata convention** — Define how the gallery page discovers and displays playground items: a `meta.ts` export in each item directory, a centralized config, or a Velite collection for playground entries.

2. **Build order / bootstrapping documentation** — Document that Velite must run before type-checking and editor use. Define a `postinstall` or `prepare` script that generates the `.velite/` stub so the project works immediately after `pnpm install`.

3. **Test directory structure** — Define where Playwright E2E tests live (e.g., `e2e/`), where Vitest tests are placed (colocated vs. `__tests__/`), and where test fixtures/helpers go. The tech doc specifies both test frameworks but the structure document ignores testing entirely.

4. **Generated artifact locations** — Specify where RSS/Atom XML, XML sitemap, and Pagefind index are output. These affect CI validation, `robots.txt`, and the search component.

5. **Image workflow documentation** — Clarify when to use `content/`-colocated images (Velite-copied to `public/static/`) vs. direct `public/images/` placement, and how each is referenced in MDX.

6. **Import order and module boundary tooling configuration** — Either add `eslint-plugin-import` order config and `eslint-plugin-boundaries` (or `dependency-cruiser`) to the tech doc's tooling list, or acknowledge that the conventions are unenforceable guidelines.
