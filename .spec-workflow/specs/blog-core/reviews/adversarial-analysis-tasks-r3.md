# Adversarial Analysis — blog-core/tasks (v3)

Reviewer stance: senior delivery lead, post-r2 sweep. The v3 tasks doc absorbed v2's high-confidence findings at the structural level — Task 6.5 introduces a shared `blog-errors.ts` constant module imported by Tasks 7 and 16; Task 20.5 adds a `verify-ci-topology.mjs` mechanical defense; Task 22.5 adds a synthetic-input walker-self test; Task 20 inverts the sentinel touch ordering; Task 16 adds a Vercel-log surfacing manual verification; Task 28's patch path now requires explicit re-runs of Tasks 24 + 26; explicit `Depends on:` footers appear on Tasks 4.2, 6, 7, 16, 20.5, 22.5; a Requirements Coverage Matrix appears at the document foot. What follows is what v3 did not surface, plus what v3's edits themselves introduced.

Citations are to line numbers of `tasks.md` (v3, post-r2).

## Attack surface 1 — Requirements Coverage Matrix is itself a procedural artifact with no mechanical enforcement (novel; compounding the v2 procedural-as-structural pattern)

Task 28 closes with a coverage-audit note (lines 493–494) saying "Reviewers running the coverage audit should grep `requirements.md` for unlisted IDs and demand a task for each." The matrix (lines 411–491) lists ~50 requirement IDs across 13 sections.

- **Challenge the claim that the matrix closes r2 Attack Surface 6.** The matrix is hand-curated markdown. A new requirement added to `requirements.md` does not auto-appear here; a requirement deleted from `requirements.md` does not auto-leave. The same pattern v2 surfaced for CI topology (procedural pin without mechanical enforcement, closed by Task 20.5) recurs here: the matrix is a markdown table the reviewer must grep against by hand. Demand a parallel mechanical defense: `scripts/verify-requirements-coverage.mjs` that (a) extracts requirement IDs from `requirements.md` via a stable header pattern, (b) extracts coverage matrix entries from `tasks.md`, (c) exits non-zero with a diagnostic naming any orphan requirement OR any matrix entry pointing at a non-existent requirement. Without it, the matrix stales the moment requirements.md edits land and no one re-runs the matrix by hand.
- **Stress-test the matrix's "Req 1.1–1.3, 1.9–1.11" silence.** The matrix lists Req 1.0, 1.4, 1.5, 1.6, 1.7, 1.8, 1.12 in Req 1. Reqs 1.1, 1.2, 1.3, 1.9, 1.10, 1.11 are absent. Either those IDs do not exist in `requirements.md` (in which case the matrix is fine but the audit note is misleading because it tells the reviewer to grep for IDs without telling them which IDs are intentionally absent vs. accidentally orphaned), or those IDs DO exist and are orphaned. The audit note shifts this burden to "implementers MUST flag any such gap before marking Task 28 complete" — but Task 28's success criterion (line 403) does not include "ran the coverage audit and confirmed no orphans." So the audit is unenforceable. Pin: Task 28's success criterion must include "ran `scripts/verify-requirements-coverage.mjs` and it exited 0."
- **Tear apart the matrix's section-numbering against `requirements.md`'s actual section structure.** The matrix splits Reqs into sections labeled "Req 1 (posts collection)", "Req 11 (RSS feed)", etc. — but `requirements.md`'s actual section labels are not cited here. If a reviewer wants to verify section coverage, they must open two files and cross-reference labels. Demand the matrix cite section labels verbatim from `requirements.md` (e.g., "Req 1: <verbatim section heading from requirements.md>") so a reviewer can grep one file against the other without disambiguation.
- **Stress-test "Req 6.0, 6.1" silence in the matrix.** Task 4.3's `_Requirements:` footer lists `6.0, 6.1, 6.5`. The matrix's Req 6 section lists 6.3, 6.4, 6.4a, 6.5 — Reqs 6.0 and 6.1 are absent from the matrix. Either they're consciously not listed (orphan despite being claimed by Task 4.3), or the matrix is incomplete. The audit note doesn't disambiguate. Same pattern likely repeats elsewhere — spot-check: Task 2's footer claims 6.1; matrix Req 6 has no 6.1 entry; Task 4.3 claims 6.0; matrix Req 6 has no 6.0 entry. Pin: either explain the omissions inline in the matrix ("Req 6.0 covered transitively by 4.3; not surfaced") or add them.

## Attack surface 2 — `Depends on:` footers are inconsistent (novel)

v3 introduces explicit `Depends on:` footers (revision history line 8: "Add explicit `Depends on:` ordering footers between sibling tasks that have a real ordering edge"). Spot-check:

- Task 4.2: `_Depends on: 4.1_` (line 77)
- Task 6: `_Depends on: 4.1_` (line 120)
- Task 7: `_Depends on: 4.4, 6.5_` (line 145)
- Task 9: `_Depends on: 8_` (line 166)
- Task 16: `_Depends on: 6.5_` (line 250)
- Task 20.5: `_Depends on: 20_` (line 310)
- Task 22.5: `_Depends on: 2_` (line 345)

- **Challenge the completeness of the dependency edges.** Many tasks have genuine ordering edges that are NOT pinned with `Depends on:`. Task 11's `getPublishedPosts()` import obviously depends on Task 7 — no footer. Task 12 depends on Tasks 7, 10, 12 — no footer. Task 14 depends on Tasks 4.4, 5, 7 — no footer. Task 17 depends on the presence of `src/lib/blog.ts` (Task 7) — no footer. Task 27 depends on Tasks 1 (node-html-parser), 4.4 (bodyHtml emit), 11/12 (rendered pages) — no footer. The new convention is applied selectively, which is worse than not applying it at all: a reader sees `Depends on:` on some tasks and (correctly?) infers its absence on others means no dependency, when in fact dependencies exist. Demand either (a) every task gets a complete `Depends on:` footer or (b) the revision history note explicitly says "applied only to non-obvious dependency edges" — but even that's a slippery slope.
- **Stress-test Task 22's missing footer.** Task 22 (line 319) imports `countWordsFromMdast` from `@/lib/build/word-count` (Task 2) AND reads `#site/content` (requires Tasks 4–6 to have built). Yet Task 22 has no `Depends on:` footer. Task 22.5 — which is a strictly smaller subset of Task 22's deps (just Task 2) — DOES carry `Depends on: 2_`. The pattern is inverted: the more complex task lacks the footer, the simpler task has it. Demand Task 22 carry `Depends on: 2, 4.4, 6_` at minimum.
- **Tear apart Task 20.5's `Depends on: 20`.** Task 20.5's body (lines 295–310) says "This task also updates ci.yml to wire the invocation" (line 310, in the prompt restrictions). So 20.5 depends on 20 AND modifies 20's output file. If 20.5 runs after 20, both succeed; if 20.5 runs before 20 lands, 20.5 has nothing to wire into. The footer captures only one direction of the coupling. Either (a) merge 20 and 20.5 into a single task (the cleanup is artificial — both edit ci.yml), or (b) pin in 20.5 that 20.5 MUST land in the same PR as 20, not a follow-up PR. The current shape allows a "land 20 now, land 20.5 next sprint" anti-pattern that leaves CI procedurally defended in the interim.
- **Demand a structural-defense for the depends-on graph itself.** Same pattern as the coverage matrix: hand-curated markdown that stales. `scripts/verify-task-dependencies.mjs` that (a) parses tasks.md for `Depends on:` footers, (b) topologically sorts, (c) exits non-zero on cycles or forward references. Otherwise the next maintainer adds a `Depends on:` footer that creates a cycle and no one notices until implementation time.

## Attack surface 3 — Task 6.5's `checkVercelDraftGuard()` helper has no env-var-naming pin and no test-isolation guarantee (novel)

Task 6.5 (lines 122–132) introduces `BLOG_DRAFT_LEAK_GUARD_MSG_PRODUCTION`, `BLOG_DRAFT_LEAK_GUARD_MSG_PREVIEW`, and an optional `checkVercelDraftGuard()` helper.

- **Challenge the "optional helper" framing.** Task 7 (line 137) and Task 16 (line 243) both unconditionally call `checkVercelDraftGuard()` — it is not optional in practice, it is load-bearing for both consumers. The "optional" framing in Task 6.5's body is misleading and may suggest to the implementer that they can skip it. Demand Task 6.5 reframe the helper as required (not optional), since dropping it forces the two consumers to re-implement the predicate locally, which is exactly the runbook drift v2 surfaced.
- **Stress-test the env-var-name source.** Task 6.5's restrictions (line 132) list the env vars `VERCEL`, `VERCEL_ENV`, `BLOG_INCLUDE_DRAFTS`. Task 7's body and Task 16's body also reference these. But the literal string values (`VERCEL === '1'`, `VERCEL_ENV === 'production' | 'preview'`) are not exported as named constants. If Vercel renames `VERCEL_ENV` (the design-r3 staleness pattern), the strings are scattered across `blog-errors.ts`, `blog.ts`, `next.config.ts`, and the CI workflow. Pin: either export `VERCEL_ENV_VAR_NAME`, `VERCEL_FLAG_VAR_NAME`, `DRAFT_FLAG_VAR_NAME` as constants from `blog-errors.ts` (or a sibling `blog-env.ts`), or admit that the v3 architecture punts on this and document the staleness path.
- **Tear apart Task 22's env-var test pattern against Task 6.5.** Task 22's restrictions (line 334) say "Env-var mutations scoped via beforeEach/afterEach." But Task 6.5's `checkVercelDraftGuard()` is a pure function — its env reads happen at call time. Task 22 tests `getPublishedPosts()` (line 322 cases), which calls through `checkVercelDraftGuard()`. The test mutation pattern works for both. BUT Task 22 does NOT explicitly test `checkVercelDraftGuard()` against its own truth table (the four state combinations Task 6.5's success criterion enumerates on line 132). The helper is therefore tested only transitively through `getPublishedPosts()`, and only for the throw-paths — the helper's `null` return (the happy path where no guard fires) is asserted only implicitly. Demand a dedicated `src/lib/blog-errors.test.ts` (or merge into Task 22) that asserts the helper's truth table directly.
- **Stress-test multi-line constant strings against `.eslintrc` and Prettier.** Task 6.5 line 125 says the constants are "multi-line, name the variables, the Vercel-side fix, and references Req 7.3 by section." Multi-line template literals or string concatenation? If template literals, leading/trailing whitespace is preserved literally — the rendered Vercel log message gets the indentation of the source. If string concatenation, the implementer has to remember `\n`. Task 22 does not pin which form. Demand the body say "template literals, no leading whitespace per line" or similar.

## Attack surface 4 — Task 20.5's verifier scope vs. the actual ci.yml edits (compounding the procedural-defense pattern)

Task 20.5 (lines 295–310) asserts five pins on ci.yml — (a) no job-level `BLOG_INCLUDE_DRAFTS`, (b) no Build-2 env, (c) `rm -rf` has `if: always()`, (d) sentinel-touch precedes e2e and validate-feed, (e) Build 2 runs verify-production-build.mjs after `pnpm build`.

- **Challenge whether pin (d) actually catches the v2 inversion bug.** Pin (d) says "Build 1's sentinel-touch step runs before `pnpm test:e2e` and `validate-feed.mjs`." But the v2 inversion bug was different: the sentinel was touched at the END of Build 1 (after e2e completion), so a failed e2e meant the sentinel was never created and Build 2's "absent" check was trivially green. Pin (d) catches that. Good — but: it catches it only by step name pattern. If a maintainer renames the sentinel-touch step or merges it into another step, pin (d)'s "identified by step name pattern" (line 301) fails to find the step and the verifier either errors or false-passes. Pin: the verifier MUST exit non-zero when it cannot find a step matching the expected pattern, NOT skip the assertion.
- **Stress-test pin (b)'s "Build 2's `pnpm build` step identified by step name pattern."** Same identification fragility. The v3 task body in Task 20 (lines 281–293) does NOT pin the literal step names — the maintainer can write `name: "Build (production-mode)"` or `name: "Build 2"` or omit the `name:` field entirely. Demand Task 20 pin the literal step names (e.g., `name: "Build 1 (with drafts)"`, `name: "Build 2 (production-mode)"`, `name: "Touch Build 1 sentinel"`, etc.) AND demand Task 20.5's verifier match those exact strings. Otherwise the verifier is sensitive to cosmetic edits in ci.yml.
- **Tear apart pin (a)'s "job-level `env` block does not contain BLOG_INCLUDE_DRAFTS."** What about workflow-level `env` (above the `jobs:` key)? GitHub Actions allows env at workflow, job, and step scope. Pin (a) covers only job. A maintainer who promotes `BLOG_INCLUDE_DRAFTS` to workflow-level (sibling to `jobs:`) defeats the verifier. Demand pin (a) cover BOTH workflow-level and job-level env blocks.
- **Demand a self-test for the verifier.** Task 20.5's success criterion (line 310) says "Manual run against the current ci.yml exits 0; planted job-level `BLOG_INCLUDE_DRAFTS` env entry fails non-zero with named diagnostic." Only one planted-failure case is required. A robust verifier should have a test fixture for EACH of the five pins (a)–(e), so the verifier itself is verified. Pin: add to Task 20.5 a sixth requirement — a `scripts/verify-ci-topology.test.mjs` (or inline tests) with five fixture ci.yml files, each violating exactly one pin, each producing the expected diagnostic.

## Attack surface 5 — Task 22.5's synthetic-mdast test does not pin the construction utility, and the assertion math has an unverified premise (novel)

Task 22.5 (lines 336–345) constructs an mdast tree in-test and asserts `countWordsFromMdast(tree) === 75`.

- **Challenge the construction substrate.** Task 22.5 line 338 says "Construct an mdast tree in-test (not from a fixture) with known structure." Constructing valid mdast by hand is error-prone — mdast nodes have required fields (`type`, `children`, `position`, etc.). If the implementer builds an under-specified tree (e.g., omits `position`), `unist-util-visit` may still walk it correctly OR it may behave subtly differently than a parser-produced tree. The synthetic test's value depends on the synthetic tree being a faithful representation of what `remark-parse` would emit for equivalent markdown. Demand Task 22.5 specify the construction method: either (a) use `unist-builder` (the canonical mdast builder), (b) construct via `remark-parse` against an in-test markdown string (which defeats the "synthetic, no fixture" framing but is more robust), or (c) explicitly list the required fields each node type must have.
- **Stress-test the "code block of 100 words must be dropped" assertion against `countWordsFromMdast`'s actual implementation.** Task 2 (line 33) says the walker "drops `code` and `html` node types." If `countWordsFromMdast` walks via `unist-util-visit`'s default behavior, dropping happens via early-return (`visit(tree, (node) => { if (node.type === 'code' || node.type === 'html') return SKIP; ... })`). But there are TWO mdast code types: `code` (block) and `inlineCode` (inline). The Task 2 description says "drops `code`" — does it drop `inlineCode` too? An inline `code` span in a paragraph still contributes its text to `mdast-util-to-string`'s output unless explicitly excluded. Task 22.5's synthetic test doesn't cover `inlineCode`. If the walker excludes only `code` (block) and includes `inlineCode`, the reading-time count includes inline code text — which may or may not be intended. Pin: Task 2 AND Task 22.5 must disambiguate `code` vs. `inlineCode` and pin the desired behavior (likely "drop both, since inline `\`x\`` is rarely prose").
- **Tear apart the "75 words" math against the image-alt case.** Task 22.5 lines 338–340: 50 words (paragraph) + 100 words (code, dropped) + 25 words (heading) = 75. Then line 340 adds an image with `alt: "alpha beta gamma"` = 3. Then line 339 adds a whitespace edge case = 2. The three assertions are described as separate test cases ("Assert ... === 75" then "Add at least one whitespace edge case ... should count as 2" then "Add the image-alt case ... contributes 3"). The "75" assertion is for the first tree only — the whitespace and image-alt trees are SEPARATE trees with their own assertions, not extensions of the 75-word tree. Re-read carefully: lines 338–340 describe ONE tree (paragraph + code + heading); lines 339–340 describe additional trees. The body is ambiguous about whether the three are separate test fixtures or composed into one. Demand explicit "three separate `test()` cases, each with its own mdast fixture, each with its own pinned expected count" pinning.
- **Stress-test the test's `countWordsFromMdast` import.** Task 22.5 imports `countWordsFromMdast`. Task 2 places it at `src/lib/build/word-count.ts`. Task 22.5 file path is `src/lib/build/word-count.test.ts` — colocated with the source. The `_Leverage:` footer says "countWordsFromMdast (Task 2); vitest" — but Vitest's default `include` pattern (per typical defaults) is `src/**/*.{test,spec}.{ts,tsx}`. Verify the test file location actually matches the Vitest config's include pattern. If the existing project config restricts tests to a specific subdirectory (e.g., `src/__tests__/`), Task 22.5's `word-count.test.ts` won't run. Pin: Task 22.5 must verify the Vitest config's `include` pattern covers `src/lib/build/*.test.ts` BEFORE writing the test, or update the include pattern.

## Attack surface 6 — Task 28's "patch + re-run Tasks 24 + 26" doesn't address the actual failure mode (compounding from r2 Attack Surface 4)

Task 28 (lines 390–403) now requires re-running Tasks 24 and 26 if the spot-check patches globals.css.

- **Challenge whether re-running Tasks 24 + 26 actually catches the cascade regression.** Task 24 (lines 354–360) is axe accessibility. Task 26 (lines 369–376) is no-JS and explicit-override theme. Neither test asserts color-token values against the cascade; both assert higher-level behavior (a11y violations; effective color matching github-dark/light token). If Task 9's pinned variable names are wrong AND `rehype-pretty-code` emits a DIFFERENT set of names that ALSO happen to render visible colors (just not the intended ones), Task 26's color-match assertion catches it. But Task 26's specific assertion (line 372) is "code-block effective color matches github-dark plaintext token; inverse for light" — which depends on the cascade pointing at the correct variable name. If the variable name is wrong, the cascade resolves to nothing (no color set), and the assertion fails. Good — but this assumes the implementer's "patch globals.css" preserves the cascade-resolution semantic. A hasty patch that swaps `--shiki-light` for `--shiki-foreground` and leaves the rest of the cascade unchanged could produce a green Task 26 with the wrong colors. Pin: Task 28's re-run requirement must include capturing the actual emitted color values (computed-style hex) and comparing against the expected github-light/dark hex codes, not just "tests passed."
- **Stress-test the implementation-log requirement.** Task 28 line 398: "the implementation log entry for Task 28 MUST cite both re-runs by their Playwright report fragments (not just 'tests passed')." Playwright report fragments are HTML — citing them in a markdown log requires either (a) copying screenshots of the report, (b) copying the report's underlying JSON, (c) copying the console output of `pnpm test:e2e`. The task body doesn't pin which. A "test passed" line from console output is far weaker evidence than a report screenshot showing color values. Pin: define the citation format. Suggest: include the Playwright report's JSON `results` array fragment (not just `status: 'passed'`).
- **Tear apart Task 28's "Lighthouse spot-check ≥90" success criterion against Task 21.** Task 28 line 403 says "Lighthouse spot-check ≥90 across all four blog URLs." Task 21 (lines 312–317) wires the four URLs into lighthouserc.js but doesn't pin a threshold — the existing thresholds are inherited. If the existing lighthouserc.js thresholds are <90, Task 28's success criterion is stricter than Task 21's setup, and the spot-check is the only place the ≥90 contract appears. Pin: Task 21 must verify (or pin) the inherited thresholds meet ≥90 across performance/a11y/best-practices/SEO, or document Task 28's stricter contract as an explicit override.
- **Demand a path for the "verify Task 9 fails" case where re-runs are NOT needed.** Task 28 lines 393–398 cover the patch path. But Task 28 line 394 first says "If reality matches the pin, document the confirmation in the implementation log and move on." Re-running 24 + 26 only applies on patch. But: how confident is "reality matches the pin"? If the implementer opens `/blog/fixture-code`, sees colors, and writes "looks right" — that's a weaker check than running Task 24 and Task 26 anyway. The current shape lets the implementer skip the re-run by declaring the pin correct on visual inspection. Pin: Task 28 should ALWAYS run 24 and 26 against the rendered output as part of the spot-check — patch or no patch — so the spot-check is always backed by mechanical assertions.

## Top 5 Risks/Gaps

1. **Coverage matrix is a procedural artifact, not mechanically verified (novel, compounds the v2 procedural-as-structural pattern).** A new requirement in `requirements.md` does not auto-appear in the matrix; a deleted requirement does not auto-leave. The audit note (line 494) shifts the burden to "implementers MUST flag any such gap" but Task 28's success criterion does not enforce running the audit. v2 closed the CI-topology version of this pattern with Task 20.5; the matrix version is wide open. **Severity: medium.** Catches as orphan requirements surviving review.

2. **`Depends on:` footers applied inconsistently (novel).** Selectively-applied dependency footers are worse than no footers: a reader sees them on 7 tasks and infers absence-means-no-dependency, when in fact Tasks 11, 12, 14, 17, 22, 27 all have unstated dependencies. Task 22 (the larger task) has no footer; Task 22.5 (a strict subset of 22's deps) does. **Severity: medium.** Catches as an implementer starting Task 11 before Task 7 lands, or running Task 22's tests before content is built.

3. **Task 20.5 step-name matching is fragile (novel; compounds v2 procedural-defense pattern).** Pin (b) and pin (d) match Build 2's build step and Build 1's sentinel-touch step "by step name pattern" (lines 300, 302). If a maintainer renames the steps, pins (b) and (d) either error or false-pass — depending on the verifier's missing-step semantics, which the task body doesn't pin. **Severity: medium.** Catches as a silent loss of mechanical defense after a cosmetic ci.yml edit.

4. **Task 22.5's synthetic-mdast construction substrate is unpinned (novel).** Constructing valid mdast by hand is error-prone; the assertion's value depends on the synthetic tree being a faithful representation of what `remark-parse` would emit. Also: `code` vs. `inlineCode` disambiguation is unpinned. **Severity: low–medium.** Catches as a passing test whose synthetic input is structurally inequivalent to real mdast, hiding a real-world walker bug.

5. **Task 6.5's helper framed as "optional" while load-bearing for two consumers (novel).** Task 7 line 137 and Task 16 line 243 both unconditionally call `checkVercelDraftGuard()` — it is not optional. The "optional" framing in 6.5 invites the implementer to skip it and reimplement the predicate inline in `blog.ts` and `next.config.ts` — which is exactly the runbook drift v2 surfaced. **Severity: low–medium.** Catches as the v2 finding silently regressing.

## Top 3 Conclusions to Challenge or Reverse

1. **Reverse: "The Requirements Coverage Matrix at the document foot closes r2 Attack Surface 6."** It closes the visibility gap but not the staleness gap — and the staleness gap is the one that ships. Add a `scripts/verify-requirements-coverage.mjs` that extracts requirement IDs from `requirements.md` (stable header pattern), extracts matrix entries from `tasks.md`, and exits non-zero with a diagnostic naming any orphan. Wire it into Task 28's success criterion. **Reasoning:** the same procedural-defense pattern v2 surfaced for CI topology recurs here verbatim. The fix is structurally identical to Task 20.5.

2. **Reverse: "`Depends on:` footers applied to non-obvious edges only is an acceptable convention."** Selective application is worse than no application. Either every task gets a complete `Depends on:` footer (and a `scripts/verify-task-dependencies.mjs` verifies the graph topologically sorts and references real task numbers) OR remove the footers entirely and rely on natural ordering. Half-measures invite mis-inference. **Reasoning:** consistency requires either universal application or universal absence; the current state mis-trains readers about which dependencies are real.

3. **Challenge: "Task 28's re-run of Tasks 24 + 26 is acceptable closure for r2 Attack Surface 4."** Re-running 24 + 26 catches some regressions but not "cascade resolved to wrong color values" because Task 26's color-match assertion (line 372) is binary, not value-comparing. Pin Task 28 to capture and compare the actual emitted hex values against the expected github-light/dark hex codes; or extend Task 26's assertion to include value comparison so the re-run actually exercises the regression class Task 9's pin is meant to prevent. Also: drop the "if patch needed" gate — always run 24 + 26 against the rendered output as part of the spot-check, since visual inspection is weaker evidence than mechanical assertion. **Reasoning:** the patch path's re-run requirement is necessary but not sufficient; the same regression class can pass through if the wrong-but-cascade-resolves swap happens.
