## Attack 1 — The reading-time transform's mdast walk (Components > Velite `posts` collection)

The reading-time pin at design.md:112 specifies: parse `meta.content` with `remark-parse` + `remark-gfm`, walk with `unist-util-visit` dropping `code` and `html` node types AND **recursing into `mdxJsxFlowElement`/`mdxJsxTextElement` children**, then flatten with `mdast-util-to-string`.

- **Challenge the claim that `mdxJsxFlowElement`/`mdxJsxTextElement` nodes exist in the mdast tree produced by `remark-parse` + `remark-gfm` alone.** Those node types are emitted **only when the MDX micromark/remark extensions are registered** (typically via `remark-mdx`, which the design does not include in the AST-walk parser stack). With the pinned plugin set, JSX flow elements in a post body parse as `type: 'html'` nodes (or fail at the parser, depending on shape) — they never become `mdxJsxFlowElement`. The recursion the design pins is dead code with the chosen parser stack. **Demand the design either (a) add `remark-mdx` to the AST-walk parser stack — accepting a richer plugin instantiation inside the schema callback — or (b) drop the JSX-element recursion and document that JSX in a post body counts as raw HTML and is rejected upstream.** Today the design over-specifies a walk it cannot exercise.
- **Stress-test the interaction between the raw-HTML rejection visitor and the reading-time visitor on the same tree.** Both walks are described as running over "the same mdast tree" in the schema `.transform()` callback. If the rejection walk throws first, the reading-time walk never runs (fine). But if the design's implementation reorders these — say, computes reading-time first for caching reasons — then a post containing `<aside>foo</aside>` contributes "foo" to the reading-time count (because `html` nodes are dropped) but the rejection still fires. Output is the same, but the reading-time computed-then-discarded path burns build cycles. More importantly: the design specifies "the rejection visitor throws before `bodyHtml` is requested" — but neither visitor is ordered relative to the other in prose. Pin the ordering.
- **Tear apart the `mdast-util-to-string({ includeImageAlt: true })` flattening choice.** With `includeImageAlt: true`, image alt text contributes to the word count. The fixture-reading-time post is pinned to "an image with alt text" (design.md:317). A 12-word alt-text image bumps the count and the integer-rounded reading-time. The design's prose-freeze gate (the `<!-- FIXTURE-FREEZE -->` comment) freezes *prose* — alt text is not prose, but it does count. A reviewer editing the image's alt for accessibility reasons (a legitimate, expected change) silently shifts the count past the 20% tolerance edge. The freeze gate's scope is mis-specified.

## Attack 2 — `s.markdown()` pipeline divergence on MDX-only syntax beyond raw HTML

Req 3.7 (cited by the design) rejects raw HTML in post bodies, and the design correctly observes this makes the page-vs-feed JSX-tag divergence "moot." But Req 3.7 covers `type: 'html'` mdast nodes only. MDX has other syntaxes the markdown pipeline cannot parse.

- **Challenge the claim that the rejection visitor covers the full divergence surface between `s.mdx()` and `s.markdown()`.** MDX expressions — `{post.title}`, `{1 + 2}`, JSX attribute expressions — parse as `mdxFlowExpression` / `mdxTextExpression` / `mdxJsxAttribute` mdast nodes only when `remark-mdx` is active. In the `s.markdown()` pipeline, these expression syntaxes either (a) parse as literal `{text}` and survive into `bodyHtml` verbatim, or (b) fail the parser. Either is silent: there's no Req 3.7-style rejection for non-HTML MDX-only syntax. The design's "moot" claim at design.md:113 over-promises. **Demand the rejection visitor be extended** to reject `mdxFlowExpression`, `mdxTextExpression`, `mdxJsxFlowElement`, AND `mdxJsxTextElement` nodes — or document that MDX expressions in post bodies are unsupported and rely on Velite's MDX compile to reject them at `s.mdx()` time (which works, but is asymmetric and gives a worse error).
- **Stress-test the divergence on import/export statements.** A post containing `import { Foo } from '...'` at the top is legal MDX. In the markdown pipeline, this parses as a paragraph of literal text and lands in `bodyHtml`. The MDX pipeline either resolves the import (impossible without a registry) or fails. Result: page-render fails; bodyHtml succeeds and ships `import { Foo } from '...'` as visible text to RSS subscribers. The Req 11.11 parity test would catch this *if* a fixture exercises it — no fixture does. Demand a fixture or schema-level rejection.
- **Tear apart the silent-divergence detection budget.** The design's defense against page/feed divergence is the Req 11.11 parity test, which compares "element-text" structure with carve-outs for CDATA artifacts. A divergence that produces visible text in `bodyHtml` and a build failure in the page render isn't caught by the parity test (one side never builds), and the build failure is loud — so the divergence is detected by build failure, not parity. That's adequate when the page builds first. But CI's Build 1 builds both pages and feed from the same Velite output; the build ordering doesn't guarantee page-compile is attempted before feed emission. A post that fails the page MDX compile but emits a valid `bodyHtml` could ship to the feed if the build orchestration is wrong. Pin the ordering: feed assembly must consume the same Velite output that the page compile has already validated.

## Attack 3 — Reading-time integer-clamp fragility under the ±20% tolerance bound

The v1 review flagged this; v2 partially addressed via the freeze gate. The structural issue remains.

- **Recurring (escalated): Challenge the test's stability near the integer-clamp boundary.** With 1000+ words at 238 wpm, computed minutes ≈ 4.2. `Math.round(4.2) = 4`. A 119-word addition pushes 4.7 → 5 (since round breaks at 0.5). The ±20% tolerance on the actual integer-clamped value is `4 ± max(0.8, 1) = 4 ± 1` → window [3, 5]. So a single 100-word section change crosses into the upper bound and is on-the-edge stable. But a single **alt-text edit** (Attack 1's bullet 3) adds 5–15 words and shifts the ratio without warning. The freeze gate prevents prose churn but does not prevent the alt-text edit. **Compounding finding** (builds on v1's reading-time observation): the test compares against `readingTime`, but the actually-stable assertion would be against the *word count* (a pure mdast-walk computation) with a separate, looser assertion that `readingTime === wordsToReadingTime(words)`. Decoupling the count from the clamp removes the breakpoint fragility.
- **Stress-test the `± max(20%, 1 minute)` floor when computed reading-time is 1.** A short post (≤238 words) clamps to 1 minute. The tolerance window is `1 ± 1 = [0, 2]`. `Math.max(1, ...)` floors to 1, so the lower bound is unreachable. Any post pinned at exactly 1 minute passes any word count from 0 to ~476 words. The fixture is pinned ≥1000 words specifically to make the test meaningful — but if someone duplicates the test pattern for a future short post, the test silently asserts nothing.

## Attack 4 — Error-message UX on the Vercel-side build-time guards

The design promises operator-facing error messages at design.md:140–141 and design.md:382: `getPublishedPosts()` throws named errors that "name the variables and reference Req 7.3." This is the operator's only signal that Vercel env-var scoping is wrong.

- **Challenge the claim that the named error message reaches the operator via Vercel's build log.** `getPublishedPosts()` is called inside `generateStaticParams()` and `generateMetadata()`. Next.js' behavior when these throw at build time is to surface the error in the build log, but the exact format depends on the Next.js version: older versions print a generic "Error occurred prerendering page X" with the stack trace; newer versions emit a more readable block. Vercel adds its own log-truncation layer. **Demand the design either (a) verify the actual rendered error appearance against a deliberately-misconfigured preview build before launch, or (b) accept that the named error is fragility-prone and add the same guards inside `next.config.ts`'s `headers()` callback** (which is the earliest hook Vercel runs) where the error surfaces more reliably as a build-time failure.
- **Stress-test the Req 7.12(a) symmetric case at the local-dev surface.** A developer running `pnpm dev` locally with `BLOG_INCLUDE_DRAFTS=1` (because they want to preview a draft) but no `VERCEL_ENV` set — the guard does NOT fire (production guard checks both `BLOG_INCLUDE_DRAFTS=1` AND `VERCEL_ENV=production`). Fine. But a developer who has `VERCEL_ENV=preview` exported in their shell from copy-pasting a previous session's env block AND no `BLOG_INCLUDE_DRAFTS` — the (b) guard fires on every local dev run with a cryptic Req 7.3 error. This is a footgun the design does not call out. The guards correctly guard the Vercel build surface but make local-dev brittle. Either scope the guards to skip when `process.env.CI === undefined && process.env.VERCEL_ENV is forced`, or document the local-dev gotcha.
- **Tear apart the assumption that `verify-production-build.mjs`'s glob-discovery catches "zero files scanned" before the env-var guards.** Build 2 runs with no env vars set. If a future Next.js version changes the App Router emit shape so the script's glob patterns no longer match (e.g., `.next/server/app/blog/page.html` → `.next/server/app/(site)/blog/page.html`), the script's hit-count gate catches the zero-files outcome — but only if it gates on the right glob shape. The design pins the gate at "**at least one expected file** of each shape (e.g., `**/blog/*.html` or equivalent post-page emit)" — "or equivalent" is the loose phrase that lets the script silently degrade. Demand the design enumerate exactly which file shapes the script asserts exist, so a future emit-structure change fails the script explicitly rather than being silently accommodated.

## Attack 5 — Feed package version-pin discipline and dependency hygiene

v1 demanded a feed version pin. v2 added `^4.2.2`. The caret is the bug.

- **Compounding finding: Challenge the caret in `^4.2.2`.** `^4.2.2` permits `4.x.y` for any `x ≥ 2` and `y ≥ 0` — across that range, the CDATA-wrapping behavior can absolutely change in a patch or minor release. The launch-gate test catches the regression in CI on the dependency-update PR, but only if a dependency-update PR exists and the test runs. A `pnpm install` in a fresh checkout (no lockfile mismatch) could pull `4.3.0` silently. The design wrote "pinned at `^4.2.2`" — the noun "pinned" is misused. Demand exact pinning (`"feed": "4.2.2"`) and document the dependabot/renovate flow that bumps it deliberately with the launch-gate test as the merge condition.
- **Stress-test the launch-gate test's coverage of the CDATA-wrapping contract.** The test asserts the substring `<![CDATA[<pre>` appears in `feed.rss2()` output. This catches the gross failure mode (XML-escaping `<` → `&lt;`). It does NOT catch a future `feed` version that wraps with `<![CDATA[ <pre>` (note: leading space) — the substring assertion fails, which is correct. It also does not catch the case where `feed` emits well-formed CDATA but inside an unexpected element (e.g., wrapping `<description>` instead of `<content:encoded>`). The substring check happens to be valid for the v4.2.2 emit shape; it is not a structural check. A stricter test would parse the XML and assert the `<content:encoded>` element contains a CDATA section whose payload starts with `<pre`. Demand the strict-parse version of the assertion at launch.
- **Tear apart the implicit dependency between `feed` package output and `fast-xml-parser` in `validate-feed.mjs`.** The two packages have independent definitions of "well-formed RSS 2.0." The launch-gate test asserts `feed`'s output contains expected substrings. `validate-feed.mjs` asserts `fast-xml-parser` can parse the output. These two checks pass for any output that is both substring-matching AND parseable — which leaves a gap: a feed that is parseable but missing a `<channel><title>` (in violation of RSS 2.0 spec) could pass both. The design says `validate-feed.mjs` asserts `<channel> exists with required children` — pin the literal list of required children in the design, not in the script source where it can drift.

## Attack 6 — Cross-spec contracts and CI cache topology

A grab-bag of dependencies the design implicitly takes but does not explicitly own.

- **Challenge the cross-spec dependency on `THEME_STORAGE_KEY`** (design.md:433): "the same key the professional-profile axe tests use." The blog-shiki-theme test programmatically writes to `localStorage[THEME_STORAGE_KEY]`. This key is owned by `next-themes` config (or by professional-profile's test setup). If a future PR to professional-profile changes the storage key — say, to namespace it — the blog test breaks silently (the localStorage write goes to the old key, the page reads from the new key, the theme toggle test asserts whatever the system theme is). The design does not pin where this constant is sourced or how a cross-spec rename is caught. Demand: import the constant from a shared module (or hard-code in both with a comment cross-referencing), and add a Vitest assertion that the key matches the one the inline `next-themes` blocking script reads.
- **Stress-test the CI cache topology against the `rm -rf .velite .next` clean step.** The design pins the clean to "after Build 1 completes and before Build 2 starts." This works if Build 1 and Build 2 run as two sequential steps inside one CI job. The design does not specify the job topology. If a future CI refactor splits these into two jobs with `actions/cache@v4` between them (a common optimization), Build 2's job restores `.velite/` from the cache before its step list begins, and the in-job `rm -rf` step (if it's still configured at all) runs on a populated directory — which is still a clean, but the *intent* of starting Build 2 from cold-cache state is broken at the orchestration layer. **Demand the design pin "Build 1 and Build 2 run as sequential steps in a single CI job"** explicitly, OR move the draft-isolation guarantee out of the cache layer entirely (e.g., by writing the env-var-controlled output to a different `.velite` directory per build via Velite config override).
- **Tear apart the route-handler emit path glob in `validate-feed.mjs`.** App Router static route-handler emits land at variable paths — `.next/server/app/feed.xml/route.body`, `.next/server/app/feed.xml.body`, or split across chunks depending on Next.js version. The script "globs for the rendered XML file rather than asserting a literal path" — but the glob is filtered by extension `.{html,rsc,xml,json,txt}` per the `verify-production-build.mjs` pin. Next.js writes route-handler bodies with a `.body` extension or as raw chunks without a `.body` suffix — neither matches the extension filter. The validate-feed glob may need a different filter than the production-build glob, and the design treats them as the "same glob-discovery approach." Specify the filter for feed emit explicitly, or test it against an actual Next.js build before launch.

## Top 5 Risks / Gaps

1. **The reading-time AST walk recurses into MDX-only node types that the chosen parser stack does not produce.** With `remark-parse` + `remark-gfm` (no `remark-mdx`), `mdxJsxFlowElement`/`mdxJsxTextElement` never appear in the tree. The design over-specifies a walk it cannot exercise. **Severity: medium.** Catches as "spec-described behavior never observed" — implementer either adds `remark-mdx` (a design change) or silently drops the recursion (a behavior gap).

2. **`s.markdown()` pipeline divergence extends beyond raw HTML to MDX expressions and import statements.** Req 3.7's rejection visitor (mdast `type: 'html'`) does not cover `mdxFlowExpression`, `mdxTextExpression`, or import nodes. A post with `{post.title}` builds in MDX, ships verbatim in `bodyHtml`. **Severity: medium.** Catches as "feed subscribers see `{post.title}` as literal text in a rendered RSS reader."

3. **Reading-time tolerance test is fragile at the integer-clamp boundary AND at alt-text edits.** The freeze-comment gate scopes to prose only; alt text counts toward the flattened string but is not frozen. A single accessibility-driven alt-text edit can cross the rounding breakpoint. **Severity: low–medium.** Catches as intermittent CI failure that bisects to an alt-text edit, surprising the author.

4. **`feed` package pinned via caret (`^4.2.2`), not exact.** A patch or minor bump can ship CDATA-wrapping changes; the launch-gate test runs only on dependency-update PRs that exercise it. A fresh `pnpm install` in a different environment can pull a different version silently. **Severity: medium.** Catches as "feed broken in production after lockfile regeneration."

5. **CI cache topology is implicit.** The `rm -rf .velite .next` step protects against in-job cache reuse but not against `actions/cache@v4` job-split topologies. The design does not pin the job structure. **Severity: medium.** Catches as a future CI refactor silently breaking the draft-isolation guarantee.

## Top 3 Conclusions to Challenge or Reverse

1. **"The reading-time transform's mdast walk handles both markdown and MDX-flavored content."** Reverse to: the walk handles markdown only. Document that MDX syntax in post bodies (JSX tags, expressions, imports) is unsupported in blog-core and is rejected at the schema level or fails the MDX compile. Drop the `mdxJsxFlowElement`/`mdxJsxTextElement` recursion. **Reasoning:** the recursion implies support; the parser stack does not provide it. Either commit to MDX support (add `remark-mdx` to the AST-walk parser, extend the rejection visitor) or commit to markdown-only and remove the misleading recursion.

2. **"The Req 11.11 parity test covers feed/page divergence."** Reverse to: the page-build failure mode covers it. The parity test compares structure; the divergence cases that ship bad bodyHtml (MDX expressions, imports) are caught by the page-MDX compile failing on the same content, IF the build orchestration runs page-compile before feed emission. Pin the build ordering explicitly: feed assembly consumes Velite output AFTER page-compile has validated it. The parity test then defends only against intra-content rendering divergence (Shiki classes, anchor IDs), which is a narrower contract. **Reasoning:** asserting parity on content that diverges on input is a category error. Asserting page-build-validates-feed-input is structural and cheap.

3. **"`^4.2.2` is a pinned feed version."** Reverse to: `4.2.2` exact. Caret pinning provides supply-chain agility at the cost of contract stability — the launch-gate test only fires on PRs that touch the dep, and `pnpm install` in a stale environment can drift. **Reasoning:** the CDATA-wrapping contract is load-bearing for every feed consumer; "pinned" should mean exact, and bumps should be intentional PRs with the launch-gate test as the merge gate.

## What's Missing — Work Before Acting on This Document

- **Decision on MDX-syntax support in post bodies.** Currently the design implies MDX support via the JSX-element recursion but does not provide a parser stack that produces those nodes, and does not extend Req 3.7 rejection beyond raw HTML. Pick one path and update the design end-to-end.
- **Decision on integer-clamp test strategy.** Either decouple word-count assertion from reading-time-rounded assertion, or document the breakpoint risk explicitly and widen the freeze gate to include alt text.
- **Exact `feed` version pin** (drop the caret) and a documented dependency-update flow (renovate/dependabot config) that runs the launch-gate test on every bump.
- **Job-topology pin for CI Build 1 + Build 2.** Specify "single job, sequential steps, no cache between" or move the draft-isolation guarantee out of the cache layer.
- **Cross-spec `THEME_STORAGE_KEY` source pin.** Specify where the constant lives, how cross-spec renames are caught, and whether the blog test imports it or hard-codes it with a cross-reference comment.
- **Explicit emit-shape enumeration for both glob scripts.** Pin the literal directory and extension patterns each script asserts the existence of, so a future Next.js emit-structure change fails the scripts explicitly rather than being silently accommodated by "or equivalent."
- **Strict-parse upgrade for the `feed.rss2()` launch-gate test.** Parse the XML and assert the `<content:encoded>` element contains a CDATA section with the expected payload prefix, not substring-grep.
- **Build-ordering pin between page-compile and feed-emission inside `pnpm build`.** Validate the page render before consuming `bodyHtml` for the feed, so MDX-only-syntax divergence cannot ship.
