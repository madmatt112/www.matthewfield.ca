### CRITICAL: Cadence guard cannot be cleared: parser reads top entry, docs say append at bottom
- **File:** scripts/check-lighthouse-cadence.mjs:69
- **Issue:** scripts/check-lighthouse-cadence.mjs:69 uses logText.match(re) (no /g flag), which returns the FIRST '- Published projects at run time: N' line in the file. The runs-log doc (docs/projects-showcase-lighthouse-runs.md:7-8) explicitly instructs operators that 'a new run entry MUST be added below before the build can go green again' — i.e. newest entry at the BOTTOM. The script's own comment (lines 62-65) contradicts the doc, asserting 'the runs-log heading discipline appends Run K above the previous entry, so first occurrence is the latest.' Verified by simulation: with Run 1 (count 0) at top and Run 2 (count 3) appended below per the doc, match() returns 0, not 3. Consequence: once the guard fires at count=3, the operator logs Run 2 at the bottom with count 3, lastCount is STILL parsed as 0, delta stays 3, 3%3===0, and the step fires red again forever. Following the documented unblock procedure does NOT clear the guard — the core mechanism of Req 12.0 (Lighthouse cadence pin) is non-functional after its first trigger. The task's narrow launch-state AC (0 published, step green) passes only because no run has fired yet; the defect is latent but certain. Fix: use the last match (or matchAll().at(-1)) AND reconcile the contradictory comment with the doc's append-below discipline.
- **Task Requirement:** 12.0 (Lighthouse cadence pin)
- **Classification:** recurring

### WARNING: Modulo gating silently skips cadence on batch adds / non-multiple counts
- **File:** scripts/check-lighthouse-cadence.mjs:89
- **Issue:** The trigger condition at scripts/check-lighthouse-cadence.mjs:89 is `delta >= CADENCE_N && currentCount % CADENCE_N === 0`. The second clause gates firing to exact multiples of 3 in ABSOLUTE count, not on the delta-since-last-run. If more than the threshold is added between CI runs such that the count skips a multiple, the guard never fires for that batch. Example: lastCount=0, a PR publishes 4 real projects at once → currentCount=4, delta=4>=3 but 4%3===1 → no trigger; 4 projects shipped with no Lighthouse re-check until count reaches 6. Similarly, if a run is ever logged at a non-multiple count (e.g. 4), the modulo couples to absolute count and can leave a long gap. Req 12 asks for re-verification 'every 3 projects'; the intent is satisfied by `delta >= CADENCE_N` alone — the `% CADENCE_N === 0` clause is both redundant for the happy path and harmful for non-monotonic-by-one growth. Compounds with the parser bug: while lastCount is stuck at 0, this fires at every multiple of 3 and skips 4,5,7,8,...
- **Task Requirement:** 12.0 (Lighthouse cadence pin)
- **Classification:** novel
